# 1장 · 컴퓨터는 어떻게 여러 일을 동시에 하는 척하는가

## 1.1 익숙한 장면

지금 이 글을 읽고 있는 노트북에서 무슨 일이 벌어지고 있는지 생각해봅시다.

브라우저에 탭이 스무 개쯤 열려 있습니다. 그중 하나는 음악을 재생하고 있고, 다른 하나는 문서를 보여주고 있습니다. 편집기가 켜져 있고 저장할 때마다 문법 검사가 돌아갑니다. 백그라운드에서 패키지 하나를 내려받는 중입니다. 클라우드 동기화 프로그램이 조용히 파일을 올리고 있고, 백신 프로그램이 주기적으로 뭔가를 확인합니다. OS 자체도 화면을 그리고, 네트워크 패킷을 처리하고, 시계를 갱신합니다.

작업 관리자를 열어보면 실행 중인 항목이 수백 개입니다. 그런데 아무것도 끊기지 않습니다. 음악은 매끄럽게 나오고, 키를 누르면 글자가 바로 뜹니다.

전부 동시에 돌아가는 것처럼 보입니다.

그런데 그게 아닙니다.

## 1.2 CPU core는 한 번에 하나만 합니다

컴퓨터에서 실제로 계산을 하는 부품을 **CPU**라고 부르고, CPU 안에서 명령어를 실행하는 단위를 **core**라고 부릅니다. 요즘 노트북에는 core가 여덟 개나 열두 개쯤 들어 있습니다.

core 하나가 하는 일은 단순합니다. 메모리에서 명령어를 하나 가져와 실행하고, 다음 명령어를 가져와 실행하고, 그걸 반복합니다. 초당 수십억 번씩 합니다.

중요한 건 **한 순간에 하나**라는 점입니다. core 하나는 어떤 순간에도 정확히 하나의 명령어 흐름만 실행합니다. 두 프로그램의 명령어를 반씩 섞어서 동시에 실행하는 그런 일은 없습니다.

core가 여덟 개면 여덟 개의 명령어 흐름이 진짜로 동시에 돌아갑니다. 하지만 여덟은 수백보다 훨씬 작은 수입니다. 그러니까 "수백 개가 동시에 돌아가는 것처럼 보인다"는 관찰과 "core 하나는 하나만 한다"는 사실 사이에는 설명해야 할 간격이 있습니다.

그 간격을 메우는 것이 이 책의 주제입니다.

### 이미 알고 있는 같은 트릭

Node.js로 서버를 짜본 적이 있다면 이 구조가 낯설지 않을 겁니다.

Node의 JavaScript 실행은 기본적으로 thread 하나에서 일어납니다. 그런데 Node 서버는 동시에 수천 개의 연결을 처리합니다. 어떻게 하나요?

요청 하나를 처리하다가 데이터베이스 조회 같은 기다림이 필요한 지점이 나오면, 그 요청은 거기서 멈추고 event loop가 다른 요청으로 넘어갑니다. 데이터베이스가 답을 주면 멈췄던 요청이 다시 이어집니다. 이걸 아주 빠르게 반복하면, 밖에서 보기에는 수천 개가 동시에 처리되는 것처럼 보입니다.

OS가 하는 일이 정확히 이겁니다. 단지 한 단계 아래에서, 그리고 훨씬 강제적으로 할 뿐입니다.

두 가지 중요한 차이가 있는데, 미리 말해두면 뒤에서 이해가 빠릅니다.

첫째, Node의 event loop는 **코드가 협조해야** 넘어갑니다. `await`을 쓰지 않고 무한 루프를 돌리면 event loop 전체가 멈춥니다. 반면 OS는 협조를 기다리지 않습니다. 시간이 다 되면 실행 중인 프로그램에서 core를 **강제로 빼앗습니다**. 무한 루프를 도는 프로그램이 있어도 다른 프로그램은 계속 돌아갑니다.

둘째, Node의 event loop는 큐에 쌓인 콜백을 대체로 들어온 순서대로 처리합니다. OS는 순서를 정교하게 고릅니다. 지금 실행을 기다리는 수백 개 중에서 다음에 누구를 실행할지 매번 판단합니다. 그 판단을 하는 부품이 **scheduler**입니다.

이 책은 그 판단에 관한 책입니다.

## 1.3 program, process, thread

용어를 정리하고 가겠습니다. 이 셋은 자주 섞여 쓰이지만 다른 것입니다.

### program

디스크에 저장된 파일입니다. `/usr/bin/python3` 같은 실행 파일이 program입니다. 그냥 파일이라서, 아무것도 하지 않고 가만히 있습니다.

### process

program을 실행시키면 만들어지는 것이 **process**입니다. 실행 중인 인스턴스입니다.

같은 program으로 process를 여러 개 만들 수 있습니다. 터미널 window를 세 개 열면 shell process가 세 개 생깁니다. 같은 파일에서 왔지만 서로 다른 세 개입니다.

Docker를 써봤다면 image와 container의 관계와 같습니다. image는 디스크에 있는 정적인 것이고, container는 그걸 실행시킨 인스턴스입니다. image 하나로 container 여러 개를 띄울 수 있고, 각 container는 자기만의 상태를 가집니다.

process가 가지고 있는 것들:

- **메모리 공간.** 자기만의 주소 공간입니다. process A의 메모리 주소 0x1000과 process B의 0x1000은 물리적으로 다른 곳입니다. 서로의 메모리를 읽을 수 없습니다. 이게 프로그램 하나가 죽어도 다른 프로그램이 멀쩡한 이유입니다.
- **열어둔 파일들.** 어떤 파일을 어디까지 읽었는지 같은 정보입니다. 네트워크 연결도 여기 포함됩니다.
- **실행 상태.** 지금 어느 명령어까지 실행했는지, 계산 중이던 값들이 무엇인지.
- **신원 정보.** process id, 소유자, 권한.

### thread

process 안에서 실제로 명령어를 실행하는 흐름이 **thread**입니다.

process 하나에 thread가 여러 개 있을 수 있습니다. 그리고 같은 process 안의 thread들은 **메모리를 공유합니다**. 이게 process 간 관계와 결정적으로 다른 점입니다.

웹 개발에 빗대면 이렇습니다. Node를 cluster 모드로 띄워서 worker process를 네 개 만들면, 각 worker는 자기 메모리를 가집니다. 한 worker의 전역 변수를 다른 worker가 볼 수 없어서 상태를 공유하려면 Redis 같은 걸 거쳐야 합니다. 반면 Java 서버에서 thread pool을 만들면 thread들이 같은 힙을 공유합니다. 그래서 편하지만 동시에 lock을 걸어야 하는 문제가 생깁니다.

process 대 thread가 정확히 그 관계입니다.

### 그래서 scheduler는 무엇을 스케줄하나

**thread입니다.** process가 아닙니다.

process에 thread가 세 개 있으면 scheduler 입장에서는 실행 후보가 세 개입니다. Linux kernel 내부에서는 이 실행 단위를 `task`라고 부릅니다. 실제로 kernel 소스에 `struct task_struct`라는 구조체가 있고, 그게 하나의 스케줄 대상입니다.

이 시리즈에서도 **task**라는 말을 씁니다. "scheduler가 실행 여부를 결정하는 단위 하나"라는 뜻입니다. 앞으로 이 책에서 task라고 하면 그 의미입니다.

## 1.4 kernel과 user space

OS의 핵심 부분을 **kernel**이라고 부릅니다. 메모리를 나눠주고, 파일 시스템을 관리하고, 네트워크 카드와 대화하고, 그리고 scheduling을 합니다.

kernel은 특별한 권한을 가지고 실행됩니다. CPU에는 특권 모드라는 게 있어서, 그 모드에서만 실행할 수 있는 명령어가 있습니다. 하드웨어를 직접 건드리거나, 메모리 보호 설정을 바꾸거나, interrupt를 다루는 일들입니다.

우리가 만드는 프로그램은 그 권한이 없는 상태로 실행됩니다. 이 영역을 **user space**라고 부릅니다.

### 비유

프론트엔드 개발을 생각해봅시다. 브라우저에서 돌아가는 JavaScript는 사용자의 디스크에 마음대로 파일을 쓸 수 없습니다. 파일을 저장하려면 브라우저가 제공하는 API를 호출해야 하고, 브라우저는 사용자에게 확인을 받거나 정해진 위치에만 쓰게 합니다.

JavaScript 코드가 user space이고, 브라우저가 kernel입니다. 코드는 자기 샌드박스 안에서는 자유롭지만, 밖으로 나가려면 반드시 정해진 문을 통과해야 합니다.

### system call

그 문이 **system call**입니다. 줄여서 syscall이라고도 합니다.

파일을 읽고 싶으면 `read()`를 호출합니다. 네트워크로 데이터를 보내려면 `send()`를 호출합니다. 잠깐 자고 싶으면 `nanosleep()`을 호출합니다.

코드에서 보면 그냥 함수 호출처럼 생겼습니다. 하지만 실제로 일어나는 일은 함수 호출과 많이 다릅니다. 특별한 명령어가 실행되면서 CPU가 특권 모드로 전환되고, 제어권이 kernel로 넘어가고, kernel이 요청을 처리하고, 다시 user space로 돌아옵니다.

같은 프로세스 안의 함수 호출이라기보다는, 다른 서비스에 요청을 보내는 것에 더 가깝습니다. 다만 아주 빠른 요청입니다.

### 왜 이게 scheduling과 상관있나

**프로그램이 CPU를 놓게 되는 대부분의 순간이 syscall 안에서 벌어지기 때문입니다.**

파일을 읽으려고 `read()`를 불렀는데 그 데이터가 디스크에 있다면, 디스크가 데이터를 가져오는 데 시간이 걸립니다. 그동안 이 프로그램은 할 일이 없습니다. core를 붙잡고 기다리는 건 낭비입니다.

그래서 kernel은 이 프로그램을 잠재우고, 대기 중인 다른 프로그램에게 core를 넘깁니다. 디스크가 데이터를 가져오면 잠들었던 프로그램을 깨웁니다.

이 "잠들고 깨어나는" 흐름이 scheduling의 절반입니다. 나머지 절반은 강제로 빼앗는 쪽인데, 그건 뒤에서 다룹니다.

## 1.5 실행 상태란 무엇인가

CPU 안에는 **register**라는 아주 작고 아주 빠른 저장 공간들이 있습니다. 몇십 개 정도이고, 각각 숫자 하나를 담습니다.

계산은 전부 register에서 일어납니다. 메모리에서 값을 register로 가져오고, register끼리 더하고, 결과를 다시 메모리에 씁니다.

register 중에 특별한 것이 몇 개 있습니다.

- **program counter.** 다음에 실행할 명령어가 메모리 어디에 있는지 가리킵니다. 프로그램의 "현재 위치"입니다.
- **stack pointer.** 지금 호출된 함수들의 스택이 어디까지 쌓였는지 가리킵니다.

여기서 중요한 통찰이 나옵니다. **한 프로그램의 실행 상태는 결국 register 값들의 묶음입니다.**

program counter가 어디를 가리키는지, stack pointer가 어디인지, 계산 중이던 값들이 각 register에 무엇으로 들어 있는지. 이것만 있으면 프로그램의 실행을 정확히 그 지점에서 이어갈 수 있습니다.

디버거로 중단점을 걸고 멈췄을 때 보이는 화면을 떠올려보세요. 현재 줄, 콜스택, 지역 변수들. 그걸 통째로 저장해뒀다가 나중에 그대로 복원하면 아무 일도 없었던 것처럼 이어서 실행됩니다.

OS가 프로그램을 전환하는 방법이 정확히 이겁니다. 실행 중인 프로그램의 register를 전부 메모리에 저장하고, 다음에 실행할 프로그램의 저장된 register를 CPU에 채워 넣습니다. 그러면 CPU는 새 프로그램을 이어서 실행하기 시작합니다.

이 동작을 **context switch**라고 부릅니다. 나중에 한 장을 통째로 할애할 만큼 중요한 개념입니다. 공짜가 아니기 때문입니다.

## 1.6 timesharing: 착시가 만들어지는 원리

이제 재료가 다 모였습니다.

core는 한 번에 하나만 실행합니다. 하지만 실행 상태를 저장하고 복원할 수 있습니다. 그러니까 이렇게 하면 됩니다.

프로그램 A를 잠깐 실행합니다. 저장합니다. 프로그램 B를 잠깐 실행합니다. 저장합니다. 프로그램 C를 잠깐 실행합니다. 저장합니다. 다시 A로 돌아갑니다.

"잠깐"이 충분히 짧으면, 사람 눈에는 셋이 동시에 돌아가는 것으로 보입니다. 이 방식을 **timesharing**이라고 부릅니다. 시간을 쪼개서 나눠 쓴다는 뜻입니다.

각 프로그램이 한 번에 받는 시간 조각을 **time slice**라고 부릅니다. quantum이라고도 합니다. 이 책에서는 time slice로 통일합니다.

### 숫자로 감 잡기

time slice가 10밀리초라고 해봅시다. 밀리초는 천분의 1초입니다.

프로그램 세 개가 돌아가고 있으면 각 프로그램은 30밀리초에 한 번씩 차례가 옵니다. 1초 동안 33번씩 실행됩니다.

사람이 화면의 변화를 "끊긴다"고 느끼기 시작하는 지점은 대략 100밀리초 근처입니다. 30밀리초는 그보다 훨씬 짧으니까 전혀 눈치채지 못합니다.

영화가 초당 24장의 정지 화면인데 연속된 움직임으로 보이는 것과 같은 원리입니다. 충분히 빠르면 뇌가 알아서 이어붙입니다.

### 그런데 이게 왜 어려운 문제인가

지금까지의 설명만 보면 간단해 보입니다. 돌아가면서 조금씩 실행시키면 되는 거 아닌가요?

문제는 "돌아가면서"의 순서와 "조금씩"의 크기입니다.

프로그램들이 원하는 게 서로 다릅니다. 음악 재생 프로그램은 오디오 버퍼가 비기 전에 반드시 차례가 와야 합니다. 늦으면 소리가 끊깁니다. 반면 백그라운드에서 도는 압축 작업은 언제 실행되든 상관없고, 대신 한 번 실행될 때 오래 붙잡고 있는 편이 효율적입니다. 편집기는 대부분의 시간을 아무것도 안 하고 있지만, 키를 누른 그 순간에는 즉시 실행돼야 합니다.

수백 개의 프로그램이 각자 다른 요구를 가지고 있고, 어떤 요구는 서로 충돌합니다. 그리고 OS는 각 프로그램이 무엇을 원하는지 직접 물어볼 방법이 없습니다.

이 문제를 푸는 것이 scheduler의 일입니다.

## 1.7 core가 여러 개일 때

core가 여덟 개인 컴퓨터에서는 진짜로 여덟 개가 동시에 실행됩니다. 착시가 아니라 실제 병렬입니다.

이건 좋은 소식이지만 문제를 훨씬 복잡하게 만듭니다.

- **어느 core에 배치할 것인가.** 실행할 프로그램을 골랐다고 끝이 아닙니다. 어느 core에서 돌릴지도 정해야 합니다.
- **부하를 어떻게 나눌 것인가.** 한 core에는 열 개가 몰려 있고 다른 core는 놀고 있으면 안 됩니다. 주기적으로 재분배해야 합니다. 웹 서비스의 load balancer와 같은 문제입니다.
- **옮기면 손해가 납니다.** 프로그램을 core A에서 core B로 옮기면, A의 cache에 쌓아둔 데이터를 못 쓰게 됩니다. cache가 뭔지는 다음 장들에서 설명하는데, 요점은 "옮기는 게 공짜가 아니라서 균형을 맞추는 것과 그대로 두는 것 사이에 trade-off가 있다"는 겁니다.
- **자료구조를 공유해야 합니다.** 여러 core가 동시에 같은 queue를 건드리면 lock이 필요하고, lock은 경합을 낳습니다.

정리하면, multicore에서는 **어떤 순서로 실행할 것인가**라는 원래 문제 위에 **어디서 실행할 것인가**라는 두 번째 문제가 얹힙니다.

### 이 시리즈의 실험은 core 하나만 씁니다

미리 말해둡니다. 이 시리즈가 다루는 연구의 실험 환경은 core가 하나입니다.

이유는 뒤에서 자세히 다루지만, 핵심만 말하면 이렇습니다. 이 연구가 알고 싶은 것은 "실행 순서를 정하는 policy를 바꿨을 때 결과가 달라지는가"입니다. core를 여러 개로 하면 부하 분산 policy라는 두 번째 변수가 끼어들어서, 결과가 달라졌을 때 어느 쪽 때문인지 알 수 없게 됩니다.

실험에서 변수를 하나만 두는 것은 기본입니다. 그래서 core 하나입니다.

## 1장 정리

- core 하나는 한 순간에 명령어 흐름 하나만 실행합니다. 수백 개가 동시에 도는 것처럼 보이는 건 아주 빠르게 번갈아 실행하기 때문입니다. 이 방식을 timesharing이라고 하고, 한 번에 주는 시간 조각을 time slice라고 합니다.
- program은 디스크의 파일, process는 그걸 실행시킨 인스턴스, thread는 process 안에서 실제로 명령어를 실행하는 흐름입니다. scheduler가 다루는 단위는 thread이고, 이 책에서는 task라고 부릅니다.
- OS의 핵심을 kernel이라고 하고, 특권을 가지고 실행됩니다. 우리 프로그램은 user space에서 돌고, kernel의 기능을 쓰려면 system call이라는 정해진 문을 통과해야 합니다. 프로그램이 CPU를 놓는 대부분의 순간이 이 문 안에서 벌어집니다.
- 프로그램의 실행 상태는 CPU register 값들의 묶음입니다. 그래서 저장했다가 복원하면 이어서 실행할 수 있습니다. 이 전환을 context switch라고 합니다.
- 어려운 부분은 전환하는 방법이 아니라 **누구를 언제 얼마나** 실행할지 정하는 것입니다. 프로그램마다 원하는 게 다르고, OS는 그걸 물어볼 수 없습니다.

다음 장에서는 프로그램 하나가 실행되는 동안 어떤 상태들을 오가는지 봅니다. 그 상태 전이를 알아야 scheduler가 언제 개입하는지 이해할 수 있습니다.

# 2장 · process의 일생

## 2.1 실행 중이라는 말의 애매함

작업 관리자를 열면 프로그램 수백 개가 "실행 중"이라고 표시됩니다.

그런데 core는 여덟 개뿐입니다. 그러니까 진짜로 명령어를 실행하고 있는 건 많아야 여덟 개입니다. 나머지 수백 개는 실행 중이 아닙니다.

그럼 뭘 하고 있나요?

크게 두 종류입니다. **실행하고 싶은데 차례를 못 받은 것**과 **실행하고 싶지 않은 것**입니다. 이 둘은 완전히 다릅니다. 첫 번째는 scheduler가 신경 써야 할 대상이고, 두 번째는 신경 쓸 필요가 없습니다.

이 구분이 scheduling의 출발점입니다.

## 2.2 네 가지 상태

task 하나가 살아 있는 동안 오갈 수 있는 상태는 네 가지입니다. 앞 장에서 정리했듯이 task는 scheduler가 실행 여부를 결정하는 단위 하나를 말하고, 보통은 thread 하나에 해당합니다.

### Running

지금 core를 잡고 명령어를 실행하고 있는 상태입니다.

core 하나에 running 상태인 task는 정확히 하나입니다. 이건 정의상 그렇습니다.

### Ready

실행할 준비가 다 됐고, 실행하고 싶고, 다만 차례가 오지 않은 상태입니다.

기다리는 이유는 오직 하나입니다. core가 부족해서입니다. 지금 당장 core를 주면 즉시 명령어를 실행할 수 있습니다.

**여기가 scheduler의 유일한 관심사입니다.** ready 상태인 task들이 줄을 서 있고, scheduler는 그중 누구에게 core를 줄지 고릅니다.

### Blocked

무언가를 기다리고 있어서, core를 줘도 할 일이 없는 상태입니다. sleeping, waiting이라고도 부릅니다.

디스크에서 데이터가 오기를 기다리거나, 네트워크 응답을 기다리거나, 사용자가 키를 누르기를 기다리거나, 정해둔 시간이 되기를 기다립니다.

**scheduler는 blocked 상태인 task를 아예 후보에서 뺍니다.** 골라도 소용이 없기 때문입니다. 이게 앞서 말한 "실행하고 싶지 않은 것"입니다.

작업 관리자의 수백 개 중 대부분이 이 상태입니다.

### Done

끝난 상태입니다. 다시 실행되지 않습니다.

## 2.3 상태 사이의 이동

```text
                        preemption
              (time slice 소진 / 더 급한 task 도착)
        ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
   ┌─────────┐        dispatch                ┌─────────┐
   │  Ready  │ ─────────────────────────────► │ Running │
   └─────────┘        (차례를 받음)             └─────────┘
        ▲                                       │      │
        │                                       │      │ exit
        │ wake                    voluntary block│      │
        │ (기다리던 것이 도착)      (I/O·타이머·lock) │      ▼
        │                                       │  ┌────────┐
   ┌─────────┐                                  │  │  Done  │
   │ Blocked │ ◄────────────────────────────────┘  └────────┘
   └─────────┘
```

전이는 다섯 가지입니다. 하나씩 봅니다.

### Ready → Running: 차례를 받음

scheduler가 이 task를 골랐습니다. 저장돼 있던 register 값들이 CPU에 복원되고, 실행이 이어집니다.

이 전이가 일어나는 순간을 **dispatch**라고 부릅니다.

### Running → Ready: 시간이 다 됐거나, 더 급한 게 왔거나

실행 중이던 task가 강제로 내려옵니다. 아직 할 일이 남아 있고 실행하고 싶은데도 내려옵니다.

두 경우입니다. time slice를 다 썼거나, 더 priority 높은 task가 ready 상태가 되었거나.

이 강제 회수를 **preemption**이라고 부릅니다. 우리말로는 선점이라고 하는데, 이 책에서는 preemption을 그대로 씁니다.

preemption이 있어야 무한 루프를 도는 프로그램이 시스템 전체를 멈추게 하는 일을 막을 수 있습니다. 앞 장에서 Node.js의 event loop는 코드가 협조해야 넘어간다고 했는데, OS가 다른 점이 바로 이겁니다.

### Running → Blocked: 기다려야 할 일이 생김

실행 중이던 task가 스스로 내려옵니다. 기다려야 할 게 생겼기 때문입니다.

거의 항상 system call 안에서 벌어집니다. `read()`를 불렀는데 데이터가 아직 없거나, `recv()`를 불렀는데 패킷이 안 왔거나, `sleep()`을 불렀거나.

이건 강제가 아니라 자발적입니다. 그래서 **voluntary**하게 CPU를 놓았다고 표현합니다. 이 구분은 나중에 아주 중요해집니다. scheduler가 task의 성격을 추측할 때 결정적인 단서로 쓰기 때문입니다.

### Blocked → Ready: 기다리던 것이 도착함

디스크가 데이터를 가져왔습니다. 패킷이 도착했습니다. 타이머가 울렸습니다.

kernel이 이 task를 blocked에서 ready로 옮깁니다. 이 동작을 **wake**라고 부릅니다. 깨운다는 뜻입니다.

주의할 점은 wake가 곧바로 실행을 뜻하지 않는다는 겁니다. ready가 됐을 뿐이고, 여전히 차례를 기다려야 합니다. **wake된 순간부터 실제로 실행되기까지 걸리는 시간**이 나중에 performance metric으로 등장합니다. 이 연구에서 아주 중요한 숫자입니다.

### Running → Done: 끝남

`exit()`를 부르거나 main이 반환하면 끝납니다.

## 2.4 왜 task가 잠드는가

blocked 상태로 가는 이유를 세 가지로 정리하면 전체 그림이 잡힙니다.

### I/O를 기다림

디스크, 네트워크, 키보드, 화면. CPU 바깥의 무언가와 대화하는 경우입니다.

핵심은 속도 차이입니다. 감을 잡기 위한 대략적인 크기 비교를 보면 이렇습니다.

| 하는 일 | 걸리는 시간 정도 |
|---|---|
| register에서 값 하나 읽기 | 1나노초 안쪽 |
| CPU cache에서 읽기 | 몇 나노초 |
| 메인 메모리에서 읽기 | 100나노초 정도 |
| SSD에서 읽기 | 100마이크로초 정도 |
| 회전 디스크에서 읽기 | 10밀리초 정도 |
| 같은 대륙 안 네트워크 왕복 | 수십 밀리초 |

나노초는 10억분의 1초, 마이크로초는 100만분의 1초, 밀리초는 1000분의 1초입니다.

메모리 접근이 100나노초인데 SSD 접근이 100마이크로초면 천 배 차이입니다. CPU 입장에서 SSD를 기다리는 건 아주 긴 시간입니다. 그동안 명령어를 수십만 개는 실행할 수 있습니다.

그래서 기다리는 동안 core를 붙잡고 있는 건 큰 낭비이고, 반드시 놓아야 합니다.

### 시간을 기다림

프로그램이 스스로 "0.5초 뒤에 깨워줘"라고 요청하는 경우입니다.

주기적으로 뭔가를 하는 프로그램들이 이렇게 동작합니다. 시계 위젯은 1초마다 깨어나서 화면을 갱신하고 다시 잡니다. 동기화 프로그램은 5분마다 깨어나서 변경 사항을 확인합니다.

게임과 영상 재생도 이 범주입니다. 초당 60 frame이면 약 16.7밀리초마다 한 번씩 깨어나서 한 frame을 만들고 다시 잡니다. 이 패턴은 나중에 따로 한 장을 할애해서 다룹니다.

### 다른 task를 기다림

lock을 잡으려는데 다른 task가 이미 잡고 있거나, 큐에서 항목을 꺼내려는데 큐가 비어 있는 경우입니다.

여기서는 기다리는 대상이 하드웨어가 아니라 다른 task입니다. 그래서 "누가 누구를 깨우는가"라는 관계가 생깁니다.

웹 서버로 치면 이런 구조입니다. 요청을 받는 thread가 작업을 큐에 넣고, worker thread가 큐에서 꺼내 처리하고, 결과를 다시 응답 thread에 넘깁니다. 세 단계가 사슬처럼 이어져 있어서, 사용자가 체감하는 지연은 세 단계 전체의 합입니다.

이 사슬 구조는 이 시리즈의 연구에서 중요하게 다루는 모양입니다. 중간의 한 단계만 늦어도 전체가 늦어지는데, scheduler는 각 단계를 따로 보기 때문에 그 사슬을 알아채기 어렵습니다.

## 2.5 CPU burst와 sleep의 반복

프로그램 하나의 실행을 시간 축에 늘어놓으면, 대부분 이런 모양이 나옵니다.

```text
   ▓▓▓░░░░░░░░░░░░░░▓▓░░░░░░░░░░░░░░░░░░░░▓▓▓▓░░░░░░░░░
   
   ▓ = CPU를 쓰는 구간 (CPU burst)
   ░ = 자고 있는 구간 (blocked)
```

CPU를 연속으로 쓰는 한 덩어리를 **CPU burst**라고 부릅니다. burst 하나가 끝나면 대개 무언가를 기다리며 잠들고, 기다리던 게 오면 다음 burst가 시작됩니다.

이 모양이 프로그램의 성격을 드러냅니다.

### 짧은 burst와 긴 sleep

```text
   텍스트 편집기
   ▓ ░░░░░░░░░░░░ ▓ ░░░░░░░░░░░░░░░░░ ▓ ░░░░░░░░░░ ▓
```

키를 누르면 깨어나서 1, 2밀리초 동안 글자를 처리하고 화면을 갱신한 뒤 다시 잡니다. 사람이 다음 키를 누를 때까지 수백 밀리초를 잡니다.

CPU를 거의 안 씁니다. 편집기가 하루 종일 켜져 있어도 CPU 사용률은 1퍼센트도 안 됩니다.

하지만 깨어났을 때 **즉시** 실행돼야 합니다. 50밀리초쯤 밀리면 사람이 느낍니다.

### 긴 burst와 sleep 없음

```text
   압축 작업
   ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓
```

한번 시작하면 끝날 때까지 계속 계산합니다. 자발적으로 자는 일이 없습니다.

CPU를 100퍼센트 씁니다. 반면 언제 실행되든 별로 상관없습니다. 중요한 건 총 걸린 시간입니다.

### 중간 형태

```text
   웹 서버
   ▓▓ ░░░░ ▓ ░░░░░░ ▓▓▓ ░░░ ▓ ░░░░░░░░ ▓▓ ░░░░
```

요청이 오면 처리하고, 데이터베이스를 기다리며 자고, 응답을 만들고, 다음 요청을 기다리며 잡니다.

### 이게 왜 중요한가

**scheduler는 프로그램이 무엇인지 알 수 없지만, 이 패턴은 볼 수 있습니다.**

편집기가 편집기라는 걸 알아낼 방법은 없습니다. 하지만 "이 task는 항상 짧게 실행하고 자발적으로 잠든다"는 것은 관찰할 수 있습니다. 그리고 그런 task는 사람이 기다리고 있을 가능성이 높으니까 빨리 실행시켜주는 게 낫습니다.

"압축 작업이라는 걸 알아내는 것"과 "CPU를 계속 쓴다는 걸 관찰하는 것"은 다릅니다. 뒤엣것만 할 수 있습니다.

이 관찰 기반 추측이 오늘날 거의 모든 scheduler가 하는 일입니다. 뒤에서 MLFQ를 다룰 때 그 추측이 어떻게 규칙으로 만들어지는지 자세히 봅니다.

그리고 그 추측이 언제 실패하는지가 이 시리즈 연구의 출발점입니다. 미리 한 문장으로 말하면 이렇습니다. **행동이 똑같은데 올바른 대우가 다른 경우가 있고, 그때는 관찰로 알아낼 방법이 없습니다.**

## 2.6 run queue

ready 상태인 task들을 담아두는 자료구조를 **run queue**라고 부릅니다. ready queue라고도 합니다.

이름은 queue지만 실제 구현이 단순한 선입선출 큐인 경우는 드뭅니다. priority별로 여러 개일 수도 있고, 트리 구조일 수도 있습니다. 어떻게 생겼는지가 곧 scheduling 알고리즘입니다.

scheduler가 하는 일을 다시 정의하면 이렇습니다.

> run queue에 들어 있는 task들 중에서 다음에 실행할 하나를 고르고, 얼마나 오래 실행하게 할지 정한다.

이게 전부입니다. 단순해 보이지만, 골라야 할 후보가 수백 개이고, 그 판단을 초당 수만 번 해야 하며, 각 task가 무엇을 원하는지 알 수 없다는 조건이 붙습니다.

blocked 상태인 task들은 run queue에 없습니다. 각자 기다리는 대상별로 다른 목록에 들어가 있습니다. 디스크를 기다리는 목록, 특정 lock을 기다리는 목록 같은 식입니다. 기다리던 일이 일어나면 그 목록에서 빠져나와 run queue로 들어옵니다.

## 2.7 손으로 따라가보기

작은 프로그램 하나의 실행을 상태 전이로 추적해봅시다.

프로그램이 하는 일은 이렇습니다. 파일을 열어서 읽고, 내용을 처리하고, 결과를 화면에 출력하고, 끝냅니다.

```text
시각      상태 변화                          이유
────────────────────────────────────────────────────────────────
0.0ms    (없음)   →  Ready                  프로그램이 시작됨
0.3ms    Ready    →  Running                scheduler가 골랐음
0.5ms    Running  →  Blocked                open() 호출, 디스크 대기
2.1ms    Blocked  →  Ready                  파일이 열림, wake
2.4ms    Ready    →  Running                차례가 옴
2.5ms    Running  →  Blocked                read() 호출, 디스크 대기
6.8ms    Blocked  →  Ready                  데이터 도착, wake
7.9ms    Ready    →  Running                차례가 옴
17.9ms   Running  →  Ready                  time slice 소진, preemption
21.2ms   Ready    →  Running                차례가 다시 옴
24.0ms   Running  →  Blocked                write() 호출, 화면 출력 대기
24.2ms   Blocked  →  Ready                  출력 완료, wake
24.6ms   Ready    →  Running                차례가 옴
24.7ms   Running  →  Done                   exit()
```

여기서 몇 가지를 읽을 수 있습니다.

**전체 걸린 시간은 24.7밀리초입니다.** 하지만 실제로 core를 쓴 시간을 더해보면 0.2 + 0.1 + 10.0 + 2.8 + 0.1로 약 13.2밀리초입니다. 나머지 11.5밀리초는 기다리는 데 썼습니다.

**기다린 시간은 두 종류입니다.** blocked로 기다린 시간이 있고, ready인데 차례를 못 받아 기다린 시간이 있습니다. 후자를 따로 더해보면 0.3 + 0.3 + 1.1 + 3.3 + 0.4로 약 5.4밀리초입니다.

이 구분이 아주 중요합니다. **blocked로 기다린 시간은 scheduler 탓이 아닙니다.** 디스크가 느린 걸 scheduler가 어쩌겠습니까. 반면 **ready인데 못 실행된 시간은 온전히 scheduler 탓입니다.** 실행할 준비가 됐는데 다른 task를 골랐기 때문에 기다린 겁니다.

그래서 scheduler를 평가할 때는 이 두 번째 시간을 봅니다. 이 시리즈의 연구에서도 마찬가지입니다. task가 ready가 된 순간부터 실제로 실행되기 시작한 순간까지의 시간을 측정하고, 그걸 핵심 metric으로 씁니다.

**17.9밀리초에 preemption이 일어났습니다.** 7.9밀리초에 실행을 시작해서 10밀리초 동안 계속 계산했더니 time slice를 다 쓴 겁니다. 강제로 내려왔고, 3.3밀리초를 기다린 뒤 다시 올라갔습니다.

이 프로그램은 처음에는 자주 잠들다가 중간에 10밀리초를 통으로 계산했습니다. scheduler 입장에서 보면 성격이 바뀐 것처럼 보입니다. 이런 변화를 어떻게 다룰지도 scheduling 알고리즘이 답해야 할 질문입니다.

## 2장 정리

- task는 running, ready, blocked, done 네 상태를 오갑니다. running은 지금 core를 쓰는 중, ready는 실행하고 싶은데 차례를 못 받은 상태, blocked는 뭔가를 기다리느라 실행할 수 없는 상태입니다.
- scheduler의 관심 대상은 ready 상태인 task들뿐입니다. blocked인 것들은 골라도 소용없으니 후보에서 빠집니다.
- running에서 내려오는 방식이 두 가지입니다. time slice를 다 써서 강제로 내려오는 preemption과, 기다릴 게 생겨서 스스로 내려오는 voluntary block입니다. 이 구분은 뒤에서 scheduler가 task의 성격을 추측하는 핵심 단서가 됩니다.
- blocked에서 ready로 올라가는 것을 wake라고 합니다. wake가 곧 실행은 아닙니다. wake된 뒤 실제 실행까지 걸린 시간이 scheduler를 평가하는 핵심 숫자입니다.
- 프로그램의 실행은 CPU burst와 sleep의 반복입니다. burst가 짧고 sleep이 길면 사람이 기다리는 일일 가능성이 높고, burst가 길고 sleep이 없으면 계산 작업일 가능성이 높습니다.
- scheduler는 프로그램이 무엇인지는 알 수 없지만 이 패턴은 관찰할 수 있습니다. 그래서 패턴으로 성격을 추측합니다. 이 추측이 언제 실패하는지가 이 시리즈 연구의 출발점입니다.
- ready 상태인 task들이 모여 있는 자료구조를 run queue라고 부릅니다. 이 자료구조의 모양이 곧 scheduling 알고리즘입니다.

# 3장 · scheduler는 언제 불려 나오는가

## 3.1 scheduler는 프로그램이 아닙니다

scheduler를 처음 배울 때 흔히 갖는 오해가 있습니다. 어딘가에 scheduler라는 프로그램이 계속 돌면서 다른 프로그램들을 감시하고 지시한다는 그림입니다.

그렇지 않습니다.

scheduler는 kernel 안에 있는 **함수**입니다. 평소에는 실행되지 않고 가만히 있다가, 필요한 순간에 호출됩니다. 호출되면 다음에 실행할 task를 고르고, 전환을 수행하고, 끝납니다.

그리고 결정적으로, **자기가 스케줄하는 바로 그 core 위에서 실행됩니다.** 별도의 core에서 감독하는 게 아닙니다.

이 사실이 모든 것을 규정합니다. scheduler가 결정을 내리는 데 쓰는 시간은 어떤 프로그램도 일하지 못하는 시간입니다. 고민하는 만큼 손해입니다.

### 웹 개발에 빗대면

별도의 마이크로서비스가 아니라 **middleware**입니다.

Express 앱에 middleware를 하나 붙이면, 그건 백그라운드에서 도는 게 아니라 모든 요청 처리 경로 위에 얹힙니다. middleware가 1밀리초를 쓰면 모든 요청이 1밀리초씩 느려집니다. 초당 만 건을 받는 서버라면 middleware의 1밀리초는 core 열 개어치입니다.

scheduler가 그런 위치에 있습니다. 그것도 훨씬 자주 불리는 middleware입니다.

## 3.2 interrupt: 하드웨어가 끼어드는 방법

scheduler가 언제 불리는지 알려면 먼저 interrupt를 알아야 합니다.

CPU가 프로그램의 명령어를 순서대로 실행하고 있다고 합시다. 그런데 네트워크 카드에 패킷이 도착했습니다. 이 사실을 어떻게 알릴까요?

방법은 두 가지입니다. CPU가 주기적으로 "패킷 왔니?" 하고 물어보거나, 네트워크 카드가 CPU를 툭 치는 겁니다.

앞엣것을 polling, 뒤엣것을 **interrupt**라고 합니다. 대부분의 경우 interrupt를 씁니다. 안 온 패킷을 계속 물어보는 건 낭비니까요.

interrupt가 걸리면 CPU는 실행하던 명령어 흐름을 그 자리에서 멈춥니다. 현재 위치를 저장하고, 미리 등록된 처리 함수로 점프합니다. 이 함수를 **interrupt handler**라고 부릅니다. handler가 일을 마치면 원래 자리로 돌아옵니다.

프로그램 입장에서는 아무 일도 없었던 것처럼 보입니다. 자기가 잠깐 멈춰 있었다는 사실조차 모릅니다.

웹 개발에 빗대면 webhook이나 이벤트 리스너에 가깝습니다. 폴링하지 않고, 일이 생기면 알려주는 쪽이 호출합니다. 다른 점은 실행 중이던 코드를 문자 그대로 중간에 끊고 끼어든다는 점입니다.

## 3.3 timer interrupt: 규칙적으로 울리는 알람

여러 interrupt 중에 scheduling에 결정적인 것이 **timer interrupt**입니다.

컴퓨터에는 일정한 간격으로 interrupt를 발생시키는 하드웨어 타이머가 있습니다. 예전 Linux는 이걸 초당 100번에서 1000번 사이로 맞춰뒀습니다. 이 간격을 **tick**이라고 부르고, 초당 몇 번인지를 HZ라고 표기했습니다. HZ가 1000이면 1밀리초마다 한 번입니다.

timer interrupt가 걸리면 kernel이 잠깐 제어권을 얻습니다. 그 짧은 순간에 시계를 갱신하고, 만료된 타이머가 있는지 확인하고, 그리고 이렇게 묻습니다.

> 지금 실행 중인 task를 계속 실행시킬 것인가, 아니면 바꿀 것인가?

이 질문이 preemption의 물리적 기반입니다. **주기적으로 kernel이 제어권을 되찾을 수 있기 때문에** 무한 루프를 도는 프로그램에서도 core를 회수할 수 있는 겁니다.

이 장치가 없으면 프로그램이 자발적으로 놓아주기를 기다리는 수밖에 없습니다. 그게 앞에서 말한 Node.js의 event loop 상황이고, 옛날 OS들의 상황이기도 했습니다. Windows 3.1이나 초기 Mac OS는 프로그램 하나가 응답을 멈추면 시스템 전체가 멈췄습니다.

### 요즘은 조금 다릅니다

최근 kernel들은 계속 tick을 울리지 않습니다. 아무 일도 없는데 초당 1000번 깨어나는 건 배터리 낭비니까요.

그래서 필요할 때만 타이머를 맞춰두는 방식을 씁니다. "이 task의 time slice가 3밀리초 뒤에 끝나니까 그때 깨워줘"라고 예약하는 식입니다. 이를 tickless라고 부릅니다.

원리는 같습니다. 규칙적으로 울리느냐 필요할 때 울리느냐의 차이일 뿐, 하드웨어 타이머가 kernel에게 제어권을 돌려준다는 구조는 동일합니다.

## 3.4 scheduler가 불리는 다섯 순간

정리하면 이렇습니다.

### 1. 실행 중인 task가 스스로 잠들 때

`read()`를 호출했는데 데이터가 없어서 기다려야 하는 상황입니다. 이 task는 blocked가 되고, core가 비게 됩니다. 누군가는 채워야 하니 scheduler가 불립니다.

### 2. 실행 중인 task가 끝날 때

역시 core가 비니까 다음을 골라야 합니다.

### 3. time slice가 다 됐을 때

timer interrupt 안에서 확인합니다. 실행 중인 task가 할당된 시간을 다 썼으면 preemption이 일어나고 scheduler가 불립니다.

### 4. 잠들어 있던 task가 깨어났을 때

디스크에서 데이터가 도착했습니다. 기다리던 task가 ready가 됩니다.

여기서 판단이 필요합니다. 방금 깨어난 task가 지금 실행 중인 task보다 급한가요?

급하다면 실행 중인 task를 즉시 내리고 새로 깨어난 task를 올립니다. 이걸 **wakeup preemption**이라고 부릅니다. 아니라면 run queue에 넣어두고 자기 차례를 기다리게 합니다.

이 판단이 대화형 프로그램의 반응 속도를 좌우합니다. 키를 눌러서 편집기가 깨어났는데 "다음 차례에"라고 하면 사람이 기다려야 하니까요.

### 5. task의 priority가 바뀌었을 때

프로그램이 스스로 priority를 조정하거나, scheduler가 내부 규칙에 따라 조정하는 경우입니다.

## 3.5 얼마나 자주 불리는가

대략적인 감을 잡아봅시다.

일반적인 데스크톱에서 core 하나당 초당 수천 번에서 수만 번 정도 scheduler가 호출됩니다. 부하가 높거나 I/O가 많으면 더 올라갑니다.

이 숫자가 의미하는 바는 이렇습니다.

scheduler의 결정 로직이 한 번에 10마이크로초를 쓴다고 해봅시다. 10마이크로초는 100만분의 10초입니다. 굉장히 짧아 보입니다.

그런데 초당 만 번 불리면 0.1초입니다. **core 하나의 10퍼센트를 scheduler가 먹습니다.** 아무 일도 하지 않고 "누가 다음이지"를 고민하는 데만 씁니다.

그래서 실제 kernel의 scheduler는 극단적으로 최적화돼 있습니다. 대부분의 경우 마이크로초 단위, 좋을 때는 그 아래에서 결정을 끝냅니다. 자료구조도 그 목적에 맞게 고릅니다. 정렬된 리스트 대신 균형 트리를 쓰거나 priority별 배열과 비트맵을 쓰는 이유가 그겁니다.

### 이 제약이 이 연구를 규정합니다

여기서 이 시리즈가 다루는 연구의 가장 중요한 설계 제약이 나옵니다. 미리 짚어두면 나중에 이해가 훨씬 빠릅니다.

이 연구는 언어 모델이 "지금 이 컴퓨터가 무엇에 쓰이고 있는가"를 읽어내게 하려고 합니다. 그런데 언어 모델을 한 번 돌리는 데는 아무리 빨라도 수백 밀리초, 보통은 몇 초가 걸립니다.

scheduler는 마이크로초 안에 결정해야 합니다. 몇 초는 그보다 백만 배 긴 시간입니다.

그러니까 **언어 모델을 scheduler 안에 넣는 것은 불가능합니다.** 결정 경로에 두는 순간 시스템이 멈춥니다.

그래서 이 연구는 다른 구조를 씁니다. 언어 모델은 훨씬 느린 주기로 따로 돌면서 "지금 상황은 이렇다"는 판단만 내놓고, 그 판단이 scheduler의 **config**을 바꿉니다. scheduler 자체는 평소처럼 마이크로초 안에 동작합니다.

웹 개발에 빗대면 이렇습니다. 모든 요청마다 무거운 분석을 돌리는 게 아니라, 백그라운드 작업이 몇 분에 한 번 분석해서 cache나 설정을 갱신하고, 요청 처리 경로는 그 갱신된 설정을 읽기만 하는 구조입니다. feature flag를 떠올려도 좋습니다. 플래그 값을 정하는 로직은 느려도 되지만, 플래그를 읽는 것은 빨라야 합니다.

이 구조를 왜 그렇게 잡았는지, 그리고 그 선택이 어떤 결과를 낳는지는 뒤 권에서 자세히 다룹니다. 여기서는 "scheduler는 마이크로초 예산 안에서 동작해야 한다"는 물리적 사실만 기억하면 됩니다.

## 3.6 preemptive와 cooperative

scheduling 방식을 크게 두 가지로 나눕니다.

### Cooperative scheduling

task가 스스로 놓아줄 때까지 기다립니다. 강제로 빼앗지 않습니다.

장점은 단순하다는 것입니다. 전환 지점이 정해져 있으니 그 사이에는 방해받지 않는다고 가정할 수 있습니다. 그래서 lock을 덜 써도 됩니다.

단점은 치명적입니다. task 하나가 협조하지 않으면 시스템이 멈춥니다.

JavaScript의 async/await가 정확히 이 모델입니다. `await`을 만나야 다른 작업으로 넘어갑니다. 계산이 오래 걸리는 함수를 `await` 없이 실행하면 그동안 이벤트 루프 전체가 멈춥니다. 브라우저에서 그런 코드를 돌리면 화면이 얼어붙습니다.

### Preemptive scheduling

kernel이 언제든 강제로 빼앗을 수 있습니다.

장점은 견고함입니다. task 하나가 아무리 나쁘게 굴어도 다른 task들은 계속 돌아갑니다.

단점은 복잡함입니다. 실행이 언제 끊길지 모르니 공유 데이터를 건드릴 때마다 lock이 필요합니다. 그리고 전환 자체에 비용이 듭니다.

**현대 OS는 전부 preemptive입니다.** 이 책에서 다루는 알고리즘들도 특별히 언급하지 않는 한 preemptive를 전제합니다.

## 3.7 정리하면 scheduler는 무엇을 정하는가

scheduler가 답해야 하는 질문은 정확히 두 개입니다.

**첫째, 다음에 누구를 실행할 것인가.** run queue에 있는 ready task들 중에서 하나를 고릅니다.

**둘째, 얼마나 오래 실행하게 할 것인가.** time slice를 정합니다. 무제한일 수도 있고, 정해진 시간일 수도 있고, task마다 다를 수도 있습니다.

앞으로 나올 모든 scheduling 알고리즘은 이 두 질문에 대한 서로 다른 답입니다. 알고리즘을 배울 때마다 이 두 가지가 무엇인지 확인하면 구조가 잡힙니다.

## 3장 정리

- scheduler는 백그라운드에서 도는 프로그램이 아니라 kernel 안의 함수입니다. 필요한 순간에 호출되고, 자기가 스케줄하는 바로 그 core 위에서 실행됩니다. 그래서 결정에 쓰는 시간은 전부 순손실입니다.
- interrupt는 하드웨어가 실행 중인 코드를 중간에 끊고 kernel에게 제어권을 넘기는 장치입니다. 그중 timer interrupt는 일정 간격으로 울리며, 이 덕분에 kernel이 주기적으로 제어권을 되찾아 preemption을 할 수 있습니다.
- scheduler가 불리는 순간은 다섯 가지입니다. 실행 중인 task가 잠들 때, 끝날 때, time slice를 다 썼을 때, 잠들어 있던 task가 깨어났을 때, priority가 바뀔 때입니다.
- core 하나당 초당 수천에서 수만 번 호출됩니다. 결정 로직이 10마이크로초를 쓰면 core의 10퍼센트가 날아갑니다. 그래서 scheduler는 마이크로초 예산 안에서 동작하도록 극단적으로 최적화돼 있습니다.
- 이 예산 제약 때문에 언어 모델처럼 느린 것을 결정 경로에 넣을 수 없습니다. 이 시리즈의 연구가 언어 모델을 scheduler 바깥에 두고 config만 바꾸게 만든 이유가 이것입니다.
- 현대 OS는 전부 preemptive입니다. task가 협조하지 않아도 강제로 빼앗습니다.
- scheduler가 정하는 것은 딱 두 가지입니다. 다음에 누구를 실행할지, 그리고 얼마나 오래 실행하게 할지.

# 4장 · context switch의 값

## 4.1 전환은 공짜가 아닙니다

실행 중인 task를 내리고 다른 task를 올리는 동작을 **context switch**라고 부릅니다. context는 "실행 상태"를 뜻합니다.

앞에서 이렇게 설명했습니다. 프로그램의 실행 상태는 CPU register 값들의 묶음이고, 그걸 저장했다가 복원하면 이어서 실행할 수 있다고요.

맞는 설명이지만 절반만 맞습니다. register를 저장하고 복원하는 것 자체는 꽤 빠릅니다. 진짜 비용은 다른 데 있습니다.

이 장은 그 진짜 비용에 관한 것입니다. 그리고 그 비용이 왜 time slice의 길이를 결정하는지를 봅니다.

## 4.2 눈에 보이는 비용

전환할 때 실제로 저장하고 복원하는 것들입니다.

**범용 register.** 계산에 쓰는 register들입니다. 수십 개 정도이고 각각 8바이트쯤 됩니다. 다 합쳐도 수백 바이트입니다.

**program counter와 stack pointer.** 어디까지 실행했고 스택이 어디까지 쌓였는지입니다.

**부동소수점과 벡터 register.** 이건 좀 큽니다. 요즘 CPU의 벡터 register는 개당 수십 바이트씩이고 여러 개입니다. 다 합치면 킬로바이트 단위가 됩니다. 그래서 실제 kernel은 이걸 항상 저장하지 않고, 새 task가 실제로 쓰려고 할 때만 저장하는 최적화를 씁니다.

**메모리 주소 변환 정보.** 다른 process의 thread로 전환하는 경우에만 해당합니다. 각 process는 자기만의 메모리 주소 공간을 가지고 있어서, 어느 가상 주소가 어느 실제 주소인지 알려주는 표를 바꿔 끼워야 합니다.

같은 process 안의 thread끼리 전환할 때는 이 마지막 단계가 없습니다. 메모리 공간을 공유하니까요. 그래서 thread 간 전환이 process 간 전환보다 쌉니다.

여기까지가 눈에 보이는 비용입니다. 대략 마이크로초 단위, 그러니까 100만분의 몇 초 정도입니다.

## 4.3 cache: 진짜 비용을 이해하기 위한 준비

진짜 비용을 설명하려면 cache를 알아야 합니다. 잠깐 옆길로 새겠습니다.

### 메모리는 느립니다

CPU는 굉장히 빠릅니다. 1나노초에 명령어 몇 개를 실행합니다.

그런데 메인 메모리에서 값 하나를 읽어오는 데는 100나노초쯤 걸립니다. CPU 입장에서는 명령어 수백 개를 실행할 수 있는 시간입니다.

메모리에서 값을 가져올 때마다 그만큼 멍하니 기다린다면 CPU 성능의 대부분이 낭비됩니다.

### 그래서 cache가 있습니다

CPU 안에 작지만 빠른 메모리를 둡니다. 최근에 쓴 데이터를 여기 보관해두고, 다음에 같은 데이터가 필요하면 메인 메모리까지 안 가고 여기서 꺼냅니다. 이 저장소가 **cache**입니다.

보통 세 단계로 되어 있습니다.

| 단계 | 크기 정도 | 접근 시간 정도 | 위치 |
|---|---|---|---|
| L1 cache | 수십 킬로바이트 | 1나노초 정도 | core마다 하나 |
| L2 cache | 수백 킬로바이트에서 몇 메가바이트 | 몇 나노초 | core마다 하나 |
| L3 cache | 수 메가바이트에서 수십 메가바이트 | 수십 나노초 | core들이 공유 |
| 메인 메모리 | 수 기가바이트 | 100나노초 정도 | CPU 밖 |

찾는 데이터가 cache에 있으면 **cache hit**, 없어서 아래 단계까지 내려가야 하면 **cache miss**라고 합니다.

웹 개발자에게는 익숙한 구조입니다. 애플리케이션 안의 메모리 cache, Redis, 데이터베이스로 이어지는 계층과 똑같습니다. 가까울수록 빠르고 작고, 멀수록 느리고 큽니다. hit rate가 성능을 좌우하는 것도 같습니다.

### working set

프로그램이 최근에 활발히 쓰고 있는 데이터의 집합을 **working set**이라고 부릅니다.

프로그램이 한동안 실행되면 자기 working set이 cache에 올라옵니다. 그때부터는 대부분의 메모리 접근이 cache hit이 되어서 빠르게 돌아갑니다. 이 상태를 cache가 **warm하다**고 표현합니다.

### TLB

하나 더 있습니다.

각 process는 자기만의 가상 주소 공간을 씁니다. 프로그램이 주소 0x1000에 접근하면, 그게 실제 메모리의 어디인지 변환해야 합니다. 이 변환 정보는 페이지 테이블이라는 표에 들어 있는데, 표 자체가 메모리에 있습니다.

그러면 메모리 접근 한 번마다 표를 읽으려고 메모리에 또 접근해야 합니다. 배보다 배꼽이 큽니다.

그래서 최근 변환 결과를 담아두는 전용 cache가 따로 있습니다. **TLB**라고 부릅니다. 이것도 warm해야 빠릅니다.

## 4.4 보이지 않는 비용

이제 진짜 비용을 말할 수 있습니다.

task A가 한동안 실행돼서 cache가 A의 데이터로 채워졌습니다. TLB도 A의 주소 변환으로 채워졌습니다. A는 쾌적하게 돌아가고 있습니다.

여기서 context switch가 일어나 task B가 올라옵니다.

B는 자기 데이터를 쓰기 시작합니다. cache는 크기가 정해져 있으니 B의 데이터가 들어오면서 A의 데이터가 밀려납니다. TLB도 마찬가지입니다.

시간이 지나 다시 A의 차례가 옵니다. A는 register를 그대로 돌려받았으니 논리적으로는 아무 일도 없었습니다. 하지만 cache에 A의 데이터가 없습니다. **A는 처음부터 다시 cache를 데워야 합니다.**

그동안 A의 메모리 접근은 계속 cache miss가 나고, 매번 메인 메모리까지 다녀와야 합니다. A는 전환 직전보다 훨씬 느리게 돌아갑니다.

이 느려짐이 context switch의 진짜 비용입니다. register를 옮기는 몇 마이크로초보다 훨씬 크고, 무엇보다 **얼마나 큰지 예측하기 어렵습니다.** working set이 작은 프로그램은 금방 회복하고, 큰 프로그램은 오래 걸립니다.

### 웹 개발의 같은 현상

이미 겪어본 문제입니다.

서버 인스턴스를 새로 띄우면 처음 몇 분은 느립니다. 커넥션 풀이 비어 있고, 애플리케이션 cache가 비어 있고, JIT 컴파일러가 아직 최적화를 안 했습니다. 그래서 배포할 때 트래픽을 서서히 올립니다.

컨테이너가 자주 재시작되면 이 워밍업을 계속 다시 합니다. 실제 처리량이 눈에 띄게 떨어집니다.

context switch가 잦다는 건 이 워밍업을 초당 수천 번 하는 것과 같습니다.

## 4.5 그래서 time slice를 얼마로 해야 하나

이제 핵심 계산입니다.

전환 한 번에 드는 총비용을 C라고 하고, time slice를 S라고 합시다. task가 S만큼 일하고 C만큼 낭비하는 것을 반복합니다.

낭비 비율은 이렇습니다.

```text
   overhead = C / (S + C)
```

C를 5마이크로초로 놓고 S를 바꿔가며 계산해봅시다. 참고로 5마이크로초는 눈에 보이는 비용과 cache 회복 비용을 합친 대략적인 값입니다. 실제로는 상황에 따라 크게 달라지지만, 감을 잡기에는 충분합니다.

| time slice | 전환 낭비 비율 | 초당 전환 횟수 |
|---|---|---|
| 100마이크로초 | 4.8퍼센트 | 약 9500번 |
| 500마이크로초 | 1.0퍼센트 | 약 1980번 |
| 1밀리초 | 0.5퍼센트 | 약 995번 |
| 10밀리초 | 0.05퍼센트 | 약 100번 |
| 100밀리초 | 0.005퍼센트 | 약 10번 |

숫자만 보면 답이 명확해 보입니다. slice를 길게 하면 낭비가 줄어듭니다. 100밀리초로 하면 낭비가 거의 없습니다.

그런데 그러면 안 됩니다.

## 4.6 반대쪽 압력

task가 열 개 돌아가고 있고 slice가 100밀리초라고 해봅시다.

맨 뒤에 선 task는 앞의 아홉 개가 각각 100밀리초씩 쓸 때까지 기다려야 합니다. **900밀리초입니다.**

사람이 키를 눌렀는데 0.9초 뒤에 글자가 뜬다면 못 씁니다.

여기서 사람의 지각에 관한 숫자 하나를 알아두면 좋습니다. 상호작용에 대한 반응이 **0.1초** 안에 오면 사람은 즉각적이라고 느낍니다. 그보다 늦어지면 기다린다는 감각이 생깁니다. 이 값은 오래된 연구에서 나온 것이고 지금도 인터페이스 설계의 기준선으로 쓰입니다.

> **이 연구에서는.** 이 0.1초라는 값이 실제로 이 시리즈가 다루는 연구의 상수로 들어가 있습니다. 상호작용 지연이 이 값을 넘는 비율을 측정 metric 중 하나로 씁니다. 근거는 Miller가 1968년에 쓴 글과 Nielsen이 1993년에 쓴 책이고, 둘 다 원문을 확인해서 인용문까지 기록해뒀습니다. 뒤 권에서 이 metric이 어떻게 계산되는지 자세히 다룹니다.

그러니까 slice 결정에는 두 가지 압력이 반대 방향으로 작용합니다.

```text
   slice를 길게 ──────────────────► 전환 낭비 감소, 처리량 증가
                                     반응 시간 악화

   slice를 짧게 ──────────────────► 반응 시간 개선
                                     전환 낭비 증가, 처리량 감소
```

실제 시스템들이 쓰는 값은 대체로 밀리초 단위입니다. 몇 밀리초에서 수십 밀리초 사이입니다. 낭비를 1퍼센트 아래로 누르면서 반응성도 지킬 수 있는 구간이기 때문입니다.

> **이 연구에서는.** 실험의 기본 설정에서 최상위 priority의 time slice는 10밀리초입니다. 이 값은 임의로 고른 것이 아니라 널리 쓰이는 OS 교과서의 예제에서 통째로 가져왔습니다. 왜 통째로 가져왔는지, 그리고 그 선택이 결과에 얼마나 영향을 주는지 확인하기 위해 slice를 0.5밀리초부터 100밀리초까지 아홉 가지로 바꿔가며 다시 돌려보는 검사를 미리 계획에 넣어뒀습니다. 이런 식으로 "우리가 고른 값 하나 때문에 결론이 뒤집히지는 않는가"를 확인하는 절차를 sensitivity check라고 부르고, 뒤 권에서 다룹니다.

## 4.7 slice 하나로 안 되는 이유

여기서 자연스러운 질문이 나옵니다. 왜 모든 task에 같은 slice를 줘야 하나요?

줄 필요 없습니다. 그리고 실제로 안 줍니다.

편집기처럼 짧게 쓰고 잠드는 task에게는 긴 slice가 의미 없습니다. 어차피 1, 2밀리초 쓰고 스스로 내려갑니다. 반면 압축 작업 같은 task는 긴 slice를 받을수록 효율이 좋아집니다.

그래서 **task마다 다른 slice를 주는 것**이 좋은 아이디어가 됩니다. 뒤에서 다룰 MLFQ가 바로 이 아이디어를 씁니다. priority가 높은 task에게는 짧은 slice를, 낮은 task에게는 긴 slice를 줍니다.

언뜻 거꾸로인 것 같지만 이유가 있습니다. priority가 높은 task는 대화형일 가능성이 높고, 대화형 task는 어차피 slice를 다 쓰지 않습니다. priority가 낮은 task는 계산 작업일 가능성이 높고, 그런 task에게는 긴 slice가 이득입니다.

## 4.8 전환은 왜 일어나는가에 따라 값이 다릅니다

전환이 일어나는 이유는 앞에서 정리했듯이 몇 가지가 있습니다. 그중 두 가지를 비교해보면 흥미롭습니다.

**time slice를 다 써서 일어나는 전환.** 이건 순수한 손실입니다. task는 계속 일하고 싶었는데 강제로 내려왔고, 나중에 다시 올라와서 cache를 다시 데워야 합니다.

**task가 스스로 잠들어서 일어나는 전환.** 이건 손실이 아닙니다. 어차피 이 task는 기다려야 해서 core를 쓸 수 없었습니다. 오히려 안 넘기면 낭비입니다.

같은 context switch이지만 성격이 정반대입니다.

그래서 scheduler를 평가할 때 전환 횟수만 세는 것은 의미가 약합니다. **강제로 끌어내린 횟수**를 따로 세는 것이 훨씬 유용합니다.

> **이 연구에서는.** 측정 항목 중에 강제로 끌어내린 횟수를 따로 세는 것이 있습니다. task마다 몇 번이나 preemption을 당했는지 기록합니다. 자발적으로 잠든 것은 여기 안 들어갑니다.

## 4.9 core를 옮기면 더 비쌉니다

core가 여러 개인 시스템에서 task를 core A에서 core B로 옮기는 것을 **migration**이라고 합니다.

이건 같은 core에서의 전환보다 훨씬 비쌉니다. core마다 자기 L1과 L2 cache를 따로 가지고 있어서, 옮기면 그 cache를 통째로 못 쓰게 되기 때문입니다.

그래서 scheduler는 가능하면 task를 원래 있던 core에 다시 올리려고 합니다. 이 성질을 **cache affinity**라고 부릅니다.

여기서 multicore scheduling의 근본적인 긴장이 생깁니다. 부하를 고르게 나누려면 옮겨야 하는데, 옮기면 cache를 잃습니다. 균형과 지역성 사이의 trade-off입니다.

앞에서 말했듯이 이 시리즈의 실험은 core 하나만 씁니다. 그래서 이 문제는 다루지 않습니다. 하지만 실제 시스템에서 얼마나 큰 문제인지는 알아두는 게 좋습니다.

## 4.10 그런데 왜 이 연구는 전환 비용을 직접 모델링하지 않는가

미리 알아두면 좋은 설계 결정이 하나 있습니다.

이 시리즈가 다루는 연구는 실제 하드웨어가 아니라 시뮬레이터 위에서 실험합니다. 시뮬레이터는 가상의 시간축 위에서 task들이 실행되는 것을 흉내 냅니다.

그런데 이 시뮬레이터는 cache가 식는 비용을 모델링하지 않습니다. 일부러 그렇게 했습니다.

이유는 이렇습니다. cache가 얼마나 식는지는 task의 working set 크기, cache 크기, 어떤 task가 사이에 끼어들었는지에 따라 크게 달라집니다. 이걸 정확히 흉내 내려면 cache 시뮬레이터를 통째로 만들어야 하고, 그러면 결과가 그 시뮬레이터의 정확도에 좌우됩니다. 실험이 측정하려는 것은 scheduling policy의 차이인데, cache 모델의 부정확성이 그 차이를 덮어버릴 수 있습니다.

대신 다른 방식으로 접근합니다. 전환이 실제로 몇 번 일어났는지를 세어서 따로 보고합니다. 어떤 설정이 다른 설정보다 전환을 훨씬 많이 일으켰다면, 실제 하드웨어에서는 그만큼 추가 손해가 있을 것이라고 읽습니다.

측정할 수 없는 것을 추정하지 않고, 대신 그 대리 metric을 정직하게 보고하는 방식입니다. 이런 판단이 연구 설계 전반에 반복해서 나옵니다.

## 4장 정리

- context switch는 실행 중인 task를 내리고 다른 task를 올리는 동작입니다. register를 저장하고 복원하는 눈에 보이는 비용은 마이크로초 단위로 크지 않습니다.
- 진짜 비용은 cache에 있습니다. task가 실행되는 동안 자기 데이터로 cache를 채워두는데, 전환이 일어나면 다른 task의 데이터가 그걸 밀어냅니다. 다시 차례가 왔을 때 cache를 처음부터 데워야 하고, 그동안 눈에 띄게 느립니다.
- 이건 웹 서버 인스턴스를 새로 띄웠을 때 커넥션 풀과 cache가 비어 있어서 느린 것과 같은 현상입니다.
- time slice를 길게 하면 전환 낭비가 줄지만 반응 시간이 나빠집니다. 짧게 하면 반대입니다. 실제 시스템은 밀리초 단위에서 타협합니다.
- 사람은 상호작용에 대한 반응이 0.1초 안에 오면 즉각적이라고 느낍니다. 이 값이 반응 시간 쪽 압력의 기준선입니다.
- 모든 task에 같은 slice를 줄 필요는 없습니다. 대화형 task에게는 짧게, 계산 작업에게는 길게 주는 것이 합리적이고, MLFQ가 그렇게 합니다.
- 같은 전환이라도 time slice 소진으로 강제로 내려온 것과 스스로 잠들어서 내려온 것은 성격이 다릅니다. 앞엣것만 손실입니다. 그래서 강제로 끌어내린 횟수를 따로 세는 것이 의미 있습니다.
- core를 옮기는 migration은 cache를 통째로 잃기 때문에 더 비쌉니다. 부하 균형과 cache 지역성 사이에 trade-off가 있습니다.

# 5장 · 좋은 scheduling이란 무엇인가

## 5.1 "더 좋다"는 말이 성립하려면

scheduler A와 scheduler B가 있습니다. 어느 쪽이 더 좋을까요?

이 질문은 그대로는 답할 수 없습니다. **무엇을 기준으로 좋은지**를 먼저 정해야 하기 때문입니다.

이건 웹 서비스 성능 이야기와 똑같습니다. "이 서버가 더 빠르다"는 말은 평균 응답 시간을 말하는 건지, 99퍼센타일을 말하는 건지, 초당 처리 건수를 말하는 건지에 따라 완전히 다른 주장이 됩니다. 어떤 변경은 평균은 개선하면서 꼬리는 악화시킵니다.

scheduling도 같습니다. 그래서 이 장에서 metric을 하나씩 정확히 정의합니다. 이 metric들은 이 시리즈 전체에서 계속 나오니까, 여기서 확실히 잡아두면 나중이 훨씬 수월합니다.

## 5.2 시간에 관한 metric들

먼저 task 하나의 생애에서 잴 수 있는 시간들을 봅시다.

```text
   arrival        first run           completion
      │               │                    │
      ▼               ▼                    ▼
   ───┬───────────────┬────────────────────┬────────►  시간
      │               │                    │
      │◄── response ─►│                    │
      │    time       │                    │
      │                                    │
      │◄──────────  turnaround time ──────►│
```

### Response time

task가 실행 준비를 마친 순간부터, 실제로 처음 실행되기 시작한 순간까지의 시간입니다.

"얼마나 빨리 시작했는가"를 재는 metric입니다. 얼마나 오래 걸려서 끝났는지는 상관없습니다.

키를 눌렀을 때 글자가 뜨는 속도, 버튼을 눌렀을 때 화면이 반응하는 속도가 전부 이 metric입니다. **사람이 체감하는 것은 거의 전부 response time입니다.**

용어를 하나 더 짚어두면, task가 잠들었다가 깨어난 경우에도 같은 걸 잽니다. 깨어나서 ready가 된 순간부터 실제 실행까지의 시간입니다. 실제로 대화형 프로그램에서는 이쪽이 훨씬 중요합니다. 편집기는 하루에 한 번 시작하지만 키 입력마다 깨어나니까요.

> **이 연구에서는.** 이 시리즈가 다루는 연구가 가장 중요하게 보는 숫자가 이겁니다. 시뮬레이터가 남기는 기록에서 "task가 ready가 된 시각"과 "실제로 실행이 시작된 시각"을 뽑아 그 차이를 계산합니다. 그리고 그 차이가 왜 생겼는지도 함께 기록합니다. 깨어나서 기다린 것인지, 강제로 내려왔다가 다시 올라가느라 기다린 것인지를 구분합니다. 앞엣것이 사람이 느끼는 지연이고, 뒤엣것은 그렇지 않습니다.

### Turnaround time

task가 도착한 순간부터 완전히 끝난 순간까지의 시간입니다.

"얼마나 걸려서 끝났는가"를 재는 metric입니다. 중간에 얼마나 기다렸든 상관없이 총 경과 시간입니다.

빌드 작업, 인코딩, 백업 같은 일에 어울립니다. 이런 작업은 언제 시작했는지보다 언제 끝나는지가 중요합니다.

### Waiting time

task가 ready 상태로 기다린 시간의 총합입니다. blocked로 기다린 시간은 빼고, 실행할 준비가 됐는데 차례를 못 받아 기다린 시간만 셉니다.

앞에서 강조했듯이 이 구분이 중요합니다. 디스크가 느려서 기다린 것은 scheduler 탓이 아니지만, 실행 준비가 됐는데 못 실행된 것은 scheduler 탓입니다.

## 5.3 양에 관한 metric들

### Throughput

단위 시간당 완료한 task의 수입니다. 초당 몇 건 처리했는가입니다.

웹 서버의 초당 요청 처리 건수와 같은 개념입니다.

### CPU utilization

전체 시간 중 core가 실제로 일한 시간의 비율입니다.

core가 놀고 있으면 낭비이므로 높을수록 좋아 보이지만, 주의할 점이 있습니다. **낭비되는 일을 하느라 바쁜 것도 utilization은 높게 나옵니다.** context switch에 쓰는 시간, 필요 없는 작업에 쓰는 시간이 다 포함됩니다.

그래서 utilization은 단독으로 좋고 나쁨을 판단하는 metric이 아니라, 다른 metric을 해석할 때 참고하는 값으로 씁니다.

### Makespan

여러 task로 이루어진 작업 묶음 전체가 끝나는 데 걸린 시간입니다. 마지막 task가 끝난 시각입니다.

빌드처럼 여러 조각이 병렬로 도는 작업에서는 개별 조각의 시간보다 전체가 언제 끝나는지가 중요합니다. 그때 쓰는 metric입니다.

## 5.4 fairness와 starvation

### Fairness

각 task가 받아야 할 share만큼 CPU를 받았는가입니다.

task가 세 개면 각각 3분의 1씩 받는 것이 산술적으로 공정합니다. 하지만 실제로는 이렇게 단순하지 않습니다. priority가 다를 수도 있고, 중요도가 다를 수도 있습니다.

### Starvation

특정 task가 계속 차례를 못 받는 상황입니다. 우리말로는 기아라고 합니다.

priority 기반 scheduler에서 잘 생깁니다. 높은 priority task가 계속 들어오면 낮은 priority task는 영원히 실행되지 못할 수 있습니다.

평균 metric만 보면 이 문제가 안 보입니다. task 열 개 중 아홉 개가 아주 잘 돌아가고 하나가 완전히 굶고 있어도, 평균은 괜찮게 나옵니다. 그래서 starvation은 평균이 아니라 최악의 경우로 확인해야 합니다.

## 5.5 deadline에 관한 metric

어떤 작업은 "언제까지"가 정해져 있습니다.

초당 60 frame으로 화면을 그리는 게임은 약 16.7밀리초마다 한 frame을 완성해야 합니다. 늦으면 화면이 끊깁니다. 오디오를 재생하는 프로그램은 버퍼가 비기 전에 다음 조각을 채워야 합니다. 늦으면 소리가 튑니다.

정해진 시각을 **deadline**이라고 부릅니다.

### Deadline miss rate

전체 작업 중 deadline을 넘긴 비율입니다.

여기서 중요한 것은 **얼마나 늦었는지가 아니라 늦었는지 여부**라는 점입니다. frame 하나가 1밀리초 늦든 10밀리초 늦든, 사용자에게는 똑같이 끊긴 frame 하나입니다.

그래서 이런 작업에서는 평균 지연을 보는 것이 별 의미가 없습니다. 평균이 아무리 좋아도 가끔 넘기면 사용자는 끊김을 봅니다.

## 5.6 평균은 거짓말을 합니다

이제 이 장에서 가장 중요한 부분입니다.

metric을 계산할 때 대부분 평균을 냅니다. 평균 response time, 평균 turnaround time. 편하고 직관적입니다.

그런데 평균은 자주 진실을 가립니다.

### 예제로 보기

편집기에서 키를 100번 눌렀습니다. 각 키 입력에 대한 response time을 재봤습니다.

**scheduler A의 결과**

- 100번 모두 5밀리초

평균은 5밀리초입니다.

**scheduler B의 결과**

- 99번은 1밀리초
- 1번은 400밀리초

평균을 계산해보면 이렇습니다.

```text
   (99 × 1 + 1 × 400) / 100 = 499 / 100 = 4.99 밀리초
```

평균은 4.99밀리초입니다. **A보다 좋습니다.**

숫자만 보면 B가 이겼습니다. 그런데 실제로 써보면 어떨까요?

A는 항상 즉각적입니다. B는 대부분 A보다 빠르지만, 백 번에 한 번 0.4초 동안 멈춥니다. 타이핑하다가 글자가 뭉텅이로 튀어나오는 경험을 하게 됩니다.

**사람은 B를 훨씬 나쁘게 느낍니다.** 평균은 정반대를 말했습니다.

### 웹 개발에서 이미 아는 이야기

이건 API 응답 시간을 다뤄본 사람에게는 익숙한 문제입니다.

평균 응답 시간이 50밀리초라고 자랑해도, 99퍼센타일이 3초라면 사용자 백 명 중 한 명은 3초를 기다립니다. 페이지 하나에 API를 열 번 호출한다면, 한 페이지가 3초 걸릴 확률이 10퍼센트에 가깝습니다.

그래서 SLO를 정할 때 평균이 아니라 퍼센타일을 씁니다.

### percentile

**P99**는 값들을 작은 순서로 늘어놓았을 때 아래에서 99퍼센트 지점에 있는 값입니다. "100번 중 99번은 이 값보다 좋았다"는 뜻입니다.

앞의 예제를 다시 보면 이렇습니다.

| | 평균 | P50 | P99 | 최댓값 |
|---|---|---|---|---|
| scheduler A | 5.0ms | 5ms | 5ms | 5ms |
| scheduler B | 4.99ms | 1ms | 400ms | 400ms |

P99를 보면 A가 5밀리초, B가 400밀리초입니다. 80배 차이입니다. 이제 숫자가 체감과 일치합니다.

P50은 중앙값입니다. 여기서는 B가 훨씬 좋게 나옵니다. 사실입니다. B는 대부분의 경우 정말 빠릅니다.

**두 숫자를 같이 봐야 전체가 보입니다.** P50은 평소 얼마나 빠른지, P99는 가끔 얼마나 나쁜지를 말해줍니다.

### 직접 계산해보기

값이 열 개 있다고 합시다. 단위는 밀리초입니다.

```text
   2, 3, 3, 4, 4, 5, 6, 8, 12, 90
```

평균은 이렇습니다.

```text
   (2+3+3+4+4+5+6+8+12+90) / 10 = 137 / 10 = 13.7
```

정렬은 이미 되어 있습니다. P50은 가운데입니다. 값이 짝수 개일 때 중간 두 개의 평균을 쓰는 방식으로 하면 4와 5의 평균인 4.5입니다.

여기서 눈에 띄는 게 있습니다. **평균 13.7이 열 개 값 중 여덟 개보다 큽니다.** 90 하나가 평균을 끌어올렸습니다.

이런 분포에서 평균은 대표값 노릇을 못 합니다. "보통 얼마나 걸리나"를 묻는다면 4.5가 답이고, "가끔 얼마나 나쁜가"를 묻는다면 90이 답입니다. 13.7은 어느 질문에도 답이 아닙니다.

응답 시간 분포는 거의 항상 이런 모양입니다. 대부분은 몰려 있고 꼬리가 길게 늘어집니다.

> **이 연구에서는.** 지연 metric을 평균만으로 보지 않습니다. 같은 값들에 대해 평균, P50, P95, P99, 최댓값을 전부 계산해두고, 어떤 상황을 판단하느냐에 따라 다른 것을 씁니다. 게임처럼 끊김이 치명적인 상황에서는 P99를 보고, 배경 작업이 도는 상황에서는 진행량을 봅니다. 어느 상황에서 어느 숫자를 볼지를 미리 정해서 파일로 적어두고, 결과를 본 뒤에 유리한 숫자를 고르는 일이 생기지 않게 막아둡니다. 이 장치가 왜 필요한지는 뒤 권에서 자세히 다룹니다.

## 5.7 metric들은 서로 싸웁니다

이제 이 장의 결론으로 갑니다.

지금까지 metric을 여럿 봤습니다. 여기서 중요한 사실은 **이 metric들을 동시에 다 좋게 만들 수 없다**는 것입니다.

### response time과 throughput

response time을 좋게 하려면 time slice를 짧게 하고 자주 전환해야 합니다. 그러면 새로 깨어난 task가 빨리 실행됩니다.

하지만 자주 전환하면 전환 비용이 늘어나고 cache가 계속 식습니다. throughput이 떨어집니다.

### turnaround time과 fairness

전체 turnaround time을 최소화하려면 짧은 작업부터 먼저 처리해야 합니다. 이건 수학적으로 증명할 수 있는데, 다음 장에서 다룹니다.

하지만 짧은 작업을 계속 먼저 처리하면 긴 작업은 계속 밀립니다. 극단적으로는 starvation이 생깁니다.

### deadline과 throughput

deadline을 지키려면 deadline이 임박한 작업에 자주 끼어들어야 합니다. 그러면 전환이 늘고 throughput이 떨어집니다.

### 결론

**모든 상황에서 최고인 scheduler는 존재하지 않습니다.**

이건 구현을 잘하면 해결되는 문제가 아니라 논리적으로 불가능한 일입니다. metric들이 서로 반대 방향을 가리키기 때문입니다.

그래서 실제 질문은 이렇게 바뀝니다.

> **지금 이 컴퓨터에서는 어느 metric이 중요한가?**

게임을 하는 중이라면 frame deadline이 압도적으로 중요합니다. 응답 지연 몇 밀리초를 위해 전환을 늘려도 좋습니다.

빌드를 돌려놓고 자리를 비웠다면 오직 makespan만 중요합니다. 반응 속도는 아무 의미가 없습니다.

영상 통화 중이라면 오디오와 비디오의 deadline이 중요하고, 동시에 화면 공유가 끊기지 않아야 합니다.

같은 컴퓨터, 같은 하드웨어인데 **무엇을 하고 있느냐에 따라 좋은 scheduling의 정의 자체가 바뀝니다.**

## 5.8 그래서 이 시리즈가 다루는 연구가 있습니다

앞 절의 결론을 다시 읽어보면, 자연스러운 다음 질문이 나옵니다.

좋은 scheduling의 정의가 "지금 무엇을 하고 있느냐"에 달려 있다면, OS는 지금 무엇을 하고 있는지 알아야 합니다.

**그런데 OS는 그걸 모릅니다.**

OS가 볼 수 있는 것은 각 task가 CPU를 얼마나 쓰는지, 얼마나 자주 잠드는지 같은 행동 패턴뿐입니다. 이 컴퓨터에서 사람이 게임을 하고 있는지 영상을 편집하고 있는지는 알 수 없습니다.

지금까지 OS들은 두 가지 방법으로 이 문제를 우회했습니다.

첫째, 행동 패턴으로 추측합니다. 자주 잠드는 task는 대화형일 것이라고 가정하는 식입니다. 다음 장부터 다룰 알고리즘들이 이 방법을 씁니다.

둘째, 사람이 미리 목록을 적어둡니다. "이 실행 파일 이름들은 게임이다"라는 표를 만들어두는 식입니다. 실제로 그렇게 하고 있고, 뒤에서 자세히 봅니다.

이 시리즈가 다루는 연구는 세 번째 방법을 제안합니다. **지금 돌아가는 프로그램들의 이름을 언어 모델에게 보여주고, 이 컴퓨터가 무엇에 쓰이고 있는지 읽어내게 하는 것입니다.**

왜 그게 앞의 두 방법보다 나을 수 있는지, 정말 나은지, 어떻게 확인할 것인지가 이 시리즈의 나머지 전부입니다.

지금은 여기까지만 알아두면 됩니다. **좋은 scheduling의 정의는 상황에 따라 달라지고, OS는 그 상황을 모른다.**

## 5장 정리

- "어느 scheduler가 더 좋은가"는 기준을 정하지 않으면 답할 수 없는 질문입니다.
- Response time은 실행 준비가 된 순간부터 실제 실행까지의 시간입니다. 사람이 체감하는 것은 거의 전부 이 값입니다. Turnaround time은 도착부터 완료까지의 총 경과 시간이고, 배경 작업에 어울립니다.
- Throughput은 단위 시간당 완료 건수, makespan은 작업 묶음 전체가 끝나는 시각, fairness는 각자 받아야 할 share를 받았는지입니다. Starvation은 특정 task가 계속 차례를 못 받는 상황이고, 평균으로는 안 보입니다.
- Deadline이 있는 작업에서는 얼마나 늦었는지가 아니라 늦었는지 여부가 중요합니다. 그래서 miss rate를 씁니다.
- 평균은 자주 거짓말을 합니다. 대부분 빠르고 가끔 아주 느린 분포에서 평균은 어느 질문에도 답이 되지 못합니다. P50으로 평소 성능을, P99로 최악의 경우를 봐야 합니다.
- metric들은 서로 충돌합니다. response time을 좋게 하면 throughput이 나빠지고, turnaround를 최적화하면 fairness가 무너집니다. 모든 상황에서 최고인 scheduler는 논리적으로 존재할 수 없습니다.
- 그래서 진짜 질문은 "지금 이 컴퓨터에서 어느 metric이 중요한가"입니다. 그리고 OS는 그걸 모릅니다. 이 사실이 이 시리즈 전체의 출발점입니다.

# 6장 · interactive와 batch

## 6.1 scheduler가 하는 가장 중요한 구분

scheduling 알고리즘들이 어떻게 다른지 배우기 전에, 그 알고리즘들이 공통으로 붙잡고 있는 구분 하나를 먼저 봐야 합니다.

**사람이 앞에서 기다리는 일**과 **아무도 안 기다리는 일**의 구분입니다.

이 둘은 원하는 대우가 정반대입니다. 그리고 거의 모든 scheduling 알고리즘은 결국 이 둘을 어떻게 구분하고 어떻게 다르게 대우할 것인가에 대한 답입니다.

## 6.2 interactive

**interactive**한 task는 사람이 반응을 기다리고 있는 task입니다. 우리말로는 대화형이라고 합니다.

전형적인 예를 봅시다.

**텍스트 편집기.** 키를 누르면 깨어나서 글자를 처리하고 화면을 갱신합니다. 1, 2밀리초면 끝납니다. 그리고 다음 키를 기다리며 잡니다.

**터미널 shell.** 명령어를 입력하면 처리하고, 다시 기다립니다.

**웹 브라우저의 UI 부분.** 스크롤하거나 클릭하면 반응합니다.

이들의 공통점은 이렇습니다.

- **CPU를 거의 안 씁니다.** 하루 종일 켜놔도 사용률이 1퍼센트 안팎입니다.
- **대부분의 시간을 자고 있습니다.** 사람의 다음 동작을 기다립니다.
- **한 번 깨어나면 아주 짧게 일합니다.** 밀리초 단위입니다.
- **그런데 깨어난 그 순간에는 즉시 실행돼야 합니다.**

마지막 항목이 핵심입니다. 총 CPU 사용량은 무시해도 될 만큼 작은데, **언제 실행되느냐**가 전부입니다.

앞 장에서 봤듯이 사람은 0.1초 안에 반응이 오면 즉각적이라고 느낍니다. 그러니까 편집기가 깨어난 뒤 0.1초 안에 실행되기만 하면 됩니다. 그 안에만 들어오면 5밀리초든 50밀리초든 사람은 구분하지 못합니다. 하지만 200밀리초가 되면 확실히 느낍니다.

## 6.3 batch

**batch** task는 아무도 앞에서 기다리지 않는 task입니다. 우리말로는 일괄 처리라고 하는데, 이 책에서는 batch를 그대로 씁니다.

전형적인 예입니다.

**소스 코드 컴파일.** 시작하면 끝날 때까지 계산합니다.

**영상 인코딩.** 마찬가지입니다.

**백업.** 파일을 읽어서 압축하고 어딘가로 보냅니다.

**머신러닝 학습.** 몇 시간씩 GPU와 CPU를 씁니다.

**파일 색인 작업.** 디스크를 훑으면서 검색용 색인을 만듭니다.

공통점입니다.

- **CPU를 최대한 씁니다.** 주면 주는 대로 다 씁니다.
- **자발적으로 잠드는 일이 드뭅니다.** 파일을 읽을 때 잠깐 자는 정도입니다.
- **한 번 실행되면 길게 갑니다.**
- **언제 실행되는지는 중요하지 않습니다. 총 걸린 시간이 중요합니다.**

## 6.4 정반대의 대우를 원합니다

두 종류가 원하는 것을 나란히 놓아봅시다.

| | interactive | batch |
|---|---|---|
| 중요한 metric | response time | turnaround time, throughput |
| 원하는 priority | 높게 | 낮아도 됨 |
| 원하는 time slice | 짧아도 됨 | 길게 |
| 전환을 자주 당하면 | 상관없음 | 손해가 큼 |
| 총 CPU 요구량 | 아주 적음 | 아주 많음 |

여기서 좋은 소식이 하나 있습니다. **두 요구가 사실은 잘 맞습니다.**

interactive task는 priority를 높게 줘도 CPU를 거의 안 씁니다. 그러니까 높은 priority를 줘도 batch task가 크게 손해 보지 않습니다.

batch task는 priority가 낮아도 괜찮습니다. 어차피 interactive task들이 CPU를 거의 안 쓰니까, 남는 시간을 다 가져가면 됩니다.

그래서 고전적인 해법이 나옵니다.

> **interactive에게는 높은 priority와 짧은 time slice를, batch에게는 낮은 priority와 긴 time slice를 준다.**

priority가 높은데 slice가 짧은 게 이상해 보이지만 앞에서 설명했듯이 이유가 있습니다. interactive task는 어차피 slice를 다 안 씁니다. 몇 밀리초 쓰고 스스로 내려갑니다. 그러니 긴 slice를 줘봤자 의미가 없고, 짧게 줘도 손해가 없습니다.

반대로 batch task는 긴 slice를 받을수록 좋습니다. 전환이 줄고 cache가 유지되니까요.

이 조합이 뒤에서 다룰 MLFQ의 핵심 아이디어입니다.

## 6.5 그런데 누가 어느 쪽인지 어떻게 아는가

여기가 진짜 문제입니다.

프로그램이 스스로 "저는 대화형입니다"라고 말해줄 수도 있습니다. 실제로 그런 방법이 있고, 뒤에서 다룹니다. 하지만 대부분의 프로그램은 아무 말도 안 합니다.

그래서 OS는 **행동을 보고 추측합니다.**

### 핵심 단서: 어떻게 CPU를 놓았는가

앞에서 정리했듯이 실행 중인 task가 core를 놓는 방식은 두 가지입니다.

**time slice를 다 써서 강제로 내려온 경우.** 이 task는 계속 계산하고 싶었습니다. 주어진 시간을 다 쓰고도 모자랐습니다. 그러니까 batch일 가능성이 높습니다.

**스스로 잠들어서 내려온 경우.** 이 task는 할 일을 마치고 뭔가를 기다리러 갔습니다. 짧게 일하고 잠들었다면 interactive일 가능성이 높습니다.

이 단서 하나로 꽤 잘 구분됩니다. 그래서 거의 모든 실제 scheduler가 이걸 씁니다.

규칙으로 쓰면 이렇습니다.

```text
   slice를 다 씀      →  batch스럽다     →  priority를 낮춘다
   스스로 잠듦        →  interactive스럽다 →  priority를 유지한다
```

### 다른 단서들

**깨어나는 빈도와 규칙성.** 규칙적으로 깨어나면 주기적인 작업, 불규칙하게 깨어나면 이벤트 기반 작업일 가능성이 높습니다.

**한 번에 쓰는 시간의 분포.** 항상 1밀리초 안팎이면 interactive스럽고, 항상 slice를 다 쓰면 batch스럽습니다.

**누구를 깨우는가.** 다른 task를 깨우는 task는 어떤 흐름의 중간 단계일 가능성이 있습니다.

## 6.6 이 추측이 틀리는 경우들

행동 관찰은 잘 동작합니다. 하지만 완벽하지 않습니다. 틀리는 경우를 하나씩 봅시다.

### 성격이 바뀌는 프로그램

편집기가 저장 버튼을 누르는 순간 큰 파일을 압축해서 쓴다고 해봅시다. 몇 초 동안 batch처럼 행동합니다. 그러면 scheduler는 priority를 낮춥니다.

저장이 끝나고 다시 타이핑을 시작하면 interactive로 돌아가야 하는데, scheduler는 이미 낮춰버린 priority를 가지고 있습니다. 회복이 늦으면 그동안 반응이 굼뜹니다.

이 문제 때문에 대부분의 scheduler에 "주기적으로 모두 원상복구하는" 장치가 들어갑니다. 뒤에서 다룹니다.

### 대부분의 프로그램이 섞여 있습니다

현실의 프로그램은 순수한 interactive나 순수한 batch가 아닙니다.

웹 브라우저를 생각해봅시다. 스크롤에 반응하는 부분은 완벽하게 interactive입니다. 그런데 JavaScript를 실행하는 부분은 상황에 따라 batch처럼 행동합니다. 영상을 재생하는 탭은 주기적인 작업입니다. 백그라운드 탭은 아무것도 안 합니다.

이들이 전부 같은 프로그램 안에 있고, 실제로는 여러 process와 thread로 나뉘어 있습니다. 어떤 것은 interactive고 어떤 것은 아닙니다.

### 그리고 결정적인 문제

여기가 이 시리즈 전체에서 가장 중요한 지점입니다.

**행동이 완전히 똑같은데 올바른 대우가 다른 경우가 있습니다.**

예를 봅시다.

컴퓨터에서 게임이 돌아가고 있습니다. 동시에 배경에서 대용량 파일 하나가 내려받아지고 있습니다.

scheduler가 보는 것은 이렇습니다.

- 게임 process: 주기적으로 깨어나서 frame을 만드는 task들
- 다운로드 process: 네트워크에서 데이터를 받아 디스크에 쓰는 task

이 상황이 두 가지일 수 있습니다.

**상황 1.** 사용자가 게임을 하다가 다음에 플레이할 콘텐츠를 미리 받아두는 중입니다. 지금 게임에 집중하고 있고, 다운로드는 언제 끝나든 상관없습니다.

**상황 2.** 사용자가 친구들과 같이 하려고 게임 업데이트를 받는 중입니다. 다운로드가 끝나기를 기다리면서 시간을 때우려고 다른 모드를 돌리고 있습니다. 다운로드가 빨리 끝나는 게 중요합니다.

**올바른 scheduling이 정반대입니다.**

상황 1에서는 다운로드를 억눌러서 게임 frame을 지켜야 합니다. 다운로드가 조금 느려져도 사용자는 신경 쓰지 않습니다.

상황 2에서는 다운로드에 자원을 줘야 합니다. 게임 frame이 조금 떨어져도 사용자는 다운로드 진행률을 보고 있습니다.

그런데 **scheduler가 관찰할 수 있는 행동은 두 상황에서 완전히 동일합니다.** CPU 사용 패턴, 깨어나는 빈도, 잠드는 방식, 전부 같습니다.

무엇이 다른가요? **사용자의 의도**가 다릅니다. 그리고 의도는 행동에 나타나지 않습니다.

### 다른 예

같은 종류의 상황은 많습니다.

컴퓨터가 몇 시간째 CPU를 100퍼센트 쓰고 있습니다.

- 사용자가 직접 시작한 머신러닝 학습일 수도 있습니다. 결과를 기다리고 있으니 빨리 끝나야 합니다.
- 백신 프로그램의 예약 전체 검사일 수도 있습니다. 아무도 부탁하지 않았고, 사용자가 뭘 하든 방해하면 안 됩니다.

행동은 똑같습니다. CPU를 계속 쓰고, 디스크를 읽고, 가끔 잠듭니다.

올바른 대우는 정반대입니다.

## 6.7 그래서 사람이 표를 만들었습니다

이 문제를 실제 OS들이 어떻게 다루고 있을까요?

**목록을 만들어뒀습니다.**

Windows와 macOS에는 게임 모드가 있습니다. 알려진 게임 실행 파일의 목록을 가지고 있다가, 그중 하나가 실행되면 시스템 설정을 바꿉니다. 배경 작업을 억누르고 게임에 자원을 몰아줍니다.

priority class라는 것도 있습니다. 프로그램이 스스로 "저는 배경 작업입니다"라고 선언하면 OS가 그에 맞게 대우합니다.

이 방법들은 실제로 동작합니다. 하지만 한계가 명확합니다.

**목록에 없는 프로그램은 알 수 없습니다.** 어제 나온 게임, 소규모 개발자가 만든 프로그램, 회사 내부 도구는 목록에 없습니다.

**목록은 하나의 구분만 표현합니다.** "게임이냐 아니냐"를 아는 표는 "이 배경 작업을 사용자가 기다리고 있느냐"를 알려주지 못합니다. 그걸 알려면 표를 또 만들어야 합니다.

**그리고 조합은 표로 못 만듭니다.** 앞의 다운로드 예제를 다시 보세요. 게임 실행 파일 이름과 다운로드 프로그램 이름을 둘 다 목록에 넣어둬도, 두 상황을 구분할 수 없습니다. 구분은 개별 프로그램이 아니라 **조합과 맥락**에 있기 때문입니다.

## 6.8 이 시리즈의 연구가 서 있는 자리

지금까지의 이야기를 한 줄로 정리하면 이렇습니다.

> scheduler는 행동을 보고 추측한다. 추측이 안 되는 부분은 사람이 표로 적어둔다. 그런데 그 표가 표현할 수 없는 것이 있다.

이 시리즈가 다루는 연구는 세 번째 방법을 제안합니다.

**지금 실행 중인 프로그램들의 이름을 언어 모델에게 보여주고, 이 컴퓨터가 무엇에 쓰이고 있는지 문장으로 읽어내게 하는 것입니다.**

언어 모델은 세상에 어떤 소프트웨어가 있고 그게 무엇에 쓰이는지 이미 알고 있습니다. 어제 나온 게임의 실행 파일 이름을 보고도 그게 게임 같다고 짐작할 수 있습니다. 그리고 프로그램 이름들의 조합을 보고 "게임을 하면서 뭔가를 받고 있다"는 상황을 읽어낼 수 있습니다.

물론 이건 아직 주장일 뿐입니다. 정말 그런지, 그리고 그게 실제로 더 나은 scheduling으로 이어지는지는 측정해야 압니다. 그 측정을 설계하고 수행하는 것이 이 연구입니다.

지금은 문제가 무엇인지만 확실히 잡아두면 됩니다. 다음 장부터는 실제 scheduling 알고리즘들이 이 문제를 어떻게 다루는지 하나씩 봅니다.

## 6장 정리

- scheduling에서 가장 중요한 구분은 사람이 앞에서 기다리는 interactive 작업과 아무도 안 기다리는 batch 작업입니다.
- interactive는 CPU를 거의 안 쓰고 대부분 자고 있지만, 깨어난 순간 즉시 실행돼야 합니다. batch는 CPU를 최대한 쓰고 자발적으로 잠들지 않으며, 언제 실행되든 총 걸린 시간만 중요합니다.
- 두 요구는 잘 맞습니다. interactive에게 높은 priority와 짧은 slice를, batch에게 낮은 priority와 긴 slice를 주면 둘 다 만족합니다.
- 누가 어느 쪽인지는 행동으로 추측합니다. 핵심 단서는 CPU를 어떻게 놓았는가입니다. slice를 다 쓰고 강제로 내려왔으면 batch, 스스로 잠들었으면 interactive로 봅니다.
- 이 추측은 대체로 잘 맞지만 세 가지 경우에 틀립니다. 프로그램의 성격이 도중에 바뀔 때, 하나의 프로그램 안에 두 성격이 섞여 있을 때, 그리고 행동이 똑같은데 올바른 대우가 다를 때입니다.
- 마지막 경우가 결정적입니다. 게임 중에 도는 다운로드를 사용자가 기다리고 있는지 아닌지는 행동으로 구분되지 않지만, 올바른 scheduling은 정반대입니다. 차이는 사용자의 의도에 있고 의도는 행동에 나타나지 않습니다.
- 지금 시스템들은 이 부분을 사람이 손으로 적은 목록으로 메웁니다. 목록에 없는 프로그램은 다룰 수 없고, 목록 하나는 구분 하나만 표현하며, 무엇보다 조합과 맥락은 목록으로 표현할 수 없습니다.

# 7장 · 가장 단순한 것부터: FIFO, SJF, STCF

## 7.1 이 장에서 할 일

이제 실제 scheduling 알고리즘을 봅니다.

가장 단순한 것부터 시작해서, 그게 어떤 문제를 일으키는지 보고, 그 문제를 고치는 다음 알고리즘으로 넘어가는 식으로 갑니다. 각 알고리즘이 어떤 실패를 고치려고 나왔는지 알면 전체 계보가 잡힙니다.

앞 장에서 정리했듯이 scheduler가 답해야 할 질문은 두 개입니다. **다음에 누구를 실행할 것인가**, 그리고 **얼마나 오래 실행하게 할 것인가**. 알고리즘마다 이 두 질문의 답을 확인하면서 읽으면 좋습니다.

### 이 장에서 쓸 예제

계산을 따라가기 쉽게 단순한 상황을 씁니다.

- task가 세 개 있습니다. A, B, C라고 부릅니다.
- 셋 다 시각 0에 도착합니다.
- A는 CPU를 20밀리초 써야 끝납니다. B와 C는 각각 5밀리초입니다.
- 셋 다 중간에 잠들지 않습니다. 순수하게 계산만 합니다.
- core는 하나입니다.

이 상황을 여러 알고리즘으로 돌려보면서 결과를 비교하겠습니다.

## 7.2 FIFO

**FIFO**는 First In, First Out의 약자입니다. 먼저 온 순서대로 처리합니다. FCFS라고도 부릅니다. First Come, First Served의 약자입니다.

규칙은 이렇습니다.

- **누구를 실행할 것인가:** 가장 먼저 도착한 task.
- **얼마나 오래:** 끝날 때까지, 혹은 스스로 잠들 때까지. time slice가 없습니다.

가장 단순합니다. 은행 창구의 대기표와 같습니다.

### 예제 돌려보기

A, B, C 순서로 도착했다고 합시다.

```text
   0        5        10       15       20       25       30
   ├────────┼────────┼────────┼────────┼────────┼────────┤
   │██████████████████████████████████████│▓▓▓▓▓▓▓▓│░░░░░░░░│
   │             A (20ms)                 │ B (5)  │ C (5)  │
```

각 task의 결과를 계산해봅시다. 앞 장의 정의를 다시 확인하면, response time은 도착부터 처음 실행까지, turnaround time은 도착부터 완료까지입니다.

| task | 도착 | 시작 | 완료 | response time | turnaround time |
|---|---|---|---|---|---|
| A | 0 | 0 | 20 | 0 | 20 |
| B | 0 | 20 | 25 | 20 | 25 |
| C | 0 | 25 | 30 | 25 | 30 |

평균을 냅니다.

```text
   평균 response time  = (0 + 20 + 25) / 3 = 15 ms
   평균 turnaround time = (20 + 25 + 30) / 3 = 25 ms
```

### 문제: convoy effect

여기서 문제가 보입니다.

B와 C는 각각 5밀리초짜리 작은 작업입니다. 그런데 A 뒤에 줄을 서는 바람에 20밀리초, 25밀리초를 기다렸습니다. 자기 작업 시간의 네다섯 배를 기다린 겁니다.

이 현상을 **convoy effect**라고 부릅니다. 우리말로 호위 효과라고 하는데, 느린 트럭 한 대 뒤에 자동차들이 줄줄이 밀리는 모습에서 온 이름입니다.

마트 계산대에서 카트 가득 담은 사람 뒤에 껌 하나 든 사람이 서 있는 상황과 같습니다. 껌 하나 사는 데 20분을 기다립니다.

### 순서를 바꿔보면

만약 B, C, A 순서로 도착했다면 어땠을까요?

```text
   0        5        10       15       20       25       30
   ├────────┼────────┼────────┼────────┼────────┼────────┤
   │▓▓▓▓▓▓▓▓│░░░░░░░░│██████████████████████████████████████│
   │ B (5)  │ C (5)  │             A (20ms)                 │
```

| task | 도착 | 시작 | 완료 | response time | turnaround time |
|---|---|---|---|---|---|
| B | 0 | 0 | 5 | 0 | 5 |
| C | 0 | 5 | 10 | 5 | 10 |
| A | 0 | 10 | 30 | 10 | 30 |

```text
   평균 response time  = (0 + 5 + 10) / 3 = 5 ms
   평균 turnaround time = (5 + 10 + 30) / 3 = 15 ms
```

**똑같은 작업들인데 평균 turnaround time이 25에서 15로 줄었습니다.** 40퍼센트 개선입니다. 아무것도 안 바꾸고 순서만 바꿨습니다.

이 관찰에서 다음 알고리즘이 나옵니다.

### FIFO가 그래도 쓸모 있는 경우

FIFO가 나쁘기만 한 건 아닙니다.

**전환이 없습니다.** 한 task가 끝날 때까지 붙잡고 있으니 context switch가 최소입니다. cache도 유지됩니다.

**작업 길이가 비슷하면 문제가 없습니다.** convoy effect는 길이가 크게 차이 날 때 생깁니다.

**구현이 극단적으로 단순합니다.** 판단 비용이 거의 0입니다.

그래서 특수한 환경에서는 여전히 쓰입니다. 그리고 다른 알고리즘과 비교할 때 기준선 역할을 합니다.

> **이 연구에서는.** 이 시리즈가 다루는 연구의 시뮬레이터가 지원하는 네 가지 알고리즘 중 하나가 FIFO입니다. 설정할 수 있는 값이 하나도 없는 가장 단순한 선택지로 들어가 있습니다. 배경 작업만 도는 상황처럼 전환을 최소화하는 것이 최선인 경우에 쓸 수 있는 선택지로 남겨둔 것입니다.

## 7.3 SJF

앞의 관찰이 알려준 것은 **짧은 작업을 먼저 처리하면 평균이 좋아진다**는 것입니다.

이걸 규칙으로 만든 것이 **SJF**입니다. Shortest Job First의 약자입니다.

- **누구를 실행할 것인가:** 남은 작업 시간이 가장 짧은 task.
- **얼마나 오래:** 끝날 때까지.

앞의 예제에서 SJF는 자동으로 B, C, A 순서를 고릅니다. 그러니까 평균 turnaround time 15밀리초를 얻습니다.

### SJF는 최적입니다

여기서 흥미로운 사실이 있습니다. **모든 task가 동시에 도착하고 중간에 멈추지 않는다면, SJF는 평균 turnaround time을 최소화합니다.** 이건 증명 가능한 사실입니다.

왜 그런지 감을 잡아봅시다.

순서가 정해진 목록에서 인접한 두 task의 순서를 바꿔봅니다. 앞에 있는 것이 긴 작업 L이고 뒤에 있는 것이 짧은 작업 S라고 합시다.

원래 순서에서 L은 자기 시간만큼 걸려 끝나고, S는 L의 시간에 자기 시간을 더한 만큼 걸립니다.

순서를 바꾸면 S가 먼저 끝나고, L은 S의 시간을 추가로 기다립니다.

두 경우의 합을 비교해보면, S가 앞에 있는 쪽이 항상 작거나 같습니다. 짧은 것을 앞에 두면 그 뒤의 모든 작업이 조금씩 이득을 보는데, 긴 것을 앞에 두면 그 뒤의 모든 작업이 크게 손해를 보기 때문입니다.

그러니까 어떤 순서든 "긴 것이 짧은 것 앞에 있는" 자리를 찾아 바꾸면 항상 개선됩니다. 더 이상 바꿀 곳이 없을 때가 짧은 순서로 정렬된 상태이고, 그게 최적입니다.

### 그런데 쓸 수 없습니다

SJF에는 치명적인 문제가 있습니다.

**작업이 얼마나 걸릴지 미리 알 수 없습니다.**

컴파일러를 실행시켰을 때 그게 3초 걸릴지 3분 걸릴지 OS는 모릅니다. 프로그램 자신도 모르는 경우가 많습니다.

이건 구현이 어렵다는 뜻이 아니라 **정보가 존재하지 않는다**는 뜻입니다. 아무리 좋은 알고리즘을 짜도 없는 정보를 만들어낼 수는 없습니다.

앞에서 이렇게 표현했습니다. scheduler는 미래를 볼 수 없습니다. SJF는 미래를 봐야 동작하는 알고리즘입니다.

그래서 SJF는 실제로 쓰이지 않습니다. 대신 **기준점**으로 쓰입니다. "이론적으로 가능한 최선"이 어디인지 알려주는 값으로요.

### 도착 시각이 다르면 또 문제

SJF의 두 번째 문제입니다. 앞에서는 셋 다 시각 0에 도착했지만, 현실에서는 작업이 계속 들어옵니다.

상황을 바꿔봅시다.

- A는 시각 0에 도착, 20밀리초 필요
- B는 시각 5에 도착, 5밀리초 필요
- C는 시각 6에 도착, 5밀리초 필요

SJF는 한번 실행을 시작하면 끝까지 갑니다. 그래서 시각 0에 A만 있으니 A를 고르고, A가 끝나는 시각 20까지 붙잡고 있습니다.

```text
   0        5        10       15       20       25       30
   ├────────┼────────┼────────┼────────┼────────┼────────┤
   │██████████████████████████████████████│▓▓▓▓▓▓▓▓│░░░░░░░░│
   │             A (20ms)                 │   B    │   C    │
             ↑        ↑
             B 도착   C 도착
```

| task | 도착 | 시작 | 완료 | turnaround time |
|---|---|---|---|---|
| A | 0 | 0 | 20 | 20 |
| B | 5 | 20 | 25 | 20 |
| C | 6 | 25 | 30 | 24 |

```text
   평균 turnaround time = (20 + 20 + 24) / 3 = 21.33 ms
```

B와 C는 5밀리초짜리인데 20밀리초 넘게 걸렸습니다. FIFO와 별로 다르지 않습니다.

문제는 **한번 시작하면 안 놓는다**는 데 있습니다.

## 7.4 STCF

그럼 중간에 빼앗으면 됩니다.

**STCF**는 Shortest Time-to-Completion First의 약자입니다. 남은 시간이 가장 짧은 것을 고르되, **새 task가 도착할 때마다 다시 판단합니다.**

- **누구를 실행할 것인가:** 남은 작업 시간이 가장 짧은 task.
- **얼마나 오래:** 더 짧은 task가 도착할 때까지. 그러면 즉시 빼앗습니다.

앞의 상황을 STCF로 돌려봅시다.

시각 0에 A만 있으니 A를 실행합니다.

시각 5에 B가 도착합니다. 여기서 다시 판단합니다. A는 15밀리초 남았고 B는 5밀리초입니다. B가 짧으니 A를 내리고 B를 올립니다.

시각 6에 C가 도착합니다. 또 판단합니다. B는 4밀리초 남았고 C는 5밀리초입니다. B가 여전히 짧으니 그대로 둡니다.

시각 10에 B가 끝납니다. 남은 것은 A가 15밀리초, C가 5밀리초입니다. C를 올립니다.

시각 15에 C가 끝납니다. A를 다시 올려서 시각 30에 끝냅니다.

```text
   0        5        10       15       20       25       30
   ├────────┼────────┼────────┼────────┼────────┼────────┤
   │████████│▓▓▓▓▓▓▓▓│░░░░░░░░│██████████████████████████│
   │   A    │   B    │   C    │           A              │
```

| task | 도착 | 시작 | 완료 | response time | turnaround time |
|---|---|---|---|---|---|
| A | 0 | 0 | 30 | 0 | 30 |
| B | 5 | 5 | 10 | 0 | 5 |
| C | 6 | 10 | 15 | 4 | 9 |

```text
   평균 response time  = (0 + 0 + 4) / 3 = 1.33 ms
   평균 turnaround time = (30 + 5 + 9) / 3 = 14.67 ms
```

SJF의 21.33에서 14.67로 크게 좋아졌습니다.

**세 알고리즘을 나란히 놓으면 이렇습니다.**

| 알고리즘 | 평균 turnaround time | 평균 response time |
|---|---|---|
| FIFO | 21.33 ms | 11.33 ms |
| SJF | 21.33 ms | 11.33 ms |
| STCF | 14.67 ms | 1.33 ms |

FIFO의 숫자를 직접 확인해보면 이렇습니다. A는 시각 0에 도착해 0에 시작하고 20에 끝나니 response 0, turnaround 20입니다. B는 5에 도착해 20에 시작하고 25에 끝나니 response 15, turnaround 20입니다. C는 6에 도착해 25에 시작하고 30에 끝나니 response 19, turnaround 24입니다.

이 상황에서 FIFO와 SJF의 결과가 같은 이유는, 시각 0에 실행 후보가 A 하나뿐이라 SJF도 A를 고를 수밖에 없고, 그 뒤로는 도착 순서와 짧은 순서가 우연히 일치하기 때문입니다. 알고리즘이 같아서가 아닙니다.

### STCF도 미래를 알아야 합니다

STCF는 SJF보다 낫지만 같은 근본 문제를 안고 있습니다. **남은 시간을 알아야 합니다.**

여전히 실제로는 쓸 수 없습니다.

### 그리고 긴 작업이 굶습니다

STCF의 두 번째 문제입니다.

짧은 작업이 계속 들어온다고 해봅시다. 그러면 긴 작업 A는 계속 밀립니다. 짧은 작업이 도착할 때마다 빼앗기니까요.

극단적으로는 A가 영원히 끝나지 않습니다. 앞 장에서 정리한 **starvation**입니다.

평균 turnaround time은 훌륭하게 나옵니다. 짧은 작업 수백 개가 다 빨리 끝났으니까요. 하지만 A 하나는 완전히 방치됐습니다.

이게 앞 장에서 말한 "평균은 거짓말을 한다"의 또 다른 사례입니다. 평균 뒤에 굶고 있는 task가 숨어 있습니다.

## 7.5 그럼 실행 시간을 예측하면 되지 않나

SJF와 STCF가 좋은데 미래를 몰라서 못 쓴다면, 예측해보면 어떨까요?

실제로 오래된 Unix 계열 시스템들이 이걸 했습니다. 방법은 이렇습니다.

**과거의 CPU burst 길이를 보고 다음 burst를 추정합니다.**

앞에서 CPU burst라는 말을 썼는데, 다시 짚으면 task가 CPU를 연속으로 쓰는 한 덩어리를 말합니다. 편집기는 burst가 1밀리초쯤이고, 압축 작업은 burst가 slice 전체입니다.

추정 방식은 지수 이동 평균입니다.

```text
   다음_추정 = α × 이번_실제 + (1 - α) × 이전_추정
```

α는 0과 1 사이의 값입니다. 크면 최근 값을 많이 반영하고, 작으면 과거를 오래 기억합니다.

이 방법의 장점은 **task의 성격 변화를 따라간다**는 것입니다. 편집기가 갑자기 큰 계산을 시작하면 burst가 길어지고, 추정값도 따라 올라갑니다.

단점도 있습니다. 성격이 바뀌었을 때 반응이 느립니다. 그리고 애초에 이 방법은 "미래는 과거와 비슷할 것"이라는 가정 위에 서 있는데, 그 가정이 항상 맞지는 않습니다.

### 여기서 관점을 바꾸면

burst 길이를 정확히 추정하려는 대신, 이렇게 물어볼 수도 있습니다.

> 이 task가 **짧은 burst를 반복하는 종류**인가, **긴 burst를 계속하는 종류**인가?

정확한 숫자를 맞힐 필요 없이 종류만 구분하면 됩니다. 그리고 이 구분은 관찰로 꽤 잘 됩니다. 앞 장에서 본 대로 CPU를 어떻게 놓았는지를 보면 됩니다.

이 관점의 전환에서 나온 것이 뒤에서 다룰 MLFQ입니다.

## 7장 정리

- FIFO는 먼저 온 순서대로 끝까지 실행합니다. 단순하고 전환이 없지만, 긴 작업 뒤에 짧은 작업들이 줄줄이 밀리는 convoy effect가 생깁니다.
- 순서만 바꿔도 평균 turnaround time이 크게 달라집니다. 짧은 작업을 먼저 처리하면 좋아집니다.
- SJF는 남은 시간이 짧은 작업을 먼저 실행합니다. 모두 동시에 도착하는 경우 평균 turnaround time을 최소화하는 것이 증명되어 있습니다.
- 하지만 SJF는 작업이 얼마나 걸릴지 미리 알아야 합니다. 그 정보는 존재하지 않으므로 실제로 쓸 수 없습니다. 대신 이론적 최선을 알려주는 기준점으로 씁니다.
- 작업이 시간차를 두고 도착하면 SJF는 무너집니다. 한번 시작하면 안 놓기 때문입니다.
- STCF는 새 작업이 도착할 때마다 다시 판단하고 필요하면 빼앗습니다. 훨씬 좋아지지만 여전히 미래를 알아야 하고, 긴 작업이 굶는 문제가 있습니다.
- 실행 시간을 과거 기록으로 추정하는 방법이 있습니다. 정확한 숫자를 맞히는 대신 "짧은 burst를 반복하는 종류인가 긴 burst를 계속하는 종류인가"만 구분하면 된다는 관점 전환이 다음 알고리즘들로 이어집니다.

# 8장 · 시간을 쪼개기: Round Robin

## 8.1 남은 문제

앞 장에서 본 알고리즘들은 전부 "한 task를 끝까지 실행한다"는 전제 위에 있었습니다. 순서만 다르게 골랐을 뿐입니다.

그래서 뒤에 선 task는 앞의 것이 끝날 때까지 아무것도 못 합니다. 대화형 프로그램에게는 치명적입니다. 키를 눌렀는데 앞에 20밀리초짜리 작업이 있으면 20밀리초를 기다려야 합니다. 앞에 3초짜리 컴파일이 있으면 3초를 기다립니다.

게다가 SJF와 STCF는 작업 시간을 미리 알아야 해서 애초에 쓸 수 없었습니다.

그래서 완전히 다른 접근을 봅니다. **끝까지 실행하지 않는 것**입니다.

## 8.2 Round Robin

**Round Robin**은 이렇게 동작합니다. 줄여서 RR이라고 씁니다.

- **누구를 실행할 것인가:** queue의 맨 앞.
- **얼마나 오래:** 정해진 time slice만큼. 다 쓰면 queue 맨 뒤로 보내고 다음으로 넘어갑니다.

돌아가면서 조금씩 실행합니다. 그게 전부입니다.

작업 시간을 알 필요가 없습니다. 미래를 몰라도 됩니다. 그냥 순서대로 돌리면 됩니다.

트럼프 카드를 돌리는 것과 같습니다. 한 장씩 순서대로, 계속 돌아가면서.

### 예제 돌려보기

앞 장에서 쓰던 예제로 돌아갑니다.

- A, B, C가 모두 시각 0에 도착
- A는 20밀리초, B와 C는 각각 5밀리초 필요
- 중간에 잠들지 않음

time slice를 2밀리초로 놓고 돌려봅시다. 전환 비용은 일단 0으로 가정합니다.

```text
   0    2    4    6    8   10   12   14  15 16              30
   ├────┼────┼────┼────┼────┼────┼────┼───┼──┼───────────────┤
   │ A  │ B  │ C  │ A  │ B  │ C  │ A  │B │C │       A        │
   └────┴────┴────┴────┴────┴────┴────┴───┴──┴───────────────┘
                                        ↑   ↑                ↑
                                     B 완료 C 완료         A 완료
```

하나씩 따라가봅시다.

- 0에서 2까지 A가 실행됩니다. A는 18밀리초 남았습니다.
- 2에서 4까지 B. B는 3밀리초 남았습니다.
- 4에서 6까지 C. C는 3밀리초 남았습니다.
- 6에서 8까지 A. 16 남음.
- 8에서 10까지 B. 1 남음.
- 10에서 12까지 C. 1 남음.
- 12에서 14까지 A. 14 남음.
- 14에서 B가 남은 1밀리초를 씁니다. **시각 15에 B 완료.**
- 15에서 C가 남은 1밀리초를 씁니다. **시각 16에 C 완료.**
- 이제 A만 남았습니다. 14밀리초를 연달아 씁니다. **시각 30에 A 완료.**

| task | 도착 | 처음 실행 | 완료 | response time | turnaround time |
|---|---|---|---|---|---|
| A | 0 | 0 | 30 | 0 | 30 |
| B | 0 | 2 | 15 | 2 | 15 |
| C | 0 | 4 | 16 | 4 | 16 |

```text
   평균 response time  = (0 + 2 + 4) / 3 = 2 ms
   평균 turnaround time = (30 + 15 + 16) / 3 = 20.33 ms
```

### 앞 장의 결과들과 비교

같은 상황을 여러 알고리즘으로 돌린 결과를 모아봅시다. 셋 다 시각 0에 도착하는 경우입니다.

| 알고리즘 | 평균 response time | 평균 turnaround time |
|---|---|---|
| FIFO, A→B→C 순서 | 15 ms | 25 ms |
| SJF, 즉 B→C→A 순서 | 5 ms | 15 ms |
| Round Robin, slice 2ms | **2 ms** | 20.33 ms |

읽어야 할 것이 두 가지 있습니다.

**Round Robin의 response time이 압도적으로 좋습니다.** SJF보다도 좋습니다. 모든 task가 늦어도 4밀리초 안에 한 번은 실행됐습니다.

**대신 turnaround time은 SJF보다 나쁩니다.** 20.33 대 15입니다.

이유는 명확합니다. RR은 짧은 작업도 조금씩 나눠서 처리하기 때문에, 끝날 수 있었던 작업을 늦게 끝냅니다. B는 5밀리초짜리인데 15밀리초 걸렸습니다.

### 극단을 생각해보면

Round Robin은 **모든 task를 조금씩 동시에 진행시키는** 방향이고, SJF는 **하나씩 확실히 끝내는** 방향입니다. 정반대입니다.

극단적으로 생각하면 이해가 쉽습니다. 작업 100개가 각각 1초씩 필요하다고 합시다.

**하나씩 끝내면** 첫 작업은 1초, 마지막은 100초에 끝납니다. 평균 turnaround time은 약 50초입니다.

**전부 조금씩 동시에 진행시키면** 전부 100초 근처에 끝납니다. 평균 turnaround time은 약 100초입니다.

두 배 나쁩니다. 하지만 모든 작업이 첫 1초 안에 한 번씩은 실행됐습니다.

이게 근본적인 trade-off입니다. 웹 서비스로 치면 요청을 하나씩 처리해서 빨리 끝내는 것과, 모든 요청을 조금씩 진행시켜서 아무도 방치되지 않게 하는 것의 차이입니다.

## 8.3 slice 길이를 바꿔보면

같은 예제에서 slice만 바꿔보겠습니다.

### slice 1밀리초

A, B, C가 1밀리초씩 번갈아 실행됩니다.

B는 시각 1, 4, 7, 10, 13에 각각 1밀리초씩 받아서 시각 14에 완료됩니다. C는 2, 5, 8, 11, 14에 받아서 시각 15에 완료됩니다. A는 그때까지 5밀리초를 썼고, 15밀리초가 남아서 시각 30에 완료됩니다.

response time은 A가 0, B가 1, C가 2입니다. 평균 1밀리초입니다.
turnaround time은 30, 14, 15입니다. 평균 19.67밀리초입니다.

### slice 5밀리초

A가 0에서 5까지, B가 5에서 10까지 실행되어 완료, C가 10에서 15까지 완료, A가 15에서 30까지 실행되어 완료됩니다.

response time은 0, 5, 10입니다. 평균 5밀리초입니다.
turnaround time은 30, 10, 15입니다. 평균 18.33밀리초입니다.

### 표로 정리

| slice | 평균 response time | 평균 turnaround time |
|---|---|---|
| 1 ms | 1.00 ms | 19.67 ms |
| 2 ms | 2.00 ms | 20.33 ms |
| 5 ms | 5.00 ms | 18.33 ms |

**response time은 slice에 정확히 비례합니다.** slice가 짧을수록 좋습니다. 이건 항상 성립합니다. task가 n개일 때 최악의 response time은 대략 slice 곱하기 n 빼기 1이기 때문입니다.

**turnaround time은 단순하지 않습니다.** 여기서는 slice 5가 가장 좋았습니다.

이유는 slice가 길어질수록 RR이 FIFO에 가까워지기 때문입니다. slice를 20밀리초 이상으로 하면 아무도 중간에 안 끊기니까 완전히 FIFO가 됩니다. 그리고 이 예제에서는 짧은 작업들이 뒤에 있어서 FIFO에 가까워지는 것이 중간 지점에서는 이득이었습니다.

작업 구성이 다르면 결과도 달라집니다. 여기서 기억할 것은 **response time은 slice에 대해 단순하고 예측 가능하지만, turnaround time은 그렇지 않다**는 점입니다.

## 8.4 전환 비용을 넣으면

지금까지는 전환 비용을 0으로 놨습니다. 현실을 넣어봅시다.

앞에서 정리했듯이 context switch의 비용은 register를 저장하고 복원하는 눈에 보이는 비용에, cache가 식어서 느려지는 눈에 안 보이는 비용을 더한 것입니다. 대략 몇 마이크로초 정도라고 잡겠습니다.

전환 비용을 C, slice를 S라고 하면 낭비 비율은 이렇습니다.

```text
   overhead = C / (S + C)
```

C를 5마이크로초로 놓고 계산하면 이렇게 나옵니다.

| slice | 낭비 비율 | 30밀리초 작업이 실제로 걸리는 시간 |
|---|---|---|
| 50 µs | 9.1% | 33.0 ms |
| 100 µs | 4.8% | 31.5 ms |
| 500 µs | 1.0% | 30.3 ms |
| 1 ms | 0.5% | 30.15 ms |
| 10 ms | 0.05% | 30.015 ms |

앞 절에서 slice가 짧을수록 response time이 좋아진다고 했습니다. 하지만 무한정 줄일 수는 없습니다. 50마이크로초로 하면 CPU의 9퍼센트가 전환에만 날아갑니다.

그래서 실제 시스템은 밀리초 단위에서 타협합니다. 낭비를 1퍼센트 아래로 누르면서, task가 몇 개 안 될 때는 response time도 사람이 못 느낄 만큼 유지되는 구간입니다.

### 그래도 부족합니다

task가 100개 있고 slice가 1밀리초라면, 맨 뒤 task는 99밀리초를 기다립니다. 앞에서 본 0.1초 기준선에 딱 걸립니다.

task가 1000개라면 1초 가까이 기다립니다. 사람이 확실히 느낍니다.

slice를 더 줄이면 전환 비용이 감당이 안 됩니다.

**Round Robin만으로는 이 문제를 풀 수 없습니다.** 모두를 똑같이 대우하기 때문입니다.

## 8.5 잠드는 task가 섞이면

지금까지 예제에서는 아무도 잠들지 않았습니다. 현실을 넣어봅시다.

편집기 하나와 압축 작업 하나가 있습니다.

- 편집기: 1밀리초 실행하고 50밀리초 잠들기를 반복
- 압축: 계속 계산

slice가 5밀리초인 RR로 돌리면 이렇게 됩니다.

```text
   0    1         6         11        16   17
   ├────┼─────────┼─────────┼─────────┼────┼─────►
   │편집│  압축   │  압축   │  압축   │편집│ 압축 ...
   └────┴─────────┴─────────┴─────────┴────┴─────►
        ↑                                  ↑
     편집기 잠듦                       편집기 깨어남
     (50ms 뒤 깨어남)
```

편집기는 1밀리초만 쓰고 스스로 잠듭니다. slice 5밀리초를 다 안 씁니다. 남은 4밀리초는 압축 작업에게 넘어갑니다.

50밀리초 뒤 편집기가 깨어나면 queue에 들어갑니다. 압축 작업이 slice를 쓰는 중이면 최대 5밀리초를 기다립니다.

**여기서 두 가지가 보입니다.**

첫째, **잠드는 task가 섞이면 CPU가 낭비되지 않습니다.** 편집기가 자는 동안 압축 작업이 CPU를 씁니다. 이걸 overlap이라고 부릅니다. I/O 대기와 계산이 겹쳐서 진행됩니다.

둘째, **편집기의 response time은 압축 작업의 slice에 좌우됩니다.** 편집기가 깨어났을 때 압축 작업이 막 slice를 시작했다면 5밀리초를 기다립니다.

두 번째가 문제입니다. 편집기는 CPU를 거의 안 쓰는데도 압축 작업 때문에 기다립니다.

여기서 자연스러운 아이디어가 나옵니다.

> **깨어난 task가 지금 실행 중인 task보다 급하면 즉시 빼앗으면 되지 않나?**

맞습니다. 그렇게 합니다. 앞에서 wakeup preemption이라고 부른 것이 이겁니다.

그런데 "급하다"를 어떻게 판단하나요? 그러려면 task마다 급한 정도를 매겨야 합니다.

priority가 필요합니다.

## 8.6 Round Robin의 한계

정리하면 RR의 한계는 하나입니다.

**모두를 똑같이 대우합니다.**

편집기와 압축 작업이 같은 크기의 slice를 받고, 같은 순서로 돌아갑니다. 하지만 앞 장에서 봤듯이 이 둘은 완전히 다른 것을 원합니다.

편집기는 CPU를 거의 안 쓰니까 우선권을 줘도 손해가 없습니다. 압축 작업은 언제 실행되든 상관없으니 뒤로 밀려도 됩니다.

**차등 대우가 필요합니다.**

다음 장에서 priority를 도입합니다. 그리고 그 다음 장에서, priority를 사람이 정해주는 대신 scheduler가 관찰로 알아내는 방법을 봅니다.

---

## 8장 정리

- Round Robin은 queue의 맨 앞 task를 정해진 time slice만큼 실행하고, 다 쓰면 맨 뒤로 보냅니다. 작업 시간을 미리 알 필요가 없어서 실제로 쓸 수 있습니다.
- response time이 아주 좋습니다. 모든 task가 짧은 시간 안에 한 번은 실행됩니다. 대신 turnaround time은 나쁩니다. 끝낼 수 있는 작업을 끝내지 않고 나눠서 진행하기 때문입니다.
- Round Robin과 SJF는 정반대 방향입니다. 하나는 모두를 조금씩 진행시키고, 다른 하나는 하나씩 확실히 끝냅니다.
- slice가 짧을수록 response time이 좋아집니다. 이건 항상 성립합니다. turnaround time은 작업 구성에 따라 달라져서 단순하지 않습니다.
- slice를 무한정 줄일 수는 없습니다. 전환 비용이 비율로 커지기 때문입니다. 실제 시스템은 밀리초 단위에서 타협합니다.
- task가 많아지면 slice를 아무리 조정해도 대기 시간을 사람이 못 느낄 수준으로 유지할 수 없습니다.
- 잠드는 task가 섞이면 CPU가 낭비되지 않고 겹쳐서 진행됩니다. 하지만 자주 잠드는 대화형 task가 계산 작업의 slice 때문에 기다리는 문제가 남습니다.
- Round Robin의 근본 한계는 모두를 똑같이 대우한다는 것입니다. 차등 대우를 하려면 priority가 필요합니다.

# 9장 · priority와 그 함정

## 9.1 차등 대우의 가장 단순한 형태

앞 장에서 Round Robin의 한계를 봤습니다. 모두를 똑같이 대우한다는 것이었습니다.

가장 단순한 해결책은 이겁니다. **task마다 숫자를 하나 붙이고, 큰 숫자를 먼저 실행합니다.**

이 숫자를 **priority**라고 부릅니다. 우리말로는 우선순위라고 하는데, 이 책에서는 priority를 그대로 씁니다.

## 9.2 Multi-level queue

priority를 구현하는 표준적인 방법은 queue를 priority마다 하나씩 두는 것입니다. 이 구조를 **multi-level queue**라고 부릅니다.

```text
   높음  ┌──────────────────────────────┐
    ▲    │ Q3 │ 편집기 │ 터미널 │        │
    │    ├──────────────────────────────┤
    │    │ Q2 │ 음악 재생 │             │
    │    ├──────────────────────────────┤
    │    │ Q1 │ 브라우저 탭 │           │
    │    ├──────────────────────────────┤
    ▼    │ Q0 │ 컴파일 │ 백업 │ 색인 │  │
   낮음  └──────────────────────────────┘
```

규칙은 두 줄입니다.

- **누구를 실행할 것인가:** 비어 있지 않은 가장 높은 queue의 맨 앞 task.
- **얼마나 오래:** 같은 queue 안에서는 Round Robin으로 돌립니다.

그러니까 Q3에 뭐라도 있으면 Q3만 실행합니다. Q3가 비어야 Q2를 봅니다.

Q3 안에 편집기와 터미널이 둘 다 있으면 그 둘끼리 번갈아 실행합니다.

### 이게 왜 좋은가

앞 장에서 남은 문제가 이거였습니다. 편집기가 깨어났는데 압축 작업이 slice를 쓰는 중이라 기다린다는 것이었습니다.

이제는 편집기가 Q3에 있고 압축 작업이 Q0에 있으니, 편집기가 깨어나는 순간 즉시 실행됩니다. 압축 작업은 바로 내려옵니다.

편집기는 CPU를 거의 안 쓰니까 압축 작업이 크게 손해 보지도 않습니다.

앞 장에서 원하던 것이 정확히 이겁니다.

## 9.3 첫 번째 함정: starvation

문제가 있습니다.

Q0에 있는 컴파일 작업을 생각해봅시다. 이 작업이 실행되려면 Q1, Q2, Q3가 전부 비어 있어야 합니다.

브라우저 탭 하나가 계속 뭔가를 하고 있으면 Q1이 안 비웁니다. 그러면 컴파일은 **영원히 실행되지 않습니다.**

앞에서 정리한 **starvation**입니다.

### 얼마나 현실적인 문제인가

꽤 현실적입니다.

높은 priority task가 하나만 계속 돌아도 아래가 전부 멈춥니다. 그리고 실제 시스템에는 높은 priority task가 여럿 있습니다. 시스템 데몬, 오디오 처리, 화면 합성 같은 것들입니다.

그래서 순수한 priority scheduling은 실제로 쓰이지 않습니다. 반드시 starvation을 막는 장치가 함께 들어갑니다. 어떤 장치인지는 다음 장에서 봅니다.

## 9.4 두 번째 함정: priority inversion

더 미묘한 문제가 있습니다.

상황을 만들어봅시다. task가 셋입니다.

- **H**: priority 높음
- **M**: priority 중간
- **L**: priority 낮음

L이 먼저 실행되어 어떤 자원의 lock을 잡았습니다. 데이터베이스 커넥션이나 공유 자료구조라고 생각하면 됩니다.

여기서 H가 깨어납니다. priority가 높으니 L을 밀어내고 실행됩니다.

그런데 H도 같은 lock이 필요합니다. L이 잡고 있으니 H는 기다려야 합니다. H가 blocked가 됩니다.

이제 L이 다시 실행되어 lock을 놓을 차례입니다. 그런데 그 순간 M이 깨어납니다. M은 L보다 priority가 높으니 L을 밀어냅니다.

**결과적으로 M이 H보다 먼저 실행됩니다.**

```text
   H (높음)  ──▶ lock 대기 ─────────────── (계속 대기) ──────
                    ▲
                    │ lock을 쥐고 있음
   M (중간)         │        ────────────────────────────▶ 실행 중
                    │              ▲
                    │              │ L을 밀어냄
   L (낮음)  ──▶ lock 획득 ────────┴── (실행 못 함) ────────
```

priority가 뒤집혔습니다. 이 현상을 **priority inversion**이라고 부릅니다.

문제는 M이 아무리 오래 돌아도 H가 계속 기다린다는 것입니다. M이 여럿이면 H는 사실상 무한정 대기합니다.

### 실제로 일어난 일

1997년 화성에 착륙한 탐사선 Pathfinder에서 이 문제가 발생했습니다.

착륙 후 시스템이 반복적으로 재부팅되는 현상이 나타났습니다. 원인을 추적해보니 정확히 이 구조였습니다. 높은 priority의 작업이 낮은 priority 작업이 쥔 자원을 기다리는 동안, 중간 priority 작업이 CPU를 계속 가져갔습니다. 그러다 감시 타이머가 "시스템이 응답하지 않는다"고 판단해서 재부팅시킨 것입니다.

지구에서 원인을 재현하고, 소프트웨어를 수정해서 화성으로 전송해서 고쳤습니다.

### 해결책

**priority inheritance**라고 부르는 방법이 표준입니다.

낮은 priority task가 높은 priority task를 기다리게 만들고 있으면, **기다리게 만드는 쪽의 priority를 일시적으로 올려줍니다.**

앞의 예에서 L이 H를 기다리게 하고 있으니 L의 priority를 H만큼 올립니다. 그러면 M이 L을 밀어낼 수 없고, L이 빨리 lock을 놓고, H가 진행할 수 있습니다. lock을 놓으면 L의 priority는 원래대로 돌아갑니다.

이 개념은 scheduling 바깥에서도 유용합니다. 웹 서비스에서 중요한 요청이 덜 중요한 요청과 같은 커넥션 풀을 놓고 경쟁할 때 비슷한 문제가 생깁니다.

## 9.5 세 번째 함정, 그리고 가장 중요한 것

지금까지의 두 함정은 알려진 문제이고 알려진 해법이 있습니다.

세 번째 문제는 해법이 없습니다.

> **priority는 누가 정하는가?**

priority scheduling은 각 task에 숫자가 이미 붙어 있다고 전제합니다. 그 숫자가 어디서 오는지는 알고리즘의 관심사가 아닙니다.

하지만 실제로는 이게 전부입니다. 숫자가 틀리면 알고리즘이 아무리 좋아도 소용없습니다.

### 방법 1: 사용자가 정한다

Unix 계열 시스템에는 **nice**라는 값이 있습니다.

`nice -n 19 ./backup.sh`라고 실행하면 이 프로그램은 낮은 priority로 돕니다. 값의 범위는 보통 -20에서 19까지이고, 낮을수록 priority가 높습니다. 이름이 nice인 이유는 값이 높을수록 다른 프로그램에게 "친절하게" 양보한다는 뜻이기 때문입니다.

이론적으로는 완벽한 해법입니다. 사용자가 자기 의도를 직접 알려주니까요.

**현실적으로는 아무도 안 씁니다.**

터미널에서 명령어를 칠 때마다 nice를 앞에 붙이는 사람은 거의 없습니다. 그리고 GUI로 프로그램을 실행할 때는 그럴 방법도 없습니다. 아이콘을 더블클릭하는 사람에게 priority를 물어볼 수는 없습니다.

무엇보다 사용자가 매번 판단해야 한다는 게 비현실적입니다. 지금 켜는 브라우저가 배경 다운로드용인지 메인 작업용인지를 실행할 때마다 지정할 수는 없습니다.

### 방법 2: 프로그램이 스스로 선언한다

프로그램이 실행되면서 "저는 배경 작업입니다"라고 OS에 알리는 방법입니다.

실제로 이런 장치가 있습니다. Windows에는 priority class가 있어서 프로그램이 자기를 배경 작업으로 등록할 수 있습니다. macOS에는 QoS class라는 게 있어서 각 작업이 "사용자가 상호작용 중", "사용자가 시작함", "유틸리티", "백그라운드" 중 하나를 선언합니다.

이것도 잘 동작할 때가 있습니다. 하지만 문제가 있습니다.

**대부분의 프로그램이 선언하지 않습니다.** 기본값으로 실행됩니다. 개발자가 신경 써서 넣어야 하는 일인데, 대부분은 신경 쓰지 않습니다.

**선언이 정직하지 않을 수 있습니다.** 모든 프로그램이 자기가 제일 중요하다고 선언하면 priority는 의미가 없어집니다. 실제로 성능에 민감한 프로그램들이 필요 이상으로 높은 priority를 요구하는 경향이 있습니다.

**그리고 결정적으로, 프로그램은 자기가 지금 무엇에 쓰이는지 모릅니다.** 브라우저가 자기를 "사용자 상호작용 중"이라고 선언한다고 합시다. 맞는 말입니다. 그런데 지금 그 브라우저 window가 최소화된 채로 파일만 내려받고 있다면 어떨까요? 브라우저는 그 사실을 알 수도 있지만, 사용자가 그 다운로드를 기다리고 있는지는 모릅니다.

**무엇보다 이 방식은 스스로에 대한 선언만 가능합니다.** 어떤 프로그램도 "지금 이 컴퓨터 전체가 게임 중이다"라고 말할 수 없습니다. 자기 자신 바깥은 모르기 때문입니다.

### 방법 3: OS가 목록을 가지고 있다

앞에서 짚은 방법입니다. 게임 실행 파일 목록 같은 것입니다.

목록에 없으면 못 알아본다는 한계, 목록 하나가 구분 하나만 표현한다는 한계, 조합은 표현할 수 없다는 한계를 앞에서 봤습니다.

### 방법 4: scheduler가 관찰해서 알아낸다

남은 방법입니다. 그리고 실제로 모든 현대 OS가 이걸 씁니다.

사용자에게 묻지 않고, 프로그램의 선언을 믿지 않고, 목록에 의존하지 않고, **행동을 관찰해서 priority를 스스로 정합니다.**

CPU를 어떻게 놓았는지, 얼마나 자주 잠드는지, burst가 얼마나 긴지를 보고 판단합니다.

이 아이디어를 규칙으로 만든 것이 다음 장에서 다룰 MLFQ입니다.

## 9.6 정적 priority의 마지막 문제

넘어가기 전에 하나만 더 짚습니다.

지금까지 이야기한 priority는 전부 **한 번 정하면 안 바뀌는** 값이었습니다. 이걸 static priority라고 합니다.

그런데 앞에서 봤듯이 프로그램의 성격은 실행 중에 바뀝니다.

편집기가 대부분의 시간은 대화형으로 동작하다가, 저장할 때는 몇 초 동안 계산 작업이 됩니다. 브라우저 탭 하나가 배경에 있다가 사용자가 전환하면 전면 작업이 됩니다. 컴파일러가 파일을 다 읽고 나면 순수 계산 단계로 넘어갑니다.

고정된 숫자 하나로는 이런 변화를 따라갈 수 없습니다.

그래서 필요한 것은 **행동을 보고 priority를 계속 조정하는** 방식입니다. 그게 다음 장의 주제입니다.

## 9장 정리

- priority scheduling은 task마다 숫자를 붙이고 높은 것을 먼저 실행합니다. queue를 priority마다 하나씩 두고 같은 queue 안에서는 Round Robin을 도는 구조를 multi-level queue라고 합니다.
- 대화형 프로그램을 높은 queue에 두면 깨어나는 즉시 실행됩니다. Round Robin이 풀지 못한 문제가 해결됩니다.
- 첫 번째 함정은 starvation입니다. 높은 queue가 안 비면 낮은 queue는 영원히 실행되지 않습니다. 그래서 순수한 priority scheduling은 실제로 쓰이지 않고, 반드시 starvation 방지 장치가 함께 들어갑니다.
- 두 번째 함정은 priority inversion입니다. 낮은 priority task가 쥔 lock을 높은 priority task가 기다리는 사이 중간 priority task가 끼어들면 순서가 뒤집힙니다. 화성 탐사선 Pathfinder에서 실제로 일어난 문제이고, priority inheritance로 해결합니다.
- 세 번째이자 가장 중요한 문제는 priority를 누가 정하느냐입니다. 사용자가 정하는 방법은 아무도 쓰지 않고, 프로그램이 선언하는 방법은 대부분 선언하지 않거나 정직하지 않으며, 무엇보다 프로그램은 자기 바깥의 맥락을 모릅니다. OS가 목록을 가지고 있는 방법은 목록에 없는 것을 다룰 수 없습니다.
- 그래서 현대 OS는 행동을 관찰해서 priority를 스스로 정합니다.
- 게다가 프로그램의 성격은 실행 중에 바뀝니다. 고정된 숫자 하나로는 따라갈 수 없어서, 계속 조정하는 방식이 필요합니다.

# 10장 · MLFQ: 행동을 보고 추측하는 기계

## 10.1 이 장이 중요한 이유

**MLFQ**는 Multi-Level Feedback Queue의 약자입니다. 여러 단계의 queue를 두고, 피드백을 받아 task를 그 사이에서 옮긴다는 뜻입니다.

이 장에 한 장을 통째로 쓰는 이유가 셋입니다.

**첫째, 실제로 쓰이는 알고리즘입니다.** Linux, macOS, Windows가 전부 이 계열의 변형을 씁니다. 세부는 다르지만 뼈대는 같습니다.

**둘째, 이 시리즈가 다루는 연구의 기준선입니다.** "언어 모델이 상황을 읽으면 더 나은가"를 묻는 실험에서, 비교 대상이 되는 것이 MLFQ입니다. MLFQ가 무엇을 잘하고 무엇을 못 하는지 정확히 알아야 그 실험을 이해할 수 있습니다.

**셋째, 이 연구가 파고드는 틈이 여기 있습니다.** MLFQ가 어떤 정보로 판단하는지를 보면, 그 정보로는 절대 알 수 없는 것이 무엇인지도 보입니다.

## 10.2 풀어야 할 문제

MLFQ가 나온 배경을 정리하면 이렇습니다.

앞에서 두 가지를 봤습니다.

**짧은 작업을 먼저 처리하면 평균이 좋아집니다.** 하지만 어느 작업이 짧은지 미리 알 수 없습니다.

**대화형 작업에 우선권을 주면 반응이 좋아집니다.** 하지만 어느 작업이 대화형인지 미리 알 수 없습니다.

두 문제 모두 "미리 알 수 없다"에서 막힙니다.

MLFQ의 답은 이렇습니다.

> **미리 알 필요 없다. 실행시켜보고 행동을 관찰해서 판단하면 된다. 그리고 판단이 틀렸으면 고치면 된다.**

이게 feedback입니다. 결과를 보고 조정한다는 뜻입니다.

## 10.3 규칙을 하나씩 쌓기

MLFQ를 한 번에 설명하면 복잡합니다. 규칙을 하나씩 추가하면서, 각 규칙이 어떤 문제를 고치려고 생겼는지 따라가겠습니다.

### 준비: queue 여러 개

queue를 여러 개 두고 각각에 priority를 매깁니다. 앞 장에서 본 multi-level queue와 같은 구조입니다.

```text
   Q2 (높음)  ┌─────────────────────┐
              │                     │
              ├─────────────────────┤
   Q1 (중간)  │                     │
              ├─────────────────────┤
   Q0 (낮음)  │                     │
              └─────────────────────┘
```

여기서는 세 개로 그렸습니다. 실제 시스템에서는 더 많을 수도 있습니다.

### 규칙 1과 2: 기본 동작

> **규칙 1.** priority가 높은 task를 먼저 실행한다.
>
> **규칙 2.** priority가 같으면 그들끼리 Round Robin으로 돌린다.

여기까지는 앞 장의 multi-level queue와 똑같습니다. Q2에 뭐라도 있으면 Q2만 실행하고, Q2 안에 여럿이면 번갈아 실행합니다.

지금은 task가 어느 queue에 들어가는지 정해지지 않았습니다. 다음 규칙이 그걸 정합니다.

### 규칙 3: 일단 최고 priority로

> **규칙 3.** task가 처음 들어오면 가장 높은 queue에 놓는다.

새 task는 무조건 Q2에서 시작합니다.

왜 이렇게 하나요? **낙관적으로 가정하는 것**입니다. 아직 아무것도 모르니까 일단 대화형일 것이라고 보고 좋은 대우를 해줍니다.

이 선택에는 이유가 있습니다. 만약 이 task가 정말 짧은 대화형 작업이라면 좋은 대우를 받고 금방 끝납니다. 만약 긴 계산 작업이라면 곧 행동으로 드러날 것이고, 그때 내리면 됩니다.

**틀렸을 때의 손해가 작은 쪽을 기본값으로 잡는** 전략입니다.

### 규칙 4: 시간을 다 쓰면 내린다

> **규칙 4.** task가 주어진 time slice를 전부 소진하면 한 단계 아래 queue로 내린다. 시간을 다 쓰기 전에 스스로 CPU를 놓으면 같은 queue에 남는다.

**이게 MLFQ의 핵심입니다.**

앞에서 정리한 관찰을 그대로 규칙으로 만든 것입니다. 다시 짚으면 이렇습니다. task가 CPU에서 내려오는 방식은 두 가지입니다. 주어진 시간을 다 써서 강제로 내려오거나, 기다릴 것이 생겨서 스스로 내려오거나.

시간을 다 썼다는 것은 더 계산하고 싶었다는 뜻입니다. 계산 작업일 가능성이 높습니다. 그러니 priority를 낮춥니다.

스스로 내려왔다는 것은 할 일을 마치고 뭔가를 기다리러 갔다는 뜻입니다. 대화형일 가능성이 높습니다. 그러니 priority를 유지합니다.

**여기서 중요한 점을 강조해둡니다.** scheduler는 "이 프로그램이 편집기다" 같은 것은 전혀 모릅니다. 오직 "이 task가 시간을 다 썼는가, 스스로 놓았는가"만 봅니다. 그 관찰 하나로 성격을 추측합니다.

### 지금까지의 동작

세 가지 task를 넣어보면 이렇게 됩니다.

```text
   편집기: 2ms 쓰고 잠듦
   → Q2에서 시작, 시간을 다 안 쓰니 계속 Q2에 남음
   → 항상 최고 priority

   컴파일: 계속 계산
   → Q2에서 시작 → 시간 다 씀 → Q1로 → 또 다 씀 → Q0로
   → 금방 바닥으로 내려감

   웹 서버: 요청 처리하고 DB 기다림
   → Q2에서 시작, 대체로 스스로 놓으니 위에 남음
   → 무거운 요청이 오면 가끔 내려감
```

**아무도 아무것도 선언하지 않았는데 적절히 분류됐습니다.** 행동만 보고요.

## 10.4 문제 하나: starvation

앞 장에서 봤던 문제가 그대로 남아 있습니다.

Q2에 대화형 task가 많으면 Q0의 컴파일은 실행되지 않습니다. 그리고 지금 규칙으로는 한번 Q0에 내려간 task가 다시 올라올 방법이 없습니다.

내려가기만 하고 올라오지 못하는 구조입니다.

## 10.5 문제 둘: 성격이 바뀌면

편집기가 큰 파일을 저장하려고 몇 초 동안 압축을 한다고 합시다.

시간을 다 쓰니까 Q2에서 Q1로, Q1에서 Q0로 내려갑니다.

저장이 끝나고 다시 타이핑을 시작합니다. 이제 편집기는 다시 대화형입니다. 그런데 Q0에 있습니다. 올라올 방법이 없습니다.

**사용자는 이제부터 계속 느린 편집기를 씁니다.**

## 10.6 문제 셋: scheduler를 속일 수 있다

이건 좀 고약합니다.

규칙 4를 다시 봅시다. "시간을 다 쓰기 전에 스스로 CPU를 놓으면 같은 queue에 남는다."

그러면 이런 프로그램을 짤 수 있습니다.

```text
   무한 반복 {
       time slice의 99% 동안 계산한다
       아주 잠깐 잠든다   ← 여기서 "스스로 놓음"으로 판정됨
   }
```

이 프로그램은 CPU를 거의 100퍼센트 쓰면서도 영원히 최고 priority에 머무릅니다. scheduler는 이 task를 착한 대화형 프로그램으로 봅니다.

다른 모든 task가 손해를 봅니다.

**의도적인 공격만 문제가 아닙니다.** 우연히 이런 패턴을 갖는 프로그램도 있습니다. 짧은 주기로 뭔가를 폴링하는 프로그램 같은 것들입니다. 나쁜 의도가 없어도 결과는 같습니다.

## 10.7 규칙 5: 주기적으로 전부 되돌린다

앞의 세 문제를 한 번에 고치는 규칙이 있습니다.

> **규칙 5.** 일정 시간마다 모든 task를 가장 높은 queue로 되돌린다.

이 동작을 **boost**라고 부릅니다. 우리말로는 승격이라고 하는데, 이 책에서는 boost를 그대로 씁니다.

무식해 보이지만 세 문제를 전부 해결합니다.

**starvation이 사라집니다.** Q0에 있던 task도 boost 때 Q2로 올라오니 반드시 실행 기회를 얻습니다.

**성격 변화를 따라갑니다.** 저장 때문에 내려간 편집기가 boost 때 올라옵니다. 다시 대화형으로 행동하면 그대로 위에 남습니다.

**속이는 프로그램의 이득이 줄어듭니다.** 물론 boost 후에도 계속 속이면 여전히 위에 남습니다. 이건 다음 절에서 따로 고칩니다.

### boost 간격은 얼마로 하나

여기서 어려운 질문이 나옵니다.

**너무 짧으면** boost가 잦아서 애써 분류한 결과가 계속 지워집니다. 계산 작업들이 계속 최고 priority로 올라와서 대화형 작업을 방해합니다. 극단적으로 짧으면 그냥 Round Robin이 됩니다.

**너무 길면** starvation이 오래 지속됩니다. 성격이 바뀐 task가 회복하는 데 오래 걸립니다.

적절한 값은 얼마일까요?

**정답이 없습니다.** 작업 구성에 따라 다르고, 상황에 따라 다릅니다.

OS 교과서 중에 널리 쓰이는 것이 하나 있는데, 그 책은 이런 값들을 **voo-doo constant**라고 부릅니다. 원래 이 표현을 쓴 사람의 말을 인용하면서, 이런 값들은 이론으로 정할 수 없고 결국 경험과 시행착오로 정한다고 설명합니다.

이건 MLFQ의 약점이라기보다 이 문제의 성질입니다. 상황에 따라 최적값이 달라지는데 상황을 모르면 하나로 고정할 수밖에 없습니다.

> **이 연구에서는.** 이 지점이 이 시리즈가 다루는 연구와 정면으로 연결됩니다. 상황에 따라 최적값이 달라진다면, 상황을 알면 값을 바꿀 수 있다는 뜻입니다. 이 연구가 하려는 것이 정확히 그겁니다. 지금 이 컴퓨터가 무엇에 쓰이고 있는지를 읽어내고, 그에 맞게 scheduler의 config를 바꿉니다. boost 간격도 그 config 중 하나입니다.
>
> 그리고 실험의 기준선을 정할 때 이 문제가 그대로 나타났습니다. 비교 대상이 될 기본 config를 정해야 하는데, 표준이라고 부를 만한 값이 존재하지 않았습니다. 실제 OS들의 값은 각자 다르고 공개된 근거도 없습니다. 그래서 앞서 말한 그 교과서의 예제에 나오는 값들을 통째로 가져다 쓰기로 했습니다. queue 세 개, 최상위 slice 10밀리초, 아래 단계마다 두 배, boost 간격 100밀리초입니다.
>
> 여러 출처에서 값을 하나씩 골라 조합하지 않고 한 출처에서 통째로 가져온 이유가 있습니다. 조합하면 그 조합 자체가 근거 없는 새로운 설정이 됩니다. 한 출처에서 통째로 가져오면 최소한 "이 교과서의 예제 설정"이라고 말할 수 있습니다. 논문에서 방어할 수 있는 형태입니다.
>
> 여기에 더해, 그 값 하나 때문에 결론이 뒤집히지 않는지 확인하는 절차도 미리 정해뒀습니다. 최상위 slice를 0.5밀리초부터 100밀리초까지 아홉 가지로 바꿔가며 전체 실험을 다시 돌리고, 결론이 유지되는지 봅니다. 유지되지 않으면 결론을 하나의 값이 아니라 범위로 보고합니다.

## 10.8 규칙 4의 개선: 속임수 막기

앞에서 본 속임수를 고칠 차례입니다.

문제는 규칙 4가 **한 번의 slice 안에서만** 판단한다는 데 있었습니다. slice의 99퍼센트를 쓰고 잠들면 "스스로 놓았다"로 판정됩니다.

고치는 방법은 **누적해서 세는 것**입니다.

> **규칙 4를 고쳐 쓰면:** task가 한 queue에서 쓴 시간을 누적해서 센다. 그 누적량이 그 queue에 할당된 share를 넘으면, 중간에 몇 번을 잠들었든 상관없이 아래로 내린다.

이 "한 queue에서 쓸 수 있는 누적 시간"을 **allotment**라고 부릅니다.

이제 앞의 속임수 프로그램을 다시 보면, slice의 99퍼센트씩 쓰는 것이 계속 누적되어 금방 allotment를 넘깁니다. 내려갑니다.

정직한 대화형 프로그램은 한 번에 1, 2밀리초씩만 쓰니까 누적이 느리게 쌓입니다. 그리고 보통 boost가 먼저 와서 초기화됩니다.

> **이 연구에서는.** 이 시리즈가 다루는 연구의 시뮬레이터는 allotment를 별도의 config로 두지 않고, slice 하나를 다 쓰면 바로 내리는 방식을 씁니다. 앞서 말한 교과서의 첫 번째 예제도 allotment를 slice와 같게 놓았기 때문에, 그 예제를 따르는 셈입니다. 다만 그 교과서의 다른 그림에서는 상위 두 단계에 slice 두 개 분량의 allotment를 주기도 하는데, 그 부분은 따르지 않았습니다. 이런 차이를 문서에 명시적으로 적어두는 것이 중요합니다. 나중에 결과를 해석할 때 "우리 모델과 인용한 예제가 정확히 어디서 다른가"를 알아야 하기 때문입니다.

## 10.9 아래 queue일수록 slice를 길게

한 가지 개선이 더 있습니다.

앞에서 봤듯이 대화형 task는 slice를 다 쓰지 않습니다. 그러니 긴 slice를 줘봤자 의미가 없습니다.

반면 계산 작업은 slice가 길수록 좋습니다. 전환이 줄고 cache가 유지됩니다.

그리고 MLFQ의 구조상 **위쪽 queue에는 대화형이, 아래쪽에는 계산 작업이 모입니다.** 그러니 이렇게 하면 됩니다.

> **아래 queue일수록 긴 slice를 준다.**

예를 들어 이렇게 설정합니다.

```text
   Q2 (높음)   slice 10 ms
   Q1 (중간)   slice 20 ms
   Q0 (낮음)   slice 40 ms
```

한 단계 내려갈 때마다 두 배씩 늘어납니다.

**대화형 task는 위에 있으니 짧은 slice를 받지만 어차피 다 안 씁니다. 손해가 없습니다.**

**계산 작업은 아래로 내려가면서 점점 긴 slice를 받습니다. 전환이 줄어 효율이 좋아집니다.**

priority가 낮아지면서 오히려 한 번에 받는 시간은 길어지는, 언뜻 이상해 보이는 구조가 이렇게 나옵니다.

## 10.10 완성된 MLFQ

규칙을 모으면 이렇습니다.

> **규칙 1.** priority가 높은 task를 먼저 실행한다.
>
> **규칙 2.** priority가 같으면 Round Robin으로 돌린다.
>
> **규칙 3.** task가 처음 들어오면 가장 높은 queue에 놓는다.
>
> **규칙 4.** 한 queue에서 쓴 누적 시간이 그 queue의 share를 넘으면 아래 queue로 내린다. 넘지 않았으면 그대로 둔다.
>
> **규칙 5.** 일정 시간마다 모든 task를 가장 높은 queue로 되돌린다.
>
> **추가.** 아래 queue일수록 한 번에 주는 시간을 길게 한다.

이 여섯 줄이 현대 OS scheduler의 뼈대입니다.

### 조정할 수 있는 값들

MLFQ에는 정해야 할 값이 여럿 있습니다.

| 값 | 무엇인가 | 크게 하면 | 작게 하면 |
|---|---|---|---|
| queue 개수 | priority 단계 수 | 구분이 세밀해짐 | 구분이 거침 |
| 최상위 slice | 가장 높은 queue의 시간 조각 | 전환이 줄고 반응이 느려짐 | 반응이 빨라지고 전환이 늘어남 |
| slice 증가 비율 | 아래 단계로 갈 때 slice가 커지는 배수 | 계산 작업에 유리 | 단계 간 차이가 작아짐 |
| boost 간격 | 전부 되돌리는 간격 | 분류가 오래 유지됨, starvation 위험 | starvation 방지, 분류가 자주 지워짐 |

**이 값들을 어떻게 정하느냐에 따라 같은 MLFQ가 전혀 다르게 동작합니다.** 그리고 앞에서 말했듯이 어떤 값이 최적인지는 지금 무슨 작업이 돌고 있느냐에 달려 있습니다.

> **이 연구에서는.** 이 네 가지 값이 그대로 실험에서 조정하는 config입니다. 언어 모델이 상황을 읽으면, 그 판단에 따라 이 네 값이 바뀝니다. 예를 들어 게임 중이라고 판단되면 최상위 slice를 짧게 해서 frame 작업의 반응을 빠르게 하는 식입니다. 값들을 아무렇게나 바꾸지 못하도록 각 값의 허용 범위도 정해뒀습니다. queue 개수는 2에서 8 사이, 최상위 slice는 500마이크로초에서 100밀리초 사이 같은 식입니다.

## 10.11 손으로 따라가보기

실제로 돌려봅시다.

**설정**

- queue 세 개. Q2가 최상위입니다.
- slice는 Q2가 10밀리초, Q1이 20밀리초, Q0이 40밀리초입니다.
- boost 간격은 100밀리초입니다.
- allotment는 slice와 같습니다. 즉 slice 하나를 다 쓰면 바로 내려갑니다.

**task**

- **편집기 E**: 30밀리초마다 깨어나서 2밀리초 계산하고 다시 잡니다.
- **컴파일 C**: 계속 계산합니다. 아주 오래 걸립니다.

둘 다 시각 0에 시작하고, E가 먼저 queue에 들어갔다고 합시다.

**진행**

```text
   t=0     E와 C 모두 Q2에서 시작 (규칙 3)
   
   0-2     E 실행. 2ms 쓰고 스스로 잠듦.
           slice 10ms를 다 안 썼으므로 Q2에 남음 (규칙 4)
           E는 t=32에 깨어남

   2-12    C 실행. Q2의 slice 10ms를 전부 소진.
           → Q1으로 내려감 (규칙 4)

   12-32   C 실행. Q1의 slice 20ms를 전부 소진.
           → Q0으로 내려감 (규칙 4)

   t=32    E가 깨어남. E는 Q2, C는 Q0.
           Q2가 더 높으므로 C를 즉시 밀어냄 (규칙 1)

   32-34   E 실행. 2ms 쓰고 잠듦. Q2에 남음.
           E는 t=64에 깨어남

   34-64   C 실행. Q0의 slice는 40ms인데 30ms만 쓰고 밀려남.

   t=64    E가 깨어남. 다시 C를 밀어냄.

   64-66   E 실행. 잠듦. t=96에 깨어남.

   66-96   C 실행.

   t=96    E가 깨어남. C를 밀어냄.

   96-98   E 실행. 잠듦.

   t=100   boost. E와 C 모두 Q2로 올라감 (규칙 5)
           C가 Q2에서 다시 시작하지만, 곧 slice를 다 쓰고
           다시 내려가기 시작함
```

**결과를 읽어봅시다.**

편집기 E의 response time은 매번 거의 0입니다. 깨어난 순간 C보다 priority가 높으니 즉시 실행됩니다.

컴파일 C는 CPU의 대부분을 씁니다. 0에서 100밀리초 사이에 E는 6밀리초를 썼고 C는 94밀리초를 썼습니다.

**둘 다 원하는 것을 얻었습니다.** E는 즉각적인 반응을, C는 대부분의 CPU 시간을요.

그리고 **아무도 자기 성격을 선언하지 않았습니다.** scheduler는 "E가 2ms 쓰고 잠들었다"와 "C가 10ms를 다 썼다"만 관찰했습니다.

### 비교: 만약 Round Robin이었다면

같은 상황을 slice 10밀리초의 Round Robin으로 돌렸다면 어떨까요?

E가 t=32에 깨어났을 때 C가 slice를 막 시작했다면, E는 최대 10밀리초를 기다립니다. 평균 5밀리초입니다.

MLFQ에서는 0밀리초입니다.

한 번에 5밀리초 차이는 별것 아닌 것 같지만, 초당 30번 깨어나는 작업이라면 누적이 됩니다. 그리고 C 같은 계산 작업이 여러 개라면 대기 시간은 그만큼 배가 됩니다.

## 10.12 MLFQ가 보는 것과 못 보는 것

이제 이 장의 결론입니다. 그리고 이 시리즈 전체에서 가장 중요한 부분 중 하나입니다.

### MLFQ가 보는 것

MLFQ의 판단 재료를 전부 나열하면 이게 전부입니다.

- task가 CPU를 얼마나 오래 썼는가
- task가 시간을 다 써서 내려왔는가, 스스로 놓았는가
- 얼마나 자주 깨어나는가
- 얼마나 오래 queue에 있었는가

전부 **행동에 관한 정보**입니다. 시간과 횟수뿐입니다.

### MLFQ가 못 보는 것

- 이 프로그램이 무엇인가
- 사람이 지금 무엇을 하고 있는가
- 이 배경 작업을 사람이 기다리고 있는가
- 화면에 지금 무엇이 보이는가
- 여러 프로그램이 함께 돌고 있다는 사실이 무엇을 뜻하는가

전부 **의미에 관한 정보**입니다. MLFQ의 재료에는 하나도 들어 있지 않습니다.

### 그래서 이런 일이 생깁니다

앞에서 든 예를 다시 가져옵니다.

게임이 돌고 있고 배경에 대용량 다운로드가 있습니다. MLFQ가 보는 것은 이렇습니다.

- 게임의 frame task: 규칙적으로 깨어나서 짧게 계산하고 잠듦 → 대화형으로 판정 → Q2에 유지
- 다운로드 task: 데이터를 받아 디스크에 씀. 가끔 잠들지만 대체로 CPU를 씀 → 중간쯤으로 판정

MLFQ는 이 판정을 두 상황에서 **똑같이** 내립니다.

사용자가 게임에 집중하고 있고 다운로드는 나중에 끝나도 되는 상황에서도, 사용자가 다운로드를 기다리며 시간을 때우는 상황에서도 똑같습니다.

**두 상황의 올바른 설정은 정반대인데, MLFQ는 구분할 방법이 없습니다.** 구분에 필요한 정보가 애초에 재료에 없기 때문입니다.

이건 MLFQ를 더 잘 만들어서 해결할 수 있는 문제가 아닙니다. 규칙을 아무리 정교하게 다듬어도, 관찰할 수 있는 데이터에 그 차이가 나타나지 않습니다.

### 다른 정보원이 필요합니다

그럼 그 차이는 어디에 나타날까요?

**프로그램의 이름에 나타납니다.**

지금 돌고 있는 프로그램들의 이름을 나열해보면 이렇습니다. 게임 실행 파일 이름, 게임 런처 이름, 다운로드하는 프로그램 이름, 음성 채팅 프로그램 이름, 브라우저 이름.

이 목록을 사람이 보면 상황을 짐작할 수 있습니다. 게임 런처가 다운로드를 하고 있고 그 게임이 아직 안 켜졌다면 업데이트를 기다리는 중일 겁니다. 게임이 이미 돌고 있는데 다른 게임의 다운로드가 돌고 있다면 미리 받아두는 중일 겁니다.

**이 짐작을 하려면 "이 이름이 무엇인지"를 알아야 합니다.** OS는 그걸 모릅니다. 사람은 압니다. 그리고 언어 모델도 압니다.

이 시리즈가 다루는 연구의 출발점이 정확히 여기입니다.

**MLFQ가 못 보는 것은 정보 부족이 아니라 정보 종류의 문제입니다. 행동 데이터에는 없고 이름에는 있습니다. 그리고 이름을 읽으려면 세상에 대한 지식이 필요합니다.**

## 10장 정리

- MLFQ는 여러 단계의 queue를 두고 task를 그 사이에서 옮기는 알고리즘입니다. Linux, macOS, Windows가 전부 이 계열의 변형을 씁니다.
- 핵심 아이디어는 미리 알 필요 없이 실행시켜보고 행동을 관찰해서 판단하고, 틀리면 고친다는 것입니다.
- 규칙은 여섯 줄입니다. 높은 queue 우선, 같은 queue는 Round Robin, 새 task는 최상위에서 시작, 할당된 시간을 다 쓰면 아래로 내리고 스스로 놓으면 유지, 주기적으로 전부 최상위로 되돌리기, 아래 queue일수록 긴 slice.
- 가장 중요한 규칙은 시간을 다 썼는지 스스로 놓았는지로 성격을 추측하는 부분입니다. 프로그램이 무엇인지 전혀 몰라도 이 관찰 하나로 대화형과 계산 작업이 자동으로 분류됩니다.
- 주기적으로 전부 되돌리는 boost가 starvation, 성격 변화, 속임수 세 문제를 한 번에 완화합니다. 대신 boost 간격을 얼마로 할지에는 정답이 없습니다. 이런 값들을 어떤 교과서는 voo-doo constant라고 부릅니다.
- 누적 시간을 세는 allotment 개념으로 slice 직전에 잠드는 속임수를 막습니다.
- 조정할 수 있는 값은 queue 개수, 최상위 slice, slice 증가 비율, boost 간격입니다. 같은 MLFQ라도 이 값들에 따라 전혀 다르게 동작합니다.
- MLFQ의 판단 재료는 전부 행동에 관한 것입니다. 시간과 횟수뿐입니다. 이 프로그램이 무엇인지, 사람이 무엇을 하고 있는지, 배경 작업을 사람이 기다리는지는 재료에 없습니다.
- 그래서 행동이 같고 의도가 다른 두 상황을 구분할 수 없습니다. 이건 알고리즘을 개선해서 해결할 문제가 아니라 정보 종류의 문제입니다. 그 차이는 프로그램의 이름에 나타나고, 이름을 읽으려면 세상에 대한 지식이 필요합니다.

# 11장 · 다른 알고리즘 가족들

## 11.1 MLFQ가 답하지 않는 질문들

앞 장에서 본 MLFQ는 하나의 질문에 답합니다.

> 누가 대화형이고 누가 계산 작업인가?

좋은 질문이고, 데스크톱 환경에서는 가장 중요한 질문이기도 합니다. 하지만 다른 질문도 있습니다.

**이 task에게 정확히 CPU의 30퍼센트를 주고 싶다.** MLFQ로는 이걸 표현할 방법이 없습니다. priority는 상대적인 순서일 뿐 정확한 비율이 아닙니다.

**이 작업은 반드시 16.7밀리초 안에 끝나야 한다.** MLFQ에는 deadline이라는 개념이 없습니다. 높은 priority를 준다고 deadline이 지켜진다는 보장은 없습니다.

이 두 질문에 답하는 다른 계열의 알고리즘들이 있습니다. 이 장에서 봅니다.

그리고 이 시리즈가 다루는 연구는 이 알고리즘들을 선택지로 가지고 있습니다. 상황에 따라 아예 다른 알고리즘으로 갈아 끼울 수 있게 설계되어 있습니다. 그래서 각각이 어떤 질문에 답하는지 알아두는 것이 중요합니다.

## 11.2 비율로 나누기: proportional share

첫 번째 계열입니다. 아이디어는 단순합니다.

> **각 task에게 "share"을 주고, 그 비율대로 CPU를 나눠 준다.**

priority처럼 순서를 정하는 게 아니라, 비율을 정합니다.

웹 서비스에 빗대면 API rate limit과 비슷합니다. "이 고객은 초당 1000건, 저 고객은 초당 100건"처럼 명시적인 비율을 주는 방식입니다.

### Lottery scheduling

가장 이해하기 쉬운 구현입니다. 1994년에 제안된 방식입니다.

각 task에게 **ticket**을 나눠 줍니다. 복권입니다.

- task A에게 ticket 75장
- task B에게 ticket 25장

scheduler는 매번 결정할 때마다 **추첨을 합니다.** 0부터 99까지의 숫자 중 하나를 무작위로 뽑고, 그 번호를 가진 ticket의 주인이 실행됩니다.

A가 뽑힐 확률은 75퍼센트, B는 25퍼센트입니다. 그러니까 **장기적으로 A가 CPU의 75퍼센트를, B가 25퍼센트를 가져갑니다.**

### 왜 이게 좋은 아이디어인가

**구현이 극단적으로 단순합니다.** 난수 하나 뽑고 ticket 목록을 훑으면 끝입니다. 복잡한 자료구조가 필요 없습니다.

**starvation이 없습니다.** ticket이 한 장이라도 있으면 언젠가는 뽑힙니다. 확률적으로 보장됩니다.

**task가 들어오고 나가는 것을 다루기 쉽습니다.** ticket 총량만 다시 계산하면 됩니다. 복잡한 재조정이 없습니다.

**비율을 명시적으로 표현할 수 있습니다.** "이 작업에 30퍼센트"를 직접 말할 수 있습니다.

### 문제: 짧게 보면 불공평합니다

무작위이기 때문에 단기적으로는 비율이 맞지 않습니다.

75대 25로 열 번 추첨하면 기댓값은 7.5대 2.5입니다. 하지만 실제로는 9대 1이 나올 수도 있고 5대 5가 나올 수도 있습니다.

추첨을 많이 할수록 비율에 수렴하지만, 짧은 구간에서는 흔들립니다.

deadline이 있는 작업에는 이 흔들림이 치명적입니다. "평균적으로는 제때 끝난다"는 보장은 frame이 끊기는 것을 막아주지 못합니다.

### Stride scheduling: 무작위를 없애기

같은 사람들이 제안한 결정론적 버전이 있습니다. **stride scheduling**입니다.

각 task에게 **stride**라는 값을 줍니다. ticket 수에 반비례하는 값입니다.

```text
   stride = 큰 상수 / ticket 수
```

큰 상수를 10000이라고 하면, ticket 75장인 A는 stride가 133이고, 25장인 B는 400입니다.

각 task는 **pass**라는 누적값을 가집니다. 처음에는 0입니다.

규칙은 이렇습니다.

> pass가 가장 작은 task를 실행하고, 실행한 뒤 그 task의 pass에 stride를 더한다.

따라가봅시다.

| 순번 | A의 pass | B의 pass | 실행할 task | 실행 후 |
|---|---|---|---|---|
| 1 | 0 | 0 | A (동점, A 우선) | A → 133 |
| 2 | 133 | 0 | B | B → 400 |
| 3 | 133 | 400 | A | A → 266 |
| 4 | 266 | 400 | A | A → 399 |
| 5 | 399 | 400 | A | A → 532 |
| 6 | 532 | 400 | B | B → 800 |
| 7 | 532 | 800 | A | A → 665 |
| 8 | 665 | 800 | A | A → 798 |
| 9 | 798 | 800 | A | A → 931 |
| 10 | 931 | 800 | B | B → 1200 |

열 번 중 A가 일곱 번, B가 세 번 실행됐습니다. 75대 25에 가깝습니다.

그리고 **무작위가 없습니다.** 항상 같은 순서가 나옵니다. 재현 가능합니다.

stride가 작은 task는 pass가 천천히 올라가니까 자주 뽑힙니다. ticket이 많다는 뜻이니 맞습니다.

### 실제로는 어떻게 쓰이나

순수한 lottery scheduling을 쓰는 상용 OS는 없습니다. 하지만 아이디어는 널리 퍼졌습니다.

컨테이너에 CPU 할당량을 주는 기능들이 개념적으로 이 계열입니다. Docker에서 컨테이너에 CPU share를 지정하는 것, 가상 머신에 CPU 비중을 주는 것이 전부 비율 기반입니다.

> **이 연구에서는.** 시뮬레이터가 지원하는 네 가지 알고리즘 중 하나가 LOTTERY입니다. 다만 task 하나하나에 ticket을 주는 방식은 아니고, task를 두 class로 나눠서 class별로 비율을 주는 방식입니다. batch class에 전체의 몇 퍼센트를 줄지를 config로 정하고, 나머지를 다른 class가 나눠 갖습니다.
>
> 그런데 이 config의 기본값을 정할 때 문제가 있었습니다. 이 값이 얼마여야 한다고 말하는 출처가 없습니다. 원래 논문은 ticket 수에 비례해서 나눈다는 원리만 제시하고 class 간 비율은 말하지 않습니다. 그래서 이 값은 근거 없는 가정이라고 문서에 명시해뒀습니다. 근거가 없으면 없다고 적는 것이 원칙입니다.

## 11.3 공평하게 나누기: fair-share

proportional share와 비슷하지만 조금 다른 계열입니다.

핵심 아이디어는 이렇습니다.

> **각 task가 지금까지 CPU를 얼마나 썼는지 추적하고, 가장 적게 쓴 task를 실행한다.**

priority도 아니고 추첨도 아닙니다. **누적 사용량을 기록해두고 가장 뒤처진 것을 밀어주는** 방식입니다.

### virtual runtime

Linux가 오랫동안 쓴 방식이 이 계열입니다. **CFS**라고 불렸는데, Completely Fair Scheduler의 약자입니다.

각 task마다 **virtual runtime**이라는 값을 유지합니다. 실제로 CPU를 쓴 시간을 그 task의 weight로 나눈 값입니다.

```text
   virtual runtime += 실제로 쓴 시간 / weight
```

weight가 크면 같은 시간을 써도 virtual runtime이 조금만 올라갑니다. 그래서 더 자주 뽑힙니다.

scheduler는 **virtual runtime이 가장 작은 task**를 실행합니다.

이 방식의 장점은 이렇습니다.

**정확히 공평합니다.** 시간이 지나면 모든 task의 virtual runtime이 비슷해집니다. weight를 반영한 공평함입니다.

**priority를 자연스럽게 표현합니다.** 앞 장에서 본 nice 값이 여기서 weight로 변환됩니다.

**대화형 작업이 자동으로 우대받습니다.** 잠들어 있는 동안 virtual runtime이 안 올라가니까, 깨어났을 때 값이 작아서 바로 뽑힙니다. MLFQ가 규칙으로 하는 일을 이 방식은 구조적으로 합니다.

### EEVDF

Linux는 2023년에 나온 kernel 버전부터 CFS를 **EEVDF**로 교체했습니다. Earliest Eligible Virtual Deadline First의 약자입니다.

기본 아이디어는 비슷하지만, 각 task에 가상의 deadline을 부여하고 그 deadline이 가장 이른 것을 고릅니다. 지연 시간에 민감한 작업을 더 잘 다루기 위한 개선입니다.

세부는 이 책의 범위를 넘습니다. 여기서 알아둘 것은 **널리 쓰이는 OS의 scheduler도 계속 바뀌고 있다**는 사실입니다. 정답이 정해진 영역이 아닙니다.

## 11.4 deadline을 지키기: real-time

세 번째 계열입니다. 질문이 완전히 다릅니다.

> **이 작업은 반드시 정해진 시각까지 끝나야 한다. 지킬 수 있는가?**

앞의 알고리즘들은 전부 "평균적으로 좋게" 또는 "공평하게"를 목표로 했습니다. 여기서는 **보장**이 목표입니다.

### 어디에 필요한가

**산업 제어.** 로봇 팔이 정해진 시각에 멈추지 않으면 사고가 납니다.

**오디오와 비디오.** 오디오 버퍼가 비기 전에 다음 조각을 채우지 못하면 소리가 튑니다. frame을 제때 못 만들면 화면이 끊깁니다.

**게임.** 초당 60 frame이면 약 16.7밀리초마다 한 frame을 완성해야 합니다.

앞의 두 개는 전통적인 real-time 영역이고, 뒤의 두 개는 일반 데스크톱에서 매일 일어나는 일입니다. 그래서 real-time 개념이 데스크톱 scheduling에도 스며들어 있습니다.

### 용어 정리

**periodic task.** 일정한 간격으로 반복되는 작업입니다. period라고 부르는 그 간격마다 한 번씩 일이 도착합니다.

**job.** periodic task이 한 번 도는 것을 job이라고 부릅니다. 60 frame 게임이 1초 동안 돌면 job이 60개 생깁니다.

**deadline.** job 하나가 끝나야 하는 시각입니다. 보통 다음 period가 시작되는 시각으로 잡습니다. 이걸 period-implicit deadline이라고 합니다.

**worst-case execution time.** job 하나가 최악의 경우 얼마나 걸리는지입니다.

### EDF

**EDF**는 Earliest Deadline First의 약자입니다. 이름 그대로입니다.

- **누구를 실행할 것인가:** deadline이 가장 임박한 job.
- **얼마나 오래:** 더 급한 deadline이 생길 때까지.

새 job이 도착할 때마다 다시 판단합니다. 그 job의 deadline이 지금 실행 중인 것보다 이르면 즉시 빼앗습니다.

### 손으로 따라가보기

periodic task이 둘 있습니다.

- **P1**: 10밀리초마다 도착하고, 한 번에 3밀리초 필요
- **P2**: 15밀리초마다 도착하고, 한 번에 5밀리초 필요

deadline은 다음 period 시작 시각입니다.

```text
   t=0    P1의 첫 job 도착 (deadline 10), P2의 첫 job 도착 (deadline 15)
          deadline이 이른 P1을 실행

   0-3    P1 실행. 완료. (deadline 10, 여유 7ms)

   3-8    P2 실행. 완료. (deadline 15, 여유 7ms)

   8-10   할 일 없음. core 유휴.

   t=10   P1의 두 번째 job 도착 (deadline 20)

   10-13  P1 실행. 완료.

   13-15  유휴.

   t=15   P2의 두 번째 job 도착 (deadline 30)

   15-20  P2 실행. 완료.

   t=20   P1의 세 번째 job 도착 (deadline 30)

   20-23  P1 실행. 완료.
```

모든 deadline이 지켜졌습니다.

### 얼마나 넣을 수 있나

여기서 real-time 이론의 유명한 결과가 나옵니다.

각 periodic task이 CPU를 얼마나 요구하는지를 계산해봅시다. 필요한 시간을 period로 나누면 됩니다.

```text
   P1: 3 / 10  = 0.30
   P2: 5 / 15  ≈ 0.333
   ─────────────────────
   합계          ≈ 0.633
```

이 합계를 **utilization**이라고 부릅니다. CPU 요구량의 총합입니다.

**EDF에 대한 정리:** deadline이 주기와 같은 periodic task들만 있을 때, utilization의 합이 1 이하이면 EDF는 모든 deadline을 지킵니다. 1을 넘으면 어떤 알고리즘으로도 지킬 수 없습니다.

이건 강력한 결과입니다. **EDF는 이 조건에서 최적입니다.** 지킬 수 있는 상황이라면 EDF가 반드시 지킵니다.

앞의 예에서 합계가 0.633이니 여유가 있습니다. 실제로 모든 deadline이 지켜졌습니다.

### 고정 priority 방식

또 다른 고전적인 방법으로 **rate monotonic** 이라는 것이 있습니다. period가 짧은 작업에 높은 priority를 고정으로 주는 방식입니다.

EDF보다 단순하지만 덜 강력합니다. 작업 개수가 많아지면 utilization이 약 69퍼센트를 넘을 때부터 deadline을 못 지킬 수 있습니다. EDF는 100퍼센트까지 갑니다.

대신 구현이 단순하고 예측하기 쉬워서 안전이 중요한 시스템에서 여전히 쓰입니다.

### EDF의 문제들

**작업 시간을 알아야 합니다.** utilization을 계산하려면 각 job이 얼마나 걸리는지 알아야 합니다. 일반 데스크톱 프로그램에 대해서는 알 수 없습니다.

**과부하에 취약합니다.** utilization이 1을 넘어가면 EDF는 급격히 무너집니다. deadline을 놓치기 시작하면 그 job이 계속 남아서 다음 job의 시간을 잡아먹고, 연쇄적으로 전부 놓칩니다. 이 현상을 domino effect라고 부릅니다.

**deadline이 없는 작업은 어떻게 하나요?** 데스크톱에는 deadline이 있는 작업과 없는 작업이 섞여 있습니다. EDF는 deadline이 있는 작업만 다룹니다.

> **이 연구에서는.** 시뮬레이터가 지원하는 네 알고리즘 중 하나가 EDF입니다. 앞의 문제들을 이렇게 다룹니다.
>
> deadline이 있는 작업은 **행동으로 판별합니다.** 주기적으로 깨어나는 방식으로 동작하는 task를 deadline class로 봅니다. 각 job의 deadline은 다음 period가 시작되는 시각입니다.
>
> deadline이 없는 작업들은 남은 시간을 Round Robin으로 나눠 씁니다. 그 Round Robin의 slice 길이가 EDF 설정에서 정할 수 있는 유일한 값입니다.
>
> 그리고 들어오는 작업을 미리 거르는 장치는 두지 않았습니다. 실제 시스템에서는 utilization을 계산해서 넘치면 새 작업을 거부하는데, 이 실험에서는 그러지 않습니다. 과부하가 나면 나는 대로 관찰합니다.

## 11.5 계열별 정리

| 계열 | 답하는 질문 | 대표 | 강점 | 약점 |
|---|---|---|---|---|
| 순서 기반 | 누가 먼저인가 | FIFO | 단순, 전환 없음 | convoy effect |
| 시간 분할 | 모두에게 골고루 | Round Robin | 반응 좋음 | 차등 불가 |
| 피드백 | 누가 대화형인가 | MLFQ | 선언 없이 자동 분류 | 의미를 못 봄 |
| 비율 | 각자 몇 퍼센트인가 | Lottery, Stride | 비율을 명시 | 단기 변동, deadline 보장 없음 |
| 공평 배분 | 누가 뒤처졌는가 | CFS, EEVDF | 정확한 공평함 | deadline 보장 없음 |
| deadline | 제때 끝낼 수 있는가 | EDF | 조건 하에서 최적 | 시간을 알아야 함, 과부하에 취약 |

여기서 읽어야 할 것은 **어느 것도 다른 것보다 무조건 낫지 않다**는 점입니다. 각자 다른 질문에 답합니다.

앞에서 봤듯이 좋은 scheduling의 정의는 지금 무슨 일이 벌어지고 있느냐에 달려 있습니다. 그러니 상황에 따라 다른 계열이 정답일 수 있습니다.

게임 중이라면 EDF 계열이 어울립니다. frame deadline이 전부이기 때문입니다. 여러 배치 작업이 도는 중이라면 비율 기반이 어울립니다. 각자 얼마씩 가져갈지가 중요하기 때문입니다. 일반적인 데스크톱 사용에서는 MLFQ가 무난합니다.

> **이 연구에서는.** 이 시리즈가 다루는 연구의 시뮬레이터는 네 가지 알고리즘을 전부 지원합니다. MLFQ, EDF, LOTTERY, FIFO입니다.
>
> 그리고 실행 중에 알고리즘을 바꿀 수 있습니다. 상황이 바뀌었다고 판단되면 아예 다른 계열로 갈아 끼웁니다. 이건 실제 OS에서는 흔하지 않은 일입니다. 그래서 갈아 끼울 때 queue에 있던 task들을 어떻게 처리할지, 실행 중이던 task는 어떻게 할지 같은 것을 하나하나 정해야 했습니다.
>
> 네 알고리즘 전부에 공통으로 적용되는 config도 하나 있습니다. **batch class가 전체 CPU의 몇 퍼센트까지만 쓸 수 있게 할 것인가**를 정하는 상한입니다. 다른 작업이 실행 대기 중일 때만 적용됩니다. 배경 작업을 억눌러야 하는 상황에서 쓰는 장치입니다.
>
> 여기서 batch class를 어떻게 판별하는지가 중요한데, **행동으로 판별합니다.** 프로그램 이름으로 판별하지 않습니다. MLFQ가 priority를 낮출 때 쓰는 것과 똑같은 증거, 즉 주어진 시간을 다 쓰는지를 봅니다. 이 판별 규칙은 네 알고리즘에서 동일하고 설정으로 바꿀 수 없게 고정해뒀습니다.
>
> 왜 고정했는지에 대해서는 이유가 있습니다. 만약 이 판별을 이름으로 한다면, 언어 모델이 이름을 읽어서 얻는 이득과 판별기가 이름을 읽어서 얻는 이득이 섞입니다. 그러면 실험이 무엇을 측정했는지 알 수 없게 됩니다. 실험에서 변수를 하나만 두는 원칙이 여기에도 적용된 것입니다.

## 11장 정리

- MLFQ는 "누가 대화형인가"에 답하지만, "각자 몇 퍼센트를 줄 것인가"와 "deadline을 지킬 수 있는가"에는 답하지 못합니다. 다른 계열들이 이 질문에 답합니다.
- Lottery scheduling은 각 task에 ticket을 주고 추첨으로 고릅니다. 구현이 단순하고 starvation이 없으며 비율을 명시적으로 표현할 수 있습니다. 대신 무작위라서 짧은 구간에서는 비율이 흔들립니다.
- Stride scheduling은 같은 아이디어의 결정론적 버전입니다. ticket 수에 반비례하는 값을 누적해가며 가장 뒤처진 것을 고릅니다. 재현 가능합니다.
- Fair-share 계열은 각 task의 누적 사용량을 추적하고 가장 적게 쓴 것을 실행합니다. Linux가 오랫동안 쓴 CFS가 이 계열이고, 지금은 EEVDF로 바뀌었습니다. 널리 쓰이는 시스템의 scheduler도 계속 바뀝니다.
- Real-time 계열은 deadline 보장이 목표입니다. EDF는 deadline이 가장 임박한 job을 실행하며, deadline이 주기와 같은 periodic task들만 있고 utilization 합이 1 이하이면 모든 deadline을 지킨다는 것이 증명되어 있습니다.
- EDF는 작업 시간을 알아야 하고, 과부하가 나면 연쇄적으로 무너지며, deadline 없는 작업을 다루지 못합니다.
- 어느 계열도 무조건 낫지 않습니다. 각자 다른 질문에 답하고, 어느 질문이 중요한지는 지금 무슨 일이 벌어지고 있느냐에 달려 있습니다.

# 12장 · periodic task: frame, deadline, chain

## 12.1 데스크톱은 periodic task로 가득합니다

앞에서 프로그램을 대화형과 계산 작업으로 나눴습니다. 유용한 구분이지만 빠진 것이 있습니다.

**정해진 박자에 맞춰 반복되는 일**입니다.

지금 컴퓨터에서 돌고 있을 법한 것들을 나열해봅시다.

- compositor가 초당 60번 화면을 갱신합니다.
- 음악 재생 프로그램이 몇 밀리초마다 오디오 버퍼를 채웁니다.
- 영상 재생 중이라면 frame을 초당 24번에서 60번 디코딩하고 표시합니다.
- 게임이 돌고 있다면 초당 60번에서 240번 frame을 만듭니다.
- 영상 통화 중이라면 카메라 입력을 받고, 인코딩하고, 상대의 영상을 디코딩하고, 표시합니다.

이들의 공통점은 이렇습니다.

**CPU를 많이 쓰지 않습니다.** 한 번에 몇 밀리초씩입니다.

**대화형처럼 짧게 일하고 잠듭니다.** 그래서 MLFQ에서 높은 queue에 머뭅니다.

**하지만 deadline이 있습니다.** 늦으면 사용자가 즉시 알아챕니다.

마지막 항목이 대화형 작업과 결정적으로 다른 점입니다. 편집기가 20밀리초 늦게 반응하면 아무도 모릅니다. frame이 20밀리초 늦으면 화면이 눈에 띄게 끊깁니다.

## 12.2 frame의 산수

초당 60 frame이면 한 frame에 주어진 시간은 이렇습니다.

```text
   1초 / 60 = 16.667 밀리초
```

초당 144 frame짜리 모니터라면 6.944밀리초입니다.

이 시간 안에 한 frame을 완성해야 합니다. 못 하면 어떻게 될까요?

**같은 화면이 두 번 표시됩니다.** 새 frame이 준비되지 않았으니 이전 것을 다시 보여줍니다.

사용자 눈에는 순간적으로 멈춘 것처럼 보입니다. 이걸 **stutter** 또는 frame 끊김이라고 부릅니다.

### 왜 평균이 의미 없는가

여기가 중요합니다.

frame 100개를 만들었는데, 99개는 8밀리초 만에 완성했고 1개는 25밀리초 걸렸다고 합시다.

평균은 8.17밀리초입니다. 16.667밀리초 예산의 절반도 안 씁니다. 숫자만 보면 아주 여유롭습니다.

하지만 **사용자는 끊김을 한 번 봤습니다.**

그리고 이 끊김은 frame이 균일하게 나올 때보다 훨씬 눈에 띕니다. 뇌가 규칙적인 흐름에 적응해 있다가 갑자기 어긋나면 즉각 알아챕니다.

그래서 이런 작업에서는 **평균이 아니라 최악의 경우를 봐야 합니다.** 앞에서 정리한 P99나 최댓값, 그리고 deadline을 넘긴 비율이 실제로 의미 있는 숫자입니다.

### 앞뒤가 안 맞는 상황

여기서 재미있는 일이 생깁니다.

scheduler 입장에서 최적화하기 좋은 metric은 평균입니다. 평균을 좋게 만드는 것은 비교적 쉽고, 측정하기도 쉽습니다.

그런데 사용자가 실제로 느끼는 것은 최악의 경우입니다.

**평균을 개선하면서 최악을 악화시키는 변경**은 얼마든지 가능합니다. 그리고 그런 변경은 숫자로는 개선처럼 보이지만 실제로는 개악입니다.

## 12.3 frame 하나를 만드는 일

frame 하나가 만들어지는 과정을 좀 더 들여다봅시다. 게임을 예로 듭니다.

```text
   ① 입력 수집     마우스와 키보드 상태를 읽는다
        │
        ▼
   ② 게임 로직     물리 계산, 인공지능, 게임 상태 갱신
        │
        ▼
   ③ 렌더 준비     무엇을 그릴지 정리해서 명령 목록을 만든다
        │
        ▼
   ④ GPU 제출      GPU에 명령을 보낸다
        │
        ▼
   ⑤ 화면 합성     compositor가 여러 window를 합쳐 최종 화면을 만든다
        │
        ▼
   ⑥ 표시          모니터에 나간다
```

여기서 중요한 점이 있습니다.

**이 단계들이 서로 다른 task입니다.**

①에서 ④까지는 게임 process 안의 여러 thread일 수 있습니다. ⑤는 아예 다른 process입니다. OS의 compositor입니다.

그리고 각 단계는 앞 단계가 끝나야 시작할 수 있습니다. **앞 단계가 뒤 단계를 깨웁니다.**

## 12.4 chain

이렇게 여러 task가 순서대로 이어져서 하나의 결과를 만드는 구조를 이 책에서는 **chain**이라고 부르겠습니다. 사슬입니다.

```text
   task A ──깨움──▶ task B ──깨움──▶ task C ──▶ 결과
```

앞에서 chain의 예를 한 번 봤습니다. 웹 서버에서 요청 수신 thread가 작업을 큐에 넣고, worker thread가 처리하고, 응답 thread가 내보내는 구조였습니다. 같은 모양입니다.

### chain의 지연은 합입니다

사용자가 체감하는 지연은 **chain 전체의 시간**입니다. 각 단계의 시간이 아닙니다.

그런데 각 단계마다 두 종류의 시간이 있습니다.

- **실제로 일한 시간**
- **차례를 기다린 시간**

앞에서 정리했듯이 뒤엣것이 scheduler 탓입니다.

숫자를 넣어봅시다. 세 단계 chain이고, 예산은 16.667밀리초입니다.

**상황 1: 대기가 거의 없을 때**

| 단계 | 기다린 시간 | 일한 시간 | 누적 |
|---|---|---|---|
| A | 0.2 ms | 2 ms | 2.2 ms |
| B | 0.3 ms | 4 ms | 6.5 ms |
| C | 0.2 ms | 5 ms | 11.7 ms |

전체 11.7밀리초입니다. 예산 안에 들어옵니다.

**상황 2: 각 단계에서 조금씩 기다릴 때**

| 단계 | 기다린 시간 | 일한 시간 | 누적 |
|---|---|---|---|
| A | 2 ms | 2 ms | 4 ms |
| B | 3 ms | 4 ms | 11 ms |
| C | 2 ms | 5 ms | 18 ms |

전체 18밀리초입니다. **deadline을 넘겼습니다.**

여기서 주목할 것이 있습니다. **각 단계만 따로 보면 아무 문제가 없습니다.** 2밀리초, 3밀리초, 2밀리초 기다린 것은 전혀 심각해 보이지 않습니다. 사람이 못 느끼는 수준입니다.

그런데 세 개가 합쳐지니 deadline을 넘겼습니다.

### 그래서 scheduler가 어렵습니다

scheduler는 각 task를 따로 봅니다. **이 task들이 하나의 사슬이라는 것을 모릅니다.**

A를 실행할지 말지 결정할 때, A가 어떤 deadline을 향해 가는 사슬의 첫 단계라는 정보가 없습니다. 그냥 방금 깨어난 task 하나로 보입니다.

각 단계에서 "이 정도 기다림은 괜찮다"고 판단한 것들이 쌓여서 deadline을 넘깁니다. 그리고 어느 단계가 원인인지도 명확하지 않습니다.

일부 시스템은 이 문제를 다루려고 특별한 장치를 둡니다. task가 다른 task를 깨울 때 자기 priority를 물려주는 식입니다. 하지만 완전한 해법은 아닙니다.

> **이 연구에서는.** 이 시리즈가 다루는 연구는 chain을 명시적으로 다룹니다.
>
> 실험에 쓰는 가상의 작업 부하 중에 세 단계 chain을 가진 것이 있습니다. 그리고 결과를 분석할 때, 각 단계의 대기 시간을 따로 보는 것과 별개로 **chain 전체가 한 바퀴 도는 데 걸린 시간**을 하나의 숫자로 계산합니다. 어느 단계에서 시작해서 어느 단계에서 끝났는지를 기록에서 재구성해서 이어붙이는 방식입니다.
>
> 이렇게 하는 이유는 앞에서 본 그대로입니다. 단계별 숫자만 보면 문제가 안 보이기 때문입니다.

## 12.5 밀리면 어떻게 되나

periodic task이 deadline을 놓치면 그 뒤가 어떻게 될까요?

두 가지 방식이 있습니다.

### 방식 1: 밀린 것을 버린다

frame 하나를 못 만들었으면 그 frame은 포기하고 다음 period로 넘어갑니다.

게임과 영상 재생이 보통 이렇게 합니다. 이미 지나간 시점의 frame을 늦게 그려봤자 소용없기 때문입니다.

사용자는 끊김을 한 번 보고, 그 다음부터는 정상으로 돌아옵니다.

### 방식 2: 밀린 것을 쌓아둔다

처리하지 못한 일이 큐에 쌓입니다.

오디오가 보통 이렇습니다. 오디오 샘플을 건너뛰면 소리가 튀기 때문에, 늦더라도 처리해서 내보내야 합니다.

이 경우 **backlog**가 생깁니다. 밀린 일이 쌓인 상태입니다.

backlog가 생기면 그 다음 주기의 일이 도착했을 때 이전 일이 아직 안 끝나 있습니다. 처리해야 할 양이 계속 늘어납니다.

CPU에 여유가 있으면 따라잡습니다. 여유가 없으면 계속 밀려서 결국 무너집니다.

### 두 방식의 차이가 측정에 미치는 영향

이 구분이 성능을 측정할 때 실제로 문제가 됩니다.

버리는 방식이라면 "deadline을 넘긴 frame의 비율"을 세면 됩니다. 명확합니다.

쌓아두는 방식이라면 조금 복잡합니다. 밀린 상태에서 처리한 job은 도착하자마자 시작한 것이 아니라 이미 큐에서 기다리고 있었습니다. 이 job의 지연을 어디서부터 재야 할까요? 원래 도착했어야 할 시각부터인가요, 아니면 실제로 처리를 시작한 시각부터인가요?

> **이 연구에서는.** 이 질문에 답을 정해두고 문서에 적어뒀습니다. 그리고 밀린 상태에 있는 periodic task이 포함된 시험용 예제를 하나 만들어서, 그 예제의 정답 숫자를 손으로 직접 계산해뒀습니다. 코드가 그 숫자와 정확히 일치하는지 자동으로 검사합니다.
>
> 이런 식으로 애매한 정의마다 손으로 계산한 예제를 붙여두는 것이 이 연구의 작업 방식입니다. 정의를 글로만 적어두면 나중에 해석이 갈리는데, 숫자가 붙어 있으면 갈릴 수 없습니다.

## 12.6 오디오와 영상은 조금씩 다릅니다

periodic task이라고 다 같지 않습니다.

### 오디오

**deadline이 가장 엄격합니다.** 오디오 버퍼가 비면 즉시 튀는 소리가 납니다. 그리고 사람의 귀는 이 결함에 아주 민감합니다.

**대신 CPU를 거의 안 씁니다.** 오디오 디코딩과 믹싱은 가벼운 작업입니다.

그래서 대부분의 시스템이 오디오 관련 task에 최고 수준의 priority를 줍니다. 비용이 거의 없으면서 실패 비용이 크기 때문입니다.

### 영상 재생

**deadline이 오디오보다 관대합니다.** frame 하나가 늦으면 눈에 띄지만 오디오만큼 치명적이지는 않습니다.

**CPU 사용량이 큽니다.** 특히 고해상도 영상의 소프트웨어 디코딩은 무겁습니다.

**그리고 오디오와 동기화되어야 합니다.** 영상이 늦으면 입 모양과 소리가 어긋납니다.

### 게임

**가장 복잡합니다.** 앞에서 본 여러 단계 chain이 매 frame 돕니다.

**CPU 사용량이 상황에 따라 크게 변합니다.** 화면에 물체가 많으면 늘어납니다.

**그리고 입력 지연까지 신경 써야 합니다.** 마우스를 움직이고 화면에 반영되기까지의 전체 시간이 중요합니다. 이건 frame 하나의 시간이 아니라 chain 전체의 시간입니다.

### 영상 통화

**두 방향 chain이 동시에 돕니다.** 내보내는 쪽은 카메라 입력을 받아 인코딩해서 네트워크로 보내고, 받는 쪽은 네트워크에서 받아 디코딩해서 화면에 표시합니다.

**네트워크가 끼어 있어서 지연이 커집니다.** 그래서 CPU 쪽 지연에 대한 여유가 더 적습니다.

## 12.7 이 장이 이 시리즈에서 갖는 의미

periodic task을 따로 다룬 이유가 있습니다.

앞에서 본 대화형과 계산 작업의 구분만으로는 이 작업들을 제대로 다룰 수 없습니다.

**MLFQ에게 periodic task은 대화형처럼 보입니다.** 짧게 일하고 스스로 잠드니까요. 그래서 높은 queue에 머뭅니다. 여기까지는 좋습니다.

**하지만 MLFQ는 deadline이 있다는 것을 모릅니다.** 높은 queue에 있어도 다른 높은 queue task와 경쟁하면 밀릴 수 있고, 밀리면 deadline을 놓칩니다. MLFQ에는 "이건 늦으면 안 된다"를 표현할 방법이 없습니다.

**그리고 chain이라는 것도 모릅니다.** 각 단계를 따로 봅니다.

앞 장에서 본 EDF는 deadline을 다룰 수 있습니다. 그러니까 **periodic task이 중요한 상황에서는 EDF가 더 나을 수 있습니다.**

그런데 언제가 그런 상황일까요?

게임을 하고 있을 때, 영상을 볼 때, 통화를 할 때입니다. 그리고 그건 컴퓨터가 지금 무엇에 쓰이고 있느냐의 문제입니다.

**같은 하드웨어에서 상황에 따라 다른 알고리즘이 정답입니다.** 그리고 어느 상황인지는 행동 관찰만으로는 알기 어렵습니다.

이 시리즈가 다루는 연구가 알고리즘 선택 자체를 상황에 따라 바꿀 수 있게 설계된 이유가 여기 있습니다.

## 12장 정리

- 현대 데스크톱에는 정해진 박자로 반복되는 작업이 많습니다. 화면 합성, 오디오 재생, 영상 디코딩, 게임 frame, 영상 통화가 전부 그렇습니다.
- 이들은 CPU를 조금만 쓰고 짧게 일하고 잠들어서 대화형처럼 보이지만, 결정적으로 deadline이 있습니다.
- 초당 60 frame이면 한 frame에 16.667밀리초가 주어집니다. 못 지키면 같은 화면이 두 번 나가고 사용자는 끊김을 봅니다.
- 이런 작업에서는 평균이 무의미합니다. 99개가 여유롭고 1개가 늦어도 사용자는 끊김을 봅니다. 최악의 경우와 deadline을 넘긴 비율을 봐야 합니다.
- frame 하나는 여러 task가 순서대로 이어져서 만들어집니다. 이 구조를 chain이라고 부릅니다.
- chain의 지연은 각 단계의 대기 시간과 작업 시간의 합입니다. 단계별로는 문제없어 보이는 작은 대기들이 쌓여서 deadline을 넘길 수 있습니다.
- scheduler는 각 task를 따로 보기 때문에 이들이 하나의 사슬이라는 것을 모릅니다.
- deadline을 놓쳤을 때 밀린 일을 버리는 방식과 쌓아두는 방식이 있습니다. 쌓아두는 경우 지연을 어디서부터 잴지 정의가 필요합니다.
- MLFQ는 periodic task을 대화형으로 분류하지만 deadline이 있다는 것도, chain이라는 것도 모릅니다. deadline이 중요한 상황에서는 EDF 같은 다른 계열이 더 나을 수 있고, 어느 상황인지는 컴퓨터가 무엇에 쓰이고 있느냐의 문제입니다.

# 13장 · 실제 OS는 무엇을 쓰나

## 13.1 교과서와 현실

지금까지 알고리즘을 하나씩 깔끔하게 나눠서 봤습니다. FIFO, Round Robin, MLFQ, lottery, EDF.

실제 OS는 이들 중 하나를 고르지 않습니다. **여러 개를 동시에 씁니다.**

전형적인 구조는 이렇습니다.

```text
   ┌──────────────────────────────────────────────┐
   │  real-time class                                │
   │  deadline이 있거나 반드시 먼저 실행돼야 하는 작업  │
   │  → 여기 뭐라도 있으면 무조건 먼저             │
   ├──────────────────────────────────────────────┤
   │  normal class                                  │
   │  대부분의 프로그램                            │
   │  → MLFQ 또는 fair-share 계열                  │
   ├──────────────────────────────────────────────┤
   │  idle class                                  │
   │  아무도 CPU를 안 쓸 때만 실행                 │
   └──────────────────────────────────────────────┘
```

class 사이에는 엄격한 priority가 있고, class 안에서는 각자의 알고리즘이 돕니다.

그리고 어느 class에 들어갈지는 대체로 **프로그램이 선언하거나 관리자가 지정합니다.** 앞에서 본 그 선언의 문제가 여기 그대로 있습니다.

이 장에서는 실제 시스템 셋을 훑어봅니다. 세부까지 파고들지는 않습니다. 목적은 **지금 쓰는 OS들이 실제로 어디쯤 와 있는지 감을 잡는 것**입니다.

## 13.2 Linux

### class 구조

Linux에는 scheduling class라는 개념이 있습니다. 위에서 아래로 priority가 있습니다.

**deadline class.** 각 task에 실행 시간, period, deadline을 지정할 수 있습니다. 앞 장에서 본 EDF 계열입니다. 새 task를 받을 때 전체 요구량이 넘치지 않는지 검사해서, 넘치면 거부합니다.

**real-time class.** 고정 priority입니다. 같은 priority 안에서 FIFO로 돌 것인지 Round Robin으로 돌 것인지 고를 수 있습니다. 오디오 처리 같은 데 씁니다.

**normal class.** 거의 모든 프로그램이 여기 들어갑니다. 뒤에서 자세히 봅니다.

**batch class.** normal class와 비슷하지만 대화형 우대를 받지 않습니다. 자기가 배경 작업이라고 선언한 프로그램용입니다.

**idle class.** 아무도 CPU를 안 쓸 때만 실행됩니다.

이 구조 자체가 앞에서 본 문제를 그대로 안고 있습니다. **어느 class에 들어갈지는 프로그램이나 사람이 정합니다.** 대부분은 아무것도 안 하고 normal class에 들어갑니다.

### normal class의 변천

Linux의 normal class는 몇 번 바뀌었습니다.

2000년대 초반에는 MLFQ 계열이었습니다. queue를 여러 개 두고 행동을 보고 priority를 조정하는 방식이었습니다. 대화형 여부를 판정하는 규칙이 점점 복잡해졌고, 그 복잡함 자체가 문제가 됐습니다.

2007년에 **CFS**로 교체됐습니다. 앞 장에서 본 fair-share 계열입니다. 각 task의 누적 사용 시간을 weight로 나눈 값을 추적하고, 가장 작은 것을 실행하는 방식입니다. 규칙 기반의 대화형 판정을 없애고 구조적으로 해결한 것이 큰 변화였습니다.

2023년에 나온 kernel 버전부터 **EEVDF**로 다시 교체됐습니다. 비슷한 기반 위에 각 task에 가상의 deadline을 두고 그것이 이른 순서로 고르는 방식입니다. 지연에 민감한 작업을 더 잘 다루려는 개선입니다.

**여기서 읽어야 할 것.** 세계에서 가장 널리 쓰이는 OS의 scheduler가 20년 사이에 세 번 바뀌었습니다. 그리고 각 교체마다 상당한 논쟁이 있었습니다.

**이 영역에 정답이 없다는 증거입니다.**

### 그룹 단위 분배

Linux에는 task들을 그룹으로 묶어서 그룹 단위로 CPU를 분배하는 기능이 있습니다. 컨테이너 기술의 기반이 되는 것입니다.

Docker에서 컨테이너에 CPU 할당량을 주는 것이 이 기능을 쓰는 것입니다. 그룹에 share를 주거나, 상한을 걸 수 있습니다.

> **이 연구에서는.** 앞 장에서 언급한 "batch class가 전체의 몇 퍼센트까지만 쓸 수 있게 하는 상한"이 이 기능과 개념적으로 같습니다. 실제 시스템에 대응물이 있다는 점을 문서에 명시해뒀습니다. 다만 상한의 범위나 class를 판별하는 규칙은 이 연구가 정한 것이고, 그 부분은 참고할 출처가 없다고 적어뒀습니다.

### policy를 갈아 끼우는 기능

최근에 중요한 변화가 있었습니다.

2024년 말에 나온 kernel 버전부터, **scheduling policy를 kernel 밖에서 프로그램으로 작성해서 넣을 수 있는 기능**이 들어갔습니다. kernel을 다시 컴파일하지 않고, 심지어 실행 중에 갈아 끼울 수 있습니다.

원래는 scheduler를 바꾸려면 kernel 코드를 고치고 다시 빌드해서 재부팅해야 했습니다. 그러니 실험 자체가 어려웠고, 새 아이디어가 실제로 쓰이기까지 몇 년이 걸렸습니다.

이제는 다릅니다. policy를 실험하고 배포하는 비용이 크게 떨어졌습니다.

> **이 연구에서는.** 이 변화가 이 시리즈가 다루는 연구의 전제입니다.
>
> "상황에 따라 scheduler 설정을 바꾸거나 아예 다른 알고리즘으로 갈아 끼운다"는 아이디어는, policy 교체가 어려운 시절에는 현실성이 없었습니다. 지금은 실제로 할 수 있는 일입니다.
>
> 이 연구가 실험을 시뮬레이터 위에서 하는 것은 사실이고, 실제 kernel에서 돌려본 것은 아닙니다. 하지만 "이 아이디어가 실제 시스템에서 구현 가능한가"라는 질문에는 이 기능의 존재가 답이 됩니다. 논문에서 이 부분을 어떻게 서술할지도 정해져 있습니다.

## 13.3 Windows

### priority 구조

Windows는 0부터 31까지의 priority 단계를 씁니다. 숫자가 클수록 높습니다.

16 이상은 real-time 영역이고, 그 아래가 일반 영역입니다.

각 task의 priority는 두 가지가 합쳐져서 정해집니다.

**priority class.** process 단위로 정합니다. real-time, 높음, 보통보다 높음, 보통, 보통보다 낮음, 유휴 중에서 고릅니다. 프로그램이 스스로 정하거나 사용자가 작업 관리자에서 바꿀 수 있습니다.

**thread priority.** 그 안에서 thread별로 조정합니다.

### 동적 조정

Windows는 실행 중에 priority를 임시로 올리는 규칙을 여럿 가지고 있습니다.

**I/O가 완료되면 올립니다.** 기다리던 것이 도착했으니 빨리 처리하라는 뜻입니다. 얼마나 올릴지는 기다린 대상에 따라 다릅니다. 디스크보다 키보드와 마우스가 더 많이 올라갑니다.

**foreground window의 thread를 올립니다.** 사용자가 지금 보고 있는 window니까 우대합니다.

**오래 기다린 task를 올립니다.** starvation을 막는 장치입니다.

이 조정들은 임시입니다. 시간이 지나면 원래 값으로 돌아옵니다. 앞에서 본 MLFQ의 boost와 비슷한 발상입니다.

**"foreground window의 thread를 올린다"는 규칙이 특히 흥미롭습니다.** 이건 행동 관찰이 아닙니다. "사용자가 지금 이 window를 보고 있다"는 의미 정보를 시스템이 알고 있고, 그걸 scheduling에 쓰는 것입니다.

즉 **의미 정보를 쓰는 것 자체는 이미 하고 있습니다.** 다만 window system이 알려줄 수 있는 아주 좁은 종류의 의미만입니다.

### Game Mode

Windows에는 게임 모드라는 기능이 있습니다.

게임이 실행되면 배경 작업을 억누르고 게임에 자원을 몰아줍니다.

**게임인지 어떻게 아는가?** 알려진 게임 실행 파일의 목록을 가지고 있습니다. 그리고 게임 개발자가 자기 프로그램을 게임으로 등록할 수도 있습니다.

**이게 앞에서 말한 하드코딩된 의미 지식의 대표적인 예입니다.** 다음 장에서 자세히 다룹니다.

## 13.4 macOS

### QoS class

macOS는 조금 다른 접근을 씁니다. priority 숫자 대신 **의도를 이름으로 선언하는** 방식입니다.

각 작업이 자기가 어떤 종류인지를 선언합니다.

| class | 뜻 | 예 |
|---|---|---|
| user-interactive | 사용자가 지금 상호작용 중 | 화면 갱신, 애니메이션 |
| user-initiated | 사용자가 시작했고 결과를 기다림 | 파일 열기, 문서 저장 |
| utility | 오래 걸리고 사용자가 진행률을 봄 | 다운로드, 데이터 가져오기 |
| background | 사용자가 모르는 유지보수 | 색인, 동기화, 백업 |

OS는 이 선언에 따라 priority뿐 아니라 CPU 주파수, 디스크 접근 priority, 타이머 정밀도까지 조정합니다.

### 이 접근의 흥미로운 점

**class 이름이 기술 용어가 아니라 의도를 나타내는 말입니다.**

"priority 15"가 아니라 "사용자가 시작했고 결과를 기다림"입니다. 사람이 읽으면 무슨 뜻인지 바로 압니다.

이건 좋은 설계입니다. 개발자가 자기 코드의 성격을 판단하기 쉽고, OS는 그 의도를 여러 subsystem에 일관되게 적용할 수 있습니다.

**그리고 이 발상은 이 시리즈가 다루는 연구와 아주 가깝습니다.**

이 연구도 "무엇이 벌어지고 있는가"를 이름으로 표현하고, 그 이름을 여러 subsystem이 각자 해석하게 하자는 구조입니다.

차이는 **누가 그 이름을 붙이느냐**입니다.

macOS에서는 각 프로그램이 자기 작업에 대해 붙입니다. 그래서 프로그램이 아는 범위, 즉 자기 자신에 대해서만 말할 수 있습니다. 어떤 프로그램도 "지금 이 컴퓨터 전체가 게임 중이다"라고 말할 수 없습니다.

이 연구에서는 **바깥에서 전체를 보고** 이름을 붙입니다. 그게 가능한 이유는 시스템 전체의 프로그램 목록을 보고 판단하기 때문입니다.

### 그리고 macOS에도 게임 모드가 있습니다

최근 버전에 게임 모드가 추가됐습니다. 게임이 전면에 있으면 배경 작업을 억누르고, 무선 주변기기의 응답 주기를 높입니다.

Windows와 마찬가지로 **게임인지 아닌지를 알아야** 동작합니다.

## 13.5 공통점

셋을 나란히 놓고 보면 구조가 비슷합니다.

| | Linux | Windows | macOS |
|---|---|---|---|
| real-time class | 있음 | 있음 | 있음 |
| normal class 알고리즘 | fair-share 계열 | priority + 동적 조정 | priority + QoS |
| 프로그램의 자기 선언 | class와 nice | priority class | QoS class |
| 행동 기반 자동 조정 | 있음 | 있음 | 있음 |
| foreground window 우대 | 부분적 | 있음 | 있음 |
| 게임 목록 | 없음 | 있음 | 있음 |

**공통 구조를 한 문장으로 정리하면 이렇습니다.**

> 행동을 관찰해서 자동으로 조정하는 것을 기본으로 하고, 그것으로 부족한 부분은 프로그램의 자기 선언과 사람이 미리 적어둔 목록으로 메운다.

앞에서 이 세 가지 정보원의 한계를 하나씩 봤습니다. 실제 시스템들은 셋을 다 쓰면서 서로의 빈틈을 메우고 있습니다.

그래도 남는 빈틈이 있습니다. 다음 장에서 그 빈틈을 정면으로 봅니다.

## 13장 정리

- 실제 OS는 알고리즘 하나를 고르지 않고 여러 class를 계층으로 쌓습니다. real-time class가 맨 위, normal class가 가운데, idle class가 아래입니다.
- 어느 class에 들어갈지는 대체로 프로그램이 선언하거나 사람이 지정합니다. 대부분은 아무것도 하지 않고 기본값으로 들어갑니다.
- Linux의 normal class는 20년 사이에 세 번 바뀌었습니다. MLFQ 계열에서 fair-share 계열로, 다시 가상 deadline 기반으로 옮겨갔습니다. 이 영역에 정답이 없다는 증거입니다.
- 최근 Linux에는 scheduling policy를 kernel 밖에서 작성해 실행 중에 갈아 끼우는 기능이 들어갔습니다. policy 교체 비용이 크게 떨어졌고, 이 시리즈가 다루는 연구의 전제이기도 합니다.
- Windows는 priority 숫자와 동적 조정 규칙을 씁니다. I/O 완료, foreground window, 오래 기다림에 따라 임시로 priority를 올립니다. foreground window 우대는 행동 관찰이 아니라 의미 정보를 쓰는 사례입니다.
- macOS는 priority 숫자 대신 의도를 이름으로 선언하게 합니다. 이 발상은 이 연구와 가깝지만, 각 프로그램이 자기 자신에 대해서만 말할 수 있다는 한계가 있습니다.
- Windows와 macOS 모두 게임 모드를 가지고 있고, 둘 다 게임인지 아닌지를 알아야 동작합니다.
- 세 시스템의 공통 구조는 이렇습니다. 행동 관찰로 자동 조정하고, 부족한 부분은 프로그램의 자기 선언과 사람이 적어둔 목록으로 메웁니다.

# 14장 · OS 안에 사람이 손으로 적어 넣은 의미

## 14.1 지금까지의 이야기

이 책의 흐름을 한 번 되짚겠습니다.

core는 한 번에 하나만 실행할 수 있어서, OS가 누구를 언제 실행할지 계속 정해야 합니다. 그 결정을 하는 것이 scheduler입니다.

좋은 결정이 무엇인지는 상황에 따라 다릅니다. 반응 속도가 중요할 때가 있고, 총 처리량이 중요할 때가 있고, deadline을 지키는 것이 전부일 때가 있습니다. 이 metric들은 서로 충돌해서 동시에 다 좋게 만들 수 없습니다.

그러니까 좋은 결정을 하려면 **지금 이 컴퓨터가 무엇에 쓰이고 있는지**를 알아야 합니다.

OS는 그걸 모릅니다. 그래서 세 가지 방법으로 메웁니다.

**행동을 관찰합니다.** MLFQ가 하는 일입니다. CPU를 어떻게 놓았는지 보고 대화형인지 계산 작업인지 추측합니다. 잘 동작하지만 의미는 볼 수 없습니다.

**프로그램의 선언을 받습니다.** macOS의 QoS class 같은 것입니다. 유용하지만 대부분 선언하지 않고, 무엇보다 프로그램은 자기 바깥을 모릅니다.

**사람이 목록을 적어둡니다.** 이 장의 주제입니다.

## 14.2 실제로 어떤 목록들이 있나

"사람이 손으로 적어 넣은 의미"가 시스템 어디에 들어 있는지 모아봅시다.

### 게임 실행 파일 목록

가장 명확한 사례입니다.

Windows와 macOS의 게임 모드는 알려진 게임의 목록을 가지고 있습니다. 그 목록에 있는 프로그램이 실행되면 시스템이 동작을 바꿉니다. 배경 작업을 억누르고, 자원을 게임에 몰아주고, 방해가 될 만한 알림을 미룹니다.

이 목록은 누군가가 만들었습니다. 새 게임이 나오면 누군가가 추가해야 합니다.

### 그래픽 드라이버의 게임별 설정

GPU 드라이버는 개별 게임마다 다른 설정을 가지고 있습니다. 어떤 최적화를 켜고 어떤 우회 처리를 적용할지가 게임 이름별로 정해져 있습니다.

이 목록은 수천 개 규모입니다. 그리고 드라이버 업데이트마다 새 게임이 추가됩니다.

### 게임 실행 플랫폼의 프로그램별 설정

게임을 구매하고 실행하는 플랫폼들도 프로그램별 설정을 가지고 있습니다. 어떤 게임에 어떤 호환 계층을 쓸지, 어떤 설정을 적용할지가 게임별로 정해져 있습니다.

### 모바일 OS의 전면과 배경 구분

스마트폰 OS는 앱이 화면에 보이는지 아닌지로 자원을 크게 다르게 줍니다. 배경으로 밀려난 앱은 CPU와 네트워크를 거의 못 씁니다.

여기에 예외 목록이 붙습니다. 음악 재생 앱, 내비게이션 앱, 통화 앱은 배경에서도 계속 돌아야 합니다. 그래서 "이 종류의 앱은 예외"라는 규칙이 들어갑니다. 그리고 그 종류를 앱이 선언하고, 플랫폼이 검토합니다.

### 전원 프로파일

노트북에서 배터리 절약 모드로 바꾸면 CPU 주파수와 scheduling 동작이 바뀝니다. 어떤 프로그램이 실행 중인지에 따라 자동으로 프로파일을 바꾸는 기능도 있습니다.

여기에도 "이 프로그램이 돌면 성능 모드"라는 목록이 있습니다.

## 14.3 공통점

이 목록들을 나란히 놓으면 하나의 패턴이 보입니다.

> **어느 시점에 사람이 앉아서, 무엇이 무엇인지를 손으로 열거했다.**

"이 실행 파일 이름들은 게임이다."
"이 앱 종류는 배경에서도 돌아야 한다."
"이 프로그램이 돌면 성능 모드로 간다."

전부 사람의 지식을 표로 옮겨 적은 것입니다.

## 14.4 중요한 구분: 메커니즘과 목록

여기서 꼭 짚고 넘어가야 할 것이 있습니다.

**이 목록들이 작동시키는 메커니즘 자체는 잘 만들어져 있습니다.**

게임 모드가 하는 일을 보면 이렇습니다. 배경 작업의 priority를 낮추고, 색인 작업을 미루고, 업데이트 확인을 연기하고, 알림을 억누릅니다.

이건 좋은 동작입니다. 실제로 효과가 있습니다. 게임 중에 백신 검사가 시작되지 않는 것은 분명한 개선입니다.

**문제는 그 메커니즘을 언제 켤지 아는 부분입니다.**

메커니즘은 이미 있습니다. 스위치도 있습니다. 없는 것은 **스위치를 언제 눌러야 하는지 아는 능력**입니다. 그 자리를 목록이 메우고 있습니다.

이 구분이 중요한 이유는, 이 시리즈가 다루는 연구가 무엇을 대체하려는지를 정확히 말해주기 때문입니다. **메커니즘을 대체하려는 것이 아닙니다. 목록을 대체하려는 것입니다.**

## 14.5 목록의 세 가지 한계

### 한계 1: 목록에 없으면 모릅니다

가장 명백한 문제입니다.

어제 출시된 게임은 목록에 없습니다. 소규모 개발자가 만든 프로그램은 목록에 없습니다. 회사 내부 도구는 목록에 없습니다. 직접 컴파일한 프로그램은 당연히 없습니다.

목록에 없는 프로그램은 게임 모드의 혜택을 못 받습니다. 그 프로그램이 게임이든 아니든 시스템은 알 방법이 없습니다.

**그리고 목록은 계속 관리해야 합니다.** 소프트웨어는 계속 나오는데 목록은 사람이 갱신해야 합니다. 관리 비용이 영원히 듭니다.

### 한계 2: 목록 하나는 구분 하나만 표현합니다

이게 덜 명백하지만 더 근본적인 문제입니다.

게임 실행 파일 목록이 답할 수 있는 질문은 정확히 하나입니다.

> 이 프로그램이 게임인가?

그게 전부입니다.

그런데 scheduling에 필요한 질문은 훨씬 많습니다.

> 이 배경 작업을 사용자가 기다리고 있는가?
>
> 이 계산 작업은 사용자가 직접 시작한 것인가, 예약된 것인가?
>
> 지금 화면에 보이는 것이 이 window인가?
>
> 이 프로그램이 지금 무거운 작업 중인가, 대기 중인가?

각 질문마다 목록을 하나씩 만들어야 합니다. 그리고 각 목록마다 갱신 부담이 생깁니다.

**목록은 확장되지 않는 해법입니다.** 새 질문이 생길 때마다 처음부터 다시 만들어야 합니다.

### 한계 3: 조합은 목록으로 표현할 수 없습니다

이게 가장 중요한 한계입니다. 그리고 이 연구의 핵심 주장이기도 합니다.

앞에서 든 예를 다시 봅시다.

컴퓨터에서 게임이 돌고 있고, 동시에 배경에서 대용량 파일 하나가 내려받아지고 있습니다.

**상황 1.** 사용자가 게임에 집중하고 있고, 다운로드는 나중에 끝나도 됩니다. 다운로드를 억눌러서 frame을 지켜야 합니다.

**상황 2.** 사용자가 다운로드가 끝나기를 기다리면서 시간을 때우려고 게임을 돌리고 있습니다. 다운로드에 자원을 줘야 합니다.

이제 목록으로 이걸 구분할 수 있는지 봅시다.

게임 실행 파일 이름을 목록에 넣어두면 "게임이 돌고 있다"는 것은 압니다. 다운로드 프로그램 이름을 목록에 넣어두면 "다운로드가 돌고 있다"는 것도 압니다.

**하지만 두 상황에서 두 사실이 똑같습니다.**

차이는 개별 프로그램에 있지 않습니다. **프로그램들의 조합, 그리고 그 조합이 놓인 맥락에 있습니다.**

그럼 조합을 목록에 넣으면 되지 않을까요?

### 조합을 목록에 넣을 수 없는 이유

계산해봅시다.

컴퓨터에서 동시에 돌 수 있는 프로그램의 종류가 1000가지라고 합시다. 실제로는 훨씬 많지만 작게 잡겠습니다.

그중 다섯 개가 동시에 돌아가는 조합의 수는 얼마일까요?

```text
   1000개 중 5개를 고르는 경우의 수 ≈ 8.25 × 10^12
```

8조 개가 넘습니다.

목록에 적을 수 있는 규모가 아닙니다. 그리고 이건 다섯 개만 골랐을 때이고, 실제 컴퓨터에는 수백 개가 돌고 있습니다.

**게다가 프로그램은 계속 새로 나옵니다.** 목록을 다 채웠다고 해도 내일 새 프로그램이 나오면 그것과 관련된 조합이 전부 새로 생깁니다.

**조합은 열거할 수 없습니다.** 이건 노력의 문제가 아니라 규모의 문제입니다.

## 14.6 그럼 무엇이 필요한가

조합을 열거할 수 없다면, 열거하지 않고 이해하는 방법이 있어야 합니다.

사람은 그걸 합니다.

프로그램 이름 목록을 사람에게 보여주면 상황을 짐작합니다.

```text
   실행 중인 프로그램:
     Discord, steam.exe, cs2.exe, chrome.exe, steamwebhelper.exe
```

이걸 본 사람은 이렇게 읽습니다. 게임을 하는 중이고, 음성 채팅을 켜놨고, 브라우저는 아마 공략을 띄워뒀을 것이라고요.

```text
   실행 중인 프로그램:
     code, node, docker, postgres, chrome.exe, slack
```

이건 개발 중입니다. 로컬 서버를 띄워놓고 데이터베이스를 돌리면서 코드를 짜고 있습니다.

**목록에 이 조합들이 적혀 있어서 아는 게 아닙니다.** 각 프로그램이 무엇인지 알고, 그것들이 함께 있다는 사실에서 상황을 추론하는 것입니다.

그리고 처음 보는 프로그램 이름이 있어도 대개 짐작할 수 있습니다. 이름의 생김새, 함께 실행된 다른 프로그램들, 이름이 풍기는 인상으로요.

**이 능력의 정체는 세상에 대한 지식입니다.** 어떤 소프트웨어가 있고, 그게 무엇에 쓰이고, 사람들이 그것들을 어떤 상황에서 함께 쓰는지에 대한 지식입니다.

OS에는 그 지식이 없습니다. 그래서 목록으로 흉내 냈습니다.

**그런데 언어 모델에는 그 지식이 있습니다.**

## 14.7 이 시리즈가 다루는 연구

여기까지 오면 연구의 제안이 자연스럽게 나옵니다.

> 지금 실행 중인 프로그램들의 이름을 언어 모델에게 보여주고, 이 컴퓨터가 무엇에 쓰이고 있는지 읽어내게 한다. 그 판단이 scheduler의 설정을 바꾼다.

앞에서 짚었듯이 언어 모델을 scheduler 안에 넣을 수는 없습니다. 너무 느립니다.

그래서 구조를 이렇게 잡습니다. 언어 모델은 훨씬 느린 주기로 따로 돌면서 상황 판단만 내놓습니다. 그 판단이 config로 번역되고, scheduler는 그 config를 가지고 평소처럼 마이크로초 단위로 동작합니다.

### 몇 가지 미리 짚어둘 것

**이건 아직 주장입니다.** 언어 모델이 상황을 잘 읽는다는 것도, 그게 실제로 더 나은 scheduling으로 이어진다는 것도 증명되지 않았습니다. 그걸 확인하는 것이 이 연구입니다.

**주장이 여러 조각으로 되어 있습니다.** "행동이 같은데 올바른 설정이 다른 상황이 실제로 존재하는가", "그 차이가 프로그램 이름에 나타나는가", "언어 모델이 그걸 읽어내는가", "읽어낸 것이 실제 성능 개선으로 이어지는가"가 전부 따로 확인해야 하는 질문입니다. 각각 독립적으로 실패할 수 있습니다.

**부정적인 결과도 결과입니다.** 만약 언어 모델이 상황은 정확히 읽는데 scheduling 성능은 개선되지 않는다면, 그것도 알아낼 가치가 있는 사실입니다. 기존의 행동 관찰 방식이 이미 충분했다는 뜻이 되니까요.

**그리고 scheduling은 검증 대상일 뿐입니다.** 이 연구가 제안하는 구조는 scheduler에만 쓰이는 것이 아닙니다. 전원 관리, 네트워크 priority 같은 다른 subsystem도 같은 판단을 읽어서 각자 쓸 수 있습니다. scheduling은 그 구조가 실제로 작동하는지 확인하기 위해 고른 첫 번째 사례입니다.

## 14.8 다음 권으로

이 책에서 할 일은 여기까지입니다.

scheduling이 무엇이고, 왜 어렵고, 지금 시스템들이 무엇을 하고 있고, 어디서 막혀 있는지를 봤습니다.

다음 권에서는 **이 문제를 다른 연구자들이 어떻게 다뤄왔는지**를 봅니다. scheduling policy를 갈아 끼울 수 있게 만든 연구들, scheduler 안에서 더 정교하게 행동을 추론하려 한 연구들, 기계학습으로 scheduler를 만들려 한 연구들, 그리고 언어 모델을 kernel policy에 쓰려 한 최근 시도들입니다.

각 연구가 무엇을 해냈고 어디서 멈췄는지 알면, 이 연구가 정확히 어느 빈자리를 노리는지가 명확해집니다.

## 14장 정리

- OS는 지금 컴퓨터가 무엇에 쓰이는지 모릅니다. 그래서 행동 관찰, 프로그램의 자기 선언, 사람이 적어둔 목록 세 가지로 메웁니다.
- 세 번째 방법이 시스템 곳곳에 있습니다. 게임 실행 파일 목록, 그래픽 드라이버의 게임별 설정, 게임 플랫폼의 프로그램별 설정, 모바일 OS의 배경 실행 예외 목록, 전원 프로파일 규칙이 전부 그렇습니다.
- 공통점은 어느 시점에 사람이 앉아서 무엇이 무엇인지를 손으로 열거했다는 것입니다.
- 목록이 작동시키는 메커니즘 자체는 잘 만들어져 있습니다. 배경 작업을 억누르고 전면 작업에 자원을 몰아주는 동작은 실제로 효과가 있습니다. 없는 것은 그 스위치를 언제 눌러야 하는지 아는 능력이고, 그 자리를 목록이 메우고 있습니다.
- 목록에는 세 가지 한계가 있습니다. 목록에 없는 소프트웨어는 다룰 수 없고, 목록 하나는 구분 하나만 표현하며, 무엇보다 프로그램들의 조합은 열거할 수 없습니다.
- 조합의 수는 천 종류 중 다섯 개만 골라도 8조 가지가 넘습니다. 노력의 문제가 아니라 규모의 문제입니다.
- 사람은 조합을 열거하지 않고도 프로그램 이름 목록에서 상황을 읽습니다. 각 프로그램이 무엇인지 알고 그 조합에서 추론하기 때문입니다. 이 능력의 정체는 세상에 대한 지식이고, 언어 모델은 그 지식을 가지고 있습니다.
- 이 시리즈가 다루는 연구는 그 지식을 OS에 연결하자는 제안입니다. 아직 주장이고, 여러 조각으로 나뉘어 있으며, 각 조각이 독립적으로 실패할 수 있습니다. 그걸 하나씩 확인하는 것이 이 연구입니다.

# 15장 · 용어 정리

이 책에 나온 English 용어를 전부 모았습니다. 나중에 다른 권을 읽다가 막히면 여기로 돌아오면 됩니다.

## 실행의 단위

| 용어 | 뜻 |
|---|---|
| **CPU** | 계산을 수행하는 부품 전체 |
| **core** | CPU 안에서 명령어를 실행하는 단위. 한 순간에 명령어 흐름 하나만 실행한다 |
| **program** | 디스크에 저장된 실행 파일. 아직 아무것도 하지 않는 정적인 것 |
| **process** | program을 실행시켜 만들어진 인스턴스. 자기만의 메모리 공간과 열어둔 파일을 가진다 |
| **thread** | process 안에서 실제로 명령어를 실행하는 흐름. 같은 process의 thread들은 메모리를 공유한다 |
| **task** | scheduler가 실행 여부를 결정하는 단위 하나. 보통 thread 하나에 해당한다. 이 시리즈가 쓰는 말 |
| **multicore** | core가 여러 개인 구조. 진짜 병렬 실행이 가능하지만 어느 core에 배치할지라는 두 번째 문제가 생긴다 |

## OS의 경계

| 용어 | 뜻 |
|---|---|
| **kernel** | OS의 핵심. 메모리, 파일 시스템, 장치, scheduling을 담당하며 특권을 가지고 실행된다 |
| **user space** | 특권 없이 실행되는 영역. 우리가 만드는 프로그램이 사는 곳 |
| **system call** | user space에서 kernel의 기능을 쓰기 위한 정해진 통로. 함수 호출처럼 생겼지만 특권 전환이 일어난다 |
| **register** | CPU 안의 아주 작고 빠른 저장 공간. 계산은 전부 여기서 일어난다 |
| **program counter** | 다음에 실행할 명령어의 주소를 담은 register. 프로그램의 현재 위치 |
| **stack pointer** | 호출된 함수들의 스택이 어디까지 쌓였는지 가리키는 register |

## 상태와 전이

| 용어 | 뜻 |
|---|---|
| **running** | 지금 core를 잡고 명령어를 실행 중인 상태 |
| **ready** | 실행할 준비가 됐지만 차례를 못 받아 기다리는 상태. scheduler의 유일한 관심 대상 |
| **blocked** | 무언가를 기다리느라 실행할 수 없는 상태. sleeping이라고도 한다 |
| **dispatch** | ready 상태의 task를 골라 실제로 실행시키는 동작 |
| **preemption** | 실행 중인 task에서 강제로 core를 회수하는 것. 시간이 다 됐거나 더 급한 것이 왔을 때 |
| **voluntary block** | task가 스스로 기다릴 것이 생겨서 core를 놓는 것. 강제가 아니다 |
| **wake** | blocked 상태의 task를 ready로 올리는 것. 실행이 시작된다는 뜻은 아니다 |
| **wakeup preemption** | 방금 깨어난 task가 더 급하다고 판단되어 실행 중인 task를 즉시 밀어내는 것 |
| **run queue** | ready 상태의 task들이 모여 있는 자료구조. 이 구조의 모양이 곧 scheduling 알고리즘이다 |
| **CPU burst** | task가 CPU를 연속으로 쓰는 한 덩어리 |

## 전환과 그 비용

| 용어 | 뜻 |
|---|---|
| **context switch** | 실행 중인 task의 상태를 저장하고 다른 task의 상태를 복원하는 동작 |
| **timesharing** | 여러 task를 아주 빠르게 번갈아 실행해서 동시 실행처럼 보이게 하는 방식 |
| **time slice** | 한 번에 주는 시간 조각. quantum이라고도 한다 |
| **cache** | CPU 안의 작고 빠른 저장소. 최근 쓴 데이터를 보관해서 메모리 접근을 줄인다 |
| **cache hit / miss** | 찾는 데이터가 cache에 있음 / 없어서 아래 단계까지 내려가야 함 |
| **working set** | 프로그램이 최근에 활발히 쓰고 있는 데이터의 집합 |
| **TLB** | 가상 주소를 실제 주소로 바꾸는 정보를 담아두는 전용 cache |
| **cache affinity** | task를 원래 있던 core에 다시 올리려는 성질. cache를 유지하기 위한 것 |
| **migration** | task를 다른 core로 옮기는 것. cache를 통째로 잃으므로 비싸다 |

## interrupt

| 용어 | 뜻 |
|---|---|
| **interrupt** | 하드웨어가 실행 중인 코드를 중간에 끊고 kernel에게 제어권을 넘기는 장치 |
| **interrupt handler** | interrupt가 걸렸을 때 실행되는 처리 함수 |
| **timer interrupt** | 일정 간격으로 울리는 interrupt. preemption의 물리적 기반이다 |
| **tick** | timer interrupt의 간격 |
| **tickless** | 항상 tick을 울리지 않고 필요할 때만 타이머를 맞추는 방식 |
| **cooperative** | task가 스스로 놓아줄 때까지 기다리는 scheduling 방식 |
| **preemptive** | kernel이 언제든 강제로 빼앗을 수 있는 방식. 현대 OS는 전부 이쪽 |

## performance metric

| 용어 | 뜻 |
|---|---|
| **response time** | 실행 준비가 된 순간부터 실제로 처음 실행되기까지의 시간. 사람이 체감하는 것 |
| **turnaround time** | 도착부터 완료까지의 총 경과 시간 |
| **waiting time** | ready 상태로 기다린 시간의 합. blocked로 기다린 시간은 빼고 센다 |
| **throughput** | 단위 시간당 완료한 작업의 수 |
| **CPU utilization** | 전체 시간 중 core가 일한 시간의 비율. 낭비되는 일도 포함되므로 단독 판단 metric이 아니다 |
| **makespan** | 작업 묶음 전체가 끝나는 시각 |
| **fairness** | 각 task가 받아야 할 share만큼 받았는가 |
| **starvation** | 특정 task가 계속 차례를 못 받는 상황. 평균으로는 안 보인다 |
| **deadline** | 작업이 끝나야 하는 시각 |
| **deadline miss rate** | deadline을 넘긴 작업의 비율. 얼마나 늦었는지가 아니라 늦었는지 여부를 센다 |
| **percentile** | 값들을 정렬했을 때 특정 지점의 값. P99는 아래에서 99퍼센트 지점 |
| **jitter** | periodic task의 실행 간격이 일정하지 않고 흔들리는 것 |

## 작업의 성격

| 용어 | 뜻 |
|---|---|
| **interactive** | 사람이 반응을 기다리는 작업. CPU를 거의 안 쓰지만 즉시 실행돼야 한다 |
| **batch** | 아무도 기다리지 않는 작업. CPU를 최대한 쓰고 총 걸린 시간만 중요하다 |
| **period** | periodic task이 반복되는 간격 |
| **job** | periodic task이 한 번 도는 것 |
| **worst-case execution time** | job 하나가 최악의 경우 걸리는 시간 |
| **frame** | 화면 한 장. 초당 60 frame이면 한 frame에 16.667밀리초가 주어진다 |
| **stutter** | frame을 제때 못 만들어 화면이 끊겨 보이는 현상 |
| **chain** | 여러 task가 순서대로 서로를 깨우며 하나의 결과를 만드는 구조 |
| **backlog** | 처리하지 못한 일이 쌓인 상태 |

## 알고리즘

| 용어 | 뜻 |
|---|---|
| **FIFO** | 먼저 온 순서대로 끝까지 실행. FCFS라고도 한다 |
| **convoy effect** | 긴 작업 뒤에 짧은 작업들이 줄줄이 밀리는 현상 |
| **SJF** | 남은 시간이 짧은 작업을 먼저. 평균 turnaround time을 최소화하지만 미래를 알아야 한다 |
| **STCF** | SJF에 preemption을 더한 것. 새 작업이 오면 다시 판단한다 |
| **Round Robin** | 정해진 slice만큼 실행하고 queue 맨 뒤로 보내기를 반복 |
| **priority** | task에 붙는 priority 값 |
| **multi-level queue** | priority마다 queue를 하나씩 두는 구조 |
| **priority inversion** | 낮은 priority task가 쥔 자원 때문에 높은 priority task가 밀리는 현상 |
| **priority inheritance** | 기다리게 만드는 쪽의 priority를 일시적으로 올려 inversion을 푸는 방법 |
| **nice** | Unix 계열에서 프로그램의 priority를 조정하는 값 |
| **MLFQ** | 여러 queue를 두고 행동을 관찰해 task를 그 사이에서 옮기는 알고리즘 |
| **boost** | 주기적으로 모든 task를 최상위 queue로 되돌리는 동작 |
| **allotment** | 한 queue에서 쓸 수 있는 누적 시간. 이걸 넘으면 아래로 내려간다 |
| **proportional share** | 각 task에 share를 주고 그 비율대로 CPU를 나누는 계열 |
| **lottery scheduling** | ticket을 나눠 주고 추첨으로 고르는 방식 |
| **stride scheduling** | lottery의 결정론적 버전. ticket 수에 반비례하는 값을 누적해 가장 뒤처진 것을 고른다 |
| **fair-share** | 누적 사용량을 추적해 가장 적게 쓴 task를 실행하는 계열 |
| **virtual runtime** | 실제 사용 시간을 weight로 나눈 값. fair-share의 핵심 |
| **CFS** | Linux가 오랫동안 쓴 fair-share 계열 scheduler |
| **EEVDF** | CFS를 대체한 것. 각 task에 가상 deadline을 두고 이른 순서로 고른다 |
| **EDF** | deadline이 가장 임박한 job을 실행. 조건이 맞으면 모든 deadline을 지킨다 |
| **rate monotonic** | period가 짧은 작업에 높은 priority를 고정으로 주는 방식 |
| **admission control** | 새 작업을 받을 때 전체 요구량이 넘치는지 검사해서 거부하는 장치 |
| **domino effect** | deadline을 한 번 놓치면 연쇄적으로 계속 놓치게 되는 현상 |

## 실제 시스템

| 용어 | 뜻 |
|---|---|
| **scheduling class** | task를 계층으로 나누는 구조. real-time, 일반, 유휴 등 |
| **QoS class** | macOS에서 작업이 자기 의도를 선언하는 이름표 |
| **Game Mode** | 게임 실행이 감지되면 배경 작업을 억누르는 기능. 게임 목록에 의존한다 |
| **voo-doo constant** | 이론으로 정할 수 없고 경험으로 정하는 config를 부르는 말 |

## 이 책을 다 읽었으면

여기까지 왔다면 다음을 할 수 있어야 합니다.

**개념 확인**

- process, thread, task의 차이를 설명할 수 있다.
- ready와 blocked의 차이가 왜 scheduler에게 결정적인지 말할 수 있다.
- context switch의 진짜 비용이 어디에 있는지 설명할 수 있다.
- response time과 turnaround time을 정확히 구분해서 정의할 수 있다.
- 왜 평균 대신 P99를 봐야 하는지 예를 들어 설명할 수 있다.

**계산 확인**

- task 세 개가 주어졌을 때 FIFO, Round Robin으로 각각 돌린 결과의 평균 response time과 turnaround time을 계산할 수 있다.
- time slice와 전환 비용이 주어졌을 때 낭비 비율을 계산할 수 있다.
- periodic task들의 utilization 합을 계산해서 EDF로 deadline을 지킬 수 있는지 판정할 수 있다.

**구조 확인**

- MLFQ의 규칙을 순서대로 나열하고, 각 규칙이 어떤 문제를 고치려고 생겼는지 말할 수 있다.
- MLFQ가 판단에 쓰는 정보를 전부 나열할 수 있고, 거기 없는 정보가 무엇인지 말할 수 있다.
- 실제 OS가 세 가지 정보원을 어떻게 조합해서 쓰는지 설명할 수 있다.

**문제 의식 확인**

- 왜 모든 상황에서 최고인 scheduler가 존재할 수 없는지 설명할 수 있다.
- 행동이 같은데 올바른 대우가 다른 상황의 예를 하나 들 수 있다.
- 사람이 손으로 적은 목록의 세 가지 한계를 말할 수 있고, 그중 조합의 문제가 왜 규모의 문제인지 설명할 수 있다.
