# Workload Scenario Catalog — Scenarios, Processes, and Source Attribution
> Status: normative · Created 2026-08-25 · Updated 2026-10-17

> Companion to source-vetting and Q7. Naming decision: **Linux-native process names** (the daemon reads Linux /proc; canonicalization and cgroup logic assume the Linux process model). Where a taxonomy source names a Windows application, the mapping is recorded in the Source column.
>
> **Schema decision — names only, no paths.** Each name is a kernel `comm` (9.10 D25); where each comes from — a campaign's trace, the game chain's source, or design — note 4 states. No grounding source attests to executable paths, and the benchmark guides list products, not process names. Paths would be authored values with no external source, violating the grounding rule, and would contaminate the recognition claim (name semantics vs. path heuristics). The workload schema therefore carries names only. Consequences: (a) the recognizer and the two name-table conditions — the shipped catalogue (`shipped_catalogue`) and the strongest name table (`strongest_name_table`) — receive the same name-only input, the shipped catalogue's lookup first mapping each bound name to its process's `argv[0]` basename, the key ananicy-cpp matches on (9.12 D105); (b) Family 5 spoofing is authored as *name collision* (a process simply bearing a trusted name), which is exactly the stated resolution limit; path-mismatch detection is future work; (c) a path a measurement records (the names workflow reads each process's command line) stays in its raw records, outside the dataset schema.
>
> Scenario ≠ segment: a segment in a workload file carries one mode/attribute label and may show several scenarios' programs (`c1-office`'s segment is tagged S1, S2 and S4). This catalog is the parts bin: it lists the scenarios and the names the dataset's files bind — the core set's, and the generated layer's, which composes the core set's C1 task sets — each grounded for its existence only; which of them share a segment is the experiment's composition, labelled design (9.10 D2). A segment's `scenario` tags name every catalog scenario whose program is alive in the segment, the program's scenario as the table below gives it; a task with no `depart` counts in the segment its arrival falls in (9.10 D168). The core set is held to the rule by `dataset/tools/tests/test_coreset.py`, and the generator applies it (`dataset/tools/gen/compose.py`): a generated segment carries the tags of the C1 segment its task set comes from (9.19 spec, decision 3) and adds those of another placement's programs alive in it, so a transition grid focus-form file's second segment names A's programs that stay beside B's. A distractor cell's second segment is A's label with the arrival's tags added (9.20 spec, decision 1): where A holds a batch job — backup, indexing, ML training or transcode, 68 cells — that job's tag stands in the second segment as well, which the rule, counting a batch job in the segment of its arrival only, does not give. In the Source column a backticked word is one of three things: a `docs/references.md` entry's id (e.g. `pcmark10`, `lavd-ossna24`); a measurement campaign, `meas-ci:<workflow>:<campaign>` (`:<campaign>` after one of the same workflow); or a name as the system spells it — a process, a package, a command, the kernel's `comm` field (e.g. `tracker-miner-fs-3`, the `7zip` package).

## Notes

1. **Coverage check against the definitions.** PCMark 10's groups define S1 (Productivity's Writing), S2 (Web Browsing), S3 (Video Conferencing), S6 (Photo Editing), S7 (Video Editing) and S13 (Video playback); SYSmark 30's scenarios S1 (Office Applications, Outlook open beside it for S4), S7 (Advanced Content Creation) and S16 (General Productivity's archive workload); SYSmark 25's Productivity description S11; CpsMark+'s scenarios S1, S2, S4, S6 and S8. The rows of S5, S9, S10, S12, S14, S15, S17 and S18 cite no benchmark definition: their existence rests on the program's own package, defaults or code, or on the trace the row cites. The Source column grounds existence only, never co-occurrence (9.10 D2), and cites external sources only — our own Family/driver-table definitions never appear in it, since they are what this catalog exists to ground (citing them would be circular).
2. **Internal cross-references live here, not in the Source column.** Which experiments consume which scenarios is design intent, not grounding: the load-bearing pair of F2 (the intent-pair family), pair P1, is S12 (ML training) against S14 (indexing) — two real, measured jobs beside S11's editor, the MNIST training run against Tracker's first index, differing in name, behaviour, declared class and label, with opposite correct policies; pair P2 is S10 (a game install the user starts during play) against S17 (the unattended upgrade), each beside the game (S9), the two files differing only in segment 1's job and label.
3. **Family 5 spoofing is authored by name collision** — a scripted process bearing a trusted name (e.g. chrome) with non-browser behavior (`c6-spoof`), or a program under another program's real name (`c6-alias`). This is precisely the stated resolution limit of name-based recognition. Path-mismatch spoofing is out of scope (no path field in the schema); path-based verification is noted as future work.
4. **Names are kernel `comm`s (9.10 D25).** A task's name is its process's kernel `comm` — the exec'd basename cut to 15 bytes, a script its own name, a `prctl` rename its new name — for a program a measurement campaign ran, the `comm` the campaign traced (e.g. `tracker-miner-f`, `thunderbird-bin`, `unattended-upgr`, `x86_64-linux-gn`, `python`); otherwise derived by the rule and confirmed where a campaign or the names workflow (`meas-ci:names:2`) shows it. The 44 names of the compiled core files are of four kinds: the `comm`s campaigns traced (most of them); the game chain's thread names from `lavd-ossna24` slide 16, with `wineserver` named by the compiler; the invented tier-4 and tier-5 names (design; C5's tier-4 strings cut to 15 bytes, e.g. `audio-stream-he`); and the deliberate spoofs (`c6-spoof`'s `chrome`, `c6-alias`'s `baloo_file` and `tracker-miner-f`; design). The generated layer binds the C1 files' names and, in the familiarity ladder, substitutes for them: tier 3's `melt-7` and `duplicity`, `comm`s campaigns traced (S7, S15), and a tier-4 table and tier-5 keyed draws, design (`dataset/grids.yaml`). The canonical lint fails a name over 15 bytes (`linux-sched-h`). The Phase 2 and Phase 7 name tables are history. No file binds `firefox`: Chrome is the browser wherever a file shows one (`docs/workload/building-plan.md` §3).
