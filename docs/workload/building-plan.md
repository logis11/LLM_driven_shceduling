# Workload Dataset Building Plan
> Status: normative · Created 2026-08-25 · Updated 2026-10-31

> Consolidates the dataset methodology decided across Q7 (segments, canonicalization, caches), source-vetting (per-source verdicts and extracted parameters), the scenario catalog (`docs/workload/scenario-catalog.md`: S1–S18, names-only schema, the existence-only source column), the archetype plan (`docs/workload/archetype-plan.md`, the archetype library), docs/references.md + dataset/sources.yaml (citation index and machine registry), and docs/simulator/interpretation-contract.md (simulator-facing semantics). Those documents are normative for their own content; this plan defines how their pieces compose into the dataset and in what order it gets built. Decision record: `_dev/archive/2026-08-26-workload-generation-grill.md`.

## 0. Design tension and the two-set resolution

The dataset must satisfy two demands that pull in opposite directions:

- **Control** — the experiments require it. The load-bearing F2 pair must differ in exactly one segment; the familiarity axis must be balanced; every driver-table cell needs coverage; the condition ladder needs files where each recognizer predictably wins or loses.
- **Realism** — the grounding requires it. Segment durations must follow the measured literature; switching structure must match observed shapes; the query-economics numbers must come from something resembling a real session.

One dataset cannot defend both: a fully controlled suite invites "cherry-picked scenarios," a fully sampled suite invites "no hypothesis is actually tested." The dataset as built answers the control side with two sets of distinct roles, and leaves the realism side to a third set in the backlog:

| | Core set | Generated layer | Naturalistic set (backlog) |
|---|---|---|---|
| construction | timelines authored by hand: 23 novel designs, 28 derived by recipe | timelines composed from the sixteen C1 task sets by `dataset/tools/generate.py` under `dataset/grids.yaml`; build products, not committed | timelines sampled from a generation model |
| organizing principle | one file per claim (coverage grid) | each rate claim's factor enumerated in full | distributions from Role C literature (segment structure and switching statistics) |
| carries | the controlled claims: the calibration files (C1), the intent pairs (C2), the attribute pairs (C7), the RQ0 gate's judging files, the resolution limits (C6, the files of F5, the adversarial-and-boundary family); the authored files of C3–C5 as existence cases | the rate claims: recognition at a transition, the stale configuration's cost, flap stress, distractor robustness, recognition by familiarity tier (§3a) | ecological validity; query economics (novel canonical sets/hour, cache hit rate); distractor rates "in the wild" |
| segment durations | as each file's claim needs: 60 s for the interactive single-situation files, the batch files as long as their whole jobs (§3 C1), the arcs and limit files as authored | 60 s segments; the return grid's middle segment 60, 10 or 2 s; the flap-stress set's 2–30 s intervals | sampled from grounded distributions |
| realism claim | program existence, situations, states, counts, each at its own decision; which programs share a segment is design | none: every file is design | its purpose |
| size | 51 files, 67 segments (C1–C7) | 1,562 files in five sets: transition grid 480, return grid 720, flap-stress 24, distractor grid 272, familiarity ladder 66 | — |

The naturalistic set's prerequisite is a source for Linux-desktop co-occurrence and transition frequency, which 9.10's search did not find (§4).

Every set compiles in one mode, `single` (lane-scaled, §5a). The compiled sets under `dataset/build/` — `coreset-single`, which also holds the RQ0 gate spec's 78 sensitivity variants (`dataset/variants.yaml`), and the five generated sets' `<set>-single` — are **the evaluated datasets**: every experiment runs on them. Each set has its own manifest: `dataset/build.manifest.json` (core), `dataset/build.variants.manifest.json`, `dataset/build.<set>.manifest.json` (generated).

Paper framing: "we validate the controlled claims on an authored suite and the rate claims on generated grids that enumerate each factor in full and claim no realism, and release both in lane-scaled form; the frequency claims wait on a naturalistic suite."

## 1. Three-layer architecture

Everything composes through three layers, named for what they hold. Lower layers never reference higher ones.

```
ARCHETYPE LIBRARY   how one kind of program behaves          (dataset/archetypes.yaml)
SCENARIO CATALOG    which scenarios and process names exist  (docs/workload/scenario-catalog.md, S1–S18)
TIMELINES           how tasks arrange in time               (dataset/timelines/coreset/*.timeline.yaml; the generated sets, §3a)
```

The layers are named, not numbered: "Layer 1" and "Layer 2" in this project's docs are the evaluation layers — recognition accuracy and consumer performance — never these three.

The scenario catalog lists which scenarios and process names exist, each grounded for its existence; it does not say which processes co-occur. Which programs share a segment of a core-set file is the experiment's composition, labelled design (9.10 D2, D33).

**Two workload formats.** Timelines are the human-facing authoring format — meta, segments with their labels, tasks as (name, archetype) bindings on a time axis, the keystroke-window (`input`) and focus tracks, and optional operations — with variant recipes (`*.variant.yaml`) that derive a file from a base through a closed op set (`rename`, `patch-segment`, `patch-task`, `add-task`, `set-segments`, `set-input`, `set-focus`, `set-operations`, `patch-meta`; `dataset/tools/wlc/deriver.py`), the derived files committed. They are consumed only by the build tools. `make dataset` derives the recipes' files and compiles the timelines into the **canonical format** — the only workload form the simulator and harness read: `archetypes.yaml` + timeline (its seed in its meta) → workload. Canonical semantics (event ops, lifetime classes, timing principle) are fixed by docs/simulator/interpretation-contract.md. Same timeline, same library and same compiler ⇒ byte-identical canonical file (`test_byte_determinism`); the manifests pin every input by SHA-256 and `make check` holds the build to them. That is what the controlled-experiment invariants diff — e.g. `c2-p1a` and `c2-p1b` hold the editor's events and segment 0 identical in the compiled files — and CI tests on the compiled artifacts hold part of it: `test_p1_pair_differs_in_segment_one_only` P1's shared arrival, segment 0 and segment spans (§3 C2). The generated layer's generator (`dataset/tools/generate.py`, `make generated`) emits timelines too, under `dataset/generated/`, so the core set and the generated layer share one compile path, one linter, and one provenance mechanism.

The binding rule: **behaviour parameters live in the archetype library.** Timelines reference scenarios and archetypes by id and bind only the values an entry names as its `binding_params` (counts, caps, total work, a program choice, a lane share, member names) and a task's `count`; each bound value carries an entry in the task's `source:` map — a registry tag, or one of the labels `design`, `convention`, `arithmetic` for a value no source states — checked by the linter against `dataset/sources.yaml` (9.10 D32; 9.18 D2). Consequences: (a) a literature or measurement update touches one library entry, not dozens of files; (b) the provenance linter (§6) audits the library's parameters and the timelines' bound values; (c) the familiarity ladder (C5) is definable as "same archetype, different name," guaranteeing that recognition differences come from the name alone.

### 2.2 Rules

- **Reference by id:** the scenario catalog and the timelines name archetypes by id; a timeline's bound values each carry a `source:` entry, checked by the linter (§1, §6).
- **Name/behavior separation:** an archetype never fixes a process name. The (name, archetype) binding happens in the timeline — this is what makes C5's name-swap and C6's name-collision files expressible without touching behavior.
- **Multiplicity is a binding-time parameter:** the user's build binds `build-orchestrator` with `spawn_count` 2,908 object jobs, the hidden tabs bind `renderer-hidden` with `count: 4` — not new archetypes.
- **Archetypes and scenarios are not one-to-one** (29 entries, 18 scenarios): one scenario's programs may be several entries (S9: the chain and the client; S18: the four session entries), and one entry may serve two scenarios (`cpu-batch`'s programs, S7 and S12).

## 3. The timelines: the core set (authored; 51 files)

Organizing frame: a coverage grid of driver-table cell (mode × `background_wanted`) × familiarity tier. Every file exists to make a specific measurement possible; if a file's absence breaks no RQ, it doesn't belong. The grid tool counts the driver-table cell in full — mode × `background_wanted` — against the tier columns, and CI fails when any of the 32 cells has no segment (Phase 7; before it the tool counted mode × tier only, which is how the attribute's `false` side went unfilled).

**Browser:** `chrome` in every file that shows a browser; no file binds `firefox`. A file showing the browser (a `web-browser` task) depicts one window of five tabs — five the median per-client peak of concurrent tabs and one window the median peak of windows in Firefox's Linux telemetry (`glam`; 9.10 D15, D16) — the page in use being `web-browser`'s own renderer and the other four tabs four `renderer-hidden` tasks, one page renderer per tab as observed in Chrome on the runner (`meas-ci:desktop:2026-10-04`). The count is a floor: the pages hold no subframes, so a real page's cross-site iframes take renderers it leaves out. The call files, `c1-meeting` and `c7-meeting`, bind one `chrome` task on `video-call` and no renderers (9.10 D14).

### C1 — Single-situation calibration (16 files, one per mode)
One file per mode of the menu, one segment each, the mode's `true` cell: office {`soffice.bin`, `chrome` ×5 — `web-browser` and four `renderer-hidden` — `thunderbird-bin`}; gaming {`Troy.exe`'s chain on `game-task-chain` with its member names and the compiler's `wineserver`, `steam` on `game-client`}; compile {`code`, `make` on `build-orchestrator`: the user's kernel build bound whole — 2,908 six-process object jobs, `child_name` `cc1`, cap 8}; media {`mpv` ×2 — `video-player`, `audio-player`}; browsing {`chrome` ×5}; idle {`gnome-shell`, `pipewire`, `systemd`, `dbus-daemon` — the four session processes, which in the core set only the idle files carry, every other core file omitting them (9.10 D28)}; mail {`thunderbird-bin`}; dev {`code`}; photo {`gimp`}; video-edit {`kdenlive`}; ml-train {`code`, `python` — PyTorch's basic MNIST example on `cpu-batch`'s `python3` program}; render {`kdenlive`, `kdenlive_render` — Kdenlive's own export}; transcode {`kdenlive`, `HandBrakeCLI` on `video-transcoder`}; backup {`kdenlive`, `deja-dup` on `incremental-backup`, scheduled and wanted}; indexing {`code`, `tracker-miner-f` on `file-indexer`, user-initiated — the same job as the unasked index of `c2-p1b` and `c7-indexing`, so the label differs by intent alone and the file is a pre-committed miss}; meeting {`chrome` on `video-call`, one task — a call in the browser}. Each task set is design, the composition the file's claim needs, with no realism claim on which programs share a segment (9.10 D2); a file header's "lifted from" names its lineage, not an observed set.
The interactive and periodic files are 60 s. Each batch job is bound whole at its measured size (9.10 D17), and a batch base's segment is the smallest whole second by which the job ends under every policy (9.10 D78): `c1-compile` 1,594 s, `c1-ml-train` 1,612 s, `c1-transcode` 4,762 s, `c1-backup` 277 s; `c1-render` and `c1-indexing` keep 60 s, their jobs ending inside it. So each batch base carries a turnaround term on a finished job.
Role: recognition floor; executor mapping sanity; and the honest baseline — **this is where the strongest name table (`strongest_name_table`) is expected to score perfectly**, reported as part of the condition-ladder narrative; not the shipped catalogue (`shipped_catalogue`, ananicy-cpp's rules as CachyOS ships them), which on ananicy-cpp's key keys every bound name of a file in only 7 of the 50 core files of the 2026-10-09 build it was counted on (9.12 D109, the related-work slice's catalogue count). In the RQ0 gate four batch bases judge — `c1-compile`, `c1-ml-train`, `c1-render`, `c1-transcode` — two-sided with their C7 counterparts (a wanted LOTTERY share is what a random row removes); `c1-indexing` and `c1-backup` report with the other files holding idle-class work, and the ten interactive and periodic bases are reporting-only (nothing runs behind the foreground) (the RQ0 gate spec, `harness/experiments/rq0-gate.yaml`, statements `judging-set` and `idle-class-files`).
Every C1 timeline declares `demand: calibration` (§5a). The class says the file is not designed to hold contention, not that its demand is low: a calibration file's utilization is whatever its bindings produce. No C1 file exceeds one lane: the four long batch bases read 0.9878–0.9985, `c1-gaming` 0.9153 through its `lane_share` binding (0.9), `c1-indexing` 0.7477 and `c1-render` 0.7054, the other interactive and periodic files 0.0004–0.4769. The compiled values are recorded per file and per segment in `dataset/build.manifest.json` under `demand`.

### C2 — Intent pairs, one-segment diffs (3 pairs and a bounding variant = 7 files)
In each pair the second file's segment-1 job is a measured job of its own — `file-indexer`, `package-upgrade`, `incremental-backup` — differing from the first's in name and behaviour, and in P1 and P3 in declared class too (the indexer and the backup `idle`, the training run and the export `normal`; P2's two jobs are both `normal`); what recognition adds over a behavioural and declared-class baseline is measured (9.12 D14, D15, D88). The shared tasks and segment 0 stay byte-identical:
- **P1 (load-bearing):** beside the editor `code`, `c2-p1a`'s training run — `python`, PyTorch's basic MNIST example on `cpu-batch`'s `python3` program, bound whole at 1,389.885 s of CPU and still running at the file's end, so no turnaround term reads it — against `c2-p1b`'s first index — `tracker-miner-f` on `file-indexer`, 39.435 s, `initiated: session`. Segment 1 is 39.435 s in both files (60–99.435 s); the pair differs in it by name, behaviour and label (ml-train, `true`, against indexing, `false`), with opposite correct policies (S12 vs S14). It carries the recognition claim — telling the wanted training run from the unwanted indexer, which a name table cannot — and its scheduling headroom on `c2-p1a`'s side: RQ0 judges `c2-p1a` and reports `c2-p1b`, the indexer's declared `idle` class placing it below every row, so that side's headroom is zero (9.14 decision 2; 9.23 D9).
- **P2:** {`Troy.exe`'s chain and `steam`, + a game install the user starts during play — `steam` on `game-download`, bound whole at the fresh install's CPU total 727.170 s, still running at the file's end} vs {the same game + the unattended upgrade — `unattended-upgr` on `package-upgrade`, 26.385 s}. Segment 1 is 26.385 s in both files (60–86.385 s); `background_wanted` flips (S10 vs S17). The measured differences: a run between blocks of 163 µs against 1.8 ms, one process of 83–84 threads against 916 processes, about 700 s of CPU against 26 s, nice 10 on three quarters of the download's CPU (9.12 D15) — the one the dataset does not carry, the download declaring `normal` at full standing as measured. `c2-p2a-idle` is `c2-p2a` with the download on `game-download-idle`, the same tables in the idle class, byte-identical but for that task's class; it sits outside the judging set and is read by the RQ0 gate spec's bounding check alone (9.11 D21; 9.13).
- **P3:** {`kdenlive` + `kdenlive_render`, Kdenlive's own export — `cpu-batch`'s `kdenlive_render` program, 16.545 s of CPU from 60 s, ending by about 99.5 s} vs {`kdenlive` + `deja-dup`, Déjà Dup's scheduled weekly incremental on `incremental-backup`, 165.668 s} — user-initiated export against scheduled backup (S7 vs S15). The mode flips (render → backup) and `initiated` (user → scheduled); both sides are wanted. Segment 1 runs 60–326 s in both files, the length 9.10 D123 set on a shared lane; under the idle class (9.13) the backup does not end inside it and is scored by progress (9.14). RQ0 judges `c2-p3a` and reports `c2-p3b`.
Each pair is a one-segment diff: its files share segment 0, the file's length and every event of the shared tasks, arrivals and wakes, in the compiled files. CI holds part of it: `test_p1_pair_differs_in_segment_one_only` P1's shared arrival, segment 0 and segment spans, `test_pair_one_task_diff` P2's and P3's shared arrivals. The rate claim on intent runs on the sixteen C1–C7 pairs; no C2 pairs are generated (the 2026-10-10 dataset audit, direction of 2026-10-11).

### C3 — Mode-transition arcs (3 files; existence cases)
Multi-segment sequences whose boundaries are real label changes (query points that must flip). Each arc's order is design; a benchmark that defines a transition is cited for that transition's existence only (9.10 D29):
- **workday arc** (`c3-workday`, 4 segments): `chrome` browsing → + `soffice.bin` writing → + `make`'s kernel build → `thunderbird-bin` mail send. CpsMark+'s CA cooperative workflow (`cpsmark-tbench23`) defines the browsing → office → mail transitions; the compile segment has no CpsMark+ counterpart.
- **evening arc** (`c3-evening`, 3 segments): browsing → gaming, the chat client `element-desktop` (on `chat-client`) beside the game → media playback (`mpv` ×2). No source defines it.
- **creation arc** (`c3-creation`, 3 segments): `gimp` → `kdenlive` → `HandBrakeCLI` transcode. SYSmark 30 Advanced Content Creation defines photo editing beside a background encode (`sysmark30`, its whitepaper v1.2, §2.2); CpsMark+ holds photo → video → transcode only as a subsequence, no handoff stated.
Role (restated 2026-10-11): existence cases — the dataset holds transitions of these shapes, in these orders. The rate claims on transition recognition — latency and correctness at a boundary, with direction, over every ordered pair of modes — and on the cost of a stale configuration are the generated layer's (§3a below): the three arcs hold seven boundaries in all (`c3-workday` three, `c3-evening` and `c3-creation` two each), each ordered pair at most once, and carry no statistical claim.

### C4 — Distractor injection (3 files)
Clones of C1 files with a label-invariant process injected mid-segment: the chat client's launch during gaming; a 7z burst during office (6 s of CPU, design, 9.10 D161); chrome open during compile. Paired with their clean originals, giving Q7's within-segment distractor-robustness as a **paired measurement**. Role since 2026-10-12: existence cases. The distractor's Layer 1 axis is the name's relation to the vocabulary — another mode's program, a program outside every mode, an unknown name (C5's axis) — and the rate claim runs on the generated distractor grid (§3a): the user stays in A while another mode's whole task set or one measured program outside the modes arrives at 60 s and stays. `c4-compile` is the authored precedent of the cell compile ← browsing.

### C5 — Familiarity ladder (2 files)
Same structure and archetypes; only the name tier changes:
1. transparent (`chrome`, `gimp`)
2. semi-opaque (`soffice.bin`, `HandBrakeCLI`)
3. opaque (`tracker-miner-f`, `cc1`, `dkms`)
4. nonexistent-compositional (e.g. `audio-stream-he` — inferable from word semantics)
5. nonexistent-opaque (e.g. `qzvd` — neither recall nor inference possible)
Tiers 4–5 separate **corpus-recall from name-composition inference** — familiarity is defined corpus-relative, not human-relative. Neither name-table condition — the shipped catalogue (`shipped_catalogue`) nor the strongest name table (`strongest_name_table`) — carries a rule for the invented names of tiers 4–5; the strongest name table's structural zero there is the headline contrast. Because all tiers bind identical archetypes, any recognition difference is attributable to the name alone.

Tier 3 is the program's **own** real name that carries no meaning; another program's real name on it (an indexer's on a player) is a name collision and lives in C6 (`c6-alias`, until 2026-10-12 this group's tier-3 file). The two authored files, `c1-media` at tiers 4 (`c5-t4`) and 5 (`c5-t5`), are existence cases; the ladder over the sixteen modes at tiers 4 and 5, with render's and backup's jobs at tier 3 (`melt-7`, `duplicity`) — with which names carry the substitute (the focus holder's, the others', all) as an axis — is generated (§3a). Every substituted name fits the kernel's 15-character `comm` field (`linux-sched-h`).

### C6 — Resolution-limit files (4 files)
Three carry pre-committed misses, annotated `pre_committed_miss`: `c6-alias` whole, `c6-fold` from the call's arrival at 30 s, `c6-spoof` from the spoof's arrival at 20 s. `c6-dual` is not one: its one segment is `ambiguous`, outside grading.
- **name-collision spoof** (`c6-spoof`): a process *named* chrome bound to `cpu-batch` — 30 s of work, program `spoof`, both design by construction — arriving at 20 s in the browsing file: the stated limit of name-based recognition (F5). The file is split at the spoof's arrival: 0–20 s browsing, `background_wanted: true`; 20–60 s browsing, `background_wanted: false`, `spoof: true`, a pre-committed miss — the oracle reads browsing/`false` from 20 s (9.23 D2). Authored by name collision only; path-mismatch spoofing is out of schema (names-only decision) and noted as future work.
- **name-collision alias** (`c6-alias`, 2026-10-12): `c1-media`'s two players under two real indexers' names (`baloo_file`, `tracker-miner-f`) — another program's real name on the whole foreground, which the spoof above does not show; no recognizer reaches `media` from these names.
- **fold-internal change** (`c6-fold`): browser tabs become a video call — a `chrome` task on `video-call` arrives at 30 s in the running browser, its launch phase replayed. The snapshot goes from `chrome` ×5 to `chrome` ×6, a count-only change, so a query fires at 30 s (`docs/data-contracts.md` §5, telemetry rule 1); nothing in the names says call (a sixth `chrome` is also what a new tab shows), so the meeting segment (30–60 s) is a pre-committed miss, pre-registered as a scope boundary; the browsing segment keeps its graded 0 s point (9.23 D1).
- **dual-active ambiguity** (`c6-dual`): equally-active dual foregrounds — gaming while actively awaiting a compile: the game chain at `lane_share` 0.6, `code`, and the user's kernel build from 10 s, the focus alternating between the editor and the game over 12,072 s — the point where even the oracle cannot assign a label (§9 of the previous revision, ratified). The co-occurrence is design: no observation shows a kernel build beside a game as usage (9.10 D31). Shipped as a file so the limit is concrete, not rhetorical.

### C7 — Attribute counterparts (16 files, one per mode)
One counterpart per mode, `c7-<mode>` derived from `c1-<mode>`: the base is the mode's `true` cell, the counterpart its `false` cell. Each counterpart is its base's first C seconds, C the CPU total of the job it holds, bound whole from 0 s: one segment labelled `background_wanted: false`, every base task departing at C, the input window (where the base has one) 2 s to C − 2 s and each operation at its fraction of the window (9.10 D41, D44, D78), so on one lane the job is alive at every instant of the segment under every policy.
- **The ten interactive modes** inject the stock Ubuntu 24.04 unattended upgrade's install stage — `package-upgrade` shown as `unattended-upgr`, the same name in every file so the ten `false` cells differ only in mode, tier 1 so no pair changes familiarity tier — bound whole at its measured CPU total C = 26.385 s (`meas-ci:background:2026-10-01`; 9.10 D3, D43, D45).
- **compile:** an observed DKMS autoinstall in place of the user's build — NVIDIA's 595 open module (`nvidia-dkms-595-open` 595.91.07) rebuilt for 2026-09-23's security kernel 7.0.0-34 by the stock unattended upgrade — task `dkms` on `module-build-orchestrator` (spawning `module-compiler-child`, `child_name` `cc1`, `parallelism_cap` 8), `initiated: scheduled`, C = 225.458 s; the compile pair differs in behaviour as well as name (9.10 D4, D56, D59).
- **indexing:** the base's own job, Tracker's first index (`tracker-miner-f` on `file-indexer`), at a first login (`initiated: session`), C = 39.435 s.
- **ml-train, render, transcode, backup:** the base's own job and name, the label flipped alone (`initiated: scheduled`) — C = 1,389.885 s (`c7-ml-train`), 16.545 s (`c7-render`), 2,970.871 s (`c7-transcode`), 165.668 s (`c7-backup`) — each shipped as a pre-committed miss, annotated `pre_committed_miss`. The batch job is itself the background work the attribute judges (recognition-vocabulary §1), and no distro or vendor was found starting an ml-train, render or transcode job unasked under a distinct name (Jellyfin's transcoder runs as plain `ffmpeg`). An unasked backup under its own name exists — dpkg's daily `dpkg-db-backup` — but it finished in the second it started on the one desktop observed and cannot hold a backup segment (9.10 D9).
A C7 pair is not a one-diff pair: the counterpart differs from its base in the unwanted job (interactive), the module build (compile) or the label alone (the other batch modes), and also in the file's length, the input window and the operation times. Its keystrokes are its base's over the same instants, less those inside its own operations — a subset, not equality (9.18 D1: the window carries `slice_of`; `test_c7_input_wakes_are_a_subset_of_the_bases_in_the_first_c_seconds`). `c7-mail`'s slice holds no keystroke — `c1-mail`'s fall after the counterpart's 26.385 s — so the file is reporting-only and the mail mode's attribute is unmeasured (9.14 D6). Scoring: a counterpart repeats its base's terms minus the batch term — unwanted work carries no term (`c7-mail` excepted: its term reads the mailer's own wakes). Role: the attribute's negative side for recognition accuracy, and the paired base-versus-counterpart headroom under each row of the driver table; where the attribute has no scheduling consequence (the purely periodic modes under EDF) the pair review says so (`docs/daemon/prior-table-pair-review.md`, finding 5).

### Counts and reuse
C1×16 + C2×7 + C3×3 + C4×3 + C5×2 + C6×4 + C7×16 = 51 files, 67 segments (C1 16, C2 14, C3 10, C4 3, C5 2, C6 6, C7 16; `dataset/coverage-grid.json`). The groups are orthogonal transforms: C4 = C1 + label-invariant injection; C5 = C1 with name substitution; C6's derived files = C1 with a spoof or a call added, or its players renamed; C7 = C1's first C seconds with one unwanted job, the module build in place of the user's build, or the label flipped alone; C2 pairs share all but one segment. Genuinely novel timeline designs number 23 (the sixteen C1 files, `c2-p1a`, `c2-p2a`, `c2-p3a`, the three arcs, `c6-dual`); the other 28 are scripted derivations from five recipe files (`c2-pairs`, `c4`, `c5`, `c6`, `c7.variant.yaml`) — build the derivation scripts, not the files.

### Balance check
Per Q7, §5.5 balance counts **segments, not files**. The segments lie on the driver-table cell (mode × `background_wanted`) × familiarity grid, `dataset/coverage-grid.json`, regenerated from the timelines and checked in CI: every one of the 32 cells has at least one segment (`derive.py --require-coverage`), pre-committed-miss segments are marked so the reader sees which cells are instanced but recognition-limited, and `ambiguous` is reported outside the 32. The same file carries the generated sets' tables (`generated`), counted from the labels each generated manifest records; no empty-cell rule applies to them — every C1 task set is the `true` side of its mode, so the generated layer fills the sixteen `true` cells alone. The grid ships in the paper as the dataset-design table.

### Label rule for mixtures
Scenario mixing is the norm; most mixtures resolve to one driver-table cell because the attributes exist to describe them ("game + Steam download" = gaming, wanted=true). Core authors only author mixtures with a defensible label (the Q7 author-specifies principle); genuinely ambiguous dual-active states are the C6 boundary above, never accidental.

## 3a. Generated layer — the grids over the C1 task sets (added 2026-10-11)

A generated layer stands beside the core set (Phase 9 spec decision 9; the audit record `_dev/docs/audit/jioh/2026-10-10-dataset-audit-before-9.15.md`, "Direction taken on the open item"). Each group whose claim is a rate has a generated set that enumerates the factor in full from the sixteen C1 task sets; every file is **design** — it claims nothing about how often or in what order desktops see the modes — and the authored files of the group remain as existence cases. The definition is `dataset/grids.yaml`, the generator `dataset/tools/generate.py`; the timelines are build products, not committed, and each set has its own manifest, `dataset/build.<set>.manifest.json`, pinning the definition, the generator, the C1 timelines and the compile's inputs by content (9.19 spec, decisions 4 and 5).

Composition rules (9.19 spec, decisions 1–3): a segment is 60 s (`segment_length`), the C1 interactive files' length, except the return grid's middle segment (60, 10 or 2 s) and the flap-stress set's alternations (2–30 s); a C1 task set lands in a segment by the dataset's one re-timing rule, 9.10 D44 — its arrive offsets kept, the input window with the C1's 2 s margins, each operation at its fraction of the window — so a segment of 4 s or less shows its task set with no keystroke; a batch job's `total_work` or `spawn_count` is the C1 value scaled to the span the job must be alive in, labelled `design` in the file's `source` map. Every seed and every split is a keyed SHA-256 draw from the cell's or the pair's id. An arrival is a program start: a task arriving mid-file replays one measured launch repeat from its arrival, its steady stream beginning when the launch phase ends (9.10 D136; 9.23 D4). The launch phases run 31–54 s for the office writer, the chat client and the two players, 210–1,051 s for the call, the video editor, the mail client, the browser, the game client and the hidden renderer; tasks with a launch phase arrive mid-file in 300 of the transition grid's 480 files, 630 of the return grid's 720, all 24 flap-stress files, 166 of the distractor grid's 272 and none of the familiarity ladder's. So the segments where tasks arrive depict applications launching, and the C1 files remain the steady-state material. Recognition (RQ1) is untouched — the telemetry is a pure function of the pinned events — while the replay reaches Layer 2: B's and the returning A's terms, the per-switch excess, `flip_cost`.

The C3 sets:
- **Transition grid** (`transition-grid`, 480 files): the 240 ordered mode pairs (A, B) in two forms. *Departs* — at 60 s A's tasks depart, B's arrive, the focus moves to B. *Focus* — B's tasks arrive and the focus moves to B; A's tasks stay to the end of the file, A typing no more once the focus has moved. The focus form and the C4 cross-mode distractor cell ("B arrives, the focus stays on A", 9.20) — the twins `tr-<A>-to-<B>-focus` and `dx-<A>-with-<B>`, 240 pairs — share the task set and the name sequence and differ in the focus, the input, the labels and the random draws (each cell's seed its own): a recognition pair (9.23 D6). Role: recognition at a transition, with direction (RQ1).
- **Return grid** (`return-grid`, 720 files): A → B → A over the same pairs, A departing at each boundary, the middle segment 60 s, 10 s or 2 s — RQ4's phase-shift family. Split by pair into a tuning half and a measurement half (120 pairs each, a pair's three variants on one side) for the hold-time plan (`_dev/docs/plan/jioh/hold-time-and-hysteresis.md`, step 4). Role: the stale configuration's cost against the speed of the change.
- **Flap-stress set** (`flap-stress`, 24 files): three ordered pairs drawn by keyed hash; a 60 s lead-in on A, then eight segments of one interval each, B and A in turn, at 2 s, 5 s, 10 s and 30 s — 5, 10 and 30 s the intervals of the daemon-level switches comparable to ours (GameMode's 5 s reaper check interval, tuned's 10 s dynamic-tuning update interval, dynamic tuning off by default, systemd-oomd's 30 s pressure sustain duration; `feral-gamemode`, `tuned`, `systemd-oomd`), 2 s a point below them, design. Each file under two seeds, tuning and measurement. Role: the hold-time plan's tuning and test material.

In the return grid and the flap-stress set every task set departs at its boundary, so each boundary closes one mode's programs and launches the other's: every boundary is a set change under both telemetry shapes (names only, and with the focus), and the launch load, the same under every condition, sets the size of a stale configuration's cost, not its direction (9.23 D5).

The C4 and C5 sets (9.20, 2026-10-12):
- **Distractor grid** (`distractor-grid`, 272 files): the user keeps working in A — A's focus and input run to the file's end, both 60 s segments labelled A, the second one's scenario list naming the programs alive in it by 9.10 D168's rule (A's staying ones and the arrival's, A's batch job, with no `depart`, counting in the first segment only) — while at 60 s another process set arrives and stays. *Cross-mode* (240): B's whole task set over the ordered pairs, the transition grid's focus form with the focus kept on A — the same open programs. *Out-of-vocabulary* (32): one measured program of the library that belongs to no mode and leaves the label unchanged — `element-desktop` to the file's end, `7z` with its work bound to the 60 s span (design) — over the sixteen modes; the library offers no third, and widening the list is a measurement backlog item. Where A's and B's focus holders share a name (`code`, `kdenlive`, `chrome`; 26 cells) the telemetry equals the focus-form twin's, so the second segment is a pre-committed miss, recorded per file. No split. Role: distractor robustness (RQ1) — does the reading hold when names arrive that the user does not turn to.
- **Familiarity ladder** (`familiarity-ladder`, 66 files): each mode's task set in one 60 s segment with its names substituted at tier 4 (a nonexistent name whose words say what the program does; a hand-written table, design) and tier 5 (four lowercase letters by keyed draw, never a known name), in the carrier forms that rename something — the focus holder's name alone, the other names alone, every name — forms renaming the same set collapsed into one cell; one real name maps to one substitute within a file, so counts are preserved; the chain's `wineserver`, named by the compiler, keeps its name (stated limit). Tier 3 where the campaign record shows the mode's job under its own opaque name: render's export as `melt-7`, backup as `duplicity`, each sourced; the C1 files of compile, indexing and gaming already carry tier-3 names. The segment carries `familiarity`. No split. Role: recognition accuracy by familiarity tier (RQ1), and whether an unknown name in the focus and an unknown name beside it read differently.

Idle's task set is the four session processes (§3 C1), so the generated layer carries them wherever it places idle: in 182 files — 60 of the transition grid's, 90 of the return grid's, 32 of the distractor grid's; the familiarity ladder's two idle cells rename them. In 62 of these they run beside another mode's programs: the transition grid's 30 focus-form files with idle on either side of the boundary, and all 32 distractor files, idle as A or as the arrival. Those 62 put the session's measured state, idle and blanked, beside running applications, which no core file does (9.10 D28, D172). They are design composition: the session's names stand beside the applications as on a real desktop, where the recognizer meets them in every mode; their demand is the idle state's, which understates an active session; an idle placement carries no scored term (`scoring.with_generated`). In the other 120 the session runs only in idle segments.

No experiment spec or scoring rule pairs the twins for Layer 2: their workloads differ, each cell's seed drawing its own event streams, and their scoring terms differ by design (9.21 spec decision 2; 9.23 D6). The focus field's Layer-2 worth is measured by running both telemetry shapes on the same files (9.17 spec decision 5).

The consumer work over the layer is 9.21's: the scoring spec assigns the generated files' terms by rule, `dataset/coverage-grid.json` carries each set's coverage table, and the harness reads each generated file's axes from its set's manifest `grid`, joined to the rows by `workload_id`, the records' columns unchanged; experiment specs select files by those axes (9.21 spec decisions 5 and 6; `harness/tools/harness/manifests.py`). The naturalistic set (§4) stays in the backlog.

## 4. The timelines: the naturalistic set (backlog)

A backlogged design, not a build step: a generation model emitting timelines whose segments, switches and co-occurrences follow observed use, for the frequency claims — how often and in what order desktops see the modes. Its prerequisite is a source for Linux-desktop co-occurrence and transition frequency, which 9.10's search did not find; the generator's design is open (`_dev/TODO.md`, Backlog). What it has to work from:

- **Segment durations:** `gonzalez-chi04` gives about 3 min per event (3 min 08 s; an event is one continuous use of a device or one interaction with a person, observed by shadowing; formal meetings, unknown and personal events excluded) and 11 min 28 s as the mean continuous segment in a working sphere before switching, central and peripheral spheres only; `mark-chi05`'s companion figure is about 11 min (11 min 4 s) in a central or peripheral sphere, its 24 informants including CHI 2004's 14. No source gives the distribution family; the design states the one it assumes.
- **Switching structure:** unsourced, hub-and-spoke switching included. DesktopBench's A → B → A interruption split (`focal-arxiv26`) is an evaluation-shape precedent only: its sessions are composed from templates, not observed, and its inter-action timings are a fixed 6.0 s. CpsMark+'s CA workflow grounds the existence of the browsing → office → mail transitions, not an order (9.10 D29).
- **Candidate observations:** SWELL-KW (`swell-icmi14`): the focus sequences of 25 students and interns in a Windows 7 lab, 2012 — a dwell median of 9.1 s per focus episode, A → B → A returns after 83.4 % of middle episodes (the reader's computations over the focus sequence with the logger's window and shell surfaces removed; the unfiltered sequence gives a median of 5.1 s), CC BY-NC-SA 4.0; BEHACOM (`behacom-dib20`): the per-minute foreground program and the switches between applications of 12 users on their own computers — eight on Windows, three on Linux, one on both. Existence and candidacy only.
- **Distractor injection:** label-invariant processes (S5, S16) injected within segments, at a rate the design has to source.
- **Labels:** derived from the generating structure — each sampled segment carries its mode/attributes by construction (the generator is the author).
- **Coverage:** a naturalistic set instances every driver-table cell — all 32 mode × `background_wanted` combinations — checked by the same 32-cell coverage table the core set runs. A generator whose output leaves a cell empty is re-parameterised, not excused.

Role: ecological validity, and the **query-economics numbers** — novel canonical sets per hour and deployment-cache hit rate, measured with the simulator counters from Q7. Controlled claims never rest on this set.

**Driver table tuning set.** The set the calibrated table is tuned on (research-proposal §4.6). It is disjoint from the core set and from the naturalistic set; its composition is fixed together with the calibrated table's tuning method, after Phase 9.

### 5a. Lane scaling and the demand budget

The simulated machine has one lane (Q1 of the archived open-questions record, ratified — `_dev/archive/2026-08-23-design-meeting-open-questions.md`; interpretation-contract §1). Two rules connect the dataset to it:

- **Lane-scaling compile pass:** one entry declares scalable fields — `game-task-chain`, whose chain RUN values the compiler scales so the chain's aggregate demand per frame is the timeline's `lane_share` of the lane (`test_lane_scaling_lands_chain_on_lane_share`); every other entry's `scalable` list is empty, its values this software's CPU on one pinned core. The scaling is our calibration, not the source's; what it leans on is LAVD's concentration statistic as Min reported it (top 30–40 tasks = 95 % of scheduling, `lavd-ossna24` s12), stated in `modeling_notes`. Archetype values themselves are never edited. The compiler knows one mode, `single`, and refuses `native` (`dataset/tools/wlc/compiler.py`; CI invariant `test_single_is_the_only_mode`; 9.5 follow-ups spec decision 14).
- **Demand budget:** a timeline's demand class names its design — `oversubscribed` (the default) marks a file designed to hold contention, `demand: calibration` one that is not — and says nothing about the file's compiled demand, which is a measured fact: the compiler records each `-single` workload's utilization per file and per ground-truth segment in its set's manifest (`dataset/build.manifest.json` for the core set) and never fails a file on it. The demand is reported, not held: since 9.10 D17 binds every job whole as measured, a file's demand follows from the measurement, and holding it to the ~100–150 %-of-the-lane window that gated `oversubscribed` files until 9.14 (9.14 decision 4) would have meant bending measured lengths; the pair review reads the contended segments. The record is a static estimate, each task's CPU spread uniformly over its lifetime — its arrival to its depart or the file's end (`dataset/tools/wlc/estimate.py`) — so a file whose batch job outlives it records offered demand, not load the lane carries: `c2-p1a` 14.505 over the file and 35.7721 lanes in its second segment, `c2-p2a` and `c2-p2a-idle` 9.3829 and 28.5251; these figures are not read as oversubscription. The gate's own per-file criterion, the file's gap read against g, applies to every judging file whatever its class: a judging file whose every term shows no headroom stays in the set and counts as not meeting g, never a file removed after the fact (the RQ0 gate spec, statements `judging-set` and `g-grounding`). The calibration class (Phase 7) is declared by the sixteen C1 timelines in their own `meta` (calibration proper), and by `patch-meta: {demand: calibration}` in the recipes of the derived families C4, C5, the three derived C6 files and C7 — a derived file's demand is its base's plus whatever the recipe adds by construction, so the pair is the control; `c6-dual` is `oversubscribed`. For C7 that puts the interactive counterparts at 1.0007–1.5878 lanes and `c7-gaming` at 1.9149; the pair review reads each judging file's contended segment's demand from the manifest and reports the regime per pair.

## 6. Provenance manifest and linter

- Every numeric field in the archetype library carries `source: <id>` or `source: <id>:<locator>` — ids from **dataset/sources.yaml**. The linter validates: the id exists in the registry; when the entry declares `locator_pattern`, the locator matches it.
- Every value a timeline binds — each task's `bind` keys, and its `count` when stated — has an entry in the task's `source:` map, and nothing else does: a registry tag or a list of tags, checked as the library's are, or one of the labels `design`, `convention`, `arithmetic` (`dataset/tools/wlc/linter.py`, `lint_bound_sources`; 9.10 D32). E.g. `c1-compile` binds `spawn_count` 2,908 (`meas-ci:build:2026-09-18`), `parallelism_cap` 8 (`design`) and `child_name` `cc1` (`meas-ci:build:2026-09-18`).
- The registry is a **subset of docs/references.md** (every registry id has a docs/references.md entry — CI-checked); citation strings live only in docs/references.md.
- Every `meas-ci` campaign tag the data carries resolves to a GitHub release in `dataset/meas-releases.yaml`, which states each release's tag, URL and each asset's SHA-256.
- `make lint` (`tools/lint.py --freeze`) fails on: a library numeric without a source tag; a timeline bound value without a source entry, or a source entry naming no bound value; `meas-pending` in the library or in a timeline's bound values; an id absent from the registry; a locator violating its pattern; a registry id absent from docs/references.md; a `meas-ci` campaign tag with no mapped release.
- Payoff: the paper states, machine-checkably, **"every numeric parameter in the archetype library traces to an external source or to our released measurements, and every value a timeline binds carries its source or a label saying what it is."**

## 7. Measurement campaign — meas-ci

Campaigns on public CI runners (GitHub Actions): the workflow files are in the repository (`.github/workflows/meas-*.yml`), so anyone can re-run them. A measured value carries the tag `meas-ci:<workflow>:<campaign>`, the campaign named by the launch date of its first batch (a letter added for a second campaign of that workflow and date; a run number names a one-run campaign from before that form). The raw records of each campaign whose tag the data carries are one or more GitHub releases, mapped in `dataset/meas-releases.yaml` (§6); the map leaves out the campaigns whose tags the data does not carry, their records held in releases the map does not list — `meas-ci:names:2`'s, which the scenario catalog's note 4 cites, in `meas-ci-2026-08-28`. The releases are made by hand when a campaign is pooled, before the 90 days after which a workflow's artifacts are deleted (`gh-artifact-retention`).

**Workflows** whose campaigns the data carries: `build` (the kernel build: `build-orchestrator`, `compiler-child`); `background` (the batch and background jobs: `file-archiver`, `game-download`, `package-upgrade`, the DKMS pair, `file-indexer`, `cpu-batch`'s programs, `video-transcoder`, `incremental-backup`); `interactive` and `playback` (the nine measured applications under Xvfb, driven by replayed input or playing media); `desktop` (`renderer-hidden`, `chat-client`, `game-client` and the launch phases); `session` (the four session entries). Five more carry no dataset value: `names` (the `comm` and command-line strings of installed packages in distro containers, which confirm a derived name, below), `probe` (what the runner can drive and observe, read before the 9.5 campaign was designed), `long-probe` (one long phase of an application, to see whether its launch-time episodes stop or recur), `sched` (the runner kernel's scheduler tunables, a configuration read) and `costs` (the runner kernel's context-switch cost and a recognizer-shaped answer's latency, `meas-ci:costs:2026-10-08`, which the research proposal cites). Each campaign with its runs and releases: `docs/workload/measurement-overview.md` §9. The measured programs run pinned to one CPU — for `session`, the four entries' processes confined to it — and `perf sched record -a`, started on the other CPUs, traces every CPU; the batch, background and build jobs are also read by a taskstats listener registered on the measured CPU (per-process CPU, elapsed time, block-I/O delay and runnable wait at exit) — the single-core tooling that replaced Phase 2's forkstat (whole-second timestamps, no CPU) and 0.5 s `/proc` sampler for the build (9.6 D3). A task's name is its process's kernel `comm` (9.10 D25): for a program a campaign ran, the `comm` the campaign traced; otherwise derived by the `comm` rule (the exec'd basename cut to 15 bytes) and confirmed where a campaign or the names workflow (`meas-ci:names:2`) shows it. The game chain's thread names are its source's (`lavd-ossna24` slide 16), `wineserver` named by the compiler, and the tier-4 and tier-5 substitutes and the deliberate spoofs are design (`docs/workload/scenario-catalog.md`, note 4).

**Scope discipline (the trust package, mirrored in the registry's `meas-ci` entry):** a measured value is a source claim about this software on this machine — a GitHub-hosted ubuntu-24.04 runner pinned to one CPU of the AMD EPYC 7763, its runner spec written into the archetype's scope with the application's pinned version — never desktop truth. The campaigns observe per-wake runs and waits from the scheduler trace, per-process CPU and block-I/O delay at exit, network waits and bytes per wake from socket rows, and process structure and `comm` strings. Repeats are added until the stability rule holds for every carried value: the 95 % confidence half-width of the across-repeat mean within 5 % of it or 1 µs, over at least five same-machine repeats (`dataset/tools/meas/stability.py`); a value whose spread follows the machine is carried with its half-width. Framing: characterization of software behavior, never desktop-performance measurement.

## 8. Standing rules inherited by all of the above

- **Names only** in the workload schema; no executable paths (the scenario catalog's header).
- **No circular grounding:** our own Family/driver-table definitions never appear as sources; internal cross-references live in notes, not source columns.
- **Citation tiers** are carried per-entry in docs/references.md: scholarly (numbered bib); deployed-system (footnote) — existence claims, the system's own documented design or behaviour stated as that source's at its pinned version or accessed date, and a figure the source publishes stated as its report with the date read, the window and how it is computed, never a behavioural or statistical claim stated as ours or a population's; talk, conference abstract or news report (footnote) — its claims the speaker's or reporter's, a number only as its report with its date.
- **Caches:** record/replay cache on during all measurement (it is the instrument); deployment cache off during Layer 1 measurement, on only in deployment/demo (Q7).
- **Canonicalization is structural-only** (ancestry, cgroup, string identity — never name semantics); it defines query points and the cache key (Q7).
