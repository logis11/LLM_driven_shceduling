# Prior table — pair review

> Status: record · Created 2026-09-09 · Updated 2026-09-09

The pre-execution check on `daemon/driver-table/prior.yaml`: for every pair of rows the experiment will hold against each other, one written judgement that names the knob that differs, the scored term of the exercising file that knob moves, and that the direction agrees with the scoring weights in `harness/scoring/scoring-spec.yaml`. The lint already refuses a same-mode pair whose default configurations are byte-identical; this document is the judgement on top of that. It is a manipulation check, not a tuning result: it shows the rows differ in the intended direction, not that they are the best rows. How much of the available spread the table captures is RQ5's empirical check after the RQ0 gate.

Two lists, per the Phase 6 spec. The 16 same-mode pairs (`wanted=true` against `wanted=false`), and the three C2 row-pairs as the judging files actually exercise them — only one of those is a same-mode pair. Rows no coreset file exercises are reviewed too, because the `random` condition can land on any row.

Reading the table's rules once (they are in the file's header): the mode picks the algorithm family and the attribute picks the cap; a wanted row's cap is the batch term's share of the file's scoring weight, an unwanted row's cap is the schema floor 0.05; params are the boot values throughout, so no pair differs by a param.

## Findings

1. **The cap does not act on a background task that is not batch-class.** `batch_bandwidth_cap` bounds the batch class, which the executor determines from observed CPU-bound behaviour. `c2-p2a`'s download (`network-bulk`, ~1 ms of RUN per ~5.7 ms) never consumes a 2 ms slice, so by the vocabulary's rule — the same evidence MLFQ demotion uses — it is not batch-class, so the `gaming/true` row's 0.333 cap, derived from the download's 0.5 weight, is inert on that file: the download's progress is whatever EDF's residual class receives. The row is still right in direction against `gaming/false`, and the pair's gate distance rests on p2b's CPU-bound scan, where the floor cap acts. This is a property of the cap's semantics, not a table defect. Decided 2026-09-09: the file and the cap stay as they are, and the asymmetry is stated — p2 tests the attribute in one direction (misreading unwanted CPU work as wanted costs frames in p2b; misreading a wanted download as unwanted costs nothing in p2a), which is itself a finding: a cap on a behaviourally inferred class can protect against unwanted CPU work but cannot favour wanted IO-shaped work. The classification rule this rests on is specified in `docs/memos/2026-09-09-batch-class-rule-for-the-simulator.md` (one full slice since the last voluntary block; the periodic class never); the conclusion holds under any rule, since a 1 ms chunk is shorter than every legal slice. Phase 8's gate spec pre-registers p2a's gap as a mode-recognition gap.
2. **Fourteen of the 32 cells have no coreset instance** — thirteen `false` rows and `meeting/true` — and in every interactive-only mode the `true` row's cap has nothing to act on in the C1 files. Their distances are correct by the table's rules and measured by nothing; they exist for `random` and for the lint. The cause is in the dataset's instrument: the building plan framed the coreset as a grid of driver-table cell × familiarity tier, but the grid tool counts mode × tier and never had a `background_wanted` axis, so the 2026-08-28 sign-off could not see that the attribute's negative side is two segments (`c2-p1b`, `c2-p2b`). Consequences: the attribute-accuracy metric is near-degenerate on this coreset (answering `true` always scores about 95 percent), and the calibrated table has nothing to tune against on those rows. Decided 2026-09-09: a new Phase 7 in `_dev/TODO.md` adds the attribute axis to the grid, derives a family of `false` files for the interactive modes from their C1 bases, and writes the all-32-cells requirement for the generalset; RQ0 is untouched, since the C2 pairs exercise the attribute where they were designed to. Until then the gate spec reads these rows as "not measured", never as "no headroom".
3. **No pair failed the sentence test.** Every pair differs on a knob a sentence can name, and the direction agrees with the weights in every case. `prior.yaml` is unchanged by this review.

Stated limitation: the workloads, the scoring weights, the table, and this review have one author, and no second reader is planned. The empirical check after the gate (RQ5's configuration search) is what tests the table against something the author did not write.
