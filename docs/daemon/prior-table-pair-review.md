# Prior table — pair review

> Status: record · Created 2026-09-09 · Updated 2026-09-11

The pre-execution check on `daemon/driver-table/prior.yaml`: for every pair of rows the experiment will hold against each other, one written judgement that names the knob that differs, the scored term of the exercising file that knob moves, and that the direction agrees with the scoring weights in `harness/scoring/scoring-spec.yaml`. The lint already refuses a same-mode pair whose default configurations are byte-identical; this document is the judgement on top of that. It is a manipulation check, not a tuning result: it shows the rows differ in the intended direction, not that they are the best rows. How much of the available spread the table captures is RQ5's empirical check after the RQ0 gate.

Two lists, per the Phase 6 spec. The 16 same-mode pairs (`wanted=true` against `wanted=false`), and the three C2 row-pairs as the judging files actually exercise them — only one of those is a same-mode pair. Rows no coreset file exercises are reviewed too, because the `random` condition can land on any row.

Reading the table's rules once (they are in the file's header): the mode picks the algorithm family and the attribute picks the cap; a wanted row's cap is the batch term's share of the file's scoring weight, an unwanted row's cap is the schema floor 0.05; params are the boot values throughout, so no pair differs by a param.

## Findings

1. **The cap does not act on a background task that is not batch-class.** `batch_bandwidth_cap` bounds the batch class, which the executor determines from observed CPU-bound behaviour. `c2-p2a`'s download (`network-bulk`, ~1 ms of RUN per ~5.7 ms) never consumes a 2 ms slice, so by the vocabulary's rule — the same evidence MLFQ demotion uses — it is not batch-class, so the `gaming/true` row's 0.333 cap, derived from the download's 0.5 weight, is inert on that file: the download's progress is whatever EDF's residual class receives. The row is still right in direction against `gaming/false`, and the pair's gate distance rests on p2b's CPU-bound scan, where the floor cap acts. This is a property of the cap's semantics, not a table defect. Decided 2026-09-09: the file and the cap stay as they are, and the asymmetry is stated — p2 tests the attribute in one direction (misreading unwanted CPU work as wanted costs frames in p2b; misreading a wanted download as unwanted costs nothing in p2a), which is itself a finding: a cap on a behaviourally inferred class can protect against unwanted CPU work but cannot favour wanted IO-shaped work. The classification rule this rests on is specified in `docs/memos/2026-09-09-batch-class-rule-for-the-simulator.md` (one full slice since the last voluntary block; the periodic class never); the conclusion holds under any rule, since a 1 ms chunk is shorter than every legal slice. Phase 8's RQ0 gate spec pre-registers p2a's gap as a mode-recognition gap.
2. **Fourteen of the 32 cells have no coreset instance** — thirteen `false` rows and `meeting/true` — and in every interactive-only mode the `true` row's cap has nothing to act on in the C1 files. Their distances are correct by the table's rules and measured by nothing; they exist for `random` and for the lint. The cause is in the dataset's instrument: the building plan framed the coreset as a grid of driver-table cell × familiarity tier, but the grid tool counts mode × tier and never had a `background_wanted` axis, so the 2026-08-28 sign-off could not see that the attribute's negative side is two segments (`c2-p1b`, `c2-p2b`). Consequences: the attribute-accuracy metric is near-degenerate on this coreset (answering `true` always scores about 95 percent), and the calibrated table has nothing to tune against on those rows. Decided 2026-09-09: a new Phase 7 in `_dev/TODO.md` adds the attribute axis to the grid, derives a family of `false` files for the interactive modes from their C1 bases, and writes the all-32-cells requirement for the generalset; RQ0 is untouched, since the C2 pairs exercise the attribute where they were designed to. Until then the RQ0 gate spec reads these rows as "not measured", never as "no headroom".
3. **No pair failed the sentence test.** Every pair differs on a knob a sentence can name, and the direction agrees with the weights in every case. `prior.yaml` is unchanged by this review.
4. **All 32 cells are instanced (Phase 7).** Finding 2's count was off by the arithmetic of its own list: the compiled ground truth before Phase 7 exercised 17 cells, and the missing fifteen were fourteen `false` cells and `indexing/true`, not thirteen and `meeting/true` (`meeting/true` was instanced by `c6-fold` alone). The grid tool now has the attribute axis and CI fails on an empty cell; 7.2 added one base per mode and 7.3 one counterpart per mode. Of the 63 segments on the grid, 18 are `false`, so an always-`true` answer still scores about 71 percent by segment count against about 95 before — a majority baseline that raw accuracy alone would flatter. The grader scores per query point, so the real baseline is unknown until the recognition log exists; either way the headline attribute metric should be balanced accuracy (the mean of `true` and `false` recall, exactly 50 for an always-`true` answer) with the confusion matrix beside it and raw accuracy reported only next to its majority baseline, readable per cell now that every cell has an instance. That is an RQ0 gate spec input (Phase 8), not a reason to add files for a 50:50 split. Five segments are pre-committed misses on the attribute side — `indexing/true` and the `ml-train`, `render`, `transcode`, `backup` `false` cells, where the counterpart differs from its base by intent alone — annotated `pre_committed_miss` and reported outside accuracy by the same rule as C6. Their rows are still measured under `oracle`.
5. **On the EDF rows whose consumers are all TIMER loops, the cap does not reach the scored term.** `meeting` and `media` score miss rates of tasks in the deadline class, which EDF serves before the residual class the scan sits in, and one slice of delay is below both tick tolerances; so the `true`/`false` distance on those two pairs is measurable only when the `random` condition draws LOTTERY or MLFQ on them. Same family as finding 1 (a knob that is right in direction but inert on the file that exercises it), different cause: there the task escaped the batch class, here the consumer never competes with it. `gaming` is not in this family because the chain's woken stages are residual-class, which is why `c2-p2b` measures its cap. Pre-registered in the RQ0 gate spec as "unmeasured on the cap axis under the row's own algorithm". The general form, across the sixteen pairs: the attribute has a scheduling consequence in three places — the interactive modes, where the cap protects a keystroke-driven foreground under MLFQ; the batch modes, where wanted and unwanted work get different algorithms and shares; and gaming, whose chain has residual-class stages — and none on the two purely periodic modes, because EDF keeps every tick on time whatever the scan does. On `c7-meeting` and `c7-media` the `oracle`-versus-`fixed` gap is therefore an EDF-versus-MLFQ result (the boot default demotes a 6.67 ms video burst after its 2 ms slice and lets it compete with the scan), counted toward the RQ0 headroom like any file but attributed to the algorithm choice, and a condition that reads the mode right and the attribute wrong is predicted to score the same as `llm_vocab` there. Both sentences go into the RQ0 gate spec as reporting lines (Phase 8).
**Addendum to finding 5, 2026-09-11 (boot default from OSTEP).** Finding 5's arithmetic rested on the 2 ms slice. With the boot default re-sourced from OSTEP §8's example (10 ms slice; EDF's residual slice 10 ms by the vocabulary's same-granularity rule) it changes in two ways. (1) Under the two EDF rows one residual slice is now 10 ms, exactly the video consumer's tick tolerance (period 16 667 µs minus burst 6 667 µs). Under the slice-granular reading this finding used, the worst-case tick starts 10 000 µs late and finishes exactly at its deadline, which the strict miss rule counts as met, so the rows still tie, but on a knife edge: whether a waking deadline task preempts a residual slice at once, and which of a slice boundary and a TIMER expiry applies first at the same instant, are executor rules the vocabulary does not fix; both are asked of 인경민 in `../memos/2026-09-11-boot-default-from-ostep.md` §5. If the boundary resolves to a miss, the two rows differ through the cap (0.5 against 0.05 governs how often the scan holds the lane while the consumers are runnable) and the cap axis is reached on these pairs for the first time. (2) The `oracle`-versus-`fixed` mechanism named above, the boot default demoting the 6.67 ms video burst after a 2 ms slice, is gone: with a 10 ms slice the burst never consumes a slice and is never demoted, and the one exposure under `fixed` is the 100 ms boost lifting the scan to Q0 with a fresh slice, the same 10 ms worst case. On the arithmetic both files are expected no headroom on every scored term, like `c1-media` and `c1-meeting`, pending the two rules. Whether they stay in the RQ0 judging set is the RQ0 gate spec's to re-decide once the rules are in; Phase 7's judging rule as written (the scored term registers the rows' difference by design) would move them to reporting-only.

6. **No C7 pair failed the sentence test.** `prior.yaml` changed in two places from this review: `indexing/true`'s cap is now derived from `c1-indexing`'s weights (same value, 0.5), and the thirteen `false` rows that gained an instance name their C7 file in the row sentence, as the `true` rows always did.

Stated limitation: the workloads, the scoring weights, the table, and this review have one author, and no second reader is planned. The empirical check after the gate (RQ5's configuration search) is what tests the table against something the author did not write.
