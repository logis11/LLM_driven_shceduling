## Scheduling mechanisms: making policy replaceable

A line of systems work has made scheduling policy a replaceable component rather than a kernel constant. ghOSt delegates kernel scheduling decisions to userspace agents, motivated by the need to iterate on policy across a fleet without deploying a new kernel or rebooting [ghost-sosp21]. sched_ext, first released in Linux 6.12, brings the same capability to the mainline kernel through BPF: a BPF scheduler "can be turned on and off dynamically anytime", and, in the kernel documentation's words, "The system integrity is maintained no matter what the BPF scheduler does. The default scheduling behavior is restored anytime an error is detected, a runnable task stalls, or on invoking the SysRq key sequence SysRq-S" [schedext-docs]. The sched-ext/scx repository ships schedulers built on it [scx], and their operators and maintainers report on them: the sched_ext maintainers' LPC 2024 slides, presented by Meta, report `scx_layered` "deployed in 1M+ machines with significant perf gains" [schedext-lpc24]; Meta's speakers at LPC 2025 report it deployed "to the entire Reality Labs GPU fleet with tens of thousands of GPUs" [lu-lpc25] and present `scx_lavd` as a candidate default fleet scheduler [dai-lpc25]; Valve's SteamOS 3.8 offers `scx_lavd` as a CPU scheduler the user selects [steamos-lavd]. A non-default policy runs at fleet scale, as its operator reports it.

This work is complementary, not competing: it answers *how* a machine runs a chosen policy, and deliberately leaves open *how the machine knows which policy fits the current situation*. We target that open question. Our recognition layer produces the situational signal; mechanisms like sched_ext are how a consumer of that signal would take effect on a real system.

*Objection absorbed: "isn't sched_ext already this?" — No; it is the actuator, not the sensor. Note: this paragraph doubles as the honest framing for why our evaluation is simulator-based with sched_ext as future work. The mechanism layer, as the sources ground it: the kernel states sched_ext's integrity and fallback, the sched_ext maintainers' slides Meta presented report `scx_layered` on "1M+ machines", Meta's speakers report it across Meta's Reality Labs GPU fleet, and Valve's SteamOS offers `scx_lavd` as a scheduler the user selects. Our simulator is one lane — exactly one simulated CPU — and no algorithm or executor of this project has a sched_ext implementation. We expect simulating the executor to forfeit less than it appears to.*

## Behavioral inference inside the scheduler

Inside the scheduler, what a deployed scheduler infers about a task it infers from runtime behavior; the other signals deployed systems act on are declared — a Linux scheduling class, nice value or unit setting [man-sched], a macOS QoS class [apple-qos] — or come from the window system (Windows' foreground and input boosts [win-priority-boosts]; Game Mode's foreground or full-screen game [gamemode-docs, apple-gamemode]) or from a name table (ananicy-cpp's catalogue [ananicy-rules]). The classic interactivity heuristics differ in what they keep: MLFQ classifies tasks by how they use the CPU [ostep, corbato-sjcc62], while CFS and EEVDF account against a fair share — a virtual run time and a lag per task, the eligible task with the earliest virtual deadline run next, a sleeping task's lag decaying — and their sleeper handling shapes where a waking task lands [eevdf-tr95, linux-sched-eevdf, linux-sched-cfs]. scx_lavd estimates each task's latency criticality from its wait and wake frequencies, its runtime and its weight, propagates it between wakers and wakees along task chains, and uses it to set the task's virtual deadline and time slice; it was motivated by gaming workloads, to reduce stuttering [scx; lavd-ossna24, slides 22 and 25].

Behavioral inference is cheap, private, and continuous, and we retain it wholesale: our executor is a behavioral scheduler. But behavior is a fundamentally limited channel for *intent*. Our load-bearing pair is two real jobs, each beside an editor, with opposite correct policies, differing in behavior and in declared class. The training side (`c2-p1a`) is PyTorch's basic MNIST example on the CPU — an actual training run; we do not claim that desktop users train MNIST — one thread, 69.49 s (±27.3 %) between voluntary blocks, at nice 0. The indexer side (`c2-p1b`) is GNOME's Tracker indexing a home folder: five processes, 1.876 ms between voluntary blocks, 0.844–0.849 of its CPU past a 10 ms slice, with `SCHED_IDLE`, nice 19 and the idle I/O class set by the program on itself. The pair tests what recognition adds over a baseline that already honours the indexer's declared class. On the indexer's side that headroom is zero, so RQ0, the gate experiment, judges `c2-p1a` and reports `c2-p1b`; the pair stays load-bearing for the recognition claim.

*Objection absorbed: "LAVD already infers latency sensitivity — why is that not enough?" — because it infers a task-level property, not a machine-level situation, and it reads behavior. Note: cite LAVD generously; we build on it rhetorically (Valve sponsors LAVD's development and ships it in SteamOS 3.8 as a scheduler the user selects, installed and configured but not enabled by default — which legitimizes 'desktop scheduling matters') and it is the strongest version of the position we argue against.*

## Learned schedulers

A second lineage replaces hand-written heuristics with learned policies. Decima learns cluster scheduling policies via RL over job DAGs [decima-sigcomm19]; FIRM learns SLO-driven resource management for microservices [firm-osdi20]; Park offers an open platform of twelve system-optimization environments for learning-augmented systems [park-neurips19]. Decima and FIRM learn a policy mapping observed system state to actions — Decima's scheduling decisions over job DAGs, FIRM's per-microservice resource limits — and Park defines such state and action spaces for the twelve environments in which agents are learned. Their limits are stated by the learned papers themselves and summarized by later LLM work: they require extensive per-workload retraining, and they operate inside a problem space a human has already formalized (features, knobs, objectives) [decima-sigcomm19 §7.4; firm-osdi20 pp. 3, 10, 13; park-neurips19 §3.3; schedcp-mlsys25 §2]. Closest to our architecture in shape, ASA classifies the workload from OS metrics with a model trained once offline, smooths its predictions by time-weighted voting, and switches among expert sched_ext schedulers through a per-machine mapping table [asa-arxiv25].

ASA shares our skeleton: recognize, then select among fixed policies rather than generate code. The difference is the recognition channel. ASA's recognizer, like the RL line, reads behavioral features, with no process identity, and each new machine needs a measurement pass that builds its mapping table, with optional fine-tuning; ours reads process identity against world knowledge that requires no training on the target machine. The two channels fail differently: behavioral recognizers cannot see intent (§behavioral above), while identity-based recognition cannot see behavior it has no name for — a limit we scope explicitly (Family 5).

*Objection absorbed: "recognition-then-routing already exists (ASA)." — Yes; the contribution is not the skeleton but the channel, and we say so plainly. Note: do not overstate ASA's closeness in the intro and then minimize it here; reviewers diff those sections.*

## LLM agents for kernel policy

Recent work applies LLM agents to kernel policy directly. Kgent synthesizes kernel extensions from natural language [kgent-ebpf24]. SchedCP, the closest prior work, frames the same semantic gap we target — kernel policies cannot understand application needs — and answers it with an agentic control plane: a Workload Analysis Engine gives agents tiered access to profiling tools, and a multi-agent system analyzes the workload, then synthesizes or selects eBPF schedulers deployed via sched_ext, reporting a 1.79× total improvement over EEVDF on kernel compilation [schedcp-mlsys25]. Beside the synthesis line, Vulcan synthesizes small policy functions offline with an LLM, in a restricted language (Anvil), evaluated on spot-VM scheduling, cache eviction and tiered memory; CPU scheduling is an example task in its interface table, not evaluated [vulcan-arxiv25]. Adjacent efforts tune the kernel's build configuration [tuneagent-kdd26] and schedule HPC jobs [jadhav-arxiv25] with LLMs in the loop. Beside them, TuxBot tunes up to 41 Linux parameters online with an LLM, out of band — "not kernel fast-path controllers such as the CPU scheduler" — on hosted Gemini 2.5 Flash and Flash-Lite, each change passing typed validation [tuxbot-arxiv26]; and LumOS, the scheduler instance, adjusts CFS's `latency_ns` and `min_granularity_ns` online with an LLM loop against a PostgreSQL workload's p99 latency, 5.0 % and 7.1 % below Bayesian optimisation in one- and two-parameter tuning [lumos-mlsys25]. AKTS has a slow agent recognize a workload regime from telemetry and switch among verified kernel policies through a sub-microsecond actuator, a BPF map write [akts-arxiv26].

We share with SchedCP the semantic gap as the problem, and with SchedCP, TuxBot, Vulcan and AKTS the LLM kept out of the scheduler's per-decision path, each stating it [schedcp-mlsys25; tuxbot-arxiv26; vulcan-arxiv25; akts-arxiv26]; Jadhav et al.'s LLM makes the HPC job-scheduling decisions itself [jadhav-arxiv25]. We differ in what the LLM's understanding becomes, and for whom. First, the output contract: SchedCP's agents produce *policy* — generated or selected scheduler code, per workload, through an agentic session with sandboxed profiling (reading source, running perf). Our model produces a *signal* — a small fixed vocabulary of modes and attributes describing the situation — from process identity alone (the names running, their counts, and which one holds the window focus), in a single inference, with all policy remaining in fixed, auditable drivers. Second, the setting: SchedCP optimizes a given workload (its evaluation runs kernel compilation, schbench and batch workloads), though it names edge and personal devices among its motivations; a desktop is not a workload to optimize but a stream of situations to track, where the same machine is a gaming rig at 8pm and a build box at 9pm. Third, and most consequential for evaluation: the nearest prior measurements of recognition are three — ASA reports its behavioral classifier's accuracy, 96.83 % and 99.19 % after online fine-tuning, over OS metrics with no process identity [asa-arxiv25]; SchedCP reports one classification outcome beside four research questions, none on recognition ("Claude Opus successfully classified all 8 workloads at $0.15 per analysis, while Claude Sonnet failed") [schedcp-mlsys25]; AKTS measures small language models routing load telemetry to a policy index, at chance (20 of 40) [akts-arxiv26]. Because our recognizer emits a graded signal against ground-truth labels, we can measure recognition *itself* — accuracy, consistency, distractor robustness — separately from scheduling benefit, and we evaluate against the strongest non-LLM implementation of semantic recognition (the strongest name table, `strongest_name_table`) rather than only against default schedulers.

*Objection absorbed: "this is SchedCP for desktops." — The rebuttal is the output contract + the measurement layer; lean on Layer 1 — SchedCP reports one classification outcome beside research questions none of which is on recognition — and on the two name-table baselines, which its evaluation has no analogue of. Note: check for a SchedCP conference-length successor before every submission; if one exists, this paragraph is rewritten against it, not against the workshop paper.*

## Semantic recognition shipped today: static name tables

Semantic recognition of desktop situations is not hypothetical — it ships, in degenerate form. On Linux, ananicy-cpp (its upstream, Ananicy, archived since 2023-03-21) applies a catalogue of rules keyed by process name: a rule's `name` is matched against the basename of the process's `argv[0]`, untruncated, and the rule's type sets the process's nice value — on every thread — its I/O class and its scheduling policy [ananicy]. The CachyOS catalogue is maintained by the CachyOS team and the community, entries contributed by pull request or issue, 15 813 entries at `03ef03fb` (tag 1.1.49) [ananicy-rules], and CachyOS's installer installs and enables ananicy-cpp with it by default [cachyos-settings]. Every entry is entered by a contributor's commit (the current entries last changed by 112 authors), and a rule acts only on a name the catalogue already carries. Game Mode is a shipped category of its own, the foreground game, and no list of executables is documented for it: Windows grants a game in the foreground with focus exclusive CPU sets and increased GPU prioritization, on by default for most games, how a game is recognised undocumented and the Game Mode APIs deprecated in Windows 10, version 1809 and later [gamemode-docs], and while a game runs it prevents Windows Update from performing driver installations and sending restart notifications [xbox-gamemode]; on a Mac with Apple silicon and macOS Sonoma 14 or later, Game Mode turns on when a game enters full screen [apple-gamemode], and an app declares support with `LSSupportsGameMode`, listed for macOS 26.0 and later [apple-lssupportsgamemode]. The name table validates our premise — process identity carries actionable scheduling information — while embodying the two limits we measure: enumeration (a table over names cannot cover the combinatorial space of co-running sets, nor novel software) and staleness (each entry costs curator labor).

We treat this quadrant as our true baseline, in two conditions. The shipped-catalogue condition (`shipped_catalogue`) reproduces the catalogue CachyOS ships enabled, matched as ananicy-cpp matches it; the strongest-name-table condition (`strongest_name_table`) is the design point at its best, a rule list in the catalogue's design covering the software the dataset presents as known. Our claim is precisely that LLM inference generalizes it: same inputs (names), same output kind (a situational judgment), with the lookup table replaced by world knowledge that covers combinations and software no curator enumerated. Where the strongest name table wins — famous software, exact matches — we report it winning.

*Objection absorbed: "Game Mode already exists." — Game Mode is another category: it gives the foreground game resources, and how it recognizes a game is undocumented. We cite it for its category only and reconstruct nothing from it. Our baseline is the name-table design point, reconstructed from the CachyOS catalogue (`ananicy-rules`), which CachyOS ships enabled, as two conditions — the shipped catalogue and the strongest name table — and the paper's headline experiments are exactly the cases where a name table cannot follow. Note: the catalogue is the citable open artifact (public, reproducible at a pinned commit).*

## Positioning

Two axes organize this landscape: what recognition reads (runtime behavior vs. process identity and world knowledge), and what it produces (generated policy vs. a selected signal over fixed policies). Behavioral heuristics and learned schedulers occupy the behavior-reading column and cannot see intent; ASA and AKTS sit in its signal-producing cell. The LLM line turns what it reads — process names and profiles, telemetry, knob schemas — into policy code (SchedCP, Kgent, Vulcan), configuration and parameters (TuneAgent, TuxBot), job decisions (Jadhav et al.) or a selection among verified policies from telemetry (AKTS), evaluated on servers, HPC queues and, for SchedCP, a laptop. In the cell that reads process identity and produces a signal — where desktop situation awareness must live — the one documented recognizer deployed today is a static name table, ananicy-cpp's catalogue, which CachyOS installs and enables. Declarations (Linux classes and units, macOS QoS, a game's request to Feral GameMode [feral-gamemode], `LSSupportsGameMode`) and window-state triggers (Game Mode's foreground or full-screen trigger) are not recognition and stay outside the figure. Mechanisms such as ghOSt and sched_ext let a policy-replacing system take effect. This work fills the identity-reading, signal-producing cell's dynamic slot: a recognition layer that reads what a name table reads, produces what a name table produces, and replaces the table with inference. To our knowledge — in the literature searched through 2026-10-08 — no prior work measures an LLM's accuracy at recognizing a desktop situation from process identity against ground-truth labels; the three nearest measurements are ASA's behavioral classifier, 96.83 % (99.19 % after online fine-tuning) over OS metrics with no process identity; SchedCP's one classification outcome, Claude Opus classifying all 8 of its workloads and Claude Sonnet failing; and AKTS's small models routing load telemetry to a policy index at chance, 20 of 40.
