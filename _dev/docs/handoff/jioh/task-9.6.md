## The one-observation situation

Both build archetypes already rest on one observation, `meas-ci:cli:3` — five repeats of a linux-6.6 defconfig `make -j8` **unpinned on 4-vCPU runners** — and the 9.3 re-analysis has re-cut its numbers to `cc1` alone (lifetime median 840 ms, CPU mean 358 ms, `make` dispatch 474 µs over 5 947 make children). The search found no external observation that replaces it, and it bounds its weak points:

- **Process population and unit.** kbuild v6.6 source (S2-01) fixes the per-object chain (`sh` → `gcc` → `cc1`, `as` → optional `objtool` → `fixdep` → `rm`; sub-make per directory; no `collect2` for vmlinux), so one make job is six or seven processes; Gregg's one-second `perf sched` capture of a build (S3-01/02: Xeon E5-2680 v2, 8 vCPUs, kernel 4.10) shows `cc1` at 6 013 ms against the `gcc` drivers' 43.6 ms; a Debian kernel build log (S3-03) gives invocation counts per tool. No source gives per-role lifetime or CPU distributions.
- **Per-compiler CPU.** Only clang data: the LLVM compile-time tracker's per-file `task-clock` (S3-04) and `.ninja_log` per-edge walls (S3-14); for gcc only a parse-share scatter (S1-10). Nothing for the kernel.
- **Disk wait.** No observation of a compiler's blocked time. Whole-build evidence says builds are CPU-bound (Traeger et al. S1-08: > 99.2 %). A runner can measure it directly: taskstats delay accounting is compiled into the runner's kernel (S4-04) and gives `blkio_delay_total` per exiting task once `kernel.task_delayacct=1` is set (S4-05).
- **Dispatch cost.** No measurement of make's own cost per job anywhere; the mechanism is fully documented (S2-03: FIFO tokens, `vfork`/`posix_spawn`, a shell for every kbuild recipe line).
- **Parallelism.** Every vendor default is `nproc` or a memory-capped variant (S2-05…S2-12, S2-20); observed choices are `parallel=6`, `-j64` on 64 threads, kcbench's N and N/2 (S3-03, S3-05, S3-15/16). No survey of what desktop users pick. The current `-j8` sits between these and its bracketing `-j4` is an interbench emulation that runs no make (S2-14).
- **Category source.** `ocallahan-atc17` read independently is a DynamoRio build (S1-01); Antfarm (S1-04) is the one paper with a named build's process count and mean lifetime (bash `make -j 20`, 815 / 748 processes, > 2 s post-exec); Coetzee names `cp` and `mkdir` (S1-02).
- **DKMS.** dkms 3.1.8 runs `make -j$(nproc) … -C <ksrc> M=<dir>` from the kernel hooks or `dkms.service` (S2-12); four real `make.log`s carry objects only (S3-10). Nothing with `-j`, duration or CPU.
- **`cpu-batch`.** interbench Burn is N spinning threads with no finite work (S2-14); CachyOS classes `ffmpeg` Heavy_CPU and `clamd`/`baloo` BG_CPUIO and dropped compiler rules three times (S2-15); encoders, PyTorch and clamd document thread defaults only (S2-18, S2-19, S2-21); the only measured saturating desktop batch populations are Blender's renders (S3-06, durations only) and two full `clamscan` runs (S3-13, durations only).

## The venue question (new)

- The existing observation is four-vCPU and unpinned; every runner measurement is single-core from now on (9.5 follow-ups decision 3, D21). No pinned build run exists.
- **The only confined-build observation in any class** is rr's `taskset` row (S1-01): the serial build on one core takes 3.36× the `-j8` wall; no process or CPU comparison. No paper, log or benchmark reports a build pinned to one CPU with process counts or CPU totals; kcbench has no `-j1` row (S3-15/16).
- **What the pin does to the tools** (S2-16, S2-23, S4-16): affinity is inherited across fork/exec, so a pinned `make` confines every child; `nproc` returns 1 inside the pin (`make -j$(nproc)` becomes `-j1`; rpm, ninja, DKMS, ffmpeg, x264 follow the mask; dpkg and PTS do not); the workflow's explicit `-j8` is unaffected; make applies no load limit without `-l`.
- **What a pinned runner can observe under the given tooling** (S4 synthesis): the runner's kernel config has every instrument's requirement built in (taskstats, delay accounting, BSD accounting, PSI, schedstats, BPF, proc connector — S4-04); per-process CPU at exit for every process, ms-lived ones included, from taskstats (listener on the pinned CPU's cpumask) or BSD accounting; blocked-on-I/O only from delay accounting; per-schedule run/wait from `perf sched timehist -C <cpu>` (needs sudo; volume and overhead on one CPU unquantified); the current CLI workflow's forkstat + 0.5 s `/proc` sampler answer none of the I/O-wait, dispatch-distribution or within-process questions, pinned or not, and no document says how the sampler's censoring changes when the build is time-shared on one CPU. `Runner.Listener`/`Runner.Worker`, a "Hosted Compute Agent" and a Docker server share the machine; sudo can move user processes and root services, not kernel threads; whether the agent is movable is undocumented (S4-22, S4-15). Two Xeon models appear under one label with a 26 % single-thread spread (S4-19), so the CPU model is logged per run.
