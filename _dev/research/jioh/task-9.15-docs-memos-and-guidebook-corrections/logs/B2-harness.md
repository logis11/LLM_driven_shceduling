## Decisions

1. **mock-chain and the seam records widened the answer's fixture list** (Outcomes): the reference simulator blocks every WAIT-first task, a LOOP's body counting, and the dataset reads "first instruction" the same way (`_first_executed`).
2. **The arrival step's line order for a TIMER-first task: `ready(arrive)`, then `ready(timer_tick)`, both before the first `run_start`** (`mock-media` both players, `mock-chain`'s `input`). It is the order the mock generator writes (stimuli `arrive` then `timer_tick` at the arrival instant). The reference simulator writes only `ready(arrive)` there today (the zero-wait line is owed, metrics §11 item 1), so it fixes no order; the records do not depend on it (both lines pair with the same `run_start`, and rows sort by cause).
3. **`music`'s tick-0 `ready_wait` is 6667, not 0:** the line falls at the arrival, outside any occupancy, so §6.1 pairs it with the next `run_start` (6667). The zero-wait reading applies inside an occupancy only.

5. **The generator's WAIT-first test covers a spawned child** (`test_a_wait_first_task_blocks_in_its_arrival_step`: a woken child runs at its wake and exits; an unwoken one writes `task_arrive` alone and gets `completed` 0, `cpu_delivered` 0, no `arrive` row; no record message). `test_same_instant_order_is_config_arrivals_then_the_rest`'s second case moved its added wake from 1 to 501: with no run at the arrival, a run closing at the same instant needs the 500 µs wake's run (500 → 501).
