## Decisions

1. **A stored wake's `ready(wake)` line is written at the arrival beside `ready(arrive)`, the WAIT-first task's own one included.** The row says the mock writes `ready(arrive)` as the reference simulator does; it does, and the wake that completed the arrival WAIT also gets its line. Reasons: metrics §11 item 1 gives every completion of a blocking primitive a `ready` line, at zero wait when it did not block, and the mock already writes it where the reference simulator does not yet (the leading TIMER's tick-0 line beside `ready(arrive)`, B2's decision 2); and the primitives pair each `ready(wake)` line with the next WAIT in program order, so without it the pairing shifts by one. Checked: with that one line left out (a scratchpad copy), the records build of the new test's workload gives "chain head: tail stage completed 3 iteration(s) for 4 consumed head tick(s)" and, for an `input` wake, "task once: 0 input ready(wake) line(s) for 1 input wake event(s)"; with it, no message. Metrics §11 item 5 (P2) states the reference simulator's `ready(cause = arrive)` and leaves the zero-wait line to item 1, which is the same reading. The reference simulator writes no zero-wait line yet (item 1; the RQ0 gate spec's `simulator-conformance` item (a)), so on it this case would trip the same two guards — one more instance of item (a), not a new item.
2. **Every wake sent before a task's arrival is stored, whatever the task's first instruction.** HEAD wrote such a wake's lines before the task's `task_arrive` line, a trace no executor can write. One rule: stored, then taken in the arrival step. For a task not WAIT-first, its stored wakes' lines sit beside `ready(arrive)`; the mock does not model when a later WAIT takes them, as it models no program after the first instruction.
3. **The mock's store is by target, not by channel.** The reference simulator keeps an external wake on its channel, completing the first WAIT on that channel; the generator pairs every wake with its `target` and ignores channels throughout (fixtures README item 2's depth: wakes complete the next WAITs), so a stored wake on another channel of the task counts here too. Stated in the docstring and the mocks README ("whatever its channel"). The dataset's channels are per task (`input:<task>`, `timer:<task>`, `job:<task>`), and no artifact has a wake before its target's arrival, so no trace depends on it.
4. **"Before" is strictly before.** A wake at the arrival's instant is not stored: a pinned wake comes after the arrival at the same µs (the loader's pass order), and a WAKE follows its waker's RUN. Unchanged from HEAD: the hand workload's chain stage, arriving at 0 with its head, still has `ready(wake)` at 0 and no `ready(arrive)`.
5. **The instructions after a completed arrival WAIT are not modelled.** The arrival is a stimulus, as the existing rule's "first run is the wake that completes that WAIT" assumes a RUN follows the WAIT; the reference simulator writes `ready(arrive)` only when `step` reaches a RUN. Every WAIT-first program in the core set is a WAIT then a RUN or a lone WAIT (N3, B2's review); the fixtures README item 4 states the RUN condition for the reference simulator.
6. **The version is bumped though no dataset or fixture trace changes.** The generator's output changes for a workload with a wake before its target's arrival, and a cache entry for such an input would be served stale under `@1`; the brief asks the bump whenever the output can change.
7. **No fixture re-derived.** The fixture traces are hand-written and replayed, not generated, and none has a wake before its target's arrival (scan below); `test_replay_returns_each_fixture_trace_byte_for_byte` and `test_records` pass unchanged.
8. **B2's review finding 2** (the count-0 LOOP skip in `_first_op` has no test) is left: no row carries it and the fix does not touch `_first_op`. Noted for 인지오 below.
