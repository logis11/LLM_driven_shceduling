## Topics

- **T1 Interaction-latency thresholds.** What published human-factors work states as the response-time limit below which a user perceives an interface's reaction to an input as immediate (keystroke echo, control activation, direct manipulation), with the value, the task, the population, and whether the value is an experimental measurement, a guideline, or a restatement of an earlier source. Includes Miller, "Response time in man-computer conversational transactions" (AFIPS FJCC 1968); Nielsen, *Usability Engineering* (1993), ch. 5, and the author's excerpt "Response Times: The 3 Important Limits"; Shneiderman, "Response Time and Display Rate in Human Performance with Computers" (ACM Computing Surveys 16(3), 1984); and any later measured thresholds (touch, keyboard or pointer latency perception studies).
- **T2 A textbook MLFQ's worked example.** In Arpaci-Dusseau & Arpaci-Dusseau, *Operating Systems: Three Easy Pieces*, chapter "Scheduling: The Multi-Level Feedback Queue" (pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched-mlfq.pdf): the number of queues, the time slice, the per-level slice growth, the priority-boost period and the allotment rule used in its examples and figures, with the text's own remarks on how these values should be chosen; the version of the chapter read. Also any lecture notes by the same authors on the Solaris time-sharing dispatch table.
- **T3 Shipped scheduler time-slice defaults.** For each of: Linux CFS (`sched_min_granularity`, `sched_latency`) and EEVDF (`sched_base_slice`) in `kernel/sched/fair.c`; sched_ext's default slice constant (`include/linux/sched/ext.h` or `kernel/sched/ext.c`); the illumos/Solaris time-sharing class's default dispatch table (`ts_dptbl.c`: levels, quanta, aging period) and its man page `ts_dptbl(5)`; MINIX 3's scheduler quanta and priority aging; the scx schedulers `scx_lavd`, `scx_bpfland`, `scx_rusty` — the value, its unit, whether it scales with CPU count or clock rate, and the tag or commit it was read at.
- **T4 Lottery scheduling's quantum and class shares.** In Waldspurger & Weihl, "Lottery Scheduling: Flexible Proportional-Share Resource Management" (OSDI 1994): the scheduling quantum used, and whether the paper states any ticket ratio between classes of work (interactive versus batch or background).
- **T5 Per-class CPU bandwidth ceilings.** Linux CFS bandwidth control (`Documentation/scheduler/sched-bwc.rst`): what it limits, over what period, on what entity, and its defaults; any other shipped per-class CPU ceiling (e.g. `SCHED_DEADLINE` bandwidth, RT throttling).
- **T6 Starvation bounds in shipped schedulers.** What bound, if any, shipped schedulers state on how long a runnable task may wait: sched_ext's watchdog timeout, Linux RT throttling (`sched_rt_runtime_us`, `sched_rt_period_us`), the deadline server for fair tasks (fair server), illumos TS's `ts_maxwait` / `ts_lwait` aging — with the value and unit.
- **T7 Missed periods in periodic real-time and media tasks.** How periodic-task tools and players treat an activation that arrives after its period has passed — accumulate a backlog, skip to the next period, or re-anchor — in rt-app (`timer` event, its `mode` options), interbench's emulated audio and video loops, and at least one media player's frame scheduling (mpv, VLC, or GStreamer's video/audio sinks), with the code or documentation passage.
- **T8 Tail-latency and scheduler benchmark reporting.** What schbench reports and which percentiles each version prints (the git.kernel.org `mason/schbench` repository and its tags, and the GitHub `masoncl/schbench` repository); what hackbench (rt-tests) reports and its defaults; whether stress-ng has a stressor that emulates timing of real work; what interbench reports per task and whether it states a jitter-perception threshold and where that value comes from.
- **T9 Declared background scheduling classes.** How a stock Linux scheduler treats a task running under `SCHED_IDLE` or at nice 19 beside default-policy tasks (weights, preemption, wake-up latency), per the kernel documentation and source; and whether desktop indexers, backup and scan tools ship with such a declared class by default (unit files, source code).
- **T10 The statistics methods.** In Brodersen, Ong, Stephan & Buhmann, "The Balanced Accuracy and Its Posterior Distribution" (ICPR 2010); Chicco & Jurman, "The advantages of the Matthews correlation coefficient (MCC) over F1 score and accuracy in binary classification evaluation" (BMC Genomics 2020); Field & Welsh, "Bootstrapping Clustered Data" (JRSS-B 69(3), 2007); Dietterich, "Approximate Statistical Tests for Comparing Supervised Classification Learning Algorithms" (Neural Computation 10(7), 1998): the definitions and the scope limits each gives for balanced accuracy, the Matthews correlation coefficient, the cluster bootstrap, and paired comparison of two classifiers on one test set.
- **T11 CI observability.** Whether a GitHub Actions hosted runner can observe any of the above on its own kernel: the running kernel's version, CPU count, and effective CFS/EEVDF base slice (debugfs `sched/base_slice_ns` or sysctl), whether sched_ext is available, RT throttling and fair-server values, and how a `SCHED_IDLE` or nice-19 CPU hog shares one CPU with a default-policy periodic task (wake-up latency of the periodic task with and without the hog).

## Record format

Each reader writes `search/S<k>-<class>.md`:

1. **Search log** — one row per query: date, engine or venue, exact query terms, hits followed, dead ends (with the HTTP status).
2. **Candidates** — per candidate: a provisional id `S<k>-NN`; full citation; copy read (URL or commit, version, date accessed, local path under `sources/<id>/`, SHA-256 of the file fetched); verbatim passages with locators (page, section, figure, slide, `file:line` at a commit); coverage per topic T1–T11 — covers (naming the object, unit, statistic, scope and population) or does not cover; whether it is one observation (one population, trace or run) and whether machine, subject and window are named.

Source copies go to `sources/<id>/` under the task folder (gitignored; they do not survive the clone). The record must be self-sufficient: everything a reader needs is in the quoted passages and the copy identification, never "see the local file". Verbatim means verbatim; a passage that cannot be quoted is not a passage.
