**Reader's evidence** (R01 C-interbench-1; re-read at `interbench/interbench.8:81-87`):

Missed periods are skipped, not run later.

### C-interbench-3 — X task

**Evidence**, `interbench/interbench.8:76-79`:
> "X is simulated as a thread that uses a variable amount of cpu ranging from 0 to 100%. This simulates an idle gui where a window is grabbed and then dragged across the screen."

`interbench.c:530-554` (opened myself):
```
 * We emulate X by running for a variable percentage of cpu from 0-100% 
 * in 1ms chunks.
...
		for (i = 0 ; i <= 100 ; i++) {
			j = 100 - i;
			deadline = periodic_schedule(th, i * 1000, j * 1000,
				deadline);
			deadline += i * 1000;
```
R01 reading (c): "Variation rule: deterministic linear ramp from 0% to 100% in 1-percentage-point (1 ms) increments, then restart at 0 (sawtooth); no randomness … each step occupies a ~100 ms window whose busy share is `i`% … Input events: the docs mention no input events and the code has none; wakeups are purely deadline/timer driven". R01's ideal-machine model gives ≈10.1 s per sweep with ≈50% average CPU. I checked the step arithmetic against `periodic_schedule()` (interbench.c:378-458) and agree.

My derivation, for context only: over a sweep, each busy share 0…100% occupies one ~100 ms window, so the time-marginal of the share is (discretely) uniform on [0, 1], and its mean of 0.5 matches the ≈50% average. What the source does not have is independent per-iteration draws, a window tied to an input gap, or input-driven wakeups.
