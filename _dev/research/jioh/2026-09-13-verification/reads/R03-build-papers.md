## ocallahan-atc17

### C-ocallahan-1 — kernel-build workload: what it builds, configuration, process count and lifetimes, next workload

**Verdict: PREMISE NOT IN SOURCE.** The paper has no kernel-build workload. Its build workload, named *make*, builds **DynamoRio 6.1.0** with `make -j8`. The count (2430 processes, "mostly short-lived") and the next workload (sambatest, 89) belong to that DynamoRio build.

(a) Verbatim, ATC '17 proceedings, §4.1 "Workloads", printed p. 383 (PDF p. 8), left column (text confirmed against page render):

> "Benchmarks were chosen to illuminate RR's strengths and weaknesses, while also containing representatives of real-world usage. They were tuned to fit in system memory (to minimize the impact of I/O on test results), to run for about 30 seconds each (except for cp where a 30s run time would require it to not fit in memory)."

> "make builds DynamoRio [8] (version 6.1.0) with make -j8 (-j8 omitted when restricting to a single core). This tests potentially-parallel execution of many short-lived processes."

(Reference [8] = "D. Bruening, Q. Zhao, and S. Amarasinghe. Transparent dynamic instrumentation. In Proceedings of the 8th International Conference on Virtual Execution Environments, March 2012.")

> "All tests run on a Dell XPS15 laptop with a quad-core Intel Skylake CPU (8 SMT threads), 16GB RAM and a 512GB SSD using Btrfs in Fedora Core 23 Linux."

§4.3 "Observations", p. 383, right column:

> "Overhead on make is significantly higher than for the other workloads. Forcing make onto a single core imposes major slowdown. Also, make forks and execs 2430 processes, mostly short-lived. (The next most prolific workload is sambatest with 89.) In-process system-call interception only starts working in a process once the interception library has been loaded, but at least 80 system calls are performed before that completes, so its effectiveness is limited for short-lived processes."

The next workload listed after *make* in §4.1 is *octane*:

> "octane runs the Google Octane benchmark under the Mozilla Spidermonkey Javascript engine (Mercurial revision 9bd900888753). This illustrates performance on CPU-intensive code in a complex language runtime."

Table 1 "Run-time overhead", p. 384 (PDF p. 9): row `make 20.99s 7.85 × 11.93× 3.36× 11.32× 14.36× 7.84× 10.97×` (baseline duration 20.99 s).

Same wording in arXiv:1705.05937v1 §4.1 (p. 11; reference number is [11] instead of [8]) and §4.3 (p. 12). In the predecessor arXiv:1610.02144v1, §4.3 (p. 7) reads: "Also, make creates many short-lived processes; it forks and execs 2430 processes. (The next most prolific workload is sambatest with 89.)"

(b) Locators: ATC '17 §4.1 and §4.3, printed p. 383; Table 1 p. 384. arXiv 1705.05937v1 §4.1 p. 11, §4.3 p. 12. arXiv 1610.02144v1 §4.1 and §4.3 p. 7.

(c) Plain reading: the build workload is a parallel `make -j8` build of the DynamoRio 6.1.0 source tree (a dynamic binary instrumentation framework), not the Linux kernel. No `.config`/kernel config exists because no kernel is built. Unit of the count: processes forked and exec'd by the whole *make* run, one number, no run-to-run spread given; population = that DynamoRio build on the 4-core/8-thread Skylake laptop (Fedora 23). "mostly short-lived" is qualitative — no threshold or fraction is given. "The next most prolific workload" refers to process count among the five benchmarks (sambatest: 89 processes). The next workload in listing order after *make* is *octane* (no process count given for it). The "about 30 seconds" tuning applies to the benchmarks in general; *make* baseline was 20.99 s.

## coetzee-arxiv12

### C-coetzee-1 — what §9 (or elsewhere) says about the Linux kernel build's processes, their number and lifetimes; is it specific to that build

**Verdict: FOUND** — qualitative only: no numeric process count and no lifetime values.

(a) Verbatim, arXiv 1203.2704v1, §9 "Preliminary experimental results", p. 9, left column (confirmed against page render; *make*, *cp*, *mkdir* are italic in the PDF):

> "Three prototype build systems were constructed.
> In the first, a ptrace-based prototype that could only perform full builds, a pessimistic locking scheme was used where build processes took locks on any files they accessed. […] Given enough concurrent processes, this build scaled to 85% the time of a parallel make build of the Linux kernel. However, it was not a complete system, as it was unable to handle unexpected new dependencies, could not perform incremental builds, and inferred its list of processes to execute from a prior make run, making it necessary to rerun the make build whenever this process sequence was changed."

> "The major performance bottleneck in this prototype was the necessity for the central build monitor process to sequentially handle all ptrace messages. A variant of this prototype used binary rewriting based on Jockey [12] to track system calls without the use of ptrace. Jockey rewrites binaries at load time by searching for system calls, and also keeps a cache of patches to apply for binaries it's seen before. In practice, even with caching, the system added too much overhead to be practical due to the Linux kernel build's enormous number of short-lived processes like cp and mkdir. This is less likely to be an issue in a more monolithic build system."

(The "[…]" marks omitted sentences, not an in-quote change.)

Related general (not kernel-specific) statement, §5.2 "System call interception", p. 6:

> "Binary rewriting suffers from a different performance issue: load-time rewriting is too expensive for short-lived processes, necessitating on-disk caching of instrumented binaries."

Other mention of the Linux kernel build, §2.2 "Selecting a resource space", p. 3 (about configuration header, not processes):

> "For example, the Linux kernel build has a single header containing all configuration options which is included by all source files. In order to make incremental builds useful in the event of configuration option changes, the Linux build tracks each option as a separate resource."

TR version (UCB/EECS-2012-27): §9 text identical (printed p. 9, PDF p. 11). A line-by-line diff of arXiv v1 vs TR body text shows only cover/copyright-page, footnote line-wrapping, and hyphenation/URL-wrapping differences.

(b) Locators: arXiv 1203.2704v1 §9 p. 9 (first prototype + Jockey variant paragraphs); §5.2 p. 6; §2.2 p. 3. TR EECS-2012-27 §9 printed p. 9 (PDF p. 11).

(c) Plain reading: the statement is made about the Linux kernel build as the workload of the authors' first (ptrace-based) prototype and its Jockey binary-rewriting variant. It says the kernel build has an "enormous number" of processes and that they are "short-lived", with `cp` and `mkdir` as examples. It gives no count, no lifetime figure, no kernel version and no config. It is specific to that build in that it names "the Linux kernel build's" processes. The authors add a scope caveat that the problem "is less likely to be an issue in a more monolithic build system". The general link between short-lived processes and load-time-rewriting cost is also stated in §5.2 without reference to the kernel. The 85% figure is the prototype's build time relative to a parallel make build of the kernel, not a process statistic.
