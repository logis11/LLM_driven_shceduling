## D2 — the unit: one make job as a per-role process chain (2026-09-17)

By 인지오's decision, scope-card item 12 (with items 1–5, 10, 13, 17, 20 depending on it): a spawn-table child of `build-orchestrator` is one make job, modelled as the chain of processes the job runs, one task per process with its own role, lifetime and CPU — for a plain C object `sh` (spawned by `make`) → `gcc` driver → `cc1`, `as` → optional `objtool` → `fixdep` → `rm`; a sub-make per directory; `modpost`/`modfinal` as later sub-makes. The parallelism cap counts jobs (shells), as make's jobserver does. Grounds for the unit over `cc1` alone: every source the slice has names the flood of short-lived processes as the trait that makes a build a scheduler workload — S1-01 (`ocallahan-atc17` §4.3, "2430 processes, mostly short-lived", a DynamoRio `make -j8`), S1-02 (`coetzee-arxiv12` §9, the kernel build's "enormous number of short-lived processes like cp and mkdir"), S2-13 (autogroup commit 5091faa449ee, "parallel kbuild has a negative impact on desktop interactivity"), S2-15 (CachyOS dropping compiler rules: "every process which gets spawned") — and `cc1` alone keeps ≈ 93 % of the CPU (S3-01: `cc1` 6 013 ms against `gcc` 44, `as` 122, `sh` 107, `fixdep` 81, `make` 54 ms in one second) while discarding the population; over the pooled family member (the current unit): the same population with per-role statistics instead of a two-cluster mixture with censored helpers, and a cap that counts what make counts (memo B3). Structure is a source claim from the programs' own source: S2-01 (kbuild v6.6 `scripts/Makefile.build:146–161, 224–243`, `scripts/Kbuild.include:160, 203–216`, `scripts/link-vmlinux.sh`), S2-02 (GCC 13.2.0 `gcc/gcc.cc:1429–1442, 1287–1292`: `cc1` then `as`, pipe-connected only with `-pipe`; `collect2` at user-space links only), S2-03 (GNU make 4.4.1 `src/job.c:1830–1889, 2709–2850`, `doc/make.texi:4079–4083, 5117–5125`: one shell per recipe line, forced by kbuild's `set -e;`, N jobs across all sub-makes, `vfork`), S2-04. Under phase decision 2: every value and every structural fact of the archetype comes from one observation, a pinned single-core run with exit-time accounting whose records (comm, parent id, start and exit, CPU, block-I/O delay per process) exhibit the roles, nesting, order, counts and concurrency by themselves; the source reads name and explain what the run shows and generalise the structure, and are not observations; the test is that removing them changes no value and no structure. The run wins any disagreement with the reading (`-pipe` overlap, objtool, sub-make count): a role the run does not exhibit is not in the chain, a value the run cannot measure is a labelled placeholder, never a literature figure. S3-01/S3-02 (Gregg's one-second `perf sched` capture, Xeon E5-2680 v2, kernel 4.10, 2017, build unnamed) is cited in `modeling_notes` only as corroboration that the same roles carry the same relative weight on Linux, no number transcribed (the treatment 9.5 D24 gave display literature). `category_source` corrects to what S1-01 and S1-02 say: a parallel make build spawns many short-lived processes; the kernel-build attribution and "compiler children" leave.
