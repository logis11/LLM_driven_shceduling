# S8 — display refresh and GPU: what the runner's Xvfb venue changes on the CPU side (follow-ups spec decision 12)

Search 2026-09-16, the four classes of phase decision 4. Two questions, in the neutral form of the topic list: (Q1) how a real vertical refresh and GPU offload change a desktop application's CPU-side wake rate, run lengths and paint cadence on Linux, against a venue with no refresh and software rasterisation; (Q2) what a compositor does per frame on a real GPU desktop. Output allowed by the spec: cited direction-and-magnitude sentences in the scope of the display-paced archetypes (`video-player`, `video-editor`, `web-browser`, `code-editor`, `video-call`) and a hand-off to 9.9; no archetype value changes (phase decision 2).

**KWin (Q2).** Zahorodnii 2020: compositing "should start immediately right after a vblank"; "Compositing won't be synchronized to vblanks" when buffer swaps do not block, "which is typical with Mesa drivers"; the proposed RenderLoop schedules from "a desired latency level that comes from a config" and "the duration of previous compositing cycles", "the one with the longest render time is used for scheduling compositing for the next frame". ## 3. Coverage against the two questions

**Q1, direction per archetype (from the toolkit sources; magnitudes not available):**

- `web-browser`, `video-call`, `code-editor` (Chromium): without display vsync the compositor is driven by the 1/60 s default timer, so the *period* of the compositor cadence measured under Xvfb is the period of a 60 Hz display; the difference on a real display is phase alignment to vblank, which changes when in the frame the compositor wakes, not how often. GPU offload: with `--disable-gpu` rasterisation and compositing run on CPU threads inside the tree (D15 records this could not be separated), so on a GPU desktop those threads' run lengths would be shorter by the raster and composite work the GPU takes; no source gives the size for these applications. Direction: measured run lengths of the compositor and raster threads are an overcount; wake period unchanged.
- `video-editor` (Kdenlive, Qt Quick on llvmpipe): the render loop paces on a blocking swap; llvmpipe's swap does not block, so a changing scene renders unthrottled. Direction: the measured wake rate of the rendering path is an overcount against a vsync-throttled real display (the llvmpipe threads themselves are already excluded, D15; Kdenlive's own threads that feed them are not), and run lengths carry software rasterisation a GPU would take. Magnitude: unknown; the only in-hand number is that the excluded llvmpipe threads carried 93 % of the driven phase's CPU (D15).
- `video-player` (mpv `--vo=x11`, default `--video-sync=audio`): frames are paced on the audio clock, not on a display, on any venue; the x11 output has no hardware acceleration by definition. Direction: no cadence distortion from the missing refresh; the frame's copy to the X server is CPU work that a GPU output (`--vo=gpu`) would move, magnitude unknown.

**Q2:** no source found that states a compositor's per-frame CPU cost on a GPU desktop; KWin's and Mutter's developers describe the schedule (start after vblank, one clock per monitor, render-time estimates) qualitatively. Hand to 9.9 as "not found, with the two developer write-ups as the nearest description of the schedule".

**Not found in any class:** a measurement of a Linux desktop application's CPU-side wake rate or run lengths with and without a real display or GPU. Class 1 terms tried: items 1–4 above; class 3: item 11.
