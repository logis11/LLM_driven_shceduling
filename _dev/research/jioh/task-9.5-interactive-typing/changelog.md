## D9 — shape of the six measured archetypes: one task, merged event stream (2026-09-14)

By 인지오's decision: each D2 archetype compiles to one task whose program is one unrolled loop of WAIT then RUN over a merged, pre-sampled event stream of two kinds — input wakes from the timeline's stimulus (D4, D5) and timer wakes from the archetype's measured idle cadence — each RUN drawn from the distribution of its wake's kind. Grounds: the observations found measure CPU per input as a distribution independent of the preceding gap (S1-lorch2003; the fraction-of-gap coupling of today's `burst_fraction` has no source, card item 11), and every observation and toolkit document reports timer-driven wakes beside input — timer messages 35.1 % vs UI 20.3 % of CPU (S1-lorch2003 Table 2), cursor blink, spell, autosave, paint and mail-check timers (S2-01…S2-06, S3-firefox-profiles). A task is one sequential program (interpretation-contract §3), so the merge is compile-time. Consequences: the campaign measures two phases per application — idle (no stimulus: timer cadence and per-tick run) and driven (replayed stimulus: per-input run) — and states the rule that attributes a wake to an input event; an unfocused application wakes on its timers for the whole segment instead of compiling to one silent WAIT, which changes every file's background demand (to 9.10 and 9.14); the recognizer-visible name multiset is unchanged. Alternatives not taken: two tasks per application via a constructor (adds a constructor-emitted name per editor); input-only loop with a measured burst (drops the timer wakes every observation reports). No value changed by this entry.

## D13 — the per-input run is the window rule (2026-09-15)

By 인지오's decision, closing method §5: `input_run` of a measured interactive archetype is rule (b) — all CPU run time of the application's process tree from a replayed input's send time until the next input, minus the idle phase's CPU rate over that span (`analyze.py` "window minus idle"). Campaign (`campaign/results.md`, runs 34839671173 and 34952672412): median per-input run under (b) — Writer 2.84 ms, VS Code 23.0 ms, Thunderbird 5.04 ms, Chrome 0.76 ms; rule (a) first-wake schedule-in 0.07–0.37 ms and rule (c) X-server-woken schedule-ins 0.54–2.61 ms undercount the follow-up work on other threads (VS Code's renderer and compositor carry the 23 ms). Under D9 the input wake's RUN is drawn from the (b) distribution; timer wakes come from the idle phase per thread comm. Consequence stated in scope: non-timer work inside a long gap (autosave after typing) is charged to the preceding input. Amended at fold-in (2026-09-15): the net value is bounded below at zero — a window quieter than the idle rate carries no input work, and a negative run is not physical; the linter rejected the unbounded tables (VS Code p1 −2.6 ms; Chrome p1–p25 negative, since Internet Explorer's sparse stream leaves windows of seconds). After the bound: Writer p50 2.84 ms, VS Code 23.0 ms, Thunderbird 5.04 ms, Chrome 0.76 ms with p1–p25 = 0. No archetype value changed by this entry; values land at fold-in.
