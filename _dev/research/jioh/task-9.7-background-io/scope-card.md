## What the source is, as one observation

`meas-ci:cli:3` is one dispatch of `.github/workflows/meas-cli.yml` (then unpinned): five repeats on 4-vCPU `ubuntu-latest` runners, release `meas-ci-2026-08-28`. For this slice it ran, per repeat: `wget` of `linux-6.6.tar.xz` from cdn.kernel.org (0.6–4.7 s; no mirror fallback fired); `tar -xf` (tar + xz); `tar -cJf` of the tree; `rsync -a` of the kernel tree warm, then cold after `vm.drop_caches=3`; `sudo updatedb` (plocate, whole filesystem) warm and cold; `freshclam` (failed, DB of unrecorded provenance — meas-report §3.1) and `clamscan -r -i Documentation` warm and cold; and a best-effort 300 s `tracker-miner-fs-3` under `dbus-run-session` with a copy of `Documentation` under a fake `$HOME/Documents`, which did not index it. Instruments: forkstat (whole-second timestamps, 1 ms durations, documented event loss under load) and `proc_sampler.py` at 0.5 s with the main thread's voluntary-switch counter and the whole process's CPU ticks. Each archetype's numbers are assembled from more than one program's phase: `io-stream` from rsync's three-process cold duty and (in prose) tar + xz; `background-crawler` from the idle miner's wakes and `updatedb.plocate`'s cold duty, with `clamscan`'s foreground duty as the contrast; `network-bulk` from two of five `wget` runs. The block and chunk granularities (3 ms, 1 ms) and every sigma are convention. Machine: two Xeon models under one runner label across repeats (9.3); disk type and link unrecorded.

## Stage 2 topics

Neutral form, for the readers (`search/input.md` carries them verbatim). Each is searched in the four classes of phase decision 4. Readers do not see the values above.

- **T1 Bulk file streams on Linux.** For programs that stream a large file set through the disk — a recursive copy (`rsync`, `cp`), a deduplicating backup (`borg`, `restic`), an archiver or compressor (`tar` with `xz`/`zstd`, `7z`) — any observation of the process's CPU share of wall time, its on-CPU run lengths between I/O waits, its time blocked on I/O, warm against cold page cache, and its process and thread structure (rsync's generator/sender/receiver, borg's single process with threads, 7z's worker threads); how each program paces itself as its source and documentation describe it (buffer and block sizes, `fsync`, `O_DIRECT`, `posix_fadvise`, bandwidth limits, `nice`/`ionice` self-setting).
- **T2 A file indexer's everyday behaviour.** For GNOME Tracker Miners / LocalSearch, KDE Baloo and plocate's `updatedb`: how the daemon decides when to work (inotify-driven, periodic crawl, timers, throttling, idle-only and AC-only conditions), what its process and thread structure is, which scheduling class it sets on itself, and any observation of its CPU per wake, wake cadence, I/O wait and duration in steady-state monitoring of a settled home directory (as distinct from a first full index, which is not this topic); how the daemon is made to index a given directory in a non-session environment (configuration keys, CLI).
- **T3 Bulk network transfer.** For a client downloading a large file (`wget`, `curl`, `aria2c`), a game client fetching a depot (Steam), and a mail client sending a message with an attachment (Thunderbird over SMTP): any observation of CPU per received or sent chunk, the CPU share of wall time, the wake structure against the socket (bytes per wake, wakes per second, receive buffer sizes), decompression and disk-write work done per chunk, process and thread structure, and throughput ranges on consumer links; documentation of chunking, buffering, multi-connection and rate-limiting behaviour, and of the process names the work runs under.
- **T4 On-demand antivirus scans.** For ClamAV's `clamscan` and `clamdscan` and comparable Linux scanners: whether an on-demand scan throttles or paces itself, what its documentation and source say about threading and I/O pattern, and any observation of its CPU share over a scan.
- **T5 Shipped treatment of background I/O work.** How shipped software classifies and prioritises these loads: the `nice`, I/O class and scheduling policy the indexers and `updatedb` set on themselves or receive from their systemd units; what process-treatment catalogues (ananicy rule sets, distribution defaults) assign to copy, backup, download, torrent and scanner processes, and whether any of them distinguishes work the user started from work started for them; any timing or rate value such a catalogue carries.
- **T6 Background I/O loads as a scheduler workload.** How scheduler evaluations and benchmarks characterise a background disk or network load next to interactive work — interbench's Write and Read loads, Kolivas-era interactivity tests, `fio`-style loads in scheduler papers, EEVDF/CFS discussions of I/O-bound tasks — with any reported CPU, run/wait or throughput figures; what the literature says such a load does to interactivity and why.
- **T7 Public traces and datasets.** Any public trace or dataset with per-process CPU and I/O of desktop background jobs on Linux (system-monitor logs, `atop`/`collectl` archives, bug reports with `perf` data for Baloo, Tracker or rsync, published rsync/borg/7z benchmark logs with CPU %, Steam download logs with throughput), and what fields each carries.
- **T8 CI observability under a single-core pin.** Given a GitHub Actions hosted runner (4 vCPUs) on which the load is confined to one CPU with `taskset` while the instruments run on the other CPUs (the tooling is quoted in `input.md`): for a copy, a backup, an archiver run, an indexer daemon, `updatedb`, a downloader, a mail send and an on-demand scan, whether the runner can observe per-process CPU at exit, lifetime, time blocked on I/O, per-schedule run and wait with wakeup events, and the wake structure against the socket (taskstats delay accounting and its `blkio` delay, BSD process accounting, `perf sched record` / `timehist`, `perf trace`, `strace`, BPF exit/exec/block-I/O tracing, cgroup PSI); what the runner's disk (type, tier, `rotational`) and network (link class, bandwidth shaping with `tc netem`/`tbf`, a local HTTP or SMTP peer on the harness CPUs) allow, and how a consumer-class link or disk could be emulated on it; how a session-less indexer daemon can be made to index a directory there and how an SMTP send and a depot-style multi-connection download can be driven without external accounts; what the pin does to each instrument and to multi-process loads such as rsync; what the runner cannot observe (a consumer link, a user's home, desktop-class storage).
