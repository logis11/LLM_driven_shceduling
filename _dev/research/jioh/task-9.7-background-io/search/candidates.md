## Per item

### 1–4. `io-stream.block_cpu`, `io_wait` (block grain, duty, spreads)

- No observation gives a copy, backup or archiver's on-CPU run length between I/O waits, or a per-block CPU (S1 Not found T1; S2 Not found T1; S3 Not found T1). The nearest to a run/wait structure is S3-22: `tar cf` of a kernel tree with a `cpudist` off-CPU histogram (mode 64–127 µs) and 38.2 of 50.8 s off-CPU, 18.4 s of it in `read` → `io_schedule`; and S3-13's voluntary-switch counts per borg job (≈ 4 × 10⁵ over 9 min for an initial backup over SSH, 87 for an unchanged run); S3-33 adds one system-wide `atop` interval during `restic backup` (22 % I/O wait, ≈ 18 000 context switches per second).
- Whole-job CPU share on Linux, the quantity the current duty stands in for: rsync 83 % vs cp 54 % on one 10 GiB file, cold cache, three rsync processes (S1-25/S3-16, 2010); `tar cf` 25 % on a kernel tree (S3-22); borg 54 % / 15 % / 92–98 % by RTT and dedup state on a 1-vCPU VPS (S3-13), and on Linux otherwise only fault states and `borg info` (S3-32); restic 297–316 % with 22 threads on a 2-core, 4-thread laptop while re-reading and hashing every file (S3-33, 2016); compressors 99 % single-threaded and 126–2005 % multi-threaded, warm cache (S3-15); xz 0.3–2.2 MB/s on ARM (S1-38). For a many-file `rsync -a` tree on current hardware: none (S3 Not found T1).
- Mechanism, from source: rsync 3.4.1 — three processes (sender → forked server → generator/receiver), 32 KiB I/O buffers, 256 KiB sender map window and receiver write buffer, block size 700 B to 128 KiB by file size, `--bwlimit` sleeps only when the accumulated delay is ≥ 100 ms, fsync only with `--fsync`, no fadvise or `O_DIRECT` (S2-01, S2-02); cp 9.7 — 256 KiB buffer, `POSIX_FADV_SEQUENTIAL`, reflink → `copy_file_range` → read/write (S2-03); borg 1.4.1 — 512 KiB–8 MiB buzhash chunks, `POSIX_FADV_DONTNEED` after every read block, 16 MiB `sync_file_range` windows + `fdatasync`, no worker threads (S2-04); restic 0.18 — 2 file readers, GOMAXPROCS blob savers, 16 MiB packs (S2-05), and its write path per its maintainer (≈ 0.9.6): 32 kB blocks to the OS, up to one pack per CPU in flight, a flush after each pack (S3-33, #2679); 7-Zip `mt=on` by default, xz multithreaded by default since 5.6.0, zstd `-T1` CLI default, tar 10 KiB records (S2-06…S2-09). None of the eight sets `nice`/`ionice`/`SCHED_IDLE` on itself (S2 row 51).
- Own measurement under the pin (S4 synthesis): per-process CPU and elapsed at exit for every process of the copy (all three rsync processes inherit the mask, S4-15, S4-26) from taskstats (S4-05) with `kernel.task_delayacct=1` set before the phase (S4-06); blocked-on-I/O per process from `blkio_delay_total` (synchronous block I/O only, S4-05), per request from `biosnoop`, system-wide from `io.pressure` (S4-12, S4-13); per-schedule run and wait with wakeups from `perf sched timehist -w` on the measured CPU (S4-09); warm/cold by `sync; drop_caches=3` (S4-24). A runner disk that is documented only as "SSD" (S4-01), with `io.max` caps or `dm-delay` as the only slow-disk emulations (S4-13, S4-24).

### 5–7. `sampling`, `pattern`, `lifetime` of `io-stream`

- The RUN/WAIT alternation at a fixed grain is a design; the only observation of an alternation is S3-22's off-CPU histogram for `tar` (thousands of sub-millisecond waits per second, not a 10 ms wait per 3 ms of CPU). The pipeline structure of rsync — three processes "delayed only when the pipelines stall or when waiting for disk I/O or CPU resources" (S2-02) — becomes a strict alternation on one CPU (S4 synthesis).

### 8. `validation_stats` (tar/xz/rsync duty; "throughput absolutes")

- Throughput and CPU % for compressors exist (S3-15, warm; S1-38, ARM); for a tar+xz stream of a file set on current x86 Linux none was found (S3 Not found T1). rsync's throughput ranges and their CPU dependence are S1-25/S3-16's (2010).

### 9–10. `category_source: interbench`, `modeling_notes` wording (Write/Read)

- S1-01 read independently confirms the class description: Write is one process `fwrite`-ing `st_blksize` blocks to a file of MemTotal capped at 1 GB, rewritten continuously, no fsync, `sync()` at the end; Read `read()`s the same file and `lseek`s back; neither is paced (`interbench.c:632–712`, `:1189–1193`). The readme's one sample table is the only published interbench Write/Read result found (S1 Not found T6: Wong et al. 2008 paywalled and by abstract without the disk loads).

### 11. `io-stream` bindings (`borg`, `7z`)

- borg: S3-13 is the one observation with CPU share of a healthy backup (1-vCPU VPS over SSH; local disk-to-disk not measured); S3-32 adds a fault-state `borg serve` at 100 %, one `top` line during `borg info` (borg 20.6 %, ssh 8.3 %, sshfs 5.6 %) and the maintainer's statement that borg uses one core; S2-04 fixes its structure (single process, content-defined chunks, fadvise, `sync_file_range`). The nearest healthy deduplicating backup on a Linux desktop is restic's, not borg's (S3-33: 297–316 %, 22 threads, 2016). 7z archiving a file set with CPU share: none (S3-25 is the in-memory `7z b` benchmark, context; the OpenBenchmarking compress-7zip result S3-36 runs the same `7zz b` and carries no CPU monitor entry); S2-06 fixes `mt=on` and LZMA2 chunking. ananicy files both under `BG_CPUIO` (S2-21). Driving both on the runner: S4-27 (borg/restic init and create with passphrase env vars), S4-22 (`7z -mmt` explicit; `xz -T0` sizes to "the system's" processors, whether it reads the affinity mask not established; `zstd -T0` counts physical cores regardless).

### 12–17. `background-crawler.scan_burst`, `io_wait`, `throttle` (values and spreads)

- No observation of an indexer daemon's CPU per wake, wake cadence or I/O wait in steady-state monitoring of a settled home exists in any class (S1 Not found T2; S2 Not found T2; S3 Not found T2). What exists: settle durations after a metadata change on a settled index — 2 236.9 s at 100 % of one thread for 11 renamed folders at ≈ 197 k files, ≈ 50 s for one directory at ≈ 130 k files, 20–30 s after the fix (S3-01); a maintainer's "≈ 25 % CPU for short periods" as normal (S3-02); extractor burst/back-off "a few seconds … then backs off for a few seconds" (S3-01 #340, qualitative); Baloo's content-indexing CPU 25–40 % of 24 threads with a 140 s flamegraph (S3-03, a first content index of multi-TB mounts, not steady state); updatedb.mlocate 57.8 s CPU over 148 s (S3-19, whole filesystem). Fault states (100 % for hours or days) are the majority of reports (S3-02, S3-14, S3-04).
- Mechanism, from source: tracker-miners 3.7.3 / localsearch 3.8.2 — steady state is inotify (`enable-monitors` default true); a full crawl only after an unclean shutdown by default (`crawling-interval` −1) or every N days; 15 s initial sleep; `throttle` 0–20 → 0–1 000 ms per queue step, +250 ms on battery; pause on low battery; miner plus a separate `tracker-extract-3` process, no worker threads in the miner (S2-10, S2-11). Baloo 6.17 — inotify batched with a 10 ms cache timer and 5–60 s pending timers; no content indexing on battery; one-thread QThreadPool driving a separate extractor process in batches of 40 (S2-14). plocate `updatedb` — single-threaded, io_uring optional, reuses the old database's directory mtimes, daily timer with 1 h random delay, AC power only (S2-12).

### 18–20. `sampling: per-iteration` on a segment-bound loop, `pattern`, `lifetime`

- The daemon's own pacing is event-driven (inotify) with timer batching (S2-10, S2-14), not a fixed burst/wait/sleep loop; a periodic element exists only in the daily `updatedb` timer (S2-12) and in the `crawling-interval` days setting (S2-10). No observation of the resulting wake stream (S3 Not found T2).

### 21. `validation_stats` (updatedb + clamscan duty cycle)

### 22. `category_source: ananicy-rules`

### 25–28. `network-bulk.chunk_cpu`, `net_wait` (chunk grain, duty, spreads)

- No timestamped trace of a downloader's bytes per wake or wakes per second (S1 Not found T3; S2 Not found T3; S3 Not found T3). The Steam client's receive pattern exists as excerpts only (S3-28): seven `recvfrom` calls over ≈ 5 s — an 8-B header and a 6 732-B payload per pair, then EAGAIN and idle periods of hundreds of ms to seconds (Arch, 32-bit client); `recvmsg` returning 516–5 600 B of 65 536 requested, without timestamps, over 15–16 connections at 0.3–1.8 MB/s (Debian 13.6, gigabit); the thread disputes whether the pattern is the client's or the server's. CPU share while downloading on Linux: wget 18.2 % of one core at 58.5 MB/s from a LAN cache (S3-17, one `top` snapshot, Xeon, 2014); curl 0–0.5 % at ≈ 10 MB/s on a one-CPU VPS and 0.3 % at 320 KB/s from localhost (S3-34, 2015); cURL ≈ 70 % under QUIC on a 1 Gbps LAN, lower under HTTP/2 (S1-23); the kernel's per-byte receive cost on a 100 Gbps server (S1-02, context). ### 35. `network-bulk` bindings (`steam` download, `thunderbird` send)

- Steam: SteamPipe splits files into ≈ 1 MB chunks, each compressed and encrypted, delivered over HTTP, decrypted and expanded on the client (S2-17); the client reaches up to 30 sources with an "intended number of connections" of five and per-connection 40–750 Mbps on cloud VMs (S1-22); a user's Linux download at 5–45 MB/s network, 10–30 MB/s disk, CPU attributed to decompression, no number (S3-21). CPU of the `steam` process during downloads on Linux: 341.5 % and 461 % in `top`/`htop` with no rate stated, the work named by a Valve developer as decryption, decompression and delta-patching (S3-31); highest core ≈ 14 % at ≈ 20 MB/s over 15–16 connections, system view (S3-28). A complete public Linux `content_log.txt` (S3-29): per-host rates every ≈ 11 s (median 54 Mbps), connection-count steps to 5 at 67–250 Mbps and to 6 at 215–260 Mbps, and — the reader's computation — ≈ 208 KB and ≈ 68 KB per chunk for two updates at ≈ 204 and ≈ 90 Mbps. Chunks are written by an asynchronous file-I/O thread (S3-30). Valve's client-side pages on download throttling and "downloads during gameplay" are client-rendered and unquotable (S2-17); Linux process names: the ananicy catalogue (S2-21) and `steam` from `ubuntu12_32` in `top`/`htop` (S3-31). Driving without an account: `steamcmd +login anonymous +app_update <appid>` for dedicated-server apps Valve's list marks anonymous (TF2 DS 232250, CS:S DS 232330, HLDS 90, Source SDK 2013 DS 244310, GMod DS 4020), or DepotDownloader (`-os linux`, 8 concurrent chunks by default) (S4-16); SteamCMD's own concurrency is undocumented (S4 Not found 4).
- Thunderbird send: the SMTP client writes caller-sized chunks with drain backpressure and Base64-encodes attachments into 72-column lines (S2-18, dev tip); one SMTP connection per server, QUIT delayed 5 s (S4-17 `mailnews.js`); CPU 10 % / ≈ 60 % of a core during a send, attributed to the progress-bar animation (S3-09, no message size). `-compose … attachment=` opens a window but does not send, and no Mozilla source documents a headless send (S4-17, S4 Not found 3): a scripted SMTP client against `aiosmtpd`/Mailpit on the harness CPUs is the working fallback (S4-29). A send is an upload; every downloader observation above is receive-side.
