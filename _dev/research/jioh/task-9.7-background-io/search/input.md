# Reader input — task 9.7 background and IO, stage 2 search

Given to each class reader verbatim. Readers do not see the repository's current values. Issue #12.

## Topics

- **T1 Bulk file streams on Linux.** For programs that stream a large file set through the disk — a recursive copy (`rsync`, `cp`), a deduplicating backup (`borg`, `restic`), an archiver or compressor (`tar` with `xz`/`zstd`, `7z`) — any observation of the process's CPU share of wall time, its on-CPU run lengths between I/O waits, its time blocked on I/O, warm against cold page cache, and its process and thread structure (rsync's generator/sender/receiver, borg's single process with threads, 7z's worker threads); how each program paces itself as its source and documentation describe it (buffer and block sizes, `fsync`, `O_DIRECT`, `posix_fadvise`, bandwidth limits, `nice`/`ionice` self-setting).
- **T2 A file indexer's everyday behaviour.** For GNOME Tracker Miners / LocalSearch, KDE Baloo and plocate's `updatedb`: how the daemon decides when to work (inotify-driven, periodic crawl, timers, throttling, idle-only and AC-only conditions), what its process and thread structure is, which scheduling class it sets on itself, and any observation of its CPU per wake, wake cadence, I/O wait and duration in steady-state monitoring of a settled home directory (as distinct from a first full index, which is not this topic); how the daemon is made to index a given directory in a non-session environment (configuration keys, CLI).
- **T3 Bulk network transfer.** For a client downloading a large file (`wget`, `curl`, `aria2c`), a game client fetching a depot (Steam), and a mail client sending a message with an attachment (Thunderbird over SMTP): any observation of CPU per received or sent chunk, the CPU share of wall time, the wake structure against the socket (bytes per wake, wakes per second, receive buffer sizes), decompression and disk-write work done per chunk, process and thread structure, and throughput ranges on consumer links; documentation of chunking, buffering, multi-connection and rate-limiting behaviour, and of the process names the work runs under.
- **T4 On-demand antivirus scans.** For ClamAV's `clamscan` and `clamdscan` and comparable Linux scanners: whether an on-demand scan throttles or paces itself, what its documentation and source say about threading and I/O pattern, and any observation of its CPU share over a scan.
- **T5 Shipped treatment of background I/O work.** How shipped software classifies and prioritises these loads: the `nice`, I/O class and scheduling policy the indexers and `updatedb` set on themselves or receive from their systemd units; what process-treatment catalogues (ananicy rule sets, distribution defaults) assign to copy, backup, download, torrent and scanner processes, and whether any of them distinguishes work the user started from work started for them; any timing or rate value such a catalogue carries.
- **T6 Background I/O loads as a scheduler workload.** How scheduler evaluations and benchmarks characterise a background disk or network load next to interactive work — interbench's Write and Read loads, Kolivas-era interactivity tests, `fio`-style loads in scheduler papers, EEVDF/CFS discussions of I/O-bound tasks — with any reported CPU, run/wait or throughput figures; what the literature says such a load does to interactivity and why.
- **T7 Public traces and datasets.** Any public trace or dataset with per-process CPU and I/O of desktop background jobs on Linux (system-monitor logs, `atop`/`collectl` archives, bug reports with `perf` data for Baloo, Tracker or rsync, published rsync/borg/7z benchmark logs with CPU %, Steam download logs with throughput), and what fields each carries.
- **T8 CI observability under a single-core pin.** Given a GitHub Actions hosted runner (4 vCPUs) on which the load is confined to one CPU with `taskset` while the instruments run on the other CPUs (the tooling is quoted below): for a copy, a backup, an archiver run, an indexer daemon, `updatedb`, a downloader, a mail send and an on-demand scan, whether the runner can observe per-process CPU at exit, lifetime, time blocked on I/O, per-schedule run and wait with wakeup events, and the wake structure against the socket (taskstats delay accounting and its `blkio` delay, BSD process accounting, `perf sched record` / `timehist`, `perf trace`, `strace`, BPF exit/exec/block-I/O tracing, cgroup PSI); what the runner's disk (type, tier, `rotational`) and network (link class, bandwidth shaping with `tc netem`/`tbf`, a local HTTP or SMTP peer on the harness CPUs) allow, and how a consumer-class link or disk could be emulated on it; how a session-less indexer daemon can be made to index a directory there and how an SMTP send and a depot-style multi-connection download can be driven without external accounts; what the pin does to each instrument and to multi-process loads such as rsync; what the runner cannot observe (a consumer link, a user's home, desktop-class storage).

## Classes

- S1 — peer-reviewed and preprint literature (T1, T2, T3, T4, T6).
- S2 — primary project and vendor documentation and source code (T1, T2, T3, T4, T5).

`dataset/tools/meas/proc_sampler.py`: a `/proc` poller at the given interval recording per-process CPU ticks, state and (with `--ctxt`) voluntary/involuntary context-switch counters, per pid and per thread. `dataset/tools/meas/runner_spec.py`: records `uname`, `nproc`, `/proc/cpuinfo` model name, `MemTotal`, `/etc/os-release`, the GitHub run ids.

The GUI campaign's instrument, also chosen for the build measurement of the neighbouring slice (not used by `meas-cli.yml`): `sudo perf sched record -k CLOCK_MONOTONIC -a -o … -- sleep <phase>` over each whole phase, read with `perf sched timehist` and `perf sched timehist -w` for the wakeup rows; the analysis counts a schedule-in as a wake only when a wakeup event for that thread lies between its previous schedule-out and this schedule-in, folding a resume after preemption into the preceding wake; plus a taskstats listener registered on the measured CPU's cpumask with `kernel.task_delayacct=1`, giving per-process user and system CPU, elapsed time, parent id, comm, block-I/O delay and runnable wait at exit. Its method notes that on a hosted runner "the runner's own agent processes (containerd, the hosted-compute agent, its .NET runtime) are not ours to pin and share the measured CPU".

## Record format

Each reader writes `search/S<k>-<class>.md`:

1. **Search log** — one row per query: date, engine or venue, query terms, hits followed, dead ends with the HTTP status.
2. **Candidates** — per candidate: a provisional id `S<k>-NN`; full citation; copy read (URL or commit, version, date accessed, local path under `sources/S<k>-NN/`, SHA-256 of each file fetched); verbatim passages with locators (page, section, slide, `file:line` at a commit); coverage per topic — covers (naming the object, unit, statistic, scope and population) or does not cover; whether it is one observation (one population, trace, run or log) and whether machine, subject (program, version, input, cache state) and window are named. Where the reader computes a number from downloaded data (a count over a log, a percentile over a file), the computation is labelled as the reader's own and the command recorded; it locates a candidate, it is not a value.
3. **Not found** — topics with no candidate, with the searches that established it.

Source copies go to `sources/S<k>-NN/` (gitignored; they do not survive this clone, so the record must be self-sufficient: everything a reader needs is in the quoted passages and the copy identification, never "see the local file"). Verbatim means verbatim; a passage that cannot be quoted is not a passage.
