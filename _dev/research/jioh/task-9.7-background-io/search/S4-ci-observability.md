## 4. Synthesis — what a pinned single-core runner can observe of these loads under the given tooling

The runner is a 4-vCPU, 16 GB Azure VM with passwordless sudo (S4-01), image `20260907.300.1`, kernel `6.17.0-1022-azure` (S4-02), whose build enables every accounting and tracing facility the tooling relies on: `CONFIG_TASKSTATS`, `TASK_DELAY_ACCT`, `TASK_IO_ACCOUNTING`, `BSD_PROCESS_ACCT_V3`, `PSI`, `PERF_EVENTS`, `FTRACE_SYSCALLS`, `BLK_DEV_IO_TRACE`, `BPF_SYSCALL`/`BPF_EVENTS`/`DEBUG_INFO_BTF`, `BLK_CGROUP`/`BLK_DEV_THROTTLING`, and `netem`/`tbf`/`htb`/`ifb`/`veth`/`dm-delay` as modules, at `HZ=1000` (S4-04). The CPU model varies between runs of the same label (Xeon 8573C, EPYC 7763, EPYC 9V74 within 30 days, S4-25), so per-run `/proc/cpuinfo` is part of every record.

**Per-process CPU at exit and lifetime.** With `kernel.task_delayacct=1` set before the phase starts (only tasks started afterwards carry delays, S4-06) and a listener registered on the measured CPU's cpumask (`TASKSTATS_CMD_ATTR_REGISTER_CPUMASK`, S4-05), every task that exits on that CPU yields `ac_utime`/`ac_stime`/`ac_etime` in microseconds, `ac_ppid`, `ac_comm`, `nvcsw`/`nivcsw`, plus a per-tgid record when the last thread exits (S4-05). Because `taskset` pins the phase command and the mask is inherited across fork and exec (S4-15), all children of a copy (rsync's sender, receiver and generator — S4-26), a backup (borg, restic), an archiver (`tar`+`xz`), `updatedb`, `clamscan`, `steamcmd`/`DepotDownloader`, the mail client and the indexer daemon exit on the measured CPU and are captured; the documented failure mode is loss under a high exit rate (S4-05). BSD accounting (`acct`, CAP_SYS_PACCT) gives the same CPU and elapsed times at tick resolution with `comp_t` compression and no usable I/O fields (S4-08); `exitsnoop` gives age at 0.01 s and exit reason but no CPU (S4-12); forkstat gives lifecycle rows with a duration in seconds and "may miss events if the system is overly busy" (S4-21). A `/proc` poller sees utime/stime, `read_bytes`/`write_bytes` and field 42 `delayacct_blkio_ticks` (centiseconds) only while the process lives (S4-07).

**Time blocked on I/O.** taskstats `blkio_delay_total`/`blkio_count` ("Delay waiting for synchronous block I/O to complete / does not account for delays in I/O submission", S4-05) is the per-process figure at exit; `delayacct_blkio_ticks` the coarse live one (S4-07); `biosnoop` gives per-request latency attributed to the on-CPU PID (S4-12); `fileslower` the VFS-level latency above a threshold (S4-12); `io.pressure`/`cpu.pressure` the stalled share of time system-wide (`/proc/pressure/*`, built in and not default-disabled, S4-04/S4-13) and per cgroup only if cgroup2 is mounted (not established, Not-found 2). Warm-versus-cold is set by `sync; sysctl vm.drop_caches=3` (drops clean cache and slab, not dirty pages, S4-24).

**Per-schedule run and wait with wakeups.** `perf sched record` on the measured CPU (`-C`, S4-09) then `perf sched timehist [-w]` gives wait time, scheduling delay and run time per schedule-in in msec.usec with wakeup rows (S4-09); as root the paranoid level is irrelevant, and the runner is root-capable (S4-01), though Ubuntu's level-4 default (S4-23) blocks any unprivileged fallback. On one CPU the trace volume is that of the load plus whatever the runner's own agent, kernel per-CPU threads (not movable, S4-15) and interrupts contribute there; the harness's rule of folding a resume-after-preemption into the preceding wake is the only way a serialised pipeline like rsync's three processes reads as "wakes", since on one CPU the pipeline "delayed only when the pipelines stall" (S4-26) becomes a strict alternation.

**Wake structure against the socket.** `perf trace -e read,write,recvfrom --cpu <N>` gives one line per syscall with duration without stopping the tracee (S4-10); `strace -f -T -e trace=%network,read,write` gives the same with a documented slowdown of the tracee that `--seccomp-bpf` only mitigates (S4-11); `tcplife`/`tcptop` give per-session and per-host bytes (S4-12). Bytes per wake are then a count over those rows — a reader's computation, not a value from any source.

**Disk and network on the runner, and their emulation.** The disk is documented only as "SSD" (S4-01); an observation shows a 72 GB root and a 4.1 GB `/mnt` (S4-37), and Azure's temporary disk on a D4ads_v5-class VM is a 150 GiB local disk rated at 19,000 random-read IOPS / 250 MBps under best-case queue depths (S4-03) — none of which is a consumer desktop drive. `queue/rotational` is readable (and writable) but is a flag (S4-33). Disk slowness can be imposed by `io.max` bytes/s and IOPS caps (bursts allowed, S4-13) or by `dm-delay` (a fixed millisecond delay per read/write/flush on a spare device, S4-24); neither reproduces desktop-class latency distributions. The network is an Azure datacentre link (S4-01) with a per-VM ceiling of 12,500 Mbps for the candidate size (S4-03); a consumer link is emulated with `netem delay/jitter/loss/rate` on the receiver's ingress (via `ifb` or a veth pair, S4-14) or a `tbf`/`htb` cap (per-jiffy quantisation at HZ=1000, S4-14/S4-04), against a local peer on the harness CPUs: `python3 -m http.server --bind 127.0.0.1 --directory <corpus>` and `python3 -m aiosmtpd -n` or Mailpit on port 1025 (S4-29), both started under `taskset -c <harness>` (S4-15). What cannot be emulated: a real consumer NIC and its driver, and desktop storage latency; what cannot be observed: a user's home (the corpus is a kernel tree copied into `$HOME/Documents`, S4-18 shows the aliases `&DOCUMENTS` that make it indexable).

**Driving each load without accounts or a session.** Copy: `rsync -a` local (three processes, S4-26). Backup: `borg init -e repokey` + `borg create` with `BORG_PASSPHRASE`, `restic init --repo` with `RESTIC_PASSWORD`, second run deduplicated (S4-27). Archiver: `tar -cJf` with `XZ_OPT=-T0` — under the pin `nproc` is 1 (S4-15) and `xz -T0` sizes to the processors "the system support" (S4-22; whether that reads the mask is not established), `zstd -T0` counts physical cores regardless (S4-22), `7z -mmt` is explicit (S4-22). Indexer daemon: `tracker-miner-fs` 3.7.1 on noble (S4-32) needs a session bus (`dbus-run-session`), reads `org.freedesktop.Tracker3.Miner.Files` `index-recursive-directories` (defaults tied to `user-dirs`, `&DOCUMENTS`), can be pointed at a directory with `localsearch index --add --recursive` / `gsettings`/`dconf`, and exits after the initial crawl with `--no-daemon` (S4-18); Baloo's `baloo_file` needs a session bus, `~/.config/baloofilerc` `[General] folders[$e]=`, lowers its own priorities, and is normally a `graphical-session.target` user unit at `CPUWeight=1 IOWeight=1` (S4-31). `updatedb`: `updatedb -l 0 -o db -U <corpus>` without root, or `sudo updatedb` with `/etc/updatedb.conf` pruning; a second run reuses the database (S4-19). Downloader: `steamcmd +login anonymous +app_update <appid>` for apps Valve's list marks anonymous (TF2 DS 232250, CS:S DS 232330, HLDS 90, Source SDK Base 2013 DS 244310, Garry's Mod DS 4020) — a multiverse package needing i386 libs and a non-root user — or DepotDownloader with `-os linux -max-downloads 8` (S4-16); or plain `wget`/`curl`/`aria2c` against the local HTTP peer. Mail send: Thunderbird's `-compose … attachment=` opens a compose window (under Xvfb, S4-34) but does not send, and needs a profile with a default account and `mail.smtpserver.*` prefs pointing at the local SMTP peer (S4-17); a scripted SMTP client (`smtplib`) is the fallback that actually completes a send. On-demand scan: `clamscan -r` loads the database each run; the database must be fetched by `freshclam` (network) or supplied via `--database=DIR`, and its identity is recordable from the CVD `.info` `name:size:sha256` (S4-20).
