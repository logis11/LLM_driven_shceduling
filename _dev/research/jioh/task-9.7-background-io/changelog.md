## D1 — `io-stream` and `network-bulk` split per bound program (2026-09-19)

By 인지오's decision, scope-card items 11 and 35 (with items 1–4, 6–8, 25–28 and 30–32 depending on them): `io-stream` and `network-bulk` are replaced by one archetype per bound program — `borg` (c1-backup, c7-backup, c2-p3b), `7z` (c4-office), the `steam` depot download (c2-p2a), the `thunderbird` send (c1-mail, c7-mail, c3-workday) — each grounded on one observation of that program under phase decision 2, the form 9.5 D2 gave `desktop-interactive`. Grounds: the bound programs' documented structure differs from the programs `meas-ci:cli:3` measured — borg is one process with no worker threads, cutting 512 KiB–8 MiB content-defined chunks with `POSIX_FADV_DONTNEED` after every read block and `sync_file_range` windows (S2-04), on one core by its maintainer (S3-32), against rsync's three pipe-connected processes (S2-01, S2-02); 7-Zip is multithreaded by default (S2-06); the Steam client fetches ≈ 1 MB compressed and encrypted chunks (S2-17), adds connections as the rate rises (S3-29), decrypts, decompresses and delta-patches per chunk (S3-31) and writes chunks on an asynchronous file-I/O thread (S3-30), against wget's one process, one thread, one connection (S2-15); Thunderbird's send is an upload over one SMTP connection per server (S4-17) with Base64-encoded attachments (S2-18), against a download; and no observation covers either class or any bound program whole (`search/candidates.md`, Not found). Alternatives not taken: one representative per class with the bound names carrying its numbers by stated approximation (the form of 9.5 D11 and 9.6 D6; D6's identity rested on source showing DKMS runs the same kbuild chain, here the sources show different structures); every bound program measured with a sharing criterion decided on the results (9.6 D7's form; within each class the two bound programs already differ in documented structure). `meas-ci:cli:3`'s rsync and wget phases leave these archetypes. The archetype ids, each program's observation — including what stands in for the Steam desktop client and how Thunderbird's send is driven on the runner — and the parameters are decided in the entries that follow. Hands to 9.10: every `io-stream` and `network-bulk` binding in the C1, C2, C3, C4 and C7 timelines rebinds. Hands to 9.14: the consumer lines the scope card lists for `borg`, `7z` and the c2-p2a download rest on per-program numbers. No value changed by this entry.

## D2 — the observation: a new pinned single-core campaign, perf sched and taskstats plus perf trace for the socket loads (2026-09-19)

By 인지오's decision, the venue question of the scope card (items 3, 6, 27, 30): each per-program archetype of D1 takes its values from a new campaign under `measurement-campaign-workflow.md` — one CPU of a 4-vCPU `ubuntu-24.04` runner, the AMD EPYC 7763 only, the machine gate, repeats until the stability rule holds, tag `meas-ci:<workflow>:<launch date>` — instrumented as 9.6 D3 instrumented the build: `perf sched record` on the measured CPU (per-schedule run, wait and delay, and wakeups; S4-09) and a taskstats listener on the measured CPU's cpumask with `kernel.task_delayacct=1` set before each phase (per-process user and system CPU, elapsed time, parent, comm and block-I/O delay at exit; S4-05, S4-06); every child and thread inherits the pin (S4-15). Not taken: 9.6 D3's two instruments alone (no socket structure for the Steam download or the SMTP send); `strace` for the socket rows (it stops the tracee at every traced call and slows it, S4-11, changing the run/wait structure being measured). The run's design — workflow, phases, corpus and cache states, network peers, the Steam and Thunderbird stand-ins, analysis rules, and whether `meas-cli.yml` retires — follows in later entries. By 인지오's decision, amending D1 for `thunderbird`: the send is not an archetype of its own but an operation `send` of 9.5's `mail-client` (Thunderbird), in the form the 9.5 follow-ups spec decisions 8–9 give an operation — its own per-thread components and a measured duration from trigger to completion, placed by the timeline, the compiler swapping in its components for the drawn span and emitting no input wakes (the form 9.5 D22 gave GIMP's unsharp mask, Kdenlive's preview render and Chrome's page load). Grounds: the send runs inside the Thunderbird process — its SMTP client is a JavaScript module of the application (S2-18), with one connection per server (S4-17) — and 9.5 D14 gives an application's whole process tree to one task; a separate send task would put a second `thunderbird` task in c1-mail, c7-mail and c3-workday and either count Thunderbird's background twice or rest on a subtraction no observation backs. Under phase decision 2 the send is measured in the same campaign as `mail-client`'s other values: after 9.5's current campaign ends, Thunderbird is re-observed whole — its setup with an SMTP server pointing at a local peer, its eight input windows cut by the committed rule, and the send's scripted repeats — in one new campaign under `measurement-campaign-workflow.md` with the current campaign's headline medians and tolerance, and its values replace the current campaign's for `mail-client` whole; the current campaign runs to its end untouched and stays in its release for reference. Stated limitation: input wakes are dropped for the send's duration (spec decision 9) although Thunderbird's interface keeps running during a send (S3-09). Not taken: the send as its own archetype (a second task for one process); the send measured alone and attached to the current campaign's Thunderbird values (two observations in one archetype). Hands to 9.5: the re-observation, landing before 9.13, with the send's completion signal, its message and attachment (chosen by the follow-ups spec decision 10 rule) and the peer fixed in the method before launch.
