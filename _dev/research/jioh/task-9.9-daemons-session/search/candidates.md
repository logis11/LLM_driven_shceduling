## Per item

### 1–2. `idle_gap` median and sigma

- No class found a per-daemon wake-gap distribution, or a per-daemon mean gap with the machine and window named, for any of the eleven programs in the current pool except through cumulative `top` rows: S3-03 `systemd` 0:06.62 of CPU over 2 d 16 h and `dbus-daemon` 0.3 % (2018, X11 laptop with applications open). S1-01 gives `udisksd` 0.1 wakeups/s (2013, no systemd). S3-11 gives a headless server floor of ≈ 20 wakeups/s for the whole machine with the big services stopped, and shows the instrument itself moving the reading by 8× (S3-11).
- Mechanisms that would set the cadence, fixed from source and documentation (S2): service watchdog keep-alive at half of `WatchdogSec=` whose upstream build default is 3 min on journald, logind, resolved, networkd and oomd (S2-01; Fedora builds it off, S2-27; Debian's rules do not override it, S2-28); journald sync every 5 min (S2-01); `systemd-timesyncd` poll 32 s → 2048 s (S2-01); `systemd-oomd` swap poll 0.15 s and pressure poll 1 s (S2-01; its idle CPU is S3-09/S3-10's finding); udevd idle-worker kill after 3 s (S2-01); chrony 64–1024 s per source (S2-02); cron once per minute (S2-03); multipathd checker 5 s rising to 20 s with five named threads (S2-07); udisksd housekeeping every 600 s (S2-08); rsyslog idle workers shut down after 60 s (S2-09); NetworkManager connectivity check 300 s when configured (S2-10); PackageKit exits after 300 s idle (S2-06); rtkit's canary every 5 s and watchdog 10 s (S2-21); dbus-daemon documents no periodic idle activity (S2-04).
- The observation the runner can add: every system-wide `perf sched` trace already records every daemon thread's switch and wakeup rows on every CPU (S4-07, S4 synthesis T7.4–T7.5), so the raw releases of the 9.5/9.6/9.7 campaigns (reachable: S4-00) hold per-wake rows of the runner's daemons beside a pinned application; what they cannot say is the wake cause or what the daemon would do on a desktop with a seat, a display and a sound card (S4 synthesis T7.5–T7.6, marked inference).

### 3–4. `wake_burst` median and sigma

- No class found CPU per wake for any system service at idle. Whole-process CPU rows exist as `ms/s` in PowerTOP tables for session processes only (`gnome-shell` 16.0 ms/s at 16.4 wakes/s with Firefox open, S3-04; `Xorg` 15.9 ms/s at 1.0 wakes/s, S3-13; `Xorg` 2.5 ms/s at 14.1 wakes/s, S3-14) and as CPU seconds per 60 s for `plasmashell` and `kwin_wayland` (0–1 s healthy, S3-07). `systemd-oomd` at 0.7–1.3 % of a core (S3-09) is the only systemd-family CPU figure with a version named, and it is a bug that was fixed.
- S1-03's "typically less than 1 %" for all daemons of an idle system is a claim in a 2008 paper, not a row.

### 5. `sampling: per-iteration` on an unbounded loop

- No candidate bears on the contract question; it is the repository's. The records show what a per-iteration observation would need: per-thread switch rows (S4-07 `/proc/<pid>/task/<tid>/status`, `perf sched timehist --state`, taskstats per-tid exit records) rather than the 0.2 s sampler's one average per process.

### 6. `pattern: loop { SLEEP; RUN }` — "aperiodic"

- The mechanisms are mixed: fixed timers (cron 60 s, multipathd 5 s, udisksd 600 s, oomd 0.15 s / 1 s, rtkit 5 s, chrony 64–1024 s, timesyncd 32–2048 s, watchdog pings at 90 s where built in — S2-01…S2-10, S2-21) beside event-driven daemons with no idle timer of their own (dbus-daemon and dbus-broker, S2-04/S2-05; the X server blocks in `ospoll_wait` with no periodic wake of its own when clients are idle, S2-16; wlroots emits frame events only on demand, S2-25; Mutter's frame clock returns to IDLE with nothing scheduled, S2-12; KWin's composite timer is armed only on repaint requests, S2-15). Whether one SLEEP/RUN loop with one constant gap stands for a timer daemon, an event daemon, or a compositor with a frame clock is stage 3's.
- Observed cadences of session processes at an idle desktop: `gnome-shell` ≈ 1 500 wakeups/s at login and ≈ 600–640/s later baseline with nobody active on Mutter 49.3 (S3-06); 16.4/s with a browser open on an older GNOME (S3-04); `kwin_x11` 63.6 + 186/s and `plasmashell` 21.1/s on Plasma 5 X11 (S3-03); `plasmashell` and `kwin_wayland` at 0–1 s CPU per 60 s on Plasma 6.7.5 (S3-07). These are per-process means over a refresh or a window, never per-wake distributions.

### 7. `lifetime`, `binding_params`, `scalable`

- Design; no candidate. PackageKit is the one daemon in the pool's namespace documented to exit at idle (300 s, S2-06), which the `segment-bound` lifetime does not express.

### 8. `validation_stats` — "wakeup rate and burst-length CDF … via /proc sidecar"

- What a `/proc` sidecar can give: per-thread voluntary and involuntary switch counters and `Cpus_allowed_list` from `/proc/<pid>/task/<tid>/status`, run time / runqueue wait / timeslice count from `/proc/<pid>/schedstat` (S4-07); no per-wake run length. A CDF needs `perf sched timehist` (run time, wait time, scheduling delay per row, `--state`, `-w`) or taskstats (S4-07); both work on daemons the workflow did not launch (S4 synthesis T7.4).

### 9. `category_source: meas` and shipped treatment

- CachyOS `ananicy-rules` @ `03ef03f` (S2-26): `LowLatency_RT` (nice −12, best-effort) for `gnome-shell`, `kwin_wayland`, `kwin_x11`, `sway`, `Xorg`, `Xwayland`, `pipewire`, `pipewire-pulse`, `wireplumber`, `pulseaudio`, `mutter-x11-frames`; `plasmashell` nice −6; `Service` (nice 10, ionice 6) for `dbus-daemon`, `dbus-broker`, `udisksd`, the `gsd-*` helpers; `BG_CPUIO` (nice 16, idle io, SCHED_IDLE) for `NetworkManager`, `chronyd`, `gdm`, `gnome-session-ctl`; no rule for any systemd daemon, cron, polkitd, packagekitd, rsyslogd or multipathd; ananicy-cpp rescans every 15 s.
- The projects' own treatment (S2): kwin_wayland sets `SCHED_RR|SCHED_RESET_ON_FORK` at the minimum RT priority on its main thread through a `CAP_SYS_NICE=+ep` file capability (S2-15); Mutter's KMS thread asks rtkit for high-priority nice by default and RT only under a debug variable (S2-12); PipeWire asks `rt.prio` 88 (server, nice −11) / 83 (clients) upstream, Fedora builds 60/55 (S2-18, S2-27); PulseAudio nice −11, RT priority 5, self-rlimits RTPRIO 9 / RTTIME 200 ms (S2-20); rtkit caps at RT 20, nice −15, RTTIME ≤ 200 ms, SCHED_RR, 15 processes / 25 threads per user (S2-21); `multipathd.service` ships `CPUWeight=1000` and `LimitRTPRIO=10` (S2-07); systemd's session/app/background user slices carry `CPUWeight` 100/100/30 and gnome-shell, kwin_wayland, pipewire, pipewire-pulse, wireplumber, pulseaudio and the user buses all ship `Slice=session.slice` (S2-01, S2-04, S2-05, S2-13, S2-15, S2-18…S2-20); `OOMScoreAdjust` journald −250, udevd −1000, oomd −900, the system buses −900, gnome-shell −1000 (S2-01, S2-04, S2-05, S2-13). No upstream `Nice=` or `CPUSchedulingPolicy=` on any of these daemons, and no session-scope `CPUWeight=` in Fedora's or Ubuntu's gnome-shell packaging (S2-27, S2-28, Not found).
- Literature treats daemons as latency-sensitive tasks given tens-of-millisecond reservations (Redline: `init` 2:50, `kjournald` 10:100, `Xorg` 15:30, `kwin` 3:30 ms — S1-04), as OS noise to confine to housekeeping CPUs (S1-13, S1-14), or as absent from the synthetic wake-up benchmarks (S1-12); the audio server's need for RT is argued and measured on JACK (S1-05).

"Stock daemons are not drift-free periodic": item 6. The cli:1 corroboration sentence: no class bears on it (repository-internal).

### 11. `gnome-shell` (compositor and shell)

- Mechanism (S2-12, S2-13, S2-14, S2-24): Mutter's per-view frame clock is a state machine on a timerfd GSource that returns to IDLE after presentation with nothing scheduled and is inhibited to IDLE when the output is off; the KMS work runs on a dedicated thread; one frame clock per monitor on Wayland, one for X11 (Ådahl); the session goes idle after 300 s by default, the shell fades the shield over 10 s and delegates blanking to gnome-settings-daemon (not read). Neither developer write-up states a per-frame CPU cost (S2-23, S2-24).
- Observation at an idle desktop: S3-06 (Mutter 49.3, AMD, nobody active: ≈ 1 500 wakeups/s at login, ≈ 600–640/s later; 12 atomic-property calls per output frame); S3-04 (16.4 wakeups/s, 16.0 ms/s CPU, browser open, 2020); bug states 30–60 % after resume (S3-17). No observation of the blanked-screen state or of one animating window (S3 Not found). The only per-frame figure in any class is the reader's division of S3-07's `kwin_wayland` CPU by its commit rate (≈ 0.7 ms per frame on a 120 Hz Framework 13, a bug state), explicitly not a stated value.
- On the runner: gnome-shell 46.0 and mutter 46.2 are published for noble amd64 and run `--headless --virtual-monitor WxH@R` or `--nested` with dummy monitors (S4-08, S4-09, S4-15); what paces the headless frame clock without vblank is not established (S4 Not found T7.2); a per-frame cost measured there is that of a timer-paced compositor on llvmpipe (S4 synthesis T7.6).

### 12. `Xorg` (display server)

- Mechanism (S2-16, S2-17): the server blocks in `ospoll_wait` with a timeout from its own timers, so no periodic wake of its own with idle clients; screensaver/DPMS blank at 10 min by default; the client scheduler uses a 5 ms interval and 15 ms maximum slice when clients are busy; Xvfb is the same server on a memory framebuffer; Xwayland paces windows by the compositor's frame callbacks; the dummy driver is an offscreen framebuffer.
- Observation: `Xorg` 30.90 cswch/s while polled by a clipboard manager and 1.65 after (S1-01, 2013); 57.3 wakeups/s on Plasma 5 X11 with applications open (S3-03, 2018); 1.0/s at 15.9 ms/s and 14.1/s at 2.5 ms/s on two laptops with a browser present (S3-13, S3-14); `Xwayland` 6.1/s (S3-04) and rows under a game (S3-02); bug state > 30 % (S3-23). Redline reserved `Xorg` 15 ms per 30 ms and argued the window manager can flood it under CFS (S1-04, 2008).
- On the runner: `xserver-xorg-video-dummy` 0.4.0 and Xvfb 21.1.12 are published; `xset dpms force off` reaches the dummy driver's DPMS entry points (S4-12, inference marked); no vblank exists on either (S4 synthesis T7.6).

### 13. `pipewire` (audio server)

- Mechanism (S2-18, S2-19, S2-20, S1-07): PipeWire's graph is woken once per period by a timerfd programmed from the device fill level and a DLL, peers wake one another through eventfd without the daemon (Taymans); defaults rate 48 000 and quantum 1024 (min-quantum 1024 in a VM), one RT data-loop thread; the driver node's timerfd is disarmed when the driver is not started; WirePlumber suspends an idle Audio/Video node after 5 s; PulseAudio suspends after 5 s. So with nothing playing the graph does not tick (S2-18, S2-19).
- Observation: none at idle. Under load: PowerTOP's `pipewire` row 0.0 µs/s with the codec's 2.44 W attributed to it while MuseScore plays (S3-08); `pipewire-pulse` sampled rows under a game (S3-02); the LAVD deck's audio servers inside the 30–40 % system-task share under a game (S1-09/S3-01); JACK's period timing (S1-05) and audio-server CPU on an ARM board (S1-08) as the nearest measured audio-server figures, neither PipeWire on a desktop.
- On the runner: the azure kernel is built without `CONFIG_SND`, so no sound card can exist; PipeWire 1.0.5 and WirePlumber 0.4.17 are published and run with a null sink that is timer-driven on `CLOCK_MONOTONIC`; RT via `RLIMIT_RTPRIO`, then the portal, then rtkit, whose policy has no VM check (S4-13, S4-14, S4-15).

### 14. `systemd` (pid 1)

- Mechanism (S2-01): pid 1's hardware watchdog is off by default (pinged at timeout/4 when on); the service watchdog keep-alives of its daemons are at half of `WatchdogSec=` (3 min upstream default; off in Fedora builds, S2-27); `CPUAffinity=` in `system.conf` applies to pid 1 and everything it forks, at boot (S4-05).
- Observation: `systemd` 0:06.62 cumulative CPU over 2 d 16 h on a 2018 laptop (S3-03); pid 1 at load 3–4 during a firmware uevent storm (S3-20, bug). No idle wake rate for pid 1 anywhere.

### 15. `dbus-daemon` (bus)

- Mechanism (S2-04, S2-05): dbus-daemon documents no periodic idle activity and no thread structure (auth timeout 30 s, service start 25 s, pending fd 150 s, reply timeout unlimited); dbus-broker is a launcher plus a broker that touches only its sockets; the user bus ships `Slice=session.slice`, the system bus `OOMScoreAdjust=-900`.
- Observation: `dbus-daemon` 0.3 % CPU on a 2018 X11 laptop with applications open (S3-03); no PowerTOP row for it in any table quoted (S3 Not found). No session-bus observation.

### 16. One archetype for two populations

- What the classes show of the two populations at an idle desktop: session processes carry the wakes and the CPU that is visible — `gnome-shell` hundreds to ≈ 1 500 wakeups/s (S3-06), `kwin_x11` and `Xorg` tens to hundreds per second (S3-03), Compiz and the X server the two largest user-space rows of a 2013 idle desktop (S1-01) — while system services do not appear in the top rows of any PowerTOP table found (S3 Not found T1) and are "typically less than 1 %" as a 2008 claim (S1-03). The headless contrast is ≈ 20 wakeups/s for a whole server with the big services stopped (S3-11) against 30–107 (S1-01, 2013), 536–1 208 context switches/s (S3-05, 2025) and 795–1 858 wakeups/s (S3-04, S3-14) for desktops with a session. The cross-desktop comparison that exists is whole-system only (S3-05).
- The compositor's idle behaviour is mechanism-fixed as event-driven with a frame clock that stops (S2-12, S2-15, S2-22, S2-25); the audio server's graph stops after 5 s idle (S2-19); the X server has no idle timer of its own (S2-16). The system services are a mix of fixed timers and event daemons (item 6). The treatment catalogues put the session processes at nice −12 and the buses and helpers at nice 10 (S2-26).
- Literature treats the two as different classes: GUI tasks with 30 ms periods and daemons with tens-of-millisecond periods, both "interactive" (S1-04); audio servers as RT threads (S1-05, S2-18, S2-20); daemons as OS noise (S1-13, S1-14).

## The T7 synthesis — what a pinned single-core runner can observe of daemons and session processes (S4)

- **What runs there.** A fresh Azure VM, 4 vCPU / 16 GB, Ubuntu 24.04 server SKU, kernel `6.17.0-1022-azure`, systemd 255.4; the image build disables apt-daily, unattended-upgrades and fwupd-refresh, holds snap refresh, enables docker, keeps the Azure agent and adds a `runner-provisioner` service and a boot-time linger session; chrony against the Hyper-V PTP clock is Microsoft's documented default with timesyncd possibly active at boot (S4-01, S4-02, S4-04). Absent: `CONFIG_SND` (no sound card possible), any compositor, display server, audio server, rtkit, seat or graphical session (S4-15, S4-05).
- **A session can be started and pinned** (documentation, not tried): gnome-shell 46 / mutter 46.2 `--headless --virtual-monitor` or `--nested`, `kwin_wayland --virtual`, sway with `WLR_BACKENDS=headless` and a 60 Hz software frame timer, Xvfb or the dummy Xorg driver, PipeWire with a null sink and WirePlumber, all published for noble amd64 and installable with sudo; the states of interest can be driven (nothing touched; `xset dpms force off`; `glxgears` on llvmpipe; `pw-play` into the null sink) (S4-08…S4-15, synthesis T7.2).
- **System daemons can be pinned or excluded at run time** as root: `taskset -a -pc` on running pids (constrains, does not migrate), `systemctl set-property <unit> AllowedCPUs=` (cgroup cpuset, immediate for running tasks), `CPUAffinity=` drop-ins for restarted services; `isolcpus`/`nohz_full` are boot parameters the job cannot set; per-CPU kernel threads stay (S4-05, S4-06, S4-07, synthesis T7.3).
- **The instruments see daemons the workflow did not launch**: `perf sched record -a` is system-wide, timehist gives wait, scheduling delay, run time, `--state` and `-w` per row for every thread; `sudo` clears Ubuntu's `perf_event_paranoid` 4; the kernel has `TASKSTATS`, `TASK_DELAY_ACCT`, `SCHEDSTATS`, HZ 1000, `PREEMPT_VOLUNTARY`; per-thread counters in `/proc/<pid>/task/<tid>/status`; taskstats exit records per CPU mask (S4-07, S4-15, S4-16, synthesis T7.4). The CPU cost of an all-CPU record and the runner's booted sysctl value are not documented (S4 Not found).
