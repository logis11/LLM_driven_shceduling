# Reader input — task 9.9 daemons and session processes, stage 2 search

Given to each class reader verbatim. Readers do not see the repository's current values. Issue #14.

## Topics

- **T1 System services at idle on Linux.** For the always-on services of a systemd-based Linux system — `systemd` (pid 1), `systemd-journald`, `systemd-udevd`, `systemd-logind`, `systemd-resolved`, `systemd-networkd` or NetworkManager, `systemd-timesyncd` or chrony, `dbus-daemon` or `dbus-broker` (system and session bus), `cron`, `polkitd`, `udisksd`, `packagekitd`, `rsyslogd`, `multipathd` and the like: what each does while nothing happens (timers, watchdog keep-alives, journal syncs, inotify and netlink events, bus traffic, polling), the intervals their documentation or source state, their process and thread structure, and any Linux observation of per-service wake cadence, CPU per wake or CPU share at idle (wakeups-per-second tables, power-tuning reports, bug reports with profiles), with the machine, distribution, state and window named.
- **T2 Session processes at idle and under drawing.** For a desktop session's compositor and shell (GNOME Shell with Mutter, KWin, Sway, wlroots compositors), display server (Xorg, Xwayland) and audio server (PipeWire with WirePlumber, PulseAudio): what each does with nobody present and no client drawing or playing (frame clock stopped or running, idle throttling, screen-blank and suspend behaviour, PipeWire's node suspension), what each does per frame or per audio period when a client draws or plays, their process and thread structure and the scheduling policy they set on themselves (real-time threads through rtkit), and any Linux observation of their wake cadence, CPU per wake or CPU share per state (idle desktop, blanked screen, one animating window, a stream playing) — including any measurement of a compositor's per-frame CPU cost on a GPU desktop.
- **T3 The idle desktop as a whole.** Any Linux observation of an idle desktop session's process population — how many processes and threads wake, at what aggregate rate, which programs dominate, and the split between system services and session processes — as distinct from a headless server or a virtual machine without a session; how that population differs between GNOME on Wayland, GNOME on X11, KDE Plasma and lighter sessions; what distributions and power-management projects report of it (idle wakeups, "wakeups from idle" counts, battery-life work), with numbers.
- **T4 Shipped treatment of system services and session processes.** What process-treatment catalogues (ananicy rule sets), distributions and the projects themselves assign to these processes: `Nice=`, `CPUWeight=`, `CPUSchedulingPolicy=`, `IOSchedulingClass=` in shipped unit files; real-time priority for audio servers and compositors through rtkit and its limits; cgroup slices for the session (`user.slice`, `session.slice`, `app.slice`) and their weights; any timing or rate value such a mechanism carries.
- **T5 Public traces and datasets.** Any public trace or dataset with per-process scheduling or CPU data of an idle Linux system, desktop or server (Perfetto, ftrace, `perf sched`, LTTng traces; powertop or `perf timechart` reports; system-monitor logs; bug reports with profiles of idle CPU use by a daemon or a compositor; kernel or scheduler-development test traces; benchmark databases with idle-power runs), and what fields each carries; any trace of a Linux game or desktop session in which system services and audio or display servers appear with their share of scheduling.
- **T6 System services and the session as a scheduler workload.** How scheduler evaluations and benchmarks treat the always-on system services and the session processes next to interactive work — as noise, as many mostly idle tasks, as a wake-up source, as latency-critical threads (audio server, compositor) — with any reported CPU, run/wait, wake or share figures; what the literature says such a load does to interactivity and why; how latency-sensitive daemons (audio, compositor) are argued to need priority.
- **T7 CI observability under a single-core pin.** Given a GitHub Actions hosted runner (4 vCPUs, Ubuntu 24.04) on which a measured load is confined to one CPU with `taskset` while the instruments run on the other CPUs (the tooling is quoted in `input.md`): which system services the runner image runs at all (the systemd units enabled on the image, the runner agent and its runtime, the Azure agent, container daemons, chrony, multipath, the disk manager), and which are absent that a desktop has; whether a desktop session can be started on the runner — GNOME Shell or Mutter under Xvfb or a headless Wayland backend, an Xorg server with the dummy driver, PipeWire and WirePlumber with a null sink — driven into the states of interest (nobody present, screen blanked, one window animating, a stream playing) and pinned; whether the system's own daemons can be pinned to the measured CPU or excluded from it (`taskset -p`, `CPUAffinity=`, `AllowedCPUs=`, a drop-in before the phase); what `perf sched record -a` / `timehist` with wakeups, taskstats and `/proc` can observe of a daemon per wake and per thread when the daemon was not launched by the workflow; what an all-CPU trace taken beside another measured application tells about the runner's daemons; what the runner cannot observe (a real display and vblank, a sound device, a logged-in session with a seat, a laptop's power management, the CPU model except through the gate).

## Classes

- S1 — peer-reviewed and preprint literature (T1, T2, T3, T6).
- S2 — primary project and vendor documentation and source code (T1, T2, T4).
- S3 — public traces, datasets, logs, bug reports with profiles and benchmark databases (T1, T2, T3, T5).
- S4 — own measurement on a CI runner (T7; documentation research and, where the reader can, checks of package availability, image contents, unit files, install routes and kernel configuration from public sources — nothing is measured in this session).

A rule for every class: a response-side value — CPU per wake, wake cadence, run and wait structure, thread and process structure — is a candidate only from a Linux observation; observations on other platforms and traces two decades old are recorded as context, marked as such. An interval, timeout or period stated by a project's documentation or source (a watchdog keep-alive, a sync interval, a polling interval, a frame clock, a node-suspend timeout) is a mechanism, recorded as such, not an observation. A treatment value (a nice level, a scheduling policy, a cgroup weight) is a treatment fact, recorded as such, never a behaviour value.

`dataset/tools/meas/phase.sh` (lines 2–10): a phase wrapper that runs one command inside a named phase, appending `{"phase","start_us","end_us","rc","pin","cpu"}` to a phases file; `MEAS_PIN=load` (default) runs the command on the one measured CPU, `MEAS_PIN=harness` on the harness CPUs, `MEAS_PIN=none` leaves it alone; a failed phase is recorded, never fatal.

`dataset/tools/meas/machine_gate.sh` (lines 2–7): "same-machine repeats (9.6 changelog D10). Source it. GitHub-hosted runners guarantee a shape (4 vCPU, 16 GB), not a processor: the jobs of one batch are independent draws from a pool of several CPU models, and one core of one model can be a quarter faster than one core of another (9.6 campaign: Xeon Platinum 8573C against EPYC 7763, cc1 CPU per process 0.74). A measured value is "this software on this machine" (9.5 D10), so a campaign names its machine and a job that drew another model stops before measuring anything." — `machine_gate "<substring of the wanted model name>"` reads `/proc/cpuinfo`'s `model name` and returns 1 when the runner is another model; the campaign's wanted model is `EPYC 7763`.

`dataset/tools/meas/stability.py` (docstring): "The pool of same-machine repeats is stable when the 95 % confidence half-width of the across-repeat mean of a carried median (t multiplier, k − 1 degrees of freedom), relative to the mean, is at most TOLERANCE [0.05]. Repeats are added one at a time until it holds; every same-machine repeat obtained is pooled and reported."

`dataset/tools/meas/proc_sampler.py`: a `/proc` poller at the given interval recording per-process CPU ticks, state and (with `--ctxt`) voluntary/involuntary context-switch counters, per pid and per thread ("`vctxt`/`nvctxt` from /proc/<pid>/status, which the kernel prints for the main thread only, and `tctxt`" per thread). `dataset/tools/meas/runner_spec.py`: records `uname`, `nproc`, `/proc/cpuinfo` model name, `MemTotal`, `/etc/os-release`, the GitHub run ids. The system's own daemons are not launched by the workflow: nothing in it pins them, and they run on any vCPU.

The campaign instrument (`dataset/tools/meas/campaign/run.sh`, `analyze.py`; the interactive, playback, build and background workflows): `run.sh` sources `machine_gate.sh` and stops before measuring on another model (lines 55–57); the application tree is launched `taskset -c "$MEAS_CPU" setsid bash -c "$LAUNCH"` (line 74) and its affinity recorded (line 76); each phase is `pin_harness sudo perf sched record -k CLOCK_MONOTONIC -a -o … -- sleep <secs>` (line 93) — `-a`, every CPU — read with `perf sched timehist --state` (line 103) and `perf sched timehist -w` for the wakeup rows (line 106), gzipped as the released raw record; `/proc` snapshots at phase boundaries record thread population, CPU time and context switches per process with each process's command line; a wake is a schedule-in preceded by a wakeup event for that thread since its last sleep, decided by the thread's previous switch-out state where the timehist carries it, a resume after preemption folded into the preceding wake. Its method notes that on a hosted runner "the runner's own agent processes (containerd, the hosted-compute agent, its .NET runtime) are not ours to pin and share the measured CPU: their rows lie outside the tree and are never counted". Raw records of the campaigns are published as GitHub releases of this repository (`logis11/LLM_driven_shceduling`, tags `meas-ci-2026-09-14`, `meas-ci-2026-09-16`, `meas-ci-build-2026-09-18`); whether they are reachable without credentials is for the S4 reader to record, not to assume.

## Record format

Each reader writes `search/S<k>-<class>.md`:

1. **Search log** — one row per query: date, engine or venue, query terms, hits followed, dead ends with the HTTP status.
2. **Candidates** — per candidate: a provisional id `S<k>-NN`; full citation; copy read (URL or commit, version, date accessed, local path under `sources/S<k>-NN/`, SHA-256 of each file fetched); verbatim passages with locators (page, section, slide, `file:line` at a commit); coverage per topic — covers (naming the object, unit, statistic, scope and population) or does not cover; whether it is one observation (one population, trace, run or log) and whether machine, subject (program, version, state — idle, blanked, drawing, playing, headless) and window are named. Where the reader computes a number from downloaded data (a count over a log, a percentile over a file), the computation is labelled as the reader's own and the command recorded; it locates a candidate, it is not a value.
3. **Not found** — topics with no candidate, with the searches that established it.

Source copies go to `sources/S<k>-NN/` (gitignored; they do not survive this clone, so the record must be self-sufficient: everything a reader needs is in the quoted passages and the copy identification, never "see the local file"). Verbatim means verbatim; a passage that cannot be quoted is not a passage.
