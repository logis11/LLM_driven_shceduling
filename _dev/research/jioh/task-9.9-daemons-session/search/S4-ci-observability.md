**T7.3 — can the system's own daemons be pinned or excluded.** Yes at run time, by three documented routes, all root: `taskset -a -pc <cpus> <pid>` sets every thread of a running daemon (S4-06 `:72-73,:78-80,:108`; without `-a` only one thread) — it constrains future placement, it does not migrate the thread by itself (S4-06 `:114`); `systemctl set-property <unit> AllowedCPUs=<cpus>` changes the unit's cpuset immediately (S4-05 `systemctl.xml:690-700`, `systemd.resource-control.xml:282-289`), and cpuset confines every task already in the cgroup to `cpuset.cpus.effective` (S4-07 `cgroup-v2.rst:2535-2541`), so it covers threads the daemon will spawn too **[inference from "tasks within the current cgroup"]**; an inactive unit only stores the change (S4-05 `systemctl.xml:704-705`). `CPUAffinity=` in a drop-in, and `CPUAffinity=` in `system.conf` for pid 1 and all forked processes, apply to *executed* processes (S4-05 `systemd.exec.xml:1401`, `systemd-system.conf.xml:168-169`), i.e. they need `daemon-reload` and a restart of the service (or a reboot for pid 1) to take effect **[inference]**. `isolcpus`/`nohz_full` are boot parameters, "irreversible" domain isolation "at boot time", and the docs point to cpusets for runtime changes (S4-07 `kernel-parameters.txt:2789-2793,2810-2817`, `:4553-4558`, `no_hz.rst:124-126`); the image's kernel command line is written at image build (S4-01 `configure-environment.sh:76-79`) and a job cannot reboot the VM into a different one **[inference]**, although the kernel itself has `CONFIG_NO_HZ_FULL=y` and `CONFIG_CPU_ISOLATION=y` (S4-15). Kernel threads (`kworker/<cpu>:*`, `migration/<cpu>`, `ksoftirqd/<cpu>`) are per-CPU and cannot be moved off their CPU **[inference from their naming and the `migration/10` row in S4-07 `perf-sched.txt:81`; no passage states it]**, so a measured CPU always keeps its own kernel threads.

**T7.4 — what the instruments observe of a daemon not launched by the workflow.** `perf sched record -a` records system-wide from all CPUs (S4-07 `perf-record.txt:234-236`), so every thread's `sched_switch` (with `prev_state`) and `sched_wakeup`/`sched_waking` (with `target_cpu`) are captured regardless of who started it (S4-07 `events-sched.h:151,166-180,250-265`); `timehist` gives per row the wait time (sched-out to next sched-in), the scheduling delay (runnable to running) and the run time, `--state` the state at switch-out, `-w` the wakeup rows, `-C` a CPU filter (S4-07 `perf-sched.txt:71-77,424-426,457-459,480-481`; `builtin-sched.c:2377,2382-2383,5342,5349`). Tracepoint access is gated by `perf_event_paranoid`: Ubuntu's level 4 requires `CAP_SYS_ADMIN` (S4-16 bug description; S4-15 `SECURITY_PERF_EVENTS_RESTRICT=y`), which `sudo` supplies (S4-03), and a user reports `sudo perf record -a` working on the x64 runner (S4-16 issue body); tracefs lives at `/sys/kernel/tracing` (S4-07 `ftrace.rst:52-53`), and the kernel has `TRACEPOINTS`, `SCHED_TRACER`, `SCHEDSTATS`, `SCHED_INFO`, `TASKSTATS`, `TASK_DELAY_ACCT` (S4-15). Per-thread counters: `/proc/<pid>/task/<tid>/status` prints that task's `voluntary_ctxt_switches`/`nonvoluntary_ctxt_switches` and `Cpus_allowed_list` (S4-07 `array.c:397-402,405-410`, `proc.rst:293-298`) **[per-thread reading is inference from the task argument]**; `/proc/<pid>/schedstat` gives run time, runqueue wait time and timeslice count (S4-07 `sched-stats.rst:192-198`, governed by `kernel.sched_schedstats`, `sysctl-kernel.rst:1269-1274`); taskstats gives per-pid and per-tgid `cpu_count`, `cpu_delay_total`, `cpu_run_real_total`, `nvcsw`, `nivcsw` on demand and, after `TASKSTATS_CMD_ATTR_REGISTER_CPUMASK`, an exit record for every task that exits on the listed CPUs (S4-07 `taskstats.rst:30-45,83-88,105-115`, `taskstats-struct.rst:34,115-116,136,180-183`, `delay-accounting.rst:94-96`). None of these needs the daemon to be a child of the workflow **[inference: all are keyed by pid/tid or by CPU]**. The cost of an all-CPU record is not documented (§3).

**T7.5 — what an all-CPU trace beside a measured, pinned application says about the daemons.** The trace carries every switch and wakeup on every CPU, so the daemons' rows are identifiable by comm/pid and can be filtered per CPU (S4-07 `perf-sched.txt:424-426`; `events-sched.h:250-266`) — which rows are daemons' is a matter of naming them from `/proc` snapshots **[inference]**. On the measured CPU, a daemon thread that lands there shares it with the pinned application under the same scheduler, so its `sch delay` is inflated by the application's run time and the application's rows show the daemon's run time as `wait time` **[inference from the column definitions, S4-07 `perf-sched.txt:71-74`]**; whether a daemon lands there depends on its affinity mask and the load balancer, which the trace shows only after the fact through `target_cpu` and the `cpu` column **[inference]**. Undecidable from such a trace: what the daemon would have done on an idle desktop with a seat, a real display and a sound card (the runner has none of these: S4-15 `CONFIG_SND` `-`; S4-05 seat definition; §3) **[inference]**; the wake *cause* (timer, socket, inotify) — `sched_waking` records the waker context but not the object **[inference from the fields in S4-07 `events-sched.h:141-163`]**; and whether a switch-out in state `R+` (preempted, S4-07 `events-sched.h:263-265`) was preemption by the measured application or by another daemon, without joining on the `next_pid` of the same row **[inference]**.

**T7.6 — what the runner cannot observe.** A real display and vblank: Xvfb "emulates a dumb framebuffer using virtual memory" (S4-12 `Xvfb.man:37-39`), the dummy driver is "virtual/offscreen" (S4-12 `dummy-README.md:1`), and the wlroots headless output paces frames from a software timer (S4-11 `output.c:31,76`) — so any per-frame CPU cost measured is that of a timer-paced compositor on llvmpipe, not of a vblank-paced GPU desktop **[inference]**. A sound card: the azure kernel is built without `CONFIG_SND` (S4-15 `annotations-azure.txt:245`), so only a null sink exists. A seat and a logged-in session: a seat needs hardware devices (S4-05 `sd-login.xml:94-96`); the runner's session is a linger session without a seat (S4-01 `systemd-linger.sh:3-5`; S4-05 `sd-login.xml:111`) **[inference]**. Laptop power management: no battery, lid, or DPMS-driven behaviour exists on an Azure VM **[inference; no passage states it, and the runner docs describe only the VM shape, S4-03]**. The CPU model: the runner documentation names only "4" processors (S4-03 `:307-318`); the model is visible only through `/proc/cpuinfo` at run time, which is what the repository's gate reads (input.md) **[inference]**. Everything in this section is documentation or inference; nothing here is a measurement.
