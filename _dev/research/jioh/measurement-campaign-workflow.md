# Measured values — campaign workflow

How a domain slice obtains the values its archetypes carry from a measurement on a GitHub-hosted runner: one CPU model, repeats added until the stability rule holds. The rule and the measurement decisions below hold for every campaign; a slice's method states only its own list, input and first batch. Fixed on 2026-09-19 from the 9.6 and 9.5 campaigns (9.6 changelog D10–D11, D23–D26; 9.5 changelog D26–D30, D32–D35); amended through 2026-09-24 (9.6 D29; 9.5 D47, D57, D64, D71; 9.7 D26, D27; 9.8 D13, D14, D17, D18, D24, D26). Parent: `research-slice-workflow.md`. Applies to every archetype whose values carry a `meas-ci` tag: 9.5's nine, 9.6's three, 9.7 (`file-backup`, `file-archiver`, `game-download`), 9.8 (`renderer-hidden`, `renderer-visible`, `chat-client`, `game-client`), 9.9 (`compositor-shell`, `audio-server`, `service-manager`, `message-bus`).

## What a measured value is

- **This software on this machine** (9.5 D10): one observation, pinned to one CPU of a 4-vCPU `ubuntu-24.04` runner (9.5 D21), its runner spec written into the archetype's scope.
- **One CPU model: the AMD EPYC 7763.** A hosted runner guarantees a shape, not a processor; each job is an independent draw from several models, and one core of another model differs by a different factor per program (9.6: a Xeon Platinum 8573C ran `cc1` at 0.72× and `fixdep` at 0.50× the EPYC's time). Machines of one nominal type differ, so the machine is held and the repeat count read on it (`maricq-osdi18`: "software run repeatedly on the same server (or a different server with supposedly identical parts) can produce performance results that differ with each execution", abstract). The EPYC 7763 is the most frequent model in the recorded draws (9.6 D11: 26 of 56 jobs; the released 9.5 campaign: 22 of 45, `task-9.5-interactive-typing/campaign/machine-draws.md`). A job on any other model measures nothing.
- **Steady behaviour starts after launch.** A phase that describes the application's steady behaviour (idle, playback) starts after its launch work ends: a settle per application, set from its traces and labelled as design (9.5 D34: at a 30 s settle, Chrome, Thunderbird, a WebRTC call and VS Code carried launch or ramp-up work into the phase at the same point in every repeat, up to 20 times the steady CPU); 9.5 D35: where the traces cannot tell launch work from behaviour that recurs, one long-phase probe first — if the episodes recur, the phase is lengthened to hold them instead of a settle skipping them).
- **One wake.** A schedule-in preceded by a wakeup event for that thread since its last sleep; a resume after preemption is folded into the wake it continues (9.5 follow-ups decision 4, 9.5 D21). Decided by the thread's previous switch-out state — a sleep state (any but R) a wake, R a resume — where the timehist carries it (`--state`); otherwise by a wakeup row after the schedule-in of the wake it would continue and at or before this schedule-in: `sched_waking` fires only for a thread already in a sleep state and can precede the sleeper's own switch-out by microseconds (kernel `try_to_wake_up`, v6.17: `trace_sched_waking` after `ttwu_state_match`, before the dequeue and the `on_cpu` wait; 9.7 D21). `merge_resumes` in `build/analyze.py` (state, else row) and `campaign/analyze.py` (row: 9.5's campaign began without the state, so the row decides for every repeat, and the state its later repeats record counts where the row disagrees, 9.5 D39; `thunderbird-send`, which starts with the state recorded: state, else row, 9.5 D40).
- **A component's gaps** (9.5 D71): over its merged wake times — every thread of it, as the compiler emits one stream per component — laid out on the span observed and wrapped round, the last wake's gap running to the first: the phase; an operation's windows end to end, so the pause between two operations is no gap of the operation's; a renderer entry's renderers end to end, one in which the thread never woke adding its time (9.8 D26). The gaps sum to the span, one per wake, so the rate a gap table implies is the rate measured. A repeat's rate is its exact count over its span, never rounded.
- **A table** (9.5 D17, D71): the ten pooled quantiles p1 … p99.9, the sample's minimum and maximum, and the measured mean of the samples in each of the eleven intervals they bound, held inside its interval with the weighted sum kept; a draw falls inside its interval on a curve that keeps the interval's mean, so the table keeps its quantiles and its mean is the sample's (`meas/distribution.py`, `wlc/sampling.py`).
- **A fresh campaign.** Nothing from an earlier run is pooled into a new campaign, and a campaign has no cross-machine check (9.6 D11).
- **Tag** `meas-ci:<workflow>:<YYYY-MM-DD>`, the launch date of the campaign's first batch (9.5 D27). A campaign spans several runs; each repeat's run id is in the pooled record and in the archetype's `validation_stats.run`. The raw records of a campaign are one release. A run-number tag (`meas-ci:cli:3`) names a one-run campaign from before this form.

## The stability rule

One rule for every campaign: the repetition method of `kalibera-ismm13` (verified, `docs/references.md`), applied by `dataset/tools/meas/stability.py` through each slice's pool. `georges-oopsla07` §4.1–§4.3 describes the same method independently. Two elements are this project's design: which values the rule covers, and the 1 µs floor.

- **It covers every value the fold-in carries** (design; 9.5 D30, 9.6 D23): each carried table — the quantile table of runs, gaps, blocks, durations or per-input runs of a component, role or program — and each carried rate or share. Each is tested on its own: per carried component and for the residual, never an average across components, which weights a thread waking a few times a phase like a busy one and lets a failing component pass behind stable ones (9.8 D17). Thread counts, carried as their observed range, are not on the list.
- **The repeat is the level of repetition**: repetition "must be done at the highest level that has random variation to avoid bias" (§3) — here the job, one full protocol on a fresh runner.
- **Per repeat, a table is its mean**; a rate or share is its value: "the multi-level interval is the same as if we had used a single-level interval for the means of all data from all but the highest level" (§9.3).
- **Interval**: the 95 % confidence half-width of the across-repeat mean, a t interval "with ν = rₙ − 1 degrees of freedom" (§9.3, Eq. 4).
- **Tolerance**: 5 % of the mean — the method states its half-widths "within 1%, 1.5%, 2.5% or 5% of the mean" (§11); the 5 % is half the smallest effect a slice reports (9.6, half of the 10 % `-j8` against `-j1` difference; 9.5, half of the +10 % stimulus-sensitivity effect) — or, for times, 1 µs where larger (design: the trace's resolution, `perf sched timehist` printing whole microseconds) (`TOLERANCE`).
- **At least five same-machine repeats**, whatever the half-width at fewer: "We do not show counts of fewer than 5 executions as they could hardly be used to get the variance estimate right" (§11).
- **Repeats are added one at a time until every value on the list holds**: the count "can be established on-line, by adding repetitions until the confidence interval is sufficiently narrow" (§11). By 인지오's decision a slice may add a batch up to the pool's own projection, then continue one at a time, the rule read after each (9.7 D26). Every same-machine repeat obtained is pooled and reported — every landing of it: an index that landed more than once, a relaunch landing while an earlier launch of it was still queued, is pooled once per landing, keyed `<index>@<run id>` (9.8 D24). Where recorded input runs out first, the values of the phases that replay it pool every window it holds and state their half-widths; the values of a phase that runs before any input, the same work in every repeat, keep adding repeats that run that phase alone (9.5 D32: the idle phase).
- **No ceiling on repeats** (9.5 D33): "the required and optimum numbers of repetitions depend on the platform, VM, and benchmark" (§11). A value that does not converge because of how it is observed or analysed is a design question (the loop, step 6), not a reason to stop.
- **A value whose spread follows the machine, not the program** (2026-09-20, 9.6 D29): carried over the repeats obtained, at least five, in place of the tolerance — by 인지오's decision per value, recorded in the slice's changelog, and only for a value that carries none of the effects the slice reports. Its 95 % half-width, observed range and repeat count, the part of the machine its spread follows, and the share of the job's time the quantity holds are stated in the archetype's scope and `validation_stats`. No reported result may rest on a difference in such a value smaller than its stated half-width.
  The decision may cover one class of a subject's values at once where the evidence is that class's: 9.8 D17 and D18 took every run mean of the four desktop subjects, their run times moving together across every thread of a repeat — a per-runner speed on the one CPU model — while the same threads' wake rates held within about 1 %. A value a reported effect rests on is not excepted; the effect is stated on an observable that holds instead (9.8 D18: the Steam client's shown-against-minimised comparison on its wake-rate ratio, 0.7 % spread, the CPU-share ratio reported with its spread). The decision is taken on the evidence after the value is read — 9.8 D17 and D18 on the first batch, before later repeats were launched; 9.8 D21, D23, D24 and 9.9 D29 after the entry's last launch — and the record states when it was taken and the pool's projection (9.8 D28, 9.9 D34). Whether a value so carried is re-measured at a count fixed in advance follows 9.14's sensitivity check.
- **A component whose rate varies between sessions** (9.5 D57): carried with its half-widths over at least five repeats, its three values — rate, gap mean, run mean — together, in place of the tolerance, by 인지오's decision per component. The spread is placed first by three findings: not the analysis (the same threads in every repeat); not the phase's placement — a window of the phase's length slid along one long run (the long-phase probe) moves the value far less than it moves across repeats (9.5: the D52 probes; 9.8: `desktop/within_run.py`); the windows overlap and are correlated, so the within-run figure understates that spread against the independent repeats (9.8 D28); and its weight, the share of the phase's wakes it holds. The scope states both spreads, the share, and, where the component wakes only a few times a phase, that count (9.5 D59; 9.8 D21, D23, D24). Whether such a spread changes a scheduling outcome is a sensitivity question for 9.14. Tooling: `SESSION_SPREAD` in `campaign/pool.py` and `desktop/pool.py`.
- **A sparse component** (9.8 D27; 9.9 D33): one that wakes a few times a phase — the renderer residuals, 1.2–3.4 and 3.6–5.5 wakes per renderer per 600 s phase; the session's audio server and system bus, 2–12 and 0–36 wakes per 1800 s phase, the bus none at all in some phases, its wake rate then read over every repeat and its gap and run means over the repeats it woke in — carried with its half-widths over at least five repeats, its three values together, and its count stated, by 인지오's decision per component. Its spread is the count's own: a window of the phase's length slid along the long-phase probe catches 0–2 of its wakes, so the within-run test that places a between-sessions component cannot place it, and the scope says so. Tooling: `SPARSE` in `desktop/pool.py`.
- **A rare event within a run** (9.5 D64): where a component's mean follows an event a repeat catches none, one or two times — `chrome`'s `MemoryInfra` heavy pass, about one per 22 minutes — the event's runs above a stated threshold (design) leave the component, which is read without them, and the pooled record states the event per repeat: its count, runs, times into the phase and its rate over the phase time pooled (`HEAVY_EVENTS` in `campaign/pool.py`).
- **Qualification**, carried wherever the rule is cited: `maricq-osdi18` recommends nonparametric intervals of the median "unless normality can be demonstrated" (§2); the rule's interval is a t interval.

## Before the first run

Written into the slice's method (a dated amendment) and changelog before the launch:

1. **The list** — every value the fold-in will carry, by the rule above (9.6: `task-9.6-compile/campaign/method.md` §8; 9.5: `task-9.5-interactive-typing/campaign/method.md` §9, the 2026-09-19 entries).
2. **The smallest effect the slice reports** — the tolerance's ground (the rule above).
3. **First batch, with its ground**, at least five repeats. 9.6: six repeats, the first count at which every median passed at the spread of an earlier run's same-model repeats. 9.5: windows 1–5, the stimulus windows already cut and committed. A job the gate stops is not a repeat; the first batch may land fewer.
4. **What a repeat is.** Identical work (a build, a scripted interaction, a playback): the next repeat index. Work driven by recorded input: the next input window, cut by the committed rule (9.5: SWELL-KW continued in participant order, the 136M stream in its seeded order), so every repeat runs the same phases. The input's limit is stated in advance, with what happens at it (9.5: SWELL-KW's Outlook conditions hold eight windows; `thunderbird`'s per-input values stop at eight and state their half-widths, its idle phase continues in repeats without the driven phases).

## Tooling

- **Machine gate** — `dataset/tools/meas/machine_gate.sh`, sourced by the run script right after `runner_spec.py > spec.json`: on another model it records `gate=wrong-machine` and `machine.model`, writes the report and exits 0, before any install or measurement (`dataset/tools/meas/build/run.sh`, `dataset/tools/meas/campaign/run.sh`, `dataset/tools/meas/background/run.sh`, `dataset/tools/meas/desktop/run.sh`).
- **Workflow** — the plan step emits `cpu_model` from the trigger file and the run step passes `MEAS_CPU_MODEL` (`meas-build.yml`, `meas-interactive.yml`, `meas-playback.yml`, `meas-background.yml`, `meas-desktop.yml`). A push that changes the trigger file (`.github/campaign-build.json`, `.github/campaign.json`, `.github/campaign-background.json`, `.github/campaign-desktop.json`) starts the runs; nothing else does. A family's `repeats` is one list for every app or a map app → list; a family with `apps: []` runs nothing. The workflows have no concurrency group: a new push never cancels a run in flight.
- **Pool** — `dataset/tools/meas/build/pool.py`, `dataset/tools/meas/campaign/pool.py`, `dataset/tools/meas/background/pool.py` and `dataset/tools/meas/desktop/pool.py`, each with `--cpu-model "EPYC 7763"`: pools only that model, lists gated jobs and other-model repeats without pooling them, carries `cpu_model`, `kernel` and `run_id` per repeat, and evaluates the rule on the slice's list (`stability.py`). The campaign, background and desktop pools find artifacts at any depth, so each run downloads into its own folder, and print per value the repeat count at which its present spread would hold.
- **Fold-in** — `dataset/tools/meas/campaign/fold_in.py` (9.5) and `dataset/tools/meas/desktop/fold_in.py` (9.8) take the scope's CPU model and kernel from the pooled record; 9.6's entries were written from `build/pool.py`'s record.
- **Loop** — `dataset/tools/meas/loop/`, run from the development machine; downloads under `$MEAS_LOOP_WORK` (default `~/.cache/meas-loop`). `launch.py <first|added|retried|probe> <family>/<app>:<k>…` writes the trigger file, commits and pushes; `status.py <family> --since N` lists each application's landed, in-flight and gated-only windows; `pool_runs.py <family>/<app> --since N` downloads every landed repeat across the campaign's runs, pools it and prints the rule and the validity of each repeat; `watch.py <family>/<app>… [--since N]` relaunches gated windows one at a time per application and exits on a landing or a failure, reading only runs from N on (default: the family's newest run at start); `cut_windows.sh N` cuts the recorded-input windows up to N and commits the new ones. A family (`interactive`, `playback`, `build`, `background`, `desktop`, `long-probe`) is a workflow and its trigger file (`loop/common.py`, `FAMILIES`); a new slice's workflow is added there.
- **Long-phase probe** (9.5 D35, D42) — `meas-long-probe.yml`, trigger `.github/campaign-long-probe.json` (loop family `long-probe`, `launch.py probe`): `campaign/run.sh <app> <k> probe` runs the settle and one idle or play phase of the trigger's `phase_s` for that application, nothing after it, under the machine gate; never a repeat. `campaign/slices.py <run-dir>…` prints the steady phase's CPU and wakes per 10 s slice, per run and averaged. A family whose phases `campaign/analyze.py` does not name runs its probe as a mode of its own workflow instead, never a repeat, its slice profile from its own analyzer (9.8 D13, D14: `meas-desktop.yml` in `probe` mode, `desktop/analyze.py`).
- **Windows** — `dataset/tools/meas/campaign/build_windows.py --repeats N` (SWELL-KW) and `dataset/tools/meas/probe/aalto_streams.py --repeats N` (136M; needs `SSL_CERT_FILE=/etc/ssl/cert.pem` on the development Mac) cut windows 1…N; windows 1…N−1 come out byte-identical and are verified so before the new ones are committed. An empty window is not committed.

## The loop

1. **Launch** (`launch.py first …`). The trigger file is written with `json.dumps(…, indent=2) + "\n"`, committed (`chore(<slug>/phase-9): campaign — …`) and pushed; the run id is noted.
2. **Gate** (`watch.py`). A job that drew another model ends within about 20 s. Read its `report.json` (`gate`, `machine.model`) before calling it gated, then relaunch the same window (recorded input) or the next index (identical work) at once. At most one relaunch or added repeat of an application is in flight at a time — except a first batch's gated indices, which are relaunched together in one push (2026-09-20, 인지오's decision): they are the indices the batch already named, and every one of them has to land for the batch. `watch.py` relaunches one at a time; a batched relaunch is `launch.py retried <family>/<app>:<k>…` naming every gated index of the batch. **The watcher reads only the runs that hold the jobs in flight** — `--since` the run of the latest launch, never the campaign's first run: reading every run of a long campaign takes minutes a pass, and a gated window waits that long unrelaunched (2026-09-19, `code` window 19).
3. **Landing** (`pool_runs.py`). Download each landed artifact into its own folder under a folder per run (`gh run download <run> -n <artifact> -D <dir>/<run>/<artifact>`; `-n` extracts flat), then pool the application.
4. **Validity** (`pool_runs.py` prints it), before a repeat counts: gate open on the EPYC 7763; every phase present (the pool drops a phase missing from any repeat); the replay sent every event of its window (`replay.jsonl` against `windows.json`) and every operation completed (`n_ok`, `n_failed`); every non-zero return code explained (`perf record` 130 is the SIGINT stop; `freshclam` 2 is the system service holding its lock, with the same signature database in every repeat); screenshots where the stimulus decides where input lands; where a settle applies, the steady phase's 10 s slice profile (9.5 D35); the measured tree holding no harness process (`gate=harness-in-tree`, 9.8 D14); a shaped network phase whose bytes went through the shaper (9.7 D27; a runner without the accelerated-networking VF stops at `gate=no-vf` and is relaunched like a machine-gate stop); the family's own checks (desktop, 9.8 D13: the renderer count against the job's minimum, the page server answering, the chat client's session reaching the homeserver, one origin count across repeats). A repeat that fails it is left out of the pool with its reason (`pool_runs.py --exclude K --exclude-why TEXT`; the artifact moves to `<pool folder>-excluded` and the pooled record carries `excluded_repeats`), and the rule, the projection and every value are read over the rest (9.5 D47).
5. **Check** (`pool_runs.py`; `cut_windows.sh`, `launch.py added`). The rule holds → the application is done; a repeat already in flight is pooled and reported when it lands. A repeat launched on a pool that held a repeat later left out by the validity step, when the rule holds over the valid repeats, was wrongly launched and is not pooled (9.7 D27: `game-download`'s repeat 23). It does not → add one repeat: cut the next window first when the input is recorded, commit the window, then push the trigger.
6. **A spread the design makes.** When the spread follows the harness rather than the application, the fix is a design decision for 인지오, not more repeats (9.5 D28: the replayed clicks and scrolls moved `soffice`'s typing up a 76-page document, a 36 % spread; the typing is now keys only and the earlier repeats are superseded). A spread that follows the input itself (9.5 `code`: denser typing by later participants, fewer language-server re-checks per key) is what added windows average over. The same holds for a spread the analysis or the observation makes (9.5 D33: a pool thread renamed per run splits into components absent from most repeats; a few long runs in some repeats moving a component's mean).
7. **Done.** The pooled `results.md` and `pooled.json` go into the slice's `campaign/` folder, titled with the campaign tag and its runs; each archetype's row — repeats, the values on the list and the widest half-width among them, what stopped it, jobs and gated draws — goes into `measurement-campaign-record.md`; the raw records are released (outward-facing: ask first); then the fold-in.
