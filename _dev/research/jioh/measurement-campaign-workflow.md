# Measured values — campaign workflow

How a domain slice obtains the values its archetypes carry from a measurement on a GitHub-hosted runner: one CPU model, repeats added until the stability rule holds. The rule and the measurement decisions below hold for every campaign; a slice's method states only its own list, input and first batch. Fixed on 2026-09-19 from the 9.6 and 9.5 campaigns (9.6 changelog D10–D11, D23–D26; 9.5 changelog D26–D30, D32–D33). Parent: `research-slice-workflow.md`. Applies to every archetype whose values carry a `meas-ci` tag — after 9.5 and 9.6: 9.7 (`file-backup`, `file-archiver`, `game-download`), 9.8 (`electron-comms`), 9.9 (`system-daemon`).

## What a measured value is

- **This software on this machine** (9.5 D10): one observation, pinned to one CPU of a 4-vCPU `ubuntu-24.04` runner (9.5 D21), its runner spec written into the archetype's scope.
- **One CPU model: the AMD EPYC 7763.** A hosted runner guarantees a shape, not a processor; each job is an independent draw from several models, and one core of another model differs by a different factor per program (9.6: a Xeon Platinum 8573C ran `cc1` at 0.72× and `fixdep` at 0.50× the EPYC's time). Machines of one nominal type differ, so the machine is held and the repeat count read on it (`maricq-osdi18`: "software run repeatedly on the same server (or a different server with supposedly identical parts) can produce performance results that differ with each execution", abstract). The EPYC 7763 is the most frequent model in the recorded draws (9.6 D11: 26 of 56 jobs; the released 9.5 campaign: 22 of 45, `task-9.5-interactive-typing/campaign/machine-draws.md`). A job on any other model measures nothing.
- **A fresh campaign.** Nothing from an earlier run is pooled into a new campaign, and a campaign has no cross-machine check (9.6 D11).
- **Tag** `meas-ci:<workflow>:<YYYY-MM-DD>`, the launch date of the campaign's first batch (9.5 D27). A campaign spans several runs; each repeat's run id is in the pooled record and in the archetype's `validation_stats.run`. The raw records of a campaign are one release. A run-number tag (`meas-ci:cli:3`) names a one-run campaign from before this form.

## The stability rule

One rule for every campaign (`dataset/tools/meas/stability.py`, applied by each slice's pool).

- **It covers every value the fold-in carries**: each carried table — the quantile table of runs, gaps, blocks, durations or per-input runs of a component, role or program — and each carried rate or share. Thread counts, carried as their observed range, are not on the list.
- **Per repeat, a table is its mean**; a rate or share is its value. The repeat is the level with random variation, and the interval is taken across repeats over their means: "the mean values x̄ᵢ across multiple VM invocations are independent" (`georges-oopsla07` §4.2); "the multi-level interval is the same as if we had used a single-level interval for the means of all data from all but the highest level" (`kalibera-ismm13` §9.3).
- **Interval**: the 95 % confidence half-width of the across-repeat mean, Student's t with k − 1 degrees of freedom (`georges-oopsla07` §4.1; `kalibera-ismm13` §9.3, Eq. 4).
- **Tolerance**: the larger of 5 % of the mean and 1 µs for times — the trace's resolution, `perf sched timehist` printing whole microseconds — and 5 % for rates and shares (`TOLERANCE`). The 5 % is half the smallest effect a slice reports: 9.6, half of the 10 % `-j8` against `-j1` difference; 9.5, half of the +10 % stimulus-sensitivity effect.
- **At least five same-machine repeats**, whatever the half-width at fewer: "We do not show counts of fewer than 5 executions as they could hardly be used to get the variance estimate right" (`kalibera-ismm13` §11).
- **Repeats are added one at a time until every value on the list holds**: the count "can be established on-line, by adding repetitions until the confidence interval is sufficiently narrow" (`kalibera-ismm13` §11). Every same-machine repeat obtained is pooled and reported. Where recorded input runs out first, the values of the phases that replay it pool every window it holds and state their half-widths; the values of a phase that runs before any input, the same work in every repeat, keep adding repeats that run that phase alone (9.5 D32: the idle phase).
- **No ceiling on repeats** (9.5 D33): `kalibera-ismm13` §11 sets none — "the required and optimum numbers of repetitions depend on the platform, VM, and benchmark". A value that does not converge because of how it is observed or analysed is a design question (the loop, step 6), not a reason to stop.
- **Qualification**, carried wherever the rule is cited: `maricq-osdi18` recommends nonparametric intervals of the median "unless normality can be demonstrated" (§2); the rule's interval is a t interval.

## Before the first run

Written into the slice's method (a dated amendment) and changelog before the launch:

1. **The list** — every value the fold-in will carry, by the rule above (9.6: `task-9.6-compile/campaign/method.md` §8; 9.5: `task-9.5-interactive-typing/campaign/method.md` §9, the 2026-09-19 entries).
2. **The smallest effect the slice reports** — the tolerance's ground (the rule above).
3. **First batch, with its ground**, at least five repeats. 9.6: six repeats, the first count at which every median passed at the spread of an earlier run's same-model repeats. 9.5: windows 1–5, the stimulus windows already cut and committed. A job the gate stops is not a repeat; the first batch may land fewer.
4. **What a repeat is.** Identical work (a build, a scripted interaction, a playback): the next repeat index. Work driven by recorded input: the next input window, cut by the committed rule (9.5: SWELL-KW continued in participant order, the 136M stream in its seeded order), so every repeat runs the same phases. The input's limit is stated in advance, with what happens at it (9.5: SWELL-KW's Outlook conditions hold eight windows; `thunderbird`'s per-input values stop at eight and state their half-widths, its idle phase continues in repeats without the driven phases).

## Tooling

- **Machine gate** — `dataset/tools/meas/machine_gate.sh`, sourced by the run script right after `runner_spec.py > spec.json`: on another model it records `gate=wrong-machine` and `machine.model`, writes the report and exits 0, before any install or measurement (`dataset/tools/meas/build/run.sh`, `dataset/tools/meas/campaign/run.sh`, `dataset/tools/meas/background/run.sh`).
- **Workflow** — the plan step emits `cpu_model` from the trigger file and the run step passes `MEAS_CPU_MODEL` (`meas-build.yml`, `meas-interactive.yml`, `meas-playback.yml`, `meas-background.yml`). A push that changes the trigger file (`.github/campaign-build.json`, `.github/campaign.json`, `.github/campaign-background.json`) starts the runs; nothing else does. A family's `repeats` is one list for every app or a map app → list; a family with `apps: []` runs nothing. The workflows have no concurrency group: a new push never cancels a run in flight.
- **Pool** — `dataset/tools/meas/build/pool.py`, `dataset/tools/meas/campaign/pool.py` and `dataset/tools/meas/background/pool.py`, each with `--cpu-model "EPYC 7763"`: pools only that model, lists gated jobs and other-model repeats without pooling them, carries `cpu_model`, `kernel` and `run_id` per repeat, and evaluates the rule on the slice's list (`stability.py`). The campaign and background pools find artifacts at any depth, so each run downloads into its own folder, and print per value the repeat count at which its present spread would hold.
- **Fold-in** — `dataset/tools/meas/campaign/fold_in.py` takes the scope's CPU model and kernel from the pooled record.
- **Loop** — `dataset/tools/meas/loop/`, run from the development machine; downloads under `$MEAS_LOOP_WORK` (default `~/.cache/meas-loop`). `launch.py <first|added|retried> <family>/<app>:<k>…` writes the trigger file, commits and pushes; `status.py <family> --since N` lists each application's landed, in-flight and gated-only windows; `pool_runs.py <family>/<app> --since N` downloads every landed repeat across the campaign's runs, pools it and prints the rule and the validity of each repeat; `watch.py <family>/<app>… [--since N]` relaunches gated windows one at a time per application and exits on a landing or a failure, reading only runs from N on (default: the family's newest run at start); `cut_windows.sh N` cuts the recorded-input windows up to N and commits the new ones. A family (`interactive`, `playback`, `build`, `background`) is a workflow and its trigger file (`loop/common.py`, `FAMILIES`); a new slice's workflow is added there.
- **Windows** — `dataset/tools/meas/campaign/build_windows.py --repeats N` (SWELL-KW) and `dataset/tools/meas/probe/aalto_streams.py --repeats N` (136M; needs `SSL_CERT_FILE=/etc/ssl/cert.pem` on the development Mac) cut windows 1…N; windows 1…N−1 come out byte-identical and are verified so before the new ones are committed. An empty window is not committed.

## The loop

1. **Launch** (`launch.py first …`). The trigger file is written with `json.dumps(…, indent=2) + "\n"`, committed (`chore(<slug>/phase-9): campaign — …`) and pushed; the run id is noted.
2. **Gate** (`watch.py`). A job that drew another model ends within about 20 s. Read its `report.json` (`gate`, `machine.model`) before calling it gated, then relaunch the same window (recorded input) or the next index (identical work) at once. At most one relaunch or added repeat of an application is in flight at a time. **The watcher reads only the runs that hold the jobs in flight** — `--since` the run of the latest launch, never the campaign's first run: reading every run of a long campaign takes minutes a pass, and a gated window waits that long unrelaunched (2026-09-19, `code` window 19).
3. **Landing** (`pool_runs.py`). Download each landed artifact into its own folder under a folder per run (`gh run download <run> -n <artifact> -D <dir>/<run>/<artifact>`; `-n` extracts flat), then pool the application.
4. **Validity** (`pool_runs.py` prints it), before a repeat counts: gate open on the EPYC 7763; every phase present (the pool drops a phase missing from any repeat); the replay sent every event of its window (`replay.jsonl` against `windows.json`) and every operation completed (`n_ok`, `n_failed`); every non-zero return code explained (`perf record` 130 is the SIGINT stop; `freshclam` 2 is the system service holding its lock, with the same signature database in every repeat); screenshots where the stimulus decides where input lands.
5. **Check** (`pool_runs.py`; `cut_windows.sh`, `launch.py added`). The rule holds → the application is done; a repeat already in flight is pooled and reported when it lands. It does not → add one repeat: cut the next window first when the input is recorded, commit the window, then push the trigger.
6. **A spread the design makes.** When the spread follows the harness rather than the application, the fix is a design decision for 인지오, not more repeats (9.5 D28: the replayed clicks and scrolls moved `soffice`'s typing up a 76-page document, a 36 % spread; the typing is now keys only and the earlier repeats are superseded). A spread that follows the input itself (9.5 `code`: denser typing by later participants, fewer language-server re-checks per key) is what added windows average over. The same holds for a spread the analysis or the observation makes (9.5 D33: a pool thread renamed per run splits into components absent from most repeats; a few long runs in some repeats moving a component's mean).
7. **Done.** The pooled `results.md` and `pooled.json` go into the slice's `campaign/` folder, titled with the campaign tag and its runs; each archetype's row — repeats, the values on the list and the widest half-width among them, what stopped it, jobs and gated draws — goes into `measurement-campaign-record.md`; the raw records are released (outward-facing: ask first); then the fold-in.
