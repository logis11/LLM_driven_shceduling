# Reader input — task 9.10 scenarios and timelines, stage 2 search

Given to each class reader verbatim. Readers do not see the repository's current values. Written 2026-10-01 from `../scope-card.md`.

## Topics

- **T1 Application co-occurrence on real desktops.** Which applications and background programs are open or running at the same time on real users' desktop computers during everyday activities — document work, web browsing, e-mail, software development and compiling, gaming, music and video playback, video calls, photo and video editing, transcoding and rendering, backups, file indexing — as logged or sampled from real machines (process lists, window lists, application-usage logs, telemetry): how many applications are open at once, which combinations occur and how often, how long each stays open, what runs unseen in the background; per population, operating system and period.
- **T2 Foreground focus and switching.** Logged or observed sequences of foreground application or window focus on desktop computers: dwell time per focus, switches per hour, return patterns (A → B → A), the length of continuous work on one activity, interruptions and resumption; the statistic each source reports (mean, median, a distribution, per user), its granularity (application, window, task, activity), its population and its logging method. Public datasets with application or window names and timestamps from desktop use — for example the SWELL-KW computer-interaction logs, BEHACOM, DesktopBench / FOCAL, the Mozilla Test Pilot studies, OS or browser telemetry releases — with the fields each carries, how to obtain it and its licence.
- **T3 Browser windows, tabs and renderer processes.** How many browser windows and tabs desktop users keep open and how many are visible at once, from logged data (browser telemetry, logging studies, field data); how Chromium on desktop Linux maps windows, tabs, sites and frames to renderer processes (site-per-process, process reuse and the process limit, the spare renderer); any observation of the number of renderer processes for a given set of open tabs.
- **T4 Games and their companions on Linux.** The process and thread population of a running game on Linux, native and under Proton / Wine: thread counts, thread names (`comm`), which threads are busy. What runs beside a game (the Steam client and its helpers, the Steam overlay, voice chat, a browser, a nested compositor such as gamescope on a desktop as against the Steam Deck). Whether and when the Steam client downloads or updates content while a game runs by default, and what its download settings do. The frame cadence a nested compositor runs at on a desktop.
- **T5 Background jobs a desktop runs unasked.** What a stock desktop Linux installation runs without the user asking — Ubuntu 24.04 desktop first; Fedora Workstation, Debian and Arch for comparison — through systemd timers, cron jobs and package-manager hooks, with each job's name, schedule, trigger and typical duration: anti-virus scans and signature updates (ClamAV), file indexers (GNOME Tracker / LocalSearch, KDE Baloo, plocate or mlocate `updatedb`), backups (`dpkg-db-backup`, Déjà Dup, Timeshift, Snapper), kernel-module rebuilds after a kernel update (DKMS autoinstall: which modules desktops commonly build — NVIDIA, VirtualBox, ZFS, v4l2loopback and others — their object counts, build durations and parallelism), man-db, fstrim, logrotate, package metadata refreshes, firmware updates. What triggers a file indexer's full rescan on a desktop, and how often.
- **T6 Batch jobs the user starts.** What batch jobs desktop users start themselves and how large they are — video transcodes and renders (source length, settings, duration on a desktop CPU), local ML training or fine-tuning, local AI inference, compiles of their own projects (objects per build, incremental against full), archive creation, backups started by hand — from surveys, telemetry, logs or benchmark definitions.
- **T7 Desktop scenario benchmarks.** What PCMark 10, SYSmark 30, SYSmark 25 and 2018, UL Procyon and CpsMark+ define as their scenarios: the applications in each, the order in which workloads run, which applications run concurrently inside a scenario (a job in the background while another application is used in the foreground), input sizes, per-scenario durations; whether any of them defines a backup, archive, malware-scan, software-compile, game-download or ML-training workload.
- **T8 Process names on Linux.** The `comm` strings (the kernel's 15-byte truncation) and executable names under which these programs appear on Ubuntu 24.04 and other current distributions, and whether each is in a default desktop install or packaged at all: LibreOffice Writer, Evince, VS Code, Google Chrome and Chromium, Firefox, Thunderbird, GIMP, darktable, Kdenlive and the process its renders run in, Blender, mpv, VLC, Spotify, Zoom, Microsoft Teams clients, Slack, Discord, Element, Steam and its helpers, gamescope, Wine / Proton (the wine server and a game's process), Tracker / LocalSearch, Baloo, plocate's `updatedb`, ClamAV (`clamscan`, `clamd`, `freshclam`), borg, rsync, rclone, 7-Zip, tar, xz, HandBrakeCLI, ffmpeg, python3, make, gcc and `cc1`, DKMS, GNOME Shell, Xorg and Xwayland, PipeWire, systemd, `dbus-daemon` and `dbus-broker`. What share of Linux desktop sessions run X11 against Wayland; when Xwayland starts and stops in a GNOME Wayland session.
- **T9 Launch and first minutes.** What a desktop application does in the minutes after it starts (start-up work, cache warm-up, first sync) as measured on Linux; how often desktop users start applications during a session (launches per hour, applications started mid-session) from logged data.
- **T10 Rates of operations in real use, and a video call's processes.** How often users perform heavy operations inside an application — send an e-mail (with or without an attachment), load a web page, apply an image filter, render a video preview, receive a chat message — per hour or per session, from logging studies, telemetry or field data. The process and thread structure of a video call on Linux for Zoom, Microsoft Teams, Google Meet and Jitsi in a browser (one process or several; audio and video threads).
- **T11 CI observability.** Given a GitHub Actions hosted runner (4 vCPUs, Ubuntu 24.04, no GPU, no physical display, Xvfb available, sudo available) on which the load is pinned to one CPU with `taskset` while the instruments run on the others (`perf sched record` on `CLOCK_MONOTONIC` read with `perf sched timehist` and its wakeup rows, taskstats with delay accounting, `/proc` snapshots with each process's command line): which of the questions above can be observed there — a game under Proton / Wine with software rendering beside the Steam client, its process and thread population and names, without a Steam account where that is required; the Steam client downloading while a game runs; a DKMS autoinstall of a real module after a kernel package is installed, its process population and duration; which systemd timers and cron jobs a stock Ubuntu 24.04 desktop install (`ubuntu-desktop` or `ubuntu-desktop-minimal`) schedules and what each runs; the `comm` strings of the programs in T8 once installed and run; an incremental backup; an application's launch work; a browser with several windows; a video call in a browser between two local peers. What the runner cannot observe.

## Classes

- **S1** — peer-reviewed and preprint literature (T1, T2, T3, T4, T6, T7, T9, T10).
- **S2** — primary project and vendor documentation and source code (T3, T4, T5, T7, T8, T10).
- **S3** — public traces, datasets, logs, bug reports with process listings or timer lists, benchmark databases (T1, T2, T3, T4, T5, T6, T9, T10). Where a dataset is open and downloadable — SWELL-KW's computer-interaction logs first: per participant, the sequence of focused applications and windows, dwell times and switches — the reader downloads it and computes what locates a candidate, labelled as the reader's own.
- **S4** — own measurement on a CI runner (T11): documentation research and, where the reader can, checks of package availability, install routes and timer units from public sources. Nothing is measured in this session.

Rules for every class:

- **Which side of the program a value describes.** A value about what a program does — its processes, threads, names, CPU, wakes, durations of its own work — is a candidate only from a Linux observation; observations on other platforms are recorded as context and marked so. A value about what the user does — which applications they keep open, focus and switching, tabs and windows, how often they send, load, filter or render, which jobs they start and how large — is a candidate from any platform, its platform, population and period recorded.
- **Documents of deployed software support existence only.** A vendor page or a project's documentation shows that a scenario, setting, timer or job exists; how often, how much or how users behave needs an observation.
- **One observation.** For each candidate state whether it is one observation (one population, one trace, one run, one log) and what it covers; several documents about the same observation count as one source.

## Record format

Each reader writes `search/S<k>-<class>.md`:

1. **Search log** — one row per query: date, engine or venue, query terms, hits followed, dead ends with the HTTP status.
2. **Candidates** — per candidate: a provisional id `S<k>-NN`; full citation; copy read (URL or commit, version, date accessed, local path under `sources/S<k>-NN/`, SHA-256 of each file fetched); verbatim passages with locators (page, section, table, `file:line` at a commit); coverage per topic — covers (naming the object, unit, statistic, scope and population) or does not cover; whether it is one observation and whether machine or platform, subject (program, version, state, population) and window are named. Where the reader computes a number from downloaded data (a count over a log, a percentile over a file), the computation is labelled as the reader's own and the command recorded; it locates a candidate, it is not a value.
3. **Not found** — topics with no candidate, with the searches that established it.

Source copies go to `sources/S<k>-NN/` (gitignored; they do not survive this clone, so the record must be self-sufficient: everything a reader needs is in the quoted passages and the copy identification, never "see the local file"). Verbatim means verbatim; a passage that cannot be quoted is not a passage.
