While this can be exceeded (e.g., if Site Isolation is enabled and the user has more open sites than the limit), Chromium makes an attempt to start randomly reusing same-site processes when over this limit. For example, if the limit is 100 processes and the user has 50 open tabs to `example.com` and 50 open tabs to `example.org`, then a new `example.com` tab will share a process with a random existing `example.com` tab, while a `chromium.org` tab will create a 101st process. Out-of-process iframes (OOPIFs) and [fenced frames](…) use this approach, such that an `example.com` iframe in a cross-site page will be placed in an existing `example.com` process (in any browsing context group), even if the process limit has not been reached."
  - lines 476–479: "**Spare Process**: Chromium often creates a spare RenderProcessHost with a live but unlocked renderer process, which is used the next time a renderer process is needed. This avoids the need to wait for a new process to start."

- **Consequence.** On Linux a Chromium or CEF window covered by another application's window is not marked occluded and its pages are not marked hidden by occlusion. Page visibility changes on minimise or when the embedder says so, not when something covers the window.

**Copy read.** Steam Linux client manifest `https://media.steampowered.com/client/steam_client_ubuntu12`, version `1788652215`, fetched 2026-09-20, SHA-256 `5228839d0ef4975c83758c10f1b06aa26b26048d2fdb4a68acf0b95c1f14c60a`; from the `bins_ubuntu12` package named in it, the member `ubuntu12_64/steamwebhelper` (10 582 536 bytes, SHA-256 `6568395326722b6eac1bd6cb55dc52b47db6afdc8d42f97f8db56458fd5f6940`) and the members `ubuntu12_64/steamwebhelper.sh` (3 928 B) and `ubuntu12_64/steamwebhelper_sniper_wrap.sh` (623 B), extracted by range request against the zip's central directory. Strings below are byte matches in the extracted binary, each quoted with its neighbours; they are names present in the binary, not observed behaviour.

- **Steam does not depend on platform occlusion.** The binary carries its own message types: `CMsgWasHidden` with fields `browser_handle` and `hidden`, and `CMsgSetWindowVisibility` with `browser_handle`, appearing together in a protobuf field-name block ("`CMsgGoForward | browser_handle | CMsgGoBack | browser_handle | CMsgWasHidden | browser_handle | hidden | CMsgSetWindowVisibility | browser_handle`") and again among generated template names (`CHTMLProtoBufMsgI13CMsgWasHiddenE`). So the client tells the helper explicitly when a browser view is hidden.
- **Steam has a throttling switch of its own.** `set_background_throttling_disabled` — the generated setter for a `background_throttling_disabled` field — sits in a block of browser-view controls: "`browserview_to_renderer | allow_autoplay_without_user_activation | insert_css | set_background_throttling_disabled | forward_to_renderer`".
- **No Chromium throttling switch is passed from the helper.** `disable-background-timer-throttling`, `disable-renderer-backgrounding` and `disable-backgrounding-occluded-windows` appear nowhere in the binary; `--disable-gpu` does. So if Steam suppresses throttling it does so through its own field, not the command line.
- **The launch scripts add only sandbox flags.** `steamwebhelper.sh` passes the client's own arguments through (`exec … steamwebhelper_sniper_wrap.sh "$@"`) and prepends `--no-sandbox`, or `--disable-seccomp-filter-sandbox`, only when unprivileged user namespaces are unavailable or it is running under Flatpak.

### 4.4 What this settles and what it does not

Settled: CEF neither disables nor exposes Chromium's background-page throttling, and gates it on page visibility; on Linux nothing marks a covered window's pages hidden by occlusion; and Steam controls both the visibility signal and a background-throttling flag itself, so the platform finding alone does not decide the outcome for Steam.

Not settled by source: what Steam actually does with those controls while a game runs — whether it sends `CMsgWasHidden` for the client's views and whether `background_throttling_disabled` is set for them. That is runtime behaviour, and no Valve source states it (§3, T3). It is decidable on our venue for the hidden/shown case without a game: run the client under Xvfb, read `/proc/<pid>/cmdline` for every helper to get each one's `--type=` role and switches, and compare the helper's wake behaviour with the client window shown against minimised. Reproducing "behind a fullscreen game" is not obtainable there (S4 §3).

### 4.5 Effect on §3

The T3 bullet is amended in place: what the client's shipped binaries state about its visibility and throttling controls is now on record, while the runtime question stays open.
