## 4. Synthesis per load (cited; inferences labelled)

**Common ground for all four.** The runner is a fresh Azure VM with 4 vCPU, 16 GB, passwordless sudo, kernel `6.17.0-1022-azure` (S4-02, S4-01). That kernel has `PERF_EVENTS`, `TRACEPOINTS`, `SCHED_TRACER`, `TASKSTATS` + `TASK_DELAY_ACCT` + `TASK_IO_ACCOUNTING`, `PSI`, `CGROUPS`/`CPUSETS`, `HZ=1000`, `PREEMPT_VOLUNTARY`, and Ubuntu's `SECURITY_PERF_EVENTS_RESTRICT` (S4-07), so `sudo perf sched record -a -k CLOCK_MONOTONIC` and `timehist -w` work once `linux-tools-6.17.0-1022-azure` is installed (S4-05, S4-06, S4-07); delay accounting must be switched on with `sysctl kernel.task_delayacct=1` before the load starts (S4-04). The pin propagates: every process forked or exec'd under `taskset -c N setsid …` inherits the mask (S4-03), including zygote-forked renderers, CEF helpers and Electron utility processes; `/proc/<pid>/status` `Cpus_allowed_list` verifies it per process, `/proc/<pid>/task/` gives threads, and null-separated `/proc/<pid>/cmdline` carries the `--type=renderer|gpu-process|utility|zygote` role marker shared by Chrome, Chromium, Electron and CEF (S4-03, S4-08, S4-10). What the pin does to a multi-process tree, documented: nothing changes structurally, but every renderer/helper thread now serialises on one CPU with the runner's own agents (input.md); llvmpipe's render threads default to the core count and would join that CPU unless `LP_NUM_THREADS` is set or `--disable-gpu` used (S4-22, inference). Sandbox on 24.04: an unprofiled Chromium-based binary aborts with "No usable sandbox!" (S4-08, S4-26); `--no-sandbox` is the documented workaround and drops the sandbox set-up from the observed tree. The display is Xvfb, a memory framebuffer with no hardware and no vsync (S4-25).

**Browser with loaded tabs (served locally).** Install: nothing to install — Google Chrome 152 (`/usr/bin/google-chrome`) and an unconfined Chromium 152 zip at `/usr/bin/chromium` are on the image; `snapd` runs, so `snap install chromium` is a second route (S4-01). Driving into the state: N URLs on the command line are all navigated at launch, the first as a foreground tab, the rest as background tabs (S4-08 `startup_browser_creator_impl.cc:431-457`), so "loaded tabs" and "backgrounded tabs" are the same launch; to keep background renderers warm pass `--disable-background-timer-throttling --disable-renderer-backgrounding --disable-backgrounding-occluded-windows` (S4-08), and to change which tab is visible from the harness use CDP `Target.activateTarget`/`createTarget(background)` over `--remote-debugging-port` (S4-24). Renderer count is set by the soft process limit that depends on memory and by `--process-per-site`/`--renderer-process-limit` (S4-08). `file://` versus served: with the *snap* Chromium, `/tmp` is a per-snap private mount, so `file:///tmp/tabs/*.html` is not the host's file; pages under a non-hidden `$HOME` path (home plug, auto-connected) or served from `python3 -m http.server` on the harness CPUs work; Flatpak Chromium has `--filesystem=home` and likewise no host `/tmp` (S4-20, S4-21). The preinstalled Chromium has no such boundary (S4-01). Observed per process and thread: yes — roles from `--type=`, threads from `/proc/<pid>/task/`, wakes from `timehist -w`, all inside the pinned tree. Not observable: a GPU process doing real GPU work (llvmpipe/SwiftShader only), display vsync, and a network with real latency (pages are local).

**Electron chat client, idle and under self-hosted traffic.** Element Desktop installs from an unauthenticated apt repository (`element-desktop` 1.12.28, 137 MB) and launches as `/opt/Element/element-desktop`; it ships an AppArmor `userns` profile for 24.04 so it can run with its sandbox, or with `--no-sandbox` as meas-gui.yml does (S4-11, S4-26). Idle without an account = the welcome/login screen, no `/sync` (inference from S4-13). Traffic without external accounts: run Synapse (`pip install matrix-synapse`) or a single binary (Conduit/Continuwuity/Dendrite) on the harness CPUs, enable registration or a shared secret (S4-12, S4-14), point Element at it through `--config`/`ELEMENT_DESKTOP_CONFIG_JSON` with `default_server_config.m.homeserver.base_url` (S4-11), register two users and have a harness script `PUT …/send/m.room.message/{txnId}` (S4-13); the client then wakes on `/sync` long-poll returns — the "client receiving messages" state. Discord's deb is a 2 MB stub that downloads the client from `updates.discord.com` on first run (version unpinned) and reaches only "register a Discord account or log in" (S4-15); Slack's deb reaches its sign-in page (S4-16); neither has a self-hosted server (Spacebar is unverified for the official client). Mattermost desktop + Mattermost server in Docker (preinstalled) is the documented self-hostable pair if a second Electron client is wanted (S4-17). Observation is per process and thread as for the browser (Electron uses the same `--type=` roles, S4-10). Not observable: a real service's message traffic and its gateway/heartbeat cadence (Discord, Slack, Teams need accounts and their servers).

**Steam client.** Install: Valve's `steam_latest.deb` (launcher 1:1.0.0.87) or Ubuntu's `steam-installer` (multiverse; depends on `steam-libs-i386`, i.e. i386 multiarch) (S4-18, S4-07); the client itself is fetched by the bootstrapper on first run ("Requires internet connection for initial installation"), into `~/.local/share/Steam`, where `ubuntu12_64/steamwebhelper` (CEF) lives (S4-18). Steam needs GL; on the runner that is llvmpipe (S4-22). Whether the client stays up at the login window without an account, and whether `-no-browser`/`-silent` suppress the CEF helper, is attested only by ArchWiki and forum posts; Valve documents no options and `steamcmd` is a different, console-only client (S4-18). Observation: the helper processes carry Chromium's `--type=` (inference from CEF; not verified by a Valve source), so role classification applies; `gameoverlayui` and a game beside the client are not obtainable — no GPU, no owned game — and at most an open-source game from universe (`supertuxkart`, `openarena`, `minetest`; S4-07) can run under Xvfb *beside* Steam, which is not "a game launched by Steam" and gives no overlay. Not observable: Steam-launched play, overlay, friends/presence traffic (needs an account), real downloads.

**Zoom client.** Install: `zoom_amd64.deb` 7.2.0.5705 (303 MB, unauthenticated), `sudo apt install ./zoom_amd64.deb` (S4-19). Process tree from the package: `/usr/bin/zoom → /opt/zoom/ZoomLauncher`, `zoom`, `ZoomWebviewHost` (CEF; carries `--type=renderer`), `cpthost`, `aomhost`, `crashpad_handler` (S4-19, reader's listing). Without an account: joining as a guest by meeting ID is documented, and the test meeting (`zoom.us/test`) is the account-free meeting; both need `zoom.us` reachable and put Zoom's servers, not a self-hosted one, on the wire (S4-19). Driving: `zoommtg://zoom.us/join?confno=…&pwd=…` through the desktop entry's `%U`, with Zoom staff's 2021 caveat that the scheme is not officially supported; the display-name prompt needs `xdotool` (S4-19, S4-07). A call with media needs a loopback camera (`v4l2loopback-dkms`, module load on the Azure kernel undocumented) and a PulseAudio server with a loaded module (S4-23, S4-07). Observation per process and thread as above (`ZoomWebviewHost` helpers by `--type=`; `zoom` itself by name). Not observable: a self-hosted meeting, real camera/microphone/GPU/vsync, Zoom's helper-process semantics beyond their names.

**The runner's CPU model varying across jobs.** Documented by GitHub only as a shape (S4-02); input.md's `machine_gate.sh` handles it. Nothing found beyond that.
