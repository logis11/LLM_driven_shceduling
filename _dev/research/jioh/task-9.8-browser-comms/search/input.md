# Reader input — task 9.8 browser and comms, stage 2 search

Given to each class reader verbatim. Readers do not see the repository's current values. Issue #13.

## Topics

- **T1 Chromium's process model and an idle renderer's behaviour.** How Chromium partitions a browsing session into processes (browser, renderer, GPU, utility, zygote), how renderer processes map to tabs, sites and frames on desktop Linux (site isolation, the soft process limit, process reuse), and what a renderer process does when its tab is idle, hidden or backgrounded (timer throttling, intensive wake-up throttling, tab freezing, discarding, memory-saver modes) as Chromium's documentation and source state it; any Linux observation of an idle renderer's wake cadence, CPU per wake and CPU share, per tab state; what Electron and CEF hosts share of this model.
- **T2 Chat and conferencing clients on Linux.** For Discord, Slack, Element, Zoom (and its helper processes) and Teams: process and thread structure on Linux, what the client does while idle (heartbeats, presence, websocket keep-alives, gateway pings, polling — the intervals their protocols or documentation state), what a message or call event costs, and any Linux observation of CPU share, wake cadence or CPU per wake, idle and under traffic; how each can be run without an account or against a self-hosted server.
- **T3 The Steam client behind a running game.** The Steam client's process structure on Linux (the client, its `steamwebhelper` CEF processes and their count, `gameoverlayui`), what it does while a game is running (overlay, friends and presence, chat, downloads), and any Linux observation of its CPU share, wake cadence or CPU per wake during play or idle.
- **T4 Shipped treatment of browsers, renderers and comms clients.** What process-treatment catalogues (ananicy rule sets, distribution defaults) assign to browsers, their renderer processes, Electron chat clients, Zoom and Steam; what the browsers themselves do to background tabs and their processes (priorities, cgroups, efficiency modes); any timing or rate value such a mechanism carries.
- **T5 Public traces and datasets.** Any public trace or dataset with per-process CPU or scheduling data of a Linux desktop browsing session with several renderer processes, of an Electron or CEF client at idle, or of a conferencing client (Perfetto or `perf` traces, bug reports with profiles of idle CPU use, system-monitor logs, benchmark databases), and what fields each carries.
- **T6 Browsers and comms clients as a scheduler workload.** How scheduler evaluations and benchmarks characterise a browser with many renderer processes, an Electron application or a chat client next to interactive work — as many mostly idle processes, as a wake-up source, as background load — with any reported CPU, run/wait or wake figures; what the literature says such a load does to interactivity and why.
- **T7 CI observability under a single-core pin.** Given a GitHub Actions hosted runner (4 vCPUs) on which the load is confined to one CPU with `taskset` while the instruments run on the other CPUs (the tooling is quoted below): for a browser holding several loaded tabs (served locally), an Electron chat client (unauthenticated, or against a self-hosted Matrix homeserver or a local Discord-like server for message traffic), the Steam client, and a Zoom client, whether each can be installed and run there, driven into the state of interest (loaded tabs, backgrounded tabs, an idle client, a client receiving messages) without external accounts, and observed per process and per thread (`perf sched record` / `timehist` with wakeups, `/proc` snapshots, taskstats, process-role classification from command lines); how snap or Flatpak confinement of a browser affects `file://` access to host paths and what a locally served page changes; what the pin does to a multi-process tree; what the runner cannot observe (a service's real message traffic, a GPU, a display, a game beside the client).

## Classes

- S1 — peer-reviewed and preprint literature (T1, T2, T3, T6).
- S2 — primary project and vendor documentation and source code (T1, T2, T3, T4).
- S3 — public traces, datasets, logs, bug reports with profiles and benchmark databases (T1, T2, T3, T5).
- S4 — own measurement on a CI runner (T7; documentation research and, where the reader can, checks of package availability, install routes and kernel configuration from public sources — nothing is measured in this session).

A rule for every class: a response-side value — CPU per wake, wake cadence, run and wait structure, thread and process structure — is a candidate only from a Linux observation; observations on other platforms and traces two decades old are recorded as context, marked as such. A protocol interval (a heartbeat, a keep-alive) stated by a project's documentation or source is a mechanism, recorded as such, not an observation.

`dataset/tools/meas/phase.sh` (lines 2–10): a phase wrapper that runs one command inside a named phase, appending `{"phase","start_us","end_us","rc","pin","cpu"}` to a phases file; `MEAS_PIN=load` (default) runs the command on the one measured CPU, `MEAS_PIN=harness` on the harness CPUs, `MEAS_PIN=none` leaves it alone; a failed phase is recorded, never fatal.

`dataset/tools/meas/machine_gate.sh` (lines 2–7): "same-machine repeats (9.6 changelog D10). Source it. GitHub-hosted runners guarantee a shape (4 vCPU, 16 GB), not a processor: the jobs of one batch are independent draws from a pool of several CPU models, and one core of one model can be a quarter faster than one core of another (9.6 campaign: Xeon Platinum 8573C against EPYC 7763, cc1 CPU per process 0.74). A measured value is "this software on this machine" (9.5 D10), so a campaign names its machine and a job that drew another model stops before measuring anything." — `machine_gate "<substring of the wanted model name>"` reads `/proc/cpuinfo`'s `model name` and returns 1 when the runner is another model; the campaign's wanted model is `EPYC 7763`.

`dataset/tools/meas/stability.py` (docstring): "The pool of same-machine repeats is stable when the 95 % confidence half-width of the across-repeat mean of a carried median (t multiplier, k − 1 degrees of freedom), relative to the mean, is at most TOLERANCE [0.05]. Repeats are added one at a time until it holds; every same-machine repeat obtained is pooled and reported."

`dataset/tools/meas/proc_sampler.py`: a `/proc` poller at the given interval recording per-process CPU ticks, state and (with `--ctxt`) voluntary/involuntary context-switch counters, per pid and per thread. `dataset/tools/meas/runner_spec.py`: records `uname`, `nproc`, `/proc/cpuinfo` model name, `MemTotal`, `/etc/os-release`, the GitHub run ids.

The 9.5 campaign's instrument (`dataset/tools/meas/campaign/run.sh`, `analyze.py`; the interactive and playback workflows), the one that drove a browser with a real page: the application is installed by an app definition (`probe/appdefs.sh`; for Chrome: `google-chrome --no-sandbox --disable-gpu --no-first-run --user-data-dir=/tmp/chrome-data file:///tmp/page.html`, a locally generated page with a text area and 400 paragraphs, plus a `python3 -m http.server 8088` on the harness CPUs serving a scripted feed page for a page-load operation); `run.sh` sources `machine_gate.sh` and stops before measuring on another model (lines 27–31); the application tree is launched `taskset -c "$MEAS_CPU" setsid bash -c "$LAUNCH"` (line 46) and its affinity recorded (line 48); each phase is `pin_harness sudo perf sched record -k CLOCK_MONOTONIC -a -o … -- sleep <secs>` (line 65), read with `perf sched timehist` and `perf sched timehist -w` for the wakeup rows (lines 74, 77), gzipped as the released raw record; `/proc` snapshots at phase boundaries record thread population, CPU time and context switches per process with each process's command line; `analyze.py` `pid_roles` classifies every process from its command line — `--type=renderer` → renderer, `--type=gpu-process` → gpu, `--type=utility` → utility, `--type=zygote` or `--type=broker` → zygote, the rest main — and `pool.py --exclude-roles renderer` drops a role from the pooled record; a wake is a schedule-in preceded by a wakeup event for that thread since its last sleep, a resume after preemption folded into the preceding wake. Its method notes that on a hosted runner "the runner's own agent processes (containerd, the hosted-compute agent, its .NET runtime) are not ours to pin and share the measured CPU".

## Record format

Each reader writes `search/S<k>-<class>.md`:

1. **Search log** — one row per query: date, engine or venue, query terms, hits followed, dead ends with the HTTP status.
2. **Candidates** — per candidate: a provisional id `S<k>-NN`; full citation; copy read (URL or commit, version, date accessed, local path under `sources/S<k>-NN/`, SHA-256 of each file fetched); verbatim passages with locators (page, section, slide, `file:line` at a commit); coverage per topic — covers (naming the object, unit, statistic, scope and population) or does not cover; whether it is one observation (one population, trace, run or log) and whether machine, subject (program, version, state — idle, loaded tabs, under traffic) and window are named. Where the reader computes a number from downloaded data (a count over a log, a percentile over a file), the computation is labelled as the reader's own and the command recorded; it locates a candidate, it is not a value.
3. **Not found** — topics with no candidate, with the searches that established it.

Source copies go to `sources/S<k>-NN/` (gitignored; they do not survive this clone, so the record must be self-sufficient: everything a reader needs is in the quoted passages and the copy identification, never "see the local file"). Verbatim means verbatim; a passage that cannot be quoted is not a passage.
