# Task 9.8 — measurement campaign method (draft, 2026-09-20)

The observation behind the four entries that replace `electron-comms` — the idle hidden renderer, the idle visible renderer, the Electron chat client and the Steam desktop client (changelog D4, D6, D7, D10, D11) — run on GitHub-hosted runners (phase decision 5) under `../../measurement-campaign-workflow.md`, pinned to one CPU (9.5 follow-ups decision 3). Written before any measurement; amended only by a dated entry in §10.

Tooling: a tool tree `dataset/tools/meas/desktop/` (`run.sh`, `analyze.py`, `pool.py`), workflow `.github/workflows/meas-desktop.yml`, trigger `.github/campaign-desktop.json`, and a loop family `desktop` in `dataset/tools/meas/loop/common.py` with the four subjects of §2 as its apps. `meas-gui.yml` — the unpinned 0.2 s `/proc` sampler under forkstat that produced `meas-ci:gui:2`, which the measurement audit found unable to give per-wake distributions — is not retired by this slice: `system-daemon` also carries values from that run and is 9.9's, so the workflow goes when the last entry citing `meas-ci:gui:2` goes.

## 1. Runs

- **Machine.** The AMD EPYC 7763 only; `machine_gate.sh` stops a job that drew another model before any install or measurement, and a gated job is not a repeat (campaign workflow).
- **Tag.** `meas-ci:desktop:<YYYY-MM-DD>`, the launch date of the first batch (9.5 D27); each repeat's run id in the pooled record and in each archetype's `validation_stats.run`.
- **Repeat.** One job per subject per repeat index, that subject's phases in the order of §3. The work is identical in every repeat — this slice carries no `stimulus` and no focus windows (D10), so nothing is driven by recorded input and there are no windows to cut. An added repeat is therefore the next index, not the next window.
- **Modes.** `dry` — one job per subject on shortened phases, to verify the tooling, not pooled; `full` — the campaign. `probe` — the long-phase probe of §3, one job per subject on a single long steady phase read per 10 s slice; it runs in this family, and is never a repeat (9.5 D35, D42). Its artifacts carry the `probe` mode and are excluded from the pooled set.
- **Recorded per job.** `spec.json` (runner spec), the report with `gate` and `machine.model`, CPU model and kernel, the version of every program observed (Chrome or Chromium, Element Desktop, the homeserver, the Steam client build id), and the kernel-config lines for `PERF_EVENTS`, `SCHED_TRACER`, `TASKSTATS`, `TASK_DELAY_ACCT` and `HZ`.

## 2. Subjects

Four, one per entry. Each is run in its own job so that one subject's failure does not cost the others.

1. **Renderer, hidden** — **Google Chrome**, launched as 9.5's campaign launches it (`appdefs.sh`), one window holding a foreground control tab and N measured tabs at N distinct locally served origins, observed past the intensive-throttling grace. A tab that is not the selected tab in its window is a background page on every platform; minimising is unavailable, Xvfb running with no window manager, and a covered window is not occluded on Linux (D4). The control tab carries the same timer as the measured pages: being the selected tab it stays visible to Blink and is never throttled, so it wakes at the timer rate while the measured renderers fall to the documented budget, and the analysis drops the single fastest renderer and records the ratio to the next. It cannot be told apart any other way — a renderer's command line does not name the site it is locked to, and the components' coverage cut selects comms that every renderer shares. The browser is Chrome and not the preinstalled unconfined Chromium because `web-browser` carries Chrome's process tree minus its renderers (9.5 D14) and these entries carry the renderers: the two archetypes are two halves of one application, which the timelines compose as one browser, so they must be the same program. Reusing 9.5's launch path also keeps a working configuration on an image whose user-namespace restriction aborts an unprofiled Chromium-based binary. That path passes `--no-sandbox` (`probe/appdefs.sh`), so `web-browser` and these entries are observed under the same confinement; each entry's scope states the flag, not that the sandbox was absent — a `sandbox_ipc_thr` component appears in 9.5's pooled records with the flag passed. Under Chromium's documented process model a renderer is one site-locked process, so N counts origins and not tabs. The launch adds one flag to 9.5's, `--disable-features=SpareRendererForSitePerProcess`: the spare renderer Chromium keeps warm hosts no page, carries `--type=renderer` like any other, and cannot be told from a measured one afterwards, so it is not created. The flag changes only the renderer population, which is the half `web-browser` excludes and these entries own. Chrome's own renderers — extension processes and the top-chrome WebUI — are dropped in the analysis, read from the whole command lines because the snapshot keeps only the first 120 characters.
2. **Renderer, visible** — the same page set at the same N, opened as N separate windows of one browser, one tab each, nothing interacting with them. Every mapped window's selected tab is visible to Blink: the occlusion tracker that would hide a covered window is Windows-only (D4), so N renderers are visible at once and none is throttled. Two steady phases, the second with the page's timer removed, so both observe one process tree. The page walks a plan from its own load and the run waits until every window reports the step it wants, read from the window title: nothing is typed. Driving it by keystroke does not work here — without a window manager `xdotool windowactivate` does not move X input focus, and the dry run of 2026-09-20 sent all three navigations to one window, leaving two renderers ticking through the phase that was meant to have none.
3. **The page.** One stated local page, identical content at every origin, served over local HTTP from the runner — never `file:///tmp`, because a snap-confined browser has a private `/tmp` and that is the recorded cause of the Phase 2 run's tabs never loading. **The N origins are N loopback addresses** (`http://127.0.0.2:<port>/`, `127.0.0.3`, …), one server answering all of them: a site is scheme plus eTLD+1 (S2-01), which excludes the port, so N ports on one address would not give N site-locked renderers, while N addresses do and need no name resolution.

   **Its timer runs faster than the throttling cap**, and is a `setInterval` so the nesting level reaches the threshold intensive throttling applies at. The hidden page's *wake rate* is then Chromium's documented budget — one wake per second, one per minute past the grace, 3 ms per wake, 1 % of CPU — rather than our choice of content. The *work per wake* is ours and is deliberately trivial, the callback incrementing a counter and returning, so both renderer entries measure a floor: what a renderer costs when its page does nothing but stay alive. A callback sized to spend the allowance would report a ceiling instead, and that ceiling would be multiplied by every renderer task in every timeline on the strength of no observation. Both entries state the floor in their scope.

   Nothing throttles the visible entry, so its wake rate is the timer period we chose. It is therefore run a second time with the timer removed (§2 subject 2): the entry reads the no-timer phase where that phase yields enough, and otherwise reads the timer phase with `wakes_per_s` labelled design. The page is design, written here and released with the raw records.
4. **Chat client** — Element Desktop from the unauthenticated apt repository, pointed through `ELEMENT_DESKTOP_CONFIG_JSON` at a **Synapse** homeserver running on the harness's own CPUs with registration enabled, pinned away from the measured CPU with the driver and perf. Synapse comes from the matrix.org apt repository with its systemd unit masked and is started by the run script from `/opt/venvs/matrix-synapse` under `pin_harness`, systemd otherwise owning the process and defeating the pin. **The client is measured logged in**: an account is created with `register_new_matrix_user` against a registration shared secret and the client is signed in through its UI before the settle, because the idle phase the archetype reads is the `/sync` long poll, which no signed-out client holds — a login screen is the state D7 rejected Discord for. The job verifies the session before measuring and stops recorded if it has none. Synapse rather than Dendrite, which is archived upstream and cannot be pinned responsibly for a re-runnable campaign, and rather than Conduit because the archetype reads the idle phase (D11), where the server only holds a `/sync` long poll open — behaviour the Matrix specification fixes rather than the implementation — so reproducibility decides, and Synapse is the maintained reference implementation and packaged for Ubuntu. Conduit is the fallback if Synapse's startup proves too heavy on the runner, which is a dry-run finding and not a method decision. Two phases: idle, which the archetype reads, and under scripted message traffic, which is recorded and released but feeds no archetype (D11). **The traffic rate is an instrument setting, not a claim about users**: no source states how often a real client receives messages, so the rate is chosen high enough that the traffic phase separates measurably from idle — its purpose being to quantify the gap that the idle entry's stated limitation otherwise only declares — and it is stated here as design.
5. **Steam desktop client** — Valve's client installed from the launcher package or `steam-installer`, started under Xvfb and **logged out**. This job alone runs a window manager (`openbox`) on the harness CPUs, because minimising is a window-manager operation and the shown-against-minimised comparison below is what turns D5's inference into an observation. The renderer subjects keep the bare Xvfb that 9.5 measured `web-browser` under; each entry's scope states which it had. The job signs into nothing, drives no store and performs no account action; the Steam Subscriber Agreement §4.C prohibits automated interaction with Steam's services and §1.C makes an account strictly personal (D6). Beyond its own values this job records, for D5's open question, each helper's `--type=` role and full command line from `/proc/<pid>/cmdline`, and the helper's wake behaviour with the client window shown against minimised.

## 3. Phases

Every subject runs launch → settle → steady, and only the steady phase is carried. A settle is design and is stated per subject (9.5 D34). The settle is a sequence with recorded edges rather than one figure: `launch`, `launch-settle`, for the hidden subject the recorded moment the tabs are backgrounded, `grace-settle`, then `steady`. The grace is defined from that moment, so the moment is written to `phases.jsonl` and `edges.jsonl` and not buried inside a single number. The subjects with more than one steady phase run them in a stated order — the chat client idle before traffic, so the idle the archetype reads is not one that follows a warmed sync and unread state; the Steam client shown before minimised; the visible renderer with the timer before without.

- **Renderer, hidden.** The settle is two parts. Chrome's own launch work has no stated settle in 9.5's campaign — `settle_for()` states one for `soffice`, `gimp`, `kdenlive` and the two `mpv` subjects and for `thunderbird-send`, and a subject without one stops before measuring — and 9.5 D34 names Chrome as carrying launch work past 30 s at up to twenty times the steady CPU. Its `launch-settle` therefore comes from the probe, as `thunderbird-send`'s 390 s did. Then the grace: a hidden page's timers align to one wake per second, and intensive throttling takes them to one per minute after a grace of five minutes by default and **sixty seconds for a page that has finished loading**. The `grace-settle` ends after the grace elapses from the moment the tabs are backgrounded, measured from the load completing.
- **Phase length.** Open, and set from evidence before the first batch. At one wake per minute a short phase yields of the order of ten wakes on the throttled thread — too few for a quantile table, and too noisy a per-repeat mean for the stability rule's half-width to converge at any repeat count. One long-phase probe runs first and its steady phase is read per 10 s slice (`meas-desktop.yml` in `probe` mode; the profile is `desktop/analyze.py`'s, `campaign/slices.py` reaching it through a phase loop fixed to 9.5's names); the phase is set from what it shows and written into §10 as a dated amendment before the first batch (9.5 D35).
- **Renderer, visible; chat client; Steam client.** Nothing throttles these, so their phase lengths are not expected to need the probe, but each is stated here before the first batch rather than chosen during it. Their settles follow 9.5 D34: set from each subject's own traces, after launch and ramp-up work ends.

## 4. Instruments

`perf sched record` on the measured CPU, giving per-schedule run, wait and delay and the wakeups behind them — the instrument 9.5 and 9.6 used, and the one the audit found `meas-gui.yml`'s sampler could not substitute for. Process roles are classified from `/proc/<pid>/cmdline`, whose `--type=` marker distinguishes browser, renderer, GPU and utility processes for Chrome, Chromium, Electron and CEF alike. Affinity inherits across fork and execve, so zygote-forked renderers, Electron utilities and CEF helpers all inherit the pin. No screenshots are needed: no subject takes input.

## 5. Analysis rules, fixed before the run

- **One wake** is a schedule-in preceded by a wakeup event for that thread since its last sleep; a resume after preemption folds into the wake it continues. Decided by the thread's previous switch-out state where the timehist carries it, otherwise by a wakeup row (campaign workflow).
- **Components** are per thread comm (9.5 D16), each carrying `wakes_per_s` and measured `gap` and `run` quantile tables (D17), with a pooled residual for the comms below the coverage cut.
- **Thread counts** are carried as their observed range and are not on the stability list.
- **No pooling across subjects.** Each entry's values come from its own subject's steady phase alone; nothing is averaged across the four, which is the defect the entry being replaced carried.

## 6. The list, the tolerance, the first batch

The four items the campaign workflow requires before a first run.

1. **The list — every value the fold-in carries.** Per entry, per component: the `gap` quantile table, the `run` quantile table and `wakes_per_s`; and the pooled residual's tables. Thread counts are excluded, as above.
2. **The smallest effect the slice reports.** The slice reports two comparisons: hidden against visible renderer, whose documented separation is about sixtyfold in wake rate; and Element under traffic against idle, which under D11 feeds no archetype and lives only in the campaign results. No carried value rests on resolving a difference smaller than 10 %, so the standing tolerance is grounded for this slice unchanged: 5 % of the mean, or 1 µs where larger, `TOLERANCE` in `stability.py` with the trace's resolution as the floor. If a measured difference falls below 10 % it is reported as not resolved at this tolerance rather than as an effect.
3. **First batch.** Five repeats per subject — the rule's minimum — because no prior run of these phases exists to size the batch from, unlike 9.6, which took its first count from the spread of an earlier run. Repeats are added one at a time afterwards until every value on the list holds. A job the gate stops is not a repeat, so a batch may land fewer than five and the gated indices are relaunched together.
4. **What a repeat is.** The next repeat index, as in §1.

9.6 D29's exception — a value whose spread follows the machine rather than the program, carried over the repeats obtained with its half-width, observed range, repeat count and share of the job's time stated — is available but is not invoked in advance. It applies only by 인지오's explicit decision per value, and only to a value carrying none of the effects above.

## 7. Scope, written into every archetype

Each entry states: the runner spec and the CPU model and kernel it was measured on; the version of the program observed; the state it was observed in — hidden past the grace, visible, idle against a local homeserver, or logged out — and what that state is not; and the stated limitations. Specifically: the renderer entries are Chrome launched with `--no-sandbox` on a hosted runner without a GPU and without display vsync, under Xvfb with no window manager, on a page whose timer callback does no work, so their values are floors and not what a renderer showing live content costs; the chat-client entry carries no message-traffic wakes, is one room on a local homeserver, and stands in for account-gated clients; the Steam entry is a client that is neither logged in nor behind a running game, observed under Xvfb with a window manager so that its window can be minimised.

## 8. Release

The raw records of the campaign are one release, as 9.5, 9.6 and 9.7 released theirs. Pooled `results.md` and `pooled.json` go in this folder; each entry's row — repeats, the values on the list, the widest half-width among them, what stopped it, jobs and gated draws — goes into `../../measurement-campaign-record.md`. Publishing the raw records outward is asked before it is done.

## 9. Open before the first batch

- **The phase length of each subject, and N**, which trade directly against each other for sample count: at one wake per minute per renderer, twelve renderers yield about twelve wakes a minute. Both come from the long-phase probe of §3, whose `slices.py` output reports wakes per 10 s slice and therefore measures the yield directly, and both are written into §10 before the first batch.
- **Whether throttled wakes coincide across renderers.** Alignment is documented within a page, and the budget pool allows a lower alignment when there has been no recent wake; whether those grids coincide across renderer processes — so that N renderers wake together rather than independently — is not established by the source read, and it bears on both pooling and what the scheduler sees. The probe's 10 s slice profile shows it as clustering, so it is read there rather than assumed.
- **Whether the visible entry reads the no-timer phase.** §3 runs the visible subject twice, with the page's timer and without it. The entry takes the no-timer phase if the probe shows it yields enough wakes for the quantile tables and for the half-width to converge; otherwise it takes the timer phase and its `wakes_per_s` is labelled design, the timer period being ours. Read from the probe, written into §10 before the first batch.
- **Whether the Steam client holds a stable state logged out.** If it does not, D6's fallback retires that binding instead of measuring it.
