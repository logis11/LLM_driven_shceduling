## Decisions, in the order asked (spec session, 2026-09-09)

1. **Coverage target — all 32 cells, paired.** Three narrower options were on the table: the interactive modes with a C1 base (three files), every C1 base (five), every interactive mode (nine new bases). Rejected because controlled claims never rest on the generalset (building plan §4), so any `false` row left to it is never measured under controlled conditions; because the "five novel designs" cost was overstated (every mode had a liftable segment); and because building plan §3's own organizing frame is the driver-table cell. The first recommendation (three files) was withdrawn as resting on effort and TODO wording rather than research design.
2. **`false` in the batch modes — the same-job reading.** The batch job is itself the background work the attribute judges (the P1b precedent), so `compile/false` is a build nobody asked for. The second-job reading (wanted build plus unwanted indexer) contradicted `c2-p1b` and would make the segment's mode ambiguous. One clarifying clause in the vocabulary's attribute sentence, with changelog.
3. **Cells with no telemetry-visible cue ship as pre-committed misses**, C6 style: excluded from accuracy, reported separately, the `oracle` condition still measures the row. Scoring them would charge the model for a distinction no observer of names and behaviour could make; leaving them empty would break the all-32 target.
4. **C1 grows to sixteen; a new group C7** holds one counterpart per mode, `c7-<mode>` from `c1-<mode>`, including gaming and indexing (the C2 instances stay as two-segment versions). C2 (two-segment pairs from one design) and C4 (label-invariant injection) were rejected as homes: one transform per group.
5. **Interactive counterparts inject `clamscan` on `cpu-batch`**, one name everywhere: the ten `false` cells differ only in mode, and no pair changes tier. Per-mode variety would confound name with mode; a two-name split would need `familiarity` annotations that misstate a tier-3 name as tier 1.
6. **Batch counterparts by the P1b move, name rule tier-matched first with honest fallback**: a verified name at the base's tier; else a name at another tier, added to the tier table, mismatch stated; else the decision-3 case. Rejected: tier-matched only (discards a recognizable cue for a tidy column) and pinning by annotation (misbins the name in the grader).
7. **The scan arrives at 0 s with `total_work` 60 s** so the label holds at every instant under every policy and the pair is one task apart. Mid-segment arrival leaves thirty seconds mislabelled or breaks same-interval pairing; a smaller job finishes at a policy-dependent instant.
8. **Demand class: authored `calibration` on every C7 file and the eight existing derived files** via `patch-meta`; regime read from the manifest. `oversubscribed` cannot hold for a uniform op (gaming's base alone is 1.46); admitting inheritance keeps the exception invisible. Closes the Phase 3 item.
9. **New bases are authored C1 files with lifted task sets**, source in the header, batch jobs resized to finish in 60 s; `meeting` designed fresh on OQ-2's binding. Deriving them with `set-segments` would make C1 half generated and still need a resize op.
10. **Base terms by mode-class pattern with the mode's existing weight**, so no existing `true`-row cap changes (the prior table derives caps from these weights); `indexing/true` gets a turnaround term at 1.0 as a stated assumption, making its cap derived. Exact numbers left to the sub-task at the user's request.
11. **Grid: report and enforce.** 32 rows × five tiers, `ambiguous` outside, CI fails on an empty cell, pre-committed misses marked. Report-only was rejected as the failure mode of August.
12. **Generalset all-32 requirement written; the throwaway pool named as undefined** and left to the RQ0 gate spec rather than defined out of order.
13. **Unwanted work carries no term.** The TODO's "base's terms verbatim" was wrong for batch counterparts (it would reward the unwanted job's progress on a floor-cap row); a C7 entry repeats its base's terms minus the batch term, the lint gains that clause, and the rule explains P1b and P2b after the fact.

## Side questions answered for 인경민 (batch class and the cap)

- **Why a batch class in the simulator at all.** The cap must apply to a set; the workload file carries programs only (no archetype names, no labels), PIDs are excluded from telemetry, and the labels are what is under test, so the executor infers the class from behaviour by one rule fixed across algorithms (a full slice since the last voluntary block; TIMER tasks never). Labelling batch in advance would hand the OS intent — a different experiment.
- **Why the cap at all.** The attribute must reach the CPU scheduler through some lever; class priority is off limits (starvation guard), algorithm choice gives interactive modes nothing (both rows MLFQ), so a per-class share ceiling is the one knob that means the same thing under all four algorithms. Demotion is ordering (a demoted hog still fills every gap and a waking foreground waits a slice); a cap keeps the hog off the lane part of the time, and the idle it leaves costs nothing scored because unwanted work carries no term. Whether it pays is what the C7 interactive pairs measure; finding 5 already shows two modes where it cannot.
- **Where the cap concept came from.** Our own construct, in the proposal's architecture from the first version ("algorithm + parameters + per-class bandwidth caps"; the executor-enforced starvation floor), made the attribute's lever at the 2026-08-23 design meeting, frozen in the config schema on 2026-08-28. Its shipped counterpart is Linux CFS bandwidth control (kernel documentation, verified 2026-09-10: "allows the specification of the maximum CPU bandwidth available to a group or hierarchy", quota per period); the difference is that the kernel caps an administrator-assigned cgroup and our executor caps a behaviourally inferred class. **No reference entry exists yet**; a `linux-sched-bwc` deployed-system entry (existence only) was proposed and not yet added.
