# 2026-08-28 — Task 2.5: repo prep, onboarding guides, and the first contract freezes

Decision session record for sub-task 2.5 (repo prep + onboarding docs), which grew into the first protocol-freeze round. Decisions with rationale; facts verified in-session noted as such.

## Repo structure

- **One top-level tree per component**: `dataset/`, `simulator/`, `daemon/`, `harness/` (+ `docs/`, `_dev/`). Rationale: `dataset/` set the flat-component precedent; trees match ownership so cross-tree needs go through contracts; a `src/` umbrella would add a layer with no owner. `daemon/` is self-contained (validator lives with whoever writes the LLM call — 박이안), overruling an earlier idea of the harness owning the daemon skeleton.
- **Per-tree Makefiles**: a C++ tree and Python trees share no build machinery; owners change their entry points without touching a shared root file. Root Makefile moved to `dataset/Makefile`; CI runs `make -C dataset`.
- Proposal's role table is draft; the tree boundaries are stable under any final assignment.

## Corrected architecture framing (supersedes the first guide drafts)

- **The simulator and daemon never talk at run time.** The daemon runs the whole recognition pipeline offline and emits a **config schedule**; the simulator is a pure function (workload events, config schedule) → trace. Rationale: each side buildable/testable alone; conditions stay comparable because the simulator is condition-agnostic; every condition is "a different recognizer in the same daemon machine."
- **Query points are pinned events only** (arrivals + scripted user-closes). Rationale: keeps telemetry scheduler-independent by construction, resolving building-plan §9's old open item; the alternative (two-pass simulation to learn finite-task exits) buys realism at real complexity cost. Accepted consequences, stated as scope: finite tasks never vanish from telemetry; the recognizer reacts to launches/user-closes, not job completions.
- **Spawn-table children are telemetry-visible**, attributed to the parent's lifetime. Verified in-session: C1-compile's recognition scenario is `{code, make, cc1×N}` (building-plan §3) and the coverage grid counts spawn-child names — invisible children would gut the compile scenarios. Which children exist is compile-time knowledge; only their times are emergent.
- **The daemon has two outputs**: config schedule (simulator-facing) + **recognition log** (grader-facing). Rationale: Layer-1 grading and reasoning-based failure analysis need the per-query proposals, which the schedule deliberately strips.
- **Names+counts aggregation**: telemetry carries `{name, count}`. Verified in-session: duplicates are the canonical norm — compiled `c1-browsing` = 13 tasks named `chrome` (timeline `count:` sugar), `c1-gaming` = 300 × `game.exe` (game-task-chain constructor expansion); counts are themselves recognition signal.
- **Views are extracted by each consumer's own loader** from raw `*.workload.json`; the dataset tree stays consumer-agnostic (no run-file/projection build artifacts). Rationale: dataset tooling shouldn't know its consumers; asymmetry enforced at each parse boundary.
- **LLM inference never occupies the simulated lane** (경민's question): recognition cost is modeled as latency only. If inference consumed simulated CPU, LLM conditions would face different workloads than the oracle — destroying the controlled comparison. Real inference CPU cost is a deployment-accounting item.

## Recognition vocabulary (ratified; normative home `docs/recognition-vocabulary.md`)

- **Modes = the dataset's 16 ground-truth labels** (fine, source-backed), not the proposal's draft 5. Rationale: labels are already frozen into 24 workloads + signed-off grid; fine→coarse grading mappings would inject judgment exactly where measurement must be clean. `ambiguous` is ground-truth-only — on the menu it would be an escape hatch rewarding calibrated cowardice; C6-dual stays a pre-committed miss excluded from scoring.
- **One graded attribute: `background_wanted`** (renamed from `wanted` — bare `wanted` is ambiguous without context; matches the proposal's original `background_is_wanted`). Vacuous-true convention for segments with no background work. Dataset-wide rename executed and recompiled in-session.
- **`encoder` (`has_realtime_encoder`) not adopted.** Debated: dropping it weakens the cross-mode-recurrence argument (gaming-while-streaming becomes inexpressible; the proposal's Family-2 OBS row never got a coreset file — the zero-occurrence fact was verified in-session). Decided against because the attribute has no dataset support today, adding it would mean manufacturing derived files for an undemonstrated dimension, and it doubles the oracle's attribute space. Fixed at one attribute; no deferred-candidates memo (extension rule covers any future promotion). `initiated` overlaps `wanted` semantically and stays an annotation.

## `cpu_scheduler` config schema (frozen)

- Envelope `{algorithm, params, batch_bandwidth_cap}`; MLFQ `{num_queues, timeslice_us, timeslice_growth, boost_interval_us}` (scalar+growth over per-level arrays — arrays invite malformed LLM output and cross-field validation); EDF `{residual_timeslice_us}` with period-implicit deadlines from observed TIMER behavior (proposal's `admission_slack_ms` dropped — undefined semantics; fixed oversubscribed workloads make admission control meaningless in v1, honest misses are the metric); LOTTERY `{batch_share, timeslice_us}` (general ticket vectors reduced to the one ratio situations express; PRNG seed simulator-owned, not model-reachable); FIFO `{}` (knobs would be fake tuning surface).
- Batch class is behaviorally determined, executor-frozen, not configurable; starvation safety executor-owned with no config field (so no proposal can weaken it). Six validation rules incl. `batch_share ≤ cap` and per-variant read scope.
- Sequencing insight: the schema is the driver table's *language* and was decidable immediately; the table's *values* + row-distinctness verification remain separate work (partly gated on a running simulator).

## Trace format (frozen)

- JSONL; `meta` header + seven events: `task_arrive` (spawned children included — emergent times), `task_end`, `ready`, `run_start`, `run_end`, `deadline`, `config_applied`; `x_`-prefixed events harness-ignored (diagnostics without schema negotiation); byte-identical determinism doubles as the reproducibility test.
- **`ready` is its own event** — the load-bearing call: per-stimulus latency = `run_start − ready`, and readiness is emergent (queued wakes, sleep/timer/fork-slot ends) — the harness must never re-implement simulator semantics to reconstruct it.
- Deferred to the metric-definitions freeze: periodic-job completion definition; starvation measured from `ready`.
