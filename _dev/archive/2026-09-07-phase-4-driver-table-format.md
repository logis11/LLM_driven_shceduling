# 2026-09-07 — Phase 4: driver table format (spec session and task 4.1)

Decision session record for the Phase 4 spec and its sub-tasks. Branch `jioh/driver-table-v0` (the user's call: `_dev/` for this phase lands here, not on `main`). Decisions with rationale; facts verified in-session marked.

## Spec session

- **`llm_algo` keeps drawing from the table.** Verified: archive Q5's later resolution had already demoted `llm_full` to a subset diagnostic so that every scored condition passes through one table. The user rejected treating this as "decided" — the proposal offered options, not a decision — and asked for the options compared; option 2 below won on the ground that it is the only one where an `llm_algo`/`llm_vocab` difference is attributable to algorithm choice alone.
- **Options compared** (running example `ml-train/wanted`): (1) one entry per row, schema defaults for any other algorithm — cheapest, but `llm_algo` runs untuned constants whenever it disagrees, confounding "wrong class" with "textbook constants"; (2) every algorithm per row with a marked default — invariant by construction, cost lands in authorship; (3) situation-level knobs derived into each algorithm's params by code — a hidden second table, and the derivation caps what tuning can reach; (4) partial coverage with `held` on holes — mixes the model's score with the author's coverage; (5) drop `llm_algo`. The key-extension idea the notes rejected is option 2 in a flat layout without the default marker.
- **Weaknesses of option 2, stated.** (i) Against a calibrated default, algorithm knowledge adds nothing when the reading is right — `llm_algo` can only tie or lose, and beats `llm_vocab` only by rescuing a misread. (ii) The ceiling "by construction" holds only on the tuning pool; on evaluation files another algorithm may win, which is table transfer error, not model skill (RQ5 check 3 guards it). (iii) Cap placement decides whether "algorithm choice" also changes the cap. (iv) Distinctness must hold per algorithm across C2 pairs. (v) Hand-written non-default entries cannot be differentiated across rows.
- **The delegation rung reframed.** The user's summary, recorded for the proposal: the project answers two questions — does reading names semantically improve scheduling (`llm_vocab`), and if so how much can be delegated (`llm_vocab` / `llm_algo` / `llm_full`). Because the calibrated table is the answer key for algorithm choice, the rung is scored as: algorithm-choice accuracy against the calibrated default (no simulator); cost of delegation as a non-inferiority number; and the prior-table run where delegation can win — later dropped (see below). Handicapping the table to give `llm_algo` room was rejected: it weakens `llm_vocab`, the condition the main question rests on.
- **New rung recorded, deferred.** User's insight: if `llm_algo` scores close to `llm_vocab` on covered situations, the model's algorithm knowledge can act where the vocabulary has no row and `llm_vocab` can only fall back — a deployment claim `llm_vocab` cannot earn. Not observable in the current design (the validator forces a legal mode for every condition; `c6-dual` falls back for all). Measurable by blanking rows to schema defaults and comparing on the affected files. Deferred until after the main experiments; the format does not add a "no default" field now.
- **Cap per row**, shared by all entries — the attribute decides the cap, so keep its effect in one place; algorithm choice stays pure.
- **Schema defaults are not "textbook".** Verified: the config schema's defaults cite no source; they are the boot configuration decided at the 08-28 freeze. Label `schema-default`, not `textbook`. The user called their origin a logical hole — the `fixed` floor, hence every normalised score, would rest on numbers from nowhere — and ordered the grounding done first, not at Phase 7. Became task 4.1.
- **Prior table, one entry per row.** The user rejected generated four-entry padding for v0 ("the table feels broken"). Corrected an earlier conflation: option 4's problem was `held` on holes; with a compose-from-schema-defaults rule nothing is rejected, so the schema allows one to four entries and the calibrated table is lint-required full. `llm_algo` runs on the calibrated table only; v0 needs no non-default entries and the "delegation can beat the expert prior" reading is dropped in favour of the accuracy grading.
- **Keep v0 (pushback accepted).** Dropping it would put the kill check behind the search engine and tuning pool, lose the "untuned table passed" evidence, and leave RQ5's fragility check without a baseline. A table-free RQ0 (random config vs best-found config) was considered and not taken: it moves the gate later and changes its claim.
- **Names**: *prior table* (v0) and *calibrated table* (v1). Rejected: seed (suggests randomness), theory (overclaims grounding), untuned (defines by lack).
- **Read scope before validation.** The validator checks the composed config; `llm_algo`'s block is `{algorithm}`. Needed as a contract sentence because 박이안 would otherwise build the validator from the five rules on the raw block, in good faith, and reproduce the §4.7 bug.
- **Placement**: daemon tree, YAML, schema and lint beside it. **Lint**: structure and legality plus byte-identical `wanted` pairs; "far enough apart" stays with Phase 6.
- **Sub-tasks** 4.1 grounding → 4.2 contract and lint → 4.3 doc corrections.
- **Superseded, noted here (archives are append-only):** archive Q4's row shape ("an algorithm for the contended class, its parameters, and the per-class caps") — the frozen envelope is one flat `{algorithm, params, batch_bandwidth_cap}` with the batch class executor-owned. Row count: 32 (proposal), not "roughly twenty" (terminology, archive Q4).

## Task 4.1 — boot-default provenance

Sources fetched and read in-session (PDF text extracted; kernel sources fetched at tagged revisions): OSTEP MLFQ chapter (Version 1.10), Waldspurger & Weihl OSDI '94, Linux `kernel/sched/fair.c` at v6.5 and v6.6, illumos `ts_dptbl.c` / `ts.c` at commit de1199e (2026-09-05) and the `ts_dptbl(5)` man page. Result, recorded in `recognition-vocabulary` §2 "Provenance of the boot default" and its new §5 changelog:

- **Match OSTEP's worked example**: `num_queues` 3 (three-queue examples), `timeslice_growth` 2 (Fig. 8.6: 10/20/40 ms), `boost_interval_us` 100 ms (Fig. 8.4's example, which OSTEP itself calls "likely too small"; S is a voo-doo constant).
- **Bounded by sources, value not named**: `timeslice_us` 2 ms (OSTEP "10 or fewer ms" for top queues; Linux 0.75 ms base slice / 6 ms latency; Solaris TS 20 ms top); LOTTERY `timeslice_us` 2 ms (Waldspurger's 10 ms quantum, "shorter time quanta ... improve accuracy").
- **No source**: EDF `residual_timeslice_us` (tied to the MLFQ slice), LOTTERY `batch_share` 0.15.
- All seven remain stated assumptions; no value changed. Sensitivity check planned for the gate spec: `fixed` under OSTEP's example configuration and a Linux-like 0.75 ms slice, pair fixed before execution; floor reported as a range if the gap's sign or score ordering moves.
- References: `ostep` verified at Version 1.10 with the quoted passages; new `waldspurger-osdi94` (scholarly), `linux-sched-fair` and `illumos-ts` (deployed-system, existence claims only). Not cited: the illumos default table's quantum numbers — the unit is clock ticks and the effective milliseconds depend on `hz`, so the millisecond ranges are cited through OSTEP's description instead.

- **`config_schema.py` is the first machine-readable copy of `recognition-vocabulary` §1–§2** (16 modes, per-algorithm fields with types/ranges/defaults, cap range, bases, roles) with `check_params` (rules 2–3) and `schema_default()`. The README tells the daemon's validator to import it rather than re-type it. A drift test asserts the hand-maintained JSON schema agrees with it field by field.
- **Split of enforcement**: JSON Schema carries shape, enums, per-algorithm `params` (exact fields, types, bounds), cap type/range; the lint carries the 32-row key space (missing/duplicate), default ∈ entries, prior = exactly one entry, calibrated = all four, LOTTERY `batch_share ≤ cap`, justification required unless `basis: schema-default`, and the byte-identical `wanted` pair check on composed default configs. Schema violations are translated into one phrasing so messages do not depend on the jsonschema version.
- **Finding while writing the fixture**: the schema-default LOTTERY `batch_share` (0.15) exceeds any cap below 0.15, so the missing-entry composition rule cannot hand the mapper a legal config as-is for small-cap rows — rule 5 clamps `batch_share` down and the schedule entry is stamped `clamped`. Written into the contract's missing-entry sentence.
- **data-contracts**: new §10 (contract 9) with an example row and the invariant stated at the table; §6 proposal frozen with the read-scope-before-validation rule and the `{algorithm}` block for `llm_algo`; §12 and the intro no longer name a remaining draft; glossary gains prior/calibrated; changelog entry.
