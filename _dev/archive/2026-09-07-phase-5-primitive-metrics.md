## Decisions, in the order asked

1. **Vocabulary — (a).** Layer 1/2 keep terminology's meaning; the notes' pipeline split is named *primitives* (what lands in `records`) and *scoring* (what the scoring spec does). The user: "primitives and scorings are the correct wording." Rationale: terminology and the proposal are ratified and the recognition/performance split is the one the paper argues with; the notes' split is a pipeline boundary and its artifacts already carry these names. Rejected: amending terminology; letting both senses coexist.

2. **One metrics doc, both families — (a).** The doc defines trace primitives and recognition primitives; the grader code stays in Phase 7. The user's framing, recorded: recognition metrics are based on primitives — once primitives are settled, the recognition metrics the research needs are aggregates over them. Rationale: the handoff asks for algorithm-choice accuracy in this phase's definitions, and a grader built before its metric is written down is the §8.3 failure mode. Rejected: definitions in Phase 7 beside the grader; two docs.

3. **Records are raw observations — (a).** One row per observation with an anchor time `t`; aggregation is scoring's. The user: "primitive means raw observations. we get all the raw materials as records. then we combine them into scores … that is the whole primitive → score design." Rationale: windowing becomes a scoring-time filter (`c2-p1a`'s interesting stretch is 60–180 s and the dev-only first minute dilutes a whole-file P95) without primitives reading `ground_truth`; a statistic change never touches a trace; every paper number reduces to rows that each name a trace line. Cost accepted: file size (tens of thousands of rows for `c1-gaming`). Rejected: aggregates only; both grains in one file.

4. **`ready_wait` — (a).** One generic primitive, one row per `ready` line with `cause`; interaction latency, response time, timer dispatch delay, and starvation are filters and aggregates over it. Rationale: the primitive stays ignorant of which task is the editor; starvation gets its written definition (max `ready_wait` per task, from `ready`, never from arrival) for free. Noted: the trace does not name the channel, so a chain stage's WAIT completing is also `cause=wake`. Clarification added while drafting the simulator memo: a `ready` that falls inside the task's own occupancy has wait 0, so the simulator never has to split an occupancy interval around a queued wake. Rejected: named primitives with the reader deciding which task is interactive.

5. **Chain frame latency — reconstruct in the harness (a).** The user asked what "reconstruct" meant and whether the dataset had a hole. Answer recorded: the dataset is built exactly as the interpretation contract and archetype plan describe (input → engine → … → display, one frame per tick); the hole is in the metric mapping — data-contracts §9's table and proposal B.4 say frame latency comes from `deadline` lines, but a `deadline` line is per TIMER task, and in the chain only the input stage has a TIMER, so it answers "did the input stage finish its 230 µs burst before the next tick", not "did the frame reach the display stage". Decision: the trace reader takes the chain topology from the run file by a structural rule (a chain is the WAKE path starting at a TIMER-headed task); frame k latency = tail stage's k-th iteration end − tick k. Single-stage TIMER tasks are chains of length one, so the same rule reproduces their `deadline` line — a free cross-check. Rationale: both frozen contracts untouched; the rule is structural, the standard the canonicalisation function was held to. Rejected: (b) constructor change plus a new trace line — two frozen contracts, two owners; (c) the head-only `deadline` line — measures under a millisecond of a sixteen-stage frame; (d) deriving the chain from the `<id>.chain.<n>` naming convention — a weaker fact than the WAKE edges the file carries. Conditions carried to 인경민: wakes queue with depth so iteration k of every stage is tick k; the harness guards tail iterations against head ticks.

6. **Observation window `[0, T_end]` — (a).** `T_end` = the workload's end from the run file; observations after it dropped, CPU accounting clipped. A task alive at `T_end` is "not completed within the window", not "completed late". Rationale: makes every metric independent of an undecided simulator end rule and scoped to labelled time. Note for 인경민: the harness reads nothing past `T_end`, so stopping there is safe and cheaper — advice, not a contract line. Rejected: window = whatever the simulator emitted; a "stop at `T_end`" contract change.

7. **Batch primitives — (a).** Per task `cpu_delivered` (clipped at `T_end`), `completed` (a `task_end` with reason `exit` inside the window), `turnaround` when completed, `demand` (total RUN work read from the run file), so scoring forms the progress fraction. Rationale: the trace alone cannot say how much work was owed; `demand` in records keeps the scoring spec free of copied numbers that drift on re-sampling; summed `cpu_delivered` doubles as the utilisation sanity input. `c1-compile`'s makespan is `make`'s turnaround; each `cc1` child gets rows with emergent arrival times from the trace. Rejected: scoring spec carrying demand by hand; inferring completion from `cpu_delivered`.

8. **Periodic jobs — adopt the working definition, and require a `ready` line at zero wait — (a).** Working definition (data-contracts §9): job k starts when tick k is consumed, completes when the task next reaches a TIMER, `due` = tick k + period. Finding: under backlog the next TIMER completes instantly, the task never blocks, so no `run_end`/`ready` marks the job boundary; same for a chain tail whose next WAKE was queued and for the editor's queued keystroke. Decision: every completion of a blocking primitive emits a `ready` line, at zero wait when it did not block — a `ready` line means "a blocking primitive completed", not "the task stopped being unrunnable". The harness builds one `job` row per tick from `ready(cause=timer_tick)` and the chain rule; the simulator's `deadline` lines become a cross-check. Rationale: one rule generalises the Q4 note, cheap to emit at the consumption point, and it is the single clarification that makes the frozen trace sufficient for every metric in the table; no field or event type is added. Rejected: trusting `deadline` for single-stage tasks and reconstructing only chains (chain iterations still invisible under backlog); leaving job semantics to 인경민.

9. **Bookkeeping primitives — (a).** `config_interval` under reserved entity `schedule` (one row per `config_applied`, value = time in force, with `provenance`, `algorithm`, `index`); `preempt_count` per task; `busy` under reserved entity `lane` (idle = `T_end − busy`). Provenance shares, config age, utilisation are aggregates. Rationale: guards that read records cannot disagree with the primitives about what a trace says. Rejected: guards reading traces in Phase 7; storing every occupancy interval (no metric needs it; a new primitive is a recomputation from traces, which stay on disk). Determinism stays a trace-hash comparison.

10. **Records schema — (a), "agree".** CSV, one file per trace, self-contained rows: identity `workload_id`, `condition`, `table` (empty for `fixed`), `seed`, `sim`, `source_sha256`; observation `entity`, `metric`, `t`, `value`; nullable attributes `cause`, `provenance`, `algorithm`, `index`, `period_us`, later joined by `predicted`, `truth`, `validation` (decision 13). `met` is not stored (derivable from `value > period_us`). Rationale: the hand-computed expected values become literal CSV fixtures, diffable in review and CI; self-contained rows concatenate across the matrix; named attribute columns are statable per metric where a free JSON object would hide them. Rejected: JSONL with a free attribute object; Parquet with a sidecar.

11. **Normalisation — (i) per aggregate, (a) absolute floor per aggregate.** `(fixed − condition)/(fixed − oracle)` applied per aggregate so each is unit-free before Phase 6's weights; floor in the aggregate's own units, stated beside its definition; below it the ratio is undefined and raw values are reported with "no headroom"; negatives shown, never clipped. Rationale: per-aggregate normalisation is the only operand under which a weight vector over mixed units means anything; an absolute floor is the one a reader can check against the number, and the latency floors have a natural anchor in the perceptual constant. Rejected: normalising a weighted composite; a relative floor; no floor. The boot-default sensitivity pair stays in Phase 7's gate spec.

12. **Aggregate list with `over_threshold` — (a).** `ready_wait`: count, mean, P50, P95, P99, max, `over_threshold` against a named interaction-latency constant; `job`: count, miss rate, latency P50/P99; lifetime and bookkeeping rows: derived shares and progress fraction. Mean never a headline. The constant's source is fetched and read in the sub-task; if the usual 100 ms figure cannot be traced to its primary source it is written as a stated assumption. Rationale: "8% of stimuli exceeded the threshold" travels further than "P95 was 47 ms" and makes files comparable; percentiles keep the tail a fraction discards (B.4's reason for two frame statistics). The constant lives beside the floors so Phase 6 can reuse it for `c1-media`'s audio/video weighting. Rejected: percentiles only; threshold only.

13. **Recognition primitives in the same records shape — (a).** Per graded query (non-`ambiguous` covering segment; terminal snapshot skipped), entity `recognizer`, `t` = `t_set_change`: `mode_correct`, `attr_correct` (with `predicted`, `truth`), `latency_us`, `validation`, and `algo_choice_correct` for `llm_algo` against the calibrated table's default for the true row (the grader takes the table file as input). `trace_sha256` generalised to `source_sha256`. Rationale: one shape means one scorer and one traceability rule; the per-query grain keeps consistency and distractor robustness computable later without regrading. Notes: consistency needs several samples per query point and the log envelope has no repeat index (박이안); the familiarity split needs a per-file or per-name tag whose existence is unverified (fact to check in the sub-task). Rejected: a separate grades file; aggregates only.

14. **Four mock pairs — (a).** Reduced `c1-office` (focused editor, a keystroke queued mid-burst, an unfocused task that never wakes); `c1-media` (two TIMER tasks, one in backlog); `c2-p1a` (editor vs batch, config switch at 60 s plus latency, batch unfinished at `T_end`); reduced chain (three stages, one late frame). Each a reduced run file + trace of 20–40 lines + hand-computed expected records CSV. The simulator assumptions the mocks encode are listed in one place in the doc, so a different decision by 인경민 changes the mocks deliberately. Rationale: every decision 4–9 has a mock line that would compute wrongly if mis-implemented; the chain mock is the only pre-simulator check of the judging pair's frame metric; the mocks seed Phase 7's mock simulator. Rejected: the notes' three; mocks for all 24 files.

15. **Placement and status — (a).** The metrics doc opens the Harness section of `docs/` as normative with a changelog; data-contracts §9's two deferred definitions point at it, the `deadline` example is corrected, a changelog line added; the records schema is described in the doc and enforced by a machine schema beside the harness code, not promoted to a data contract (placement rule: machine-read files live with the program; the driver table earned its contract because two trees touch it). The three-signature line in proposal §8.2 is an open item to settle with the team. Rejected: draft until signatures (the §8.3 failure mode named twice already); records as data contract 10.

16. **Harness tree — "yep".** `harness/` mirrors the daemon and dataset trees (Python package, Makefile lint/test, pinned requirements, tests with the mock pairs as fixtures, CI workflow). Reader streams plain/gzipped JSONL, validates the closed event set, ignores `x_`, captures `meta`, takes the run file as second input; primitives are pure functions over what the reader yields; pandas deferred until the scorer. Test-first, straight to implementation on this branch. Rejected: a single script; a new layout.

17. **Sub-tasks — (a).** 5.1 mocks + expected records → 5.2 doc + constants + doc corrections ∥ 5.3 reader → 5.4 primitives + records writer + schema + CI + byte-for-byte match. Rationale: splitting mocks from the doc lets the doc and the reader proceed in parallel once expected values exist, and keeps source verification from blocking code. ## Task 5.1 — mock fixtures (2026-09-08)

Four fixture directories under `harness/tools/tests/fixtures/` (`mock-office`, `mock-media`, `mock-p1a`, `mock-chain`), each with `run.json` (run-file view: `workload_id` + `events`), `trace.jsonl`, `expected.csv`, and `worked.md` deriving every row; a fixtures README carries the decisions and the assumption list. Designed fresh — the harness guide's sample mocks were deliberately not reused. Commit `119e97a`. Reviewed by the user: "looks good".

Decisions taken at sub-task level, to be documented in the metrics doc (5.2):
- **Row order**: `entity`, `metric`, `t` (numeric), `cause`. Byte comparison needs one order; this keeps a task's rows contiguous.
- **Anchor `t`**: window-level rows (`cpu_delivered`, `demand`, `preempt_count`, `busy`, `completed`=0) at `T_end`; `completed`=1 and `turnaround` at the `task_end` time.
- **`T_end`** = the largest pinned time in the run file (arrivals, departs, wakes). The run file carries no `ground_truth`, so this is the only source; in the coreset it coincides with the end of ground truth.
- **`demand`** rows only for programs whose RUN total is finite; unbounded LOOPs have none.
- **Window edges**: a `job` is emitted only if its completion ≤ `T_end`; a `ready_wait` only if its `run_start` ≤ `T_end`; occupancy open at `T_end` is clipped.
- **Arrival whose first instruction blocks**: scheduled like any task, reaches the WAIT, blocks — a zero-length occupancy when the lane is free (mock-local choice; listed as an assumption).
- **Same-instant order** assumed by the mocks: config entries first in list order, then arrivals in file order.
- **TIMER `t₀`** assumed = arrival (simulator-guide §9.2), so tick 0 is consumed instantly at arrival with a `ready(timer_tick)` inside the occupancy.
- **Identity for mocks**: `sim` = `mock@0`; `source_sha256` = SHA-256 of the committed `trace.jsonl`.
- **`deadline` lines** are included in the media and chain traces and are never the source of `job` rows; they agree for length-one chains and disagree by design for the three-stage chain (head says met at 29900 for a frame that completed at 34600, latency 17933).
- **Chain ids** `input`/`engine`/`display` on purpose, so the reader must take topology from WAKE targets.
- **Media mock carries a distractor** (`clamscan`, RUN 31000 at 20000) because `c1-media`'s two players alone cannot produce backlog; labelled as reduction plus distractor.

Verified in-session: an independent script recomputed occupancy sums, preemption counts, `busy`, `slack_us = due − t`, and ready-row counts from the four traces; all agree with the hand-derived rows; traces are time-ordered. Row counts 15 / 33 / 17 / 32.
