## 4. Bugs fixed this session

### 4.1 Policy timers outlived a config apply (inherited from R) [confirmed]

Each MLFQ `start()` armed one more boost chain and none was cancelled. The chains kept each other in the event queue, which defeated `arm()`'s stop rule. `sim_r` on `c1-compile` × mock-switch never terminates: 24 million lines and virtual time ≈ 45 h after 15 s of wall time, with boosts at t = 100600 twice. Fix: `PolicyTimer` carries the config epoch it was armed under and is dropped on a mismatch, the same remedy as stage F's `gen`. Only schedules that re-enter MLFQ change. Stage R's verification never ran that combination.

### 4.2 EDF: a preemption landing on the slice boundary [confirmed]

When a residual task's slice ended in the same µs as a TIMER expiry, the wake was processed first. The task was recorded as preempted with its full slice still charged, so its next dispatch had horizon 0. On the boot-default memo's §5 scenario (video, music, scan) this produced 600 zero-length occupancies and 600 extra `preempt` lines. Fix: a preemption with the slice fully used counts as a slice end.

My first version of the fix dropped the task from the ready set; the scan never ran again after t = 166670. It was caught because the lane went idle while work was runnable. The second version was re-validated (§3).

## 5. Open gaps the docs already answer — implementation owed by the simulator

### 5.1 Zero-wait `ready` lines are missing; the harness misreads periodic jobs [confirmed]

- **What the docs say.** Trace-clarifications memo (2026-09-07) §4: "A `ready` line is emitted every time a blocking primitive completes … If the primitive did not actually block, the line is emitted at that instant with the task already running." There must be no fake `run_end`/`run_start` split. metrics.md §6.1 and §11 items 1 and 4 assume the same, including a `ready(timer_tick)` for tick 0 at arrival.
- **What the simulator does.** A backlogged TIMER, a mailbox-satisfied WAIT, or any non-blocking path that reaches the next RUN prints `ready cause=arrive` (the wrong cause). The task gives up the lane **without a `run_end`** and is requeued.
- **Scale under boot MLFQ, `sim_r`:**
  - `c1-gaming`: 35,803 of 86,239 `ready` lines (41%) are this case.
  - `c2-p2b`: 43,098 of 175,443.
- **Effect on the harness** (`harness/tools/records.py` run on unchanged `sim_r` traces):

  | file | guards | what goes wrong |
  |---|---|---|
  | `c1-media` | 4,798 | the harness reads every music job as 52,500 µs against a 50,000 µs period (every job "misses"); the simulator's `deadline` lines say 4,800/4,800 met. The tick numbering is off by one because tick 0 has no `ready(timer_tick)` |
  | `c1-gaming` | 170 | |
  | `c2-p2b` | 51 | |

- **Fix direction** (from the docs): the holder keeps the lane across a non-blocking primitive and a `ready` with the primitive's own cause is printed inside the occupancy. This also closes `src/notes.md` gap 4. It changes every MLFQ baseline trace and the zero-wait counts, so it should land as its own step with a before/after diff.

### 5.2 Switching into MLFQ is not a cold start [inferred — code reading, not run]

Switch memo §3–§4: a switch into MLFQ places every task in the top queue. `Mlfq::start()` keeps the per-task levels (`st`), so MLFQ→FIFO→MLFQ resumes the old levels. In S, MLFQ ignores the new `cold` flag, which keeps R's behaviour. Fixing it changes mock-switch traces.

### 5.3 A same-algorithm MLFQ entry re-arms the holder with the new slice [inferred]

metrics §11.9: "the running task finishes the slice it was granted and the new params govern from its next dispatch." `on_config_apply` re-arms the holder with the incoming policy's horizon. For MLFQ, a smaller new `timeslice_us` can make `slice_of(level) − allot` negative. That would schedule a Lane event in the past and trip `assert(e.t >= now_)`. mock-switch (10000 → 2000 at t = 600) does not hit it. EDF and LOTTERY clamp their horizon at 0.

### 5.4 TIMER t₀ is ours to pin, and the coreset does not distinguish the two live readings [confirmed]

- Guide §9.2 hands the choice to the builder ("Pick the reading … and pin it"). metrics §11.4 (t₀ = arrival) is a mock-local choice. The simulator uses D4 (t₀ = the first TIMER execution).
- 12 periodic tasks arrive mid-run (`c3-evening`, `c4-compile`), but every periodic task in the 24 files has a TIMER as its first instruction. So D4 equals arrival on every coreset file; only the global-zero reading would differ.
- This corrects `src/notes.md` gap 3, which said all periodic tasks arrive at t = 0.

### 5.5 Not implemented

- The executor's starvation safety net. EDF's deadline class and FIFO have no horizon.
- `batch_bandwidth_cap` — not even read from the config.
- Range clamping and cross-field rule 5 (`batch_share ≤ cap`) in the loader. Like MLFQ, the loader trusts the composed config.

## 6. jioh's three questions to kyungmin (boot-default memo §5; RQ0 pre-registration §4) — current behaviour; the reply is kyungmin's to send

The RQ0 spec carries jioh's proposals as assumptions "awaiting 인경민". What S does today:

1. **Does a waking deadline task take the lane from a residual slice at once?** Yes (option A). [confirmed] On the memo's own scenario under EDF: `video` waits 0 µs on all 3,600 ticks, and all 4,800 deadlines are met.
2. **Same-µs order of a slice end and a TIMER expiry.** Rule D1: config applies first, then insertion order. It is **not** "wake first" by rule. Before the §4.2 fix the ordering produced zero-length occupancies; after it there are none on that scenario. ## 7. Batch class (B1/B2) — kept in this memo only

- **B1** (executor state): `burst` = CPU received since the last voluntary block (a WAIT that blocks, SLEEP, a TIMER not yet due); reset only there; preemption never resets it. A task is batch when it is non-periodic and `burst ≥` the running config's slice. [confirmed by code; tested only on `share2`]
- **B2** (fixed at load): every task with a TIMER, plus the closure over WAKE targets. A spawn-table child with a TIMER is periodic, and its WAKE targets seed the closure (none exists in the coreset). Periodic tasks per file: c1-gaming 21, c2-p2a/b 17, c3-evening 30, … [confirmed]
- **Slice per algorithm:** MLFQ and LOTTERY `timeslice_us`, EDF `residual_timeslice_us`, FIFO the boot default's `timeslice_us` = 10000. The batch-class memo's "2000 µs" is superseded: the boot-default memo §5 says to read it as 10000. So `steps/README.md` D9 is answered.
- **Where B1 acts today:** LOTTERY's class split only, because the cap is not enforced.
- **Not verified:**
  - that the coreset's intended batch tasks (for example `c2-p2b`'s clamscan, `c2-p3b`'s borg) enter the class as the batch-class memo §4 predicts;
  - the memo's two unit tests (§7 item 6);
  - the optional `x_batch_class` diagnostic, which is not emitted.

## 8. EDF on the gaming files — depends on the open question [confirmed numbers]

S puts chain stages in the deadline class (they inherit the waker's deadline). A variant with inheritance off — stages in the residual class — gives:

| file, EDF | stages in deadline class (S) | stages in residual class |
|---|---|---|
| `c1-gaming` `deadline` lines met | 5 / 5,664 | 7,372 / 7,372 |
| `c3-evening` `deadline` lines met | 9,917 / 20,459 | 25,227 / 25,227 |
| `c2-p2b` frames (harness `job` rows for `game.chain.1`) missed | **0 / 7,199** | **5,189 / 5,201 (99.8%)** |
| `c1-gaming` frames missed | all (the harness found only 2 head ticks — §5.1) | 785 / 785 |

- `deadline` lines measure TIMER tasks only. The frame is the chain tail's iteration end (metrics §6.2), which the harness reconstructs.
- `c1-gaming` is overloaded on purpose (utilization 1.46, coreset-guide demand table). Its frames miss under every variant and under MLFQ.
- **Correction:** I earlier called the c1-gaming EDF collapse "the domino effect, not a bug". That was incomplete. The collapse of the head's and the compositor's deadlines comes from putting the 16 chain stages into the deadline class.
- The `c2-p2b` frame numbers come from traces with the §5.1 defect. The residual-class run also raised the harness's chain guard (tail 5,201 iterations for 7,199 head ticks), so treat that row as indicative.
