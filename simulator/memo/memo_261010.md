# Part A — batch class, bandwidth cap, starvation safety net

## 1. What the docs require

- **`batch_bandwidth_cap`**: "While some task that is not batch wants the CPU, the batch-class tasks together may use at most this fraction of it" (batch memo §1). Every driver-table row sets it, and the recognizer's `background_wanted` acts only through it. It is the experiment's central knob. [confirmed]
- **Batch class** (batch memo §3), identical under every algorithm:
  - **B1**: a task enters the batch class once it has consumed one full slice of CPU since its last voluntary block, and leaves at its next voluntary block. A voluntary block is a WAIT that waits, a SLEEP, or a TIMER not yet due. Preemption does not reset it.
  - **B2**: a task with a TIMER, and every task reachable from one through WAKE targets, is periodic and never batch.
- **Starvation safety net**: "every runnable task makes progress within a bounded window regardless of what any configuration says" (`recognition-vocabulary.md:70`). It is executor-owned and has no config field. It applies under FIFO too (`:102`). [confirmed]

# Part B — decisions for `sim_u`: config-switch semantics

All three changes live in `on_config_apply()`, so they land together as one step. Each changes traces only for schedules with more than one entry; the no-schedule and one-entry runs must stay byte-identical to `sim_t`.

| # | Decision | Source | Current behaviour (sim_r → sim_t) |
|---|---|---|---|
| U1 | **A switch into MLFQ is a cold start.** On `cold`, every task's level and allotment reset: everyone starts in Q0. The boost grid already restarts at `t_apply` through the S epoch | switch memo §3, metrics §11.7 | `Mlfq::start()` ignores `cold` and keeps per-task levels, so MLFQ→FIFO→MLFQ resumes the old levels [inferred, `memo_261001.md` §5.2] |
| U2 | **A same-algorithm entry does not touch the holder.** The running task finishes the slice it was granted. New params govern from its next dispatch. Queue levels kept, cap at once | metrics §11.9, switch memo §7 | the holder is re-armed with the new policy's horizon. Under MLFQ a smaller `timeslice_us` can make `slice_of(level) − allot` negative, which schedules a Lane event in the past and trips `assert(e.t >= now_)`. EDF and LOTTERY clamp at 0 and preempt at once instead [inferred, `memo_261001.md` §5.3] |
| U3 | **Drain.** A switch out of MLFQ, EDF, or LOTTERY applies when the running task's current slice ends, so `t_apply` lags `t_us` by at most one outgoing slice. `config_applied.t` is the drained instant. A switch out of FIFO applies at once, holder freshly dispatched (rule (a), already in S as `cold`) | switch memo §2, metrics §11.8 | every switch applies at `t_us`. No drain logic exists in `sim_r`/`sim_s` [confirmed by grep] |

Open details to settle while building U3:
- **Idle lane:** an entry arriving while nobody holds the lane has nothing to drain. Presumably it applies at `t_us`.
- **Overlapping entries:** a second entry can arrive while a drain is pending. Presumably the later entry replaces the pending one, but the trace must still show which index applied.
- **Interplay with U2:** U2 is a same-algorithm entry, so U2 never drains.

Out of scope for `sim_u`: A1 (Part C) is its own step, because it changes every MLFQ baseline trace.

## Result — `steps/sim_u.cpp` built [confirmed, all measured this session]

- **How U3 was built:**
  - An entry that must drain is queued (`pending_`) and logged as `x_config_pending {t, index}`.
  - `dispatch()` applies every queued entry, in order, the next time the lane is free. The lane frees on slice end, block, preemption, exit, or depart.
  - An entry that arrives while others are queued waits behind them, even if it is same-algorithm. That keeps the index order.
- **How U2 was built:**
  - A same-algorithm entry skips the holder's release and re-arm. The holder's existing Lane event is its granted slice.
  - Handoff order is kept, because the id sort applies only on `cold`.
  - MLFQ levels are clamped to the new `num_queues`.
  - `Mlfq::pick()` demotes a task whose allotment exceeds the shrunken slice. It does this lazily, at pick time.
- **Results:**
  - **Regression:** with no schedule, and with a one-entry boot schedule, all 24 coreset files are byte-identical to `sim_t` (48/48).
  - **Against the harness's hand-derived `mock-switch` trace:** all four `config_applied` instants match (0, 600, 12000, 40600). `sim_t` applied entry 2 at 10600.
  - **Cold start:** the hog's fresh 2000 µs slice after entry 3 ends at 42600, as the mock says. `sim_t` ended it at 42000 on the carried allotment.
  - **Boost grid:** 60600, 80600, as the mock says.
  - **A5:** a same-algorithm shrink (10000 → 2000 at t = 15000) while the hog holds the lane crashes `sim_t` (`assert(e.t >= now_)`). `sim_u` lets the hog finish its granted slice at 20000.
  - **Stress schedule** (9 entries, all four algorithms, back-to-back entries 100 µs and 1 µs apart, `num_queues` 3 → 2): `sim_u` 24/24 terminate, rerun byte-identical, every index applied once and in order, apply lag ≤ 10000 µs. `sim_t` aborts on 23/24.
- **Remaining diffs vs `mock-switch`, none of them U-scope:**
  1. The t = 0 zero-length occupancy for the arriving editor (open item C4, metrics §11.5).
  2. Slice expiry with no competitor: the mock demotes without a `run_end`, while the simulator emits a `run_end(preempt)`/`run_start` pair at the same µs.
  3. Demotion mid-burst: at 44600 the mock lets the editor keep running after its Q0 slice ends, although `probe` waits in Q0. That reads as a conflict with MLFQ rule 2 on the mock's side [inferred]. The simulator preempts and runs `probe`.
  4. The `x_mlfq_level` lines that the mock uses (A10).
- **Still open:**
  - Does a same-algorithm MLFQ entry restart the boost grid? `sim_u` keeps S's behaviour, which restarts it at the entry, because the epoch bumps on every apply. metrics §11.7 covers only switches *into* MLFQ.
  - A drain out of EDF with a deadline-class holder has no slice bound. It ends at that task's next block.
  - While A1 is unfixed, a RUN→RUN boundary frees the lane, so a drain can end there earlier than the true slice end. A1's fix removes that automatically.

# Part C — the RUN→RUN defect, explained (`src/notes.md` gap 10, `memo_261001.md` §5.1)

Example: `video` (`mpv`) in `c1-media`, program `LOOP unbounded [TIMER 16667, RUN 6667]`.

- **Where the wrong cause comes from.** `advance()` runs after every RUN. It steps the program forward, and if the task comes out Ready it calls `enqueue(id, "arrive")`, a hardcoded cause. It is not specific to backlog: any path that reaches the next RUN without blocking lands there. Those paths are a backlogged TIMER, a mailbox-satisfied WAIT, a WAKE, a successful FORK, or a RUN followed directly by a RUN. Tick 0 has the same problem through `on_arrive`: the first TIMER is consumed at arrival and the line says `arrive`, with no `ready(timer_tick)`.
- **Backlog itself is fine.** Consuming overdue ticks immediately is the documented rule. The defect is how the pass-through is recorded and what happens to the lane.
- **Relabelling the cause is not enough.**
  1. `advance()` cannot know the cause. Between two RUNs the program may pass zero, one, or several primitives (e.g. a backlogged TIMER, then a WAKE, then a mailbox WAIT). The docs want one `ready` line per completed primitive, with that primitive's cause, and none for a bare RUN→RUN.
  2. The lane is released with no `run_end`, so the occupancy is never closed.
  3. The task is requeued, so the policy makes a decision the docs say does not exist ("between events, nothing to decide", guide §5). That changes the schedule itself, and under LOTTERY it adds a re-draw at every such boundary.
- **The fix the docs already give** (trace-clarifications memo §4): emit `ready(cause)` inside `step()` at the instant each primitive completes, and keep the holder on the lane. The line then falls inside the task's own occupancy and the harness records a wait of zero. No fake `run_end`/`run_start`.
- **The model behind the fix:** RUNs joined without a block form **one occupancy**, one `run_start` … one `run_end`. A RUN boundary stops being a decision point. The slice still spans the whole occupancy, and preemption, block, exit, and depart still end it. MLFQ allotment and B1 `burst` count the whole occupancy, and the sum must equal today's per-RUN `charge()` total.
- **Decision — `x_run_cont` diagnostic.** At every RUN boundary inside an occupancy, emit `{"event":"x_run_cont","t":…,"task":…}`. Reasons:
  1. A bare RUN→RUN boundary leaves no other trace once the fix lands.
  2. It is the fix's positive control: the `x_run_cont` count must equal the pre-fix count of `ready(cause=arrive)` lines that came from `advance()` (e.g. 35,803 on `c1-gaming` under boot MLFQ).
  3. It lets per-RUN durations, and so the accounting, be checked from the trace.
  It is `x_`-prefixed because the harness event set is closed (data-contracts §9), and the harness ignores `x_` lines. It is always on. Estimated size cost: about 13% more lines on `c1-gaming` and 7% on `c2-p2b`, from the old `ready(arrive)` counts. If size becomes a problem, gate it behind a simulator-side flag, which the invocation contract allows in the command prefix.
- **Lands as its own step after `sim_u`**, with a before/after diff, because it changes every MLFQ baseline trace.

# Part E — decision: one mailbox (D2), 2026-10-10

**Decided:** the two mailboxes merge into one (kyungmin, 2026-10-10: "one can be removed"). Today the simulator keeps two:
- a **channel mailbox** (`chan_pending_`), filled by external `wake` events addressed by `channel`;
- a **task mailbox** (`mailbox` + `mail_dl`), filled by `WAKE` instructions addressed by `target`.

**Why it is safe [confirmed by a scan of all 24 coreset files, 6,434 tasks including spawn children]:**
- No task WAITs on more than one channel.
- No channel has more than one waiter.
- All 7,050 external wakes name a `target` that WAITs on exactly that `channel`.

So channel and task are 1:1, and merging should leave every coreset trace byte-identical. That is the regression test.

**Recommendation: keep the task mailbox and drop the channel mailbox** [inferred, not yet built]:
1. The `WAKE` instruction carries only `target` (the file gives no channel), while external `wake` events carry both `channel` and `target`. Everything can be addressed by task, but not everything can be addressed by channel.
2. D6's inherited deadlines ride the task mailbox (`mail_dl`), and jioh confirmed D6 the same day. An external wake would enqueue "no deadline" (−1) there.
3. The loader must start reading the wake event's `target`, which it ignores today (stage M). `chan_waiters_` can then go too, or stay only as a check that a wake's target waits on its channel.

Open: which step lands it. It is independent of A1 (the RUN→RUN fix).
