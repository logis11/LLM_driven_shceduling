# Part C — the two consequences of the cap, stated for confirmation

Both are measured, and both follow from rules already written down rather than from a choice I
made. I am not asking 인지오 to re-decide the cap; I am naming what it implies so that neither
turns up later as a surprise in a trace.

1. **Under FIFO the cap preempts.** FIFO has no quantum, so a ceiling on the batch class has no
   lever other than taking the lane. The executor's class rules sit below the algorithm (batch
   memo §3: "identical across algorithms"), so the cap applies under FIFO like any other. The
   measured effect is large and it is the point of the cap: the periodic task goes from **0 jobs
   to 99**.
2. **A capped stretch that opens mid-occupancy leaves a debt, not a re-arm.** The alternative —
   re-arming the holder — hands out a horizon the policy has not charged, which is exactly the
   negative-horizon defect seat U2 already hit. The overrun is repaid before the class runs again
   and is bounded by one grant (measured: one bucket depth).

If either reading is wrong, both are small changes in `cap_gate()` / `arm_cap_timer()`, but every
capped trace moves with them, so I would rather hear now than after the re-baseline.

# Part E — spawn-table WAKE targets (stage W, 2026-10-21)

*Written up in `memo_261020.md` Part G first; moved here so that one memo holds everything
addressed to 인지오.*

## E1. What was wrong

`compile_prog` resolved every `WAKE` target against the top-level `arrive` id table and
`die()`d otherwise: `"WAKE target is not a top-level task: build.j1.gcc"`. The rebuilt dataset
builds a make job out of six member processes that wake **each other** by spawn-table id
(`sh` → `gcc` → `cc1` → `gcc` → `as` → `gcc` → `sh` → `fixdep` → `sh` → `rm` → `sh`; 9.6 D19,
`dataset/tools/wlc/compiler.py:_object_job`), and the module build does the same over trees of
6, 6, 8 and 10 members (9.10 D53, `_tree_job`). So the loader rejected the whole file for
`c1-compile`, `c7-compile` (**both judging files**), `c3-workday`, `c4-compile`, `c6-dual`, the
8 compile variants the RQ0 gate spec runs, and 188 generated files.

It does not fire on the local build: the 2026-09-04 build predates the structure, and its
`c1-compile` has 100 spawn-table entries with **zero** child WAKE targets (the rebuilt one has
17,448 and its members wake each other). The rebuild and this fix therefore have to land
together — on the stale build nothing looks wrong.

Provenance of the finding: the 2026-10-10 dataset audit, blocker 1. The audit recommended
telling me at once and that notice was not sent; the 2026-10-17 rebuild memo carried it first.
It is in none of `memo_261001.md`, `memo_261010.md` or Parts A–F here, and it is **not** one of
the eight `simulator-conformance` items either — it sits beside them.

## E2. The fix, and why a wake must be held

A sibling has no task index until the parent forks it, so the index cannot be fixed at load
time the way a top-level target is. W gives every spawn-table entry a **slot**: the loader
resolves a sibling target to `-slot-1`, and the birth fills `spawn_live_[slot]`.

The part that is a decision, not a mechanism: **a wake that arrives before the birth is held and
handed to the child at its birth, not dropped.** It has to be. `fork_cap` is
`parallelism_cap × 6` (D19, D57) while the module build's trees have 8 and 10 members, so the
cap falls mid-job; a job's root is forked first and starts with a RUN (every other member starts
with its own WAIT), so the root can run and wake a member the parent has not reached yet. The
hold is what lets the job finish once earlier jobs free the slots.

Measured counterfactual on the two fixtures below — the same binary with the held branch
replaced by a drop:

| fixture | hold (W) | drop |
|---|---|---|
| `fix-object` (two 6-member object jobs, `fork_cap` 8) | 13 arrive / **13 end** | 13 arrive / 7 end — **6 never end** |
| `fix-tree` (one 8- and one 10-member conftest job, `fork_cap` 12) | 19 arrive / **19 end** | 19 arrive / 9 end — **10 never end** |

The tasks that never end are exactly job 2's members: the woken member blocks on its own channel
forever and the job deadlocks. Instrumented, the held branch fires once per fixture, both times
on `build.j2.cc1` — the member the cap had not let the parent fork yet.
