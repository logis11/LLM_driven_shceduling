## B. Stage AA — `WAIT children:<id>`, conformance (g)

- The orchestrator's `WAIT children:<own id>` completes when every child it spawned has ended. Its `ready(wake)` comes right after the last child's `task_end`. If no child is live when the WAIT is reached, it completes at once with a zero-wait line, in the arrival step or inside an occupancy like any zero-wait line. [confirmed on hand workloads]
- It is a WAIT, so the line is `ready(cause = wake)` and the block is `run_end(blocked_on = wait)`. The harness pairs that line with the program's WAIT as with any other (`primitives.py`, `next_wait`). It is not a channel: nothing but the executor completes it, so a `WAKE` sent to the orchestrator meanwhile goes to its mailbox. [confirmed from code]
- The loader refuses a `children:` WAIT naming another task, and a run-file wake on a `children:` name. The compiler writes the WAIT only into the orchestrator's own program (`children:{iid}`). [confirmed]
- Fixed beside it: `on_task_end` read "blocked with no channel" as "waiting for a fork slot". A parent blocked on SLEEP or TIMER got a false `ready(fork_slot)` and was re-stepped from its SLEEP when a child ended. Hand workload `g-sleep`: HEAD writes the line at 1000 while the parent sleeps to 5000. No dataset file reaches it (`src/notes.md` §4 item 14). [confirmed]
- **Negative control:** the 116 files without a FORK are byte-identical to `src/sim.cpp` at HEAD, with no schedule. [confirmed]
- **Positive control:** in all 13 build files the orchestrator now ends. [confirmed]
  - `c1-compile` and its four variants, and `c3-workday`, gain exactly two lines, `ready(wake)` and `task_end`. Diffed line by line on `c1-compile` and `c3-workday`.

## C. Stage AB — (a)'s last case and the RUN-end drain (`memo_261023.md` H4, H5)

- **H4.** A FORK that takes a free slot writes a zero-wait `ready(fork_slot)` line, before the child's `task_arrive`. In the arrival step the line is held until after the parent's own `ready(arrive)`, as every zero-wait line there is. After a blocked wait, the line used to come from `on_unblock_fork()`; it now comes from the retried FORK, so there is one line either way.
  - `fix-object`: `fork_slot` lines go from 4 to 12. `fix-tree`: from 6 to 18. Each equals the number of FORKs, and every other line is unchanged. [confirmed]
- **H5.** A switch waiting on the drain applies at a RUN's end inside an occupancy as at a slice end. The holder goes back to the ready set as Preempted, not SliceEnd: its slice did not run out, so the outgoing MLFQ must not demote it. Then `dispatch()` applies the switch and the incoming algorithm picks, the holder included. If it picks another task, the holder gets `run_end(preempt)` (Q2's `lane_prev_`).
  - Hand workload `h5`: EDF picks the other task at 3000. `h5b`: EDF picks the holder, and no pair is written. [confirmed]

## F. TODO 1.3 — the §7 gate's sanity checks, automated

- `tools/trace_check.py` reads a trace as a stream and checks it against its workload:
  - no line out of time order;
  - one lane: a `run_start` only on a free lane, a `run_end` only by the holder;
  - delivered CPU ≤ elapsed;
  - a task that exits received exactly its program's RUN total (LOOPs expanded);
  - a segment-bound task ends at or before its depart;
  - nothing of a task after its `task_end`, and one `task_end` per task.
- A task with a `wake_drop` line is counted apart in the demand check: only delivered ≤ demand. The trace does not name which RUNs were passed.
- Positive controls: a line moved back in time, a deleted `run_end`, and a depart brought forward. All three are caught. [confirmed]
- Over the 129 files with `sim_ac`: see G (all pass).

## F2. Unit tests, black-box on the binary (`make -C simulator/src check`)

The class is not in the trace, but the cap shows it: only a batch-class task is parked (`x_cap_park` with `in: true`). Each test therefore carries a positive control, a task that must be parked. Each also carries a `poke` task, woken every 3 ms for 200 µs, so the cap bites on every batch stretch whoever holds the lane. Without it a test can pass because nothing was runnable rather than because the class was right: the first draft of (b) passed with B2 switched off.

- **`tests/test_batch_class.py`**, the batch memo §7 item 6. Both pass: the hog is parked 189 times, the sleeper 0; the plain task 157 times, each at least 10,000 µs into its burst, the chain 0. [confirmed]
  - (a) A 1 ms RUN / 5.7 ms SLEEP loop is never parked, against a hog that is.
  - (b) A TIMER head and a two-stage chain of 15 ms RUNs are never parked. A plain task with the same bursts is parked, and only from a slice (10 ms) into each burst. The test runs under FIFO: under MLFQ the chain takes the lane whenever it is runnable, so the plain task's batch stretches never overlap a non-batch runnable one, and the cap never bites.
  - **Mutants:** with B2's closure over WAKE targets removed, (b) fails ("chain member s1 was parked"). With SLEEP no longer resetting the burst, (a) fails ("the sleeper was parked"). [confirmed]
- **`tests/test_switch_demand.py`**, memo_261010 D2: demand across switches.
  - The schedule walks MLFQ → FIFO → EDF → LOTTERY → MLFQ → MLFQ (U2, a smaller slice) → FIFO → MLFQ, with the cap on in three entries. Four entries wait on the drain, all eight apply in order, and the cap parks 8 times.
  - The three finite tasks exit with exactly their RUN totals, and the trace passes `trace_check.py`.
  - **Mutant:** a switch that hands the holder extra demand fails the test on `a`'s delivered CPU. [confirmed]
