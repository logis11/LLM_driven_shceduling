## F1. The accounting window — decision D10

The batch memo §7 item 3 left the window to this tree. **A token bucket: rate = cap, depth =
one slice** (`batch_slice_`, the same quantity B1's threshold uses).

- Accrues only inside a capped stretch — some non-batch task runnable — at the cap's rate.
- Debited only by lane time a task receives while in the batch class; the interval is split at
  the B1 threshold for an occupancy that crosses it.
- Work-conserving: outside a capped stretch there is neither accrual nor spend, so batch work
  alone on the lane takes all of it whatever the cap says.
- Empty bucket → every runnable batch task is held out of the policy's ready set; full bucket,
  or the stretch ending, gives them back in park order.
- Starts full: the cap is a ceiling, not a reservation.

In steady state the class runs `D/(1−f)` and waits `D/f`, so it is served exactly `f`; the
implied window is `slice/cap` (10 ms every 200 ms at the floor). **Why not a fixed window**: a
100 ms period would be a new constant, and cgroup `cpu.max`'s period does not transfer, because
that counterpart is a different device — as 인지오's 2026-10-20 verification states, CFS
bandwidth control throttles a group that has spent its quota whether or not another task wants
the CPU, so it is not work-conserving, while the work-conserving counterpart, cgroup v2's
`cpu.weight`, is a share and not a ceiling (`docs/recognition-vocabulary.md` §2; both cited for
existence only). Our cap is the combination of the two, so neither one's numbers carry over. The
slice is already a config field, so the bucket invents nothing.

## F3. Two defects found on the way — both only by looking at scale

1. **`drain_in` divided a negative balance.** In debt it returned a nonsense horizon (59 µs),
   which produced a zero-length occupancy; MLFQ read that as `SliceEnd`, demoted, re-dispatched,
   and the run looped at one microsecond — `c2-p3b` wrote **7.4 GB** of trace before it was
   killed. Fixed by clamping the balance at 0 and by dropping the horizon bound in `arm_lane`
   for a single mechanism, the cap's own timer.
2. **The cap timer was never armed for a holder dispatched onto an idle lane**, because the
   gate that arms it runs before the pick. The holder then ran unbounded between events and the
   debt reached **−255,706 µs**; after arming at the end of `dispatch()` it is −1.

Both runs *terminated and were reproducible*. Neither would have been caught without reading
the trace size and the minimum of `allow_`.

## F4. Needs 인지오's confirmation (both are consequences, not requests)

1. **Under FIFO the cap preempts.** A ceiling over a non-preemptive algorithm has no other
   lever, and the executor's class rules sit below the algorithm (batch memo §3, "identical
   across algorithms"). This is what moves the periodic task from 0 jobs to 99.
2. **A stretch that opens mid-occupancy leaves a debt rather than re-arming the holder.**
   Re-arming would hand out a horizon the policy has not charged — the negative-horizon seat U2
   already hit. The overrun is repaid before the class runs again and is bounded by one grant
   (measured: one bucket depth).
