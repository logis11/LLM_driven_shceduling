# Note — is `fork_cap` what makes child birth times emergent?

> Status: memo · Created 2026-10-10 · Updated 2026-10-10
> Author: kyungmin. Raised while reading the `steps/` ladder (sim_n, FORK). A question about the *rationale* for the cap, not a spec change. Later sections add asides from the same reading and three more questions for jioh (mock-switch, guide §4½).

## The question

The docs say the cc1 count is **emergent**: it "emerges from the orchestrator's behavior (fork
rate, parallelism cap, child lifetime)" (`docs/workload/archetype-plan.md:39`). My reading is that
the **cap is what makes that emergence hold**. Without it, would child birth times still depend
on the scheduler in the way the docs intend?

## What the docs already say (confirmed, quoted)

- `docs/workload/archetype-plan.md:39`: cc1 multiplicity is emergent, and this "preserves churn,
  which the Q7 material-change test and canonicalization fold need as raw material."
- `docs/simulator/simulator-guide.md:147`: "a `FORK` while the cap is full blocks until a child
  exits … *when* each one starts is an emergent, scheduler-dependent time."
- `docs/simulator/simulator-guide.md:149`: the c1…c8 → ninth FORK blocks → c3 EXITs → c9 born
  example. "c9's start time depends on how the scheduler treated c1–c8."
- `docs/guidebook/vol-06-archetypes-and-grounding.md:2455-2457`: on one lane the cap "shapes
  fork-storm width and queue depth, not throughput."

None of these says outright that the cap is *necessary* for emergence. That part is my inference.

## My reasoning (inference, not in the docs verbatim)

With **no cap**, a FORK is gated only by the parent's own RUNs. Birth times then depend on:

- **the parent's CPU share.** This is still scheduler-dependent, so emergence does **not**
  vanish entirely.
- **not on the children at all.** How fast c1…c8 finish has no effect on when c9 is born.

With **a cap**, a closed feedback loop appears. Starving the children delays slot release, which
delays the next birth. Favoring them keeps the pipeline full. The guide's c9 example describes
this loop, and it exists only because of the cap.

So the more precise claim: without the cap, emergence weakens from "depends on how the scheduler
treats the whole family" to "depends on how it treats the parent." It does not disappear.

## Aside — `deadline` scoring assumes no work is dropped (sim_p)

Unrelated to the cap. Noted while reading sim_p.

`sim_p` scores each periodic job at the next TIMER with `d = job_tick + job_period` (the grid
tick plus the period) against `now_` (`sim_p.cpp:423-426`). That gives one judgment per tick
only because K's **backlog** guarantees tick k ↔ job k ↔ one `deadline` line. Each consequence
below follows from that:

- Under a **drop** model (Proposal B in `note-for-jioh-timer-backlog-vs-drop.md`), skipped ticks
  open no job, so they get no line. Misses would vanish from the trace exactly when the scheduler
  is worst. This is K's masking problem, moved from demand to scoring. Choosing B would also
  need an explicit "dropped = miss" emission path.
- The single `job_tick` slot works because a task runs one iteration at a time. Jobs open and
  close strictly in sequence.
- The one place the code already drops work is **depart**. That is also the one place a job goes
  unjudged: an open job at depart emits no line. This is the §9.4 "miss or never-due?" question.

## Aside — RUN→RUN boundaries: where the defect came from, and a diagnostic for the fix

Unrelated to the cap. Noted while tracing `advance()` back through the ladder. Full write-up: `../memo/memo_261010.md` Part C.

- **Origin: step f.** `advance()` was born with preemption. It runs after `release()`, so every RUN
  boundary gave the lane back, and f printed an unconditional `run_end` there. That was harmless
  while output was free text.
- **Where it broke: step o.** The contract's `run_end.reason` has no "one RUN finished". O kept
  `run_end` for exit/block only, and filled the Ready case with `ready(cause="arrive")`. The
  structure (RUN boundary = lane hand-back) survived and only the labels changed, which is why
  relabelling the cause cannot fix it.
- **The model:** RUNs joined without a block are one occupancy. Passed primitives appear as
  zero-wait `ready(cause)` lines inside it (trace-clarifications memo §4).
- **Decision:** emit `x_run_cont {t, task}` at each RUN boundary inside an occupancy. Without it, a
  bare RUN→RUN boundary is invisible after the fix. Its count is also the fix's positive control
  against the pre-fix `ready(arrive)` count. It is `x_`-prefixed because the harness set is
  closed.
- Question for jioh: none. The docs already answer the fix. This is recorded for the history.

## Questions for jioh — the `mock-switch` expected trace, and guide §4½

Raised while checking `steps/sim_u` against `harness/tools/tests/fixtures/mock-switch/`. That fixture is a hand-derived expected trace (`trace.jsonl`, derivation in `worked.md`, header `"sim":"mock@0"`) that the harness tests its switch-window primitives against. **All four `config_applied` instants now match** (0, 600, 12000, 40600). The two items below are about MLFQ behaviour, not the switch.

### Q1. Does a task keep running after its slice expires, when a higher queue is waiting? [inferred: looks like a mock error]

`worked.md`, 42600–45600:

| t | mock | simulator |
|---|---|---|
| 42600 | `editor` runs in Q0 with a 2000 µs slice. `probe` has been waiting in Q0 since 40000 | same |
| 44600 | `editor`'s Q0 slice ends → Q1. **`editor` keeps running** until it blocks at 45600, then `probe` runs | `editor` → Q1 and is taken off. **`probe` (Q0) runs** 44600–45100 |

MLFQ rule 2 (guide §5: "Always run from the highest non-empty queue") says `probe` runs at 44600, because Q0 outranks Q1. The mock's own assumptions list "slice expiry with no competitor demotes without a `run_end`", but `probe` *is* a competitor here.

The same shape recurs at 64600. There the competitor is at the *same* level (`hog`, Q1). That case is the within-queue choice guide §5 leaves open ("decide and document"), so it may be deliberate. The 44600 case is not covered by that freedom.

If the mock is wrong, the fixture's `expected.csv` values that depend on it change too, for example `editor`'s and `probe`'s `ready_wait`. That is harness-side work.

### Q2. Slice expiry with no competitor: one occupancy, or a `run_end`/`run_start` pair? [confirmed difference]

At 12000 the `hog`'s slice ends, and nobody else is runnable.

- **mock:** demotes it (`x_mlfq_level 0→1`), and the hog keeps the lane. There is no `run_end`.
- **simulator:** emits `run_end(hog, preempt)` and `run_start(hog)` at the same µs.

The CPU each task receives is identical either way. What changes is the context-switch count: metrics maps it to the count of `run_end(reason=preempt)`. Under the simulator's reading, a lone hog adds one self-switch per slice. On `mock-switch` alone that is dozens of extra pairs.

The contract does not cover this case. The mock's reading matches the principle behind the RUN→RUN fix (memo_261010 Part C): "between events, nothing to decide", so the holder should not hand the lane to itself. If jioh agrees, the simulator changes, and every MLFQ baseline trace changes with it.

### Q3. guide §4½ listing is one instruction short [confirmed]

The miniature's `editor` program is `WAIT, RUN 3000, WAIT, RUN 2000`, four instructions. But the table's t = 32000 row says "next instruction WAIT → blocks", and §6's trace of the same run shows `run_end … "blocked_on":"wait"` at 32000. Both need a fifth instruction, a trailing `WAIT`. Proposed fix: add `{ "op": "WAIT", "channel": "input:e" }` to the listing. That also satisfies the linter invariant: a segment-bound task may end without `EXIT`.
